## Purpose and observed mismatch

The v1.3 compatibility preparation merged without changing frozen PR
[#31](https://github.com/FuqingZh/seqevi/pull/31), and GitHub now reports that
PR as `MERGEABLE` but `BEHIND`. Its required checks pass on the exact reviewed
head and all 96 review threads are resolved. AO preserves the live, idle PR #31
owner and reports the delivery as mergeable/open, while GitHub refuses to
complete the merge because ruleset strictness requires status checks to be
fresh against current `main`. Updating PR #31 would satisfy freshness only by
breaking its frozen-head contract. This is the observed AO/GitHub mismatch;
neither system's readback authorizes weakening any other gate.

The exact authorization baseline is:

- `main`: `4664c50c8196d2946cf16646ed60497ea4799db9`;
- PR #31: open at `0ba6e155c64d311c77a35ef3f187b99de7a56c31`, base
  `main`, GitHub `MERGEABLE` and `BEHIND`, with no auto-merge request;
- PR #41: open at `9f9ca3645b4cd0ca91ef78a13e72c25f86ea6a12`;
- the only open PR targeting `main`: PR #31;
- AO PR #31 owner: session `seqevi-17`, not terminated, idle, with its existing
  ownership retained; and
- repository ruleset `default-branch-pr-gate`, ID `19322798`, target `branch`,
  enforcement `active`, condition `~DEFAULT_BRANCH`, no bypass actors, and
  `current_user_can_bypass: never`.

The ruleset contains, in order, deletion protection, non-fast-forward
protection, the pull-request rule, and required status checks. The pull-request
rule requires review-thread resolution, requires zero approving reviews, does
not dismiss or require code-owner/last-push approval, has no required reviewers,
and allows merge, squash, and rebase. The required-status-check rule has
`do_not_enforce_on_create: false`, requires GitHub Actions integration `15368`
contexts `test (3.12)` and `test (3.13)`, and has
`strict_required_status_checks_policy: true`. These values, including array
order, form the semantic baseline; server-owned metadata such as timestamps,
links, and node IDs is not mutation input.

## Scope and immutable boundaries

Issue #44 and its PR change only this addendum and the prominent current-authority
pointer in `docs/README.md`. After that docs PR merges, the controller owns the
one-shot operational transaction below. This docs worker does not perform it.

The transaction must not update or sync a branch; rebase; use an administrator
or ruleset bypass; push or merge directly to `main`; change any ruleset field
other than the one strict boolean; write PR #31 or PR #41, their heads, branches,
worktrees, bodies, files, comments, or review threads; transfer ownership; arm
AO project auto-merge; or leave GitHub PR auto-merge armed. It grants no product
release, deployment, compatibility change, or permission to reorder or weaken
any v1.2/v1.3 gate.

## One-shot controller transaction

This is one bounded compare-and-swap transaction, not a reusable relaxed-gate
mode. The controller must use authenticated GitHub API and AO readback, retain
all evidence, and install unconditional restoration handling before the first
write. That handler is armed before step 3, but it runs only after step 4
reaches a terminal outcome: authoritative `MERGED` readback, explicit rejection,
or expiration/interruption of the finite wait.

### 1. Preconditions and fresh readback

Immediately before mutation, all of the following must be true:

1. Issue #44's ready documentation PR has merged and this addendum is present
   on current `main`.
2. PR #31 is open, targets `main`, has exact head
   `0ba6e155c64d311c77a35ef3f187b99de7a56c31`, is GitHub `MERGEABLE`, has no
   auto-merge request, and remains the sole open PR targeting `main`.
3. Required exact-head `test (3.12)` and `test (3.13)` checks pass; the settled
   automatic GitHub Codex review and designated exact-current-head review remain
   accepted; platform-native pagination proves zero unresolved review threads.
4. AO authoritatively reports the existing PR #31 owner not terminated and in
   an allowed retained state. No ownership transfer, competing writer, or
   cleanup is pending.
5. PR #41 remains open at
   `9f9ca3645b4cd0ca91ef78a13e72c25f86ea6a12` with no write or ownership change.
6. Ruleset `19322798` is active, has the exact identity and complete semantics
   recorded above, has strictness `true`, and has no additional or reordered
   rule, condition, bypass actor, required context, or field drift.

Any failed, incomplete, stale, or paginated-without-completion readback is a
stop condition before mutation. A changed head, another open `main`-target PR,
CI/review/thread regression, ruleset drift, ownership ambiguity, or PR #41
change requires a new explicit decision, not adaptation of this transaction.

### 2. Semantic snapshot and hash

Before mutation, save the complete GET response for audit and derive a semantic
snapshot containing exactly the mutable ruleset representation: `name`,
`target`, `enforcement`, `conditions`, `rules`, and `bypass_actors`. Serialize
that object as UTF-8 canonical JSON with recursively sorted object keys and
compact separators while preserving array order, then record its SHA-256 hash.
The snapshot must equal the baseline described above before proceeding.

Derive a second payload from that snapshot by changing only
`rules[type=required_status_checks].parameters.strict_required_status_checks_policy`
from `true` to `false`. A structural diff must prove that this boolean is the
only semantic difference. Submit that complete derived payload to ruleset
`19322798`; do not construct a partial or hand-recalled ruleset.

### 3. Relax only strict freshness

Read the ruleset back immediately after the write. Canonicalize it by the same
projection and algorithm. It must equal the derived snapshot and differ from
the baseline snapshot only at the strict boolean, now `false`. If equality
cannot be proved, enter restoration immediately and do not request merge.

The allowed write is precisely `strict=true` to `strict=false`. Required check
names and integration IDs, pull-request requirements, allowed merge methods,
conditions, enforcement, bypass actors, and every other field remain unchanged.

### 4. Native squash auto-merge with exact-head CAS

After repeating the PR #31 head, CI, review/thread, sole-main-target, AO owner,
and no-existing-auto-merge preconditions, request GitHub native squash
auto-merge only, with exact head compare-and-swap:

```text
gh pr merge 31 --repo FuqingZh/seqevi --auto --squash \
  --match-head-commit 0ba6e155c64d311c77a35ef3f187b99de7a56c31
```

Do not substitute `--admin`, a direct merge API, a local merge/push, update
branch, rebase, or a different merge method. Poll with a finite deadline and
backoff for GitHub to report PR #31 merged. While this bounded wait is in
progress, do not restore strictness: doing so could reapply the `BEHIND` block
after auto-merge is armed but before GitHub completes it. The success path first
requires authoritative `MERGED` readback proving that the merged PR head remains
the exact CAS head and that the resulting main advance is GitHub's native squash
merge of that PR. Explicit rejection, deadline expiry, or interruption ends the
wait as failure. A timeout or ambiguous request outcome is handled by readback
and deduplication, never by blindly issuing a second merge request.

### 5. Unconditional immediate strict restore

Restoration is a `finally` action installed before step 3. It runs immediately
after step 4 reaches authoritative `MERGED`, explicit rejection, finite-wait
timeout, interruption, or any other terminal failure. It does not run merely
because the merge request has been accepted or auto-merge has been armed, and
must not run during the bounded wait for `MERGED`. Submit the original complete
semantic snapshot, restoring `strict_required_status_checks_policy: true`. Do
not wait for downstream AO teardown or final verification before restoring.

If PR #31 has not merged, first disable any auto-merge request that readback
shows was armed, then restore strictness. If merge outcome is unknown, restore
strictness first, authoritatively read back PR state, and disable auto-merge if
the PR remains open and armed. No failure path may leave auto-merge armed or
strictness false.

Read the ruleset back, apply the same semantic projection and canonicalization,
and require byte-for-byte semantic equality and the same SHA-256 hash as the
baseline snapshot. Server-owned timestamps may change; no semantic field may.
Failure to restore or prove equality is a critical stop: preserve evidence,
make no further repository or PR write except the narrowly necessary retry of
the original snapshot restoration, and escalate to repository authority.

## Failure rollback

Before PR #31 merges, rollback is: remove any PR #31 auto-merge request, restore
the baseline ruleset snapshot with strictness `true`, prove semantic equality,
and leave `main`, PR #31, PR #41, and AO ownership unchanged. The controller may
retry restoration with a finite transient-error budget, but may not retry the
merge transaction without a new fresh authorization after rollback.

If PR #31 merged from the exact authorized head but a later verification fails,
do not revert, force-push, or rewrite `main`. Restore and prove the ruleset
first, preserve the native merge and all evidence, and escalate the specific
unproved postcondition. If any semantic field other than strictness changed,
restore from the snapshot rather than editing individual fields. If exact-head
merge cannot be proved, treat the outcome as indeterminate and preserve state
for authoritative investigation.

## Final acceptance readback

Only after strict restoration and semantic-hash equality are proved, read back
and record all final conditions:

- ruleset `19322798` is active, strictness is `true`, and its projected semantic
  JSON and SHA-256 hash equal the pre-transaction baseline;
- PR #31 is merged, its recorded head is exactly
  `0ba6e155c64d311c77a35ef3f187b99de7a56c31`, the expected native squash
  commit is on current `main`, and no PR #31 auto-merge request remains armed;
- current `main` is exactly the GitHub-read-back post-merge head and the remote
  tracking ref agrees after a fresh fetch;
- AO reports the original PR #31 owner terminated under its configured
  terminate-on-merge policy, with cleanup/resource state read back according to
  the v1.2/v1.3 ownership boundary; pending cleanup remains visible and is not
  misreported as release;
- PR #41 remains open at
  `9f9ca3645b4cd0ca91ef78a13e72c25f86ea6a12`, with its ownership, body, branch,
  files, reviews, threads, and auto-merge state unchanged; and
- no other open PR gained auto-merge, no second `main`-target PR was admitted
  during the transaction, and all v1.2/v1.3 downstream ordering, review,
  acceptance, release, and deployment gates remain in force.

This final readback closes only the exceptional PR #31 merge transaction. It
does not accept PR #41 or any later unit, release the product, deploy it, or
authorize another ruleset exception.
