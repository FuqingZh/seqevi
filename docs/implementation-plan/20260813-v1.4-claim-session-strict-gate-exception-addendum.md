## Purpose and observed mismatch

The v1.3 compatibility preparation merged without changing frozen PR
[#31](https://github.com/FuqingZh/seqevi/pull/31), and GitHub now reports that
PR as `MERGEABLE` but `BEHIND`. Its required checks pass on the exact reviewed
head and all 96 review threads are resolved. AO preserves the live, idle PR #31
owner and reports the delivery as mergeable/open, while GitHub refuses to
complete the merge because ruleset strictness requires status checks to be
fresh against current `main`. Updating PR #31 would satisfy freshness only by
breaking its frozen-head contract. This is the observed AO/GitHub mismatch;
neither system's readback authorizes weakening any other gate.

The exact authorization baseline is:

- `main`: `4664c50c8196d2946cf16646ed60497ea4799db9`;
- PR #31: open at `0ba6e155c64d311c77a35ef3f187b99de7a56c31`, base
  `main`, GitHub `MERGEABLE` and `BEHIND`, with no auto-merge request;
- PR #41: open at `9f9ca3645b4cd0ca91ef78a13e72c25f86ea6a12`;
- repository setting `delete_branch_on_merge: true`; PR #41 targets PR #31's
  head branch `ao/seqevi-17/claim-session`, so deleting that branch would
  automatically retarget PR #41 to `main` after PR #31 merges;
- the only open PR targeting `main`: PR #31;
- AO PR #31 owner: session `seqevi-17`, not terminated, idle, with its existing
  ownership retained; and
- repository ruleset `default-branch-pr-gate`, ID `19322798`, target `branch`,
  enforcement `active`, condition `~DEFAULT_BRANCH`, no bypass actors, and
  `current_user_can_bypass: never`.

The ruleset contains, in order, deletion protection, non-fast-forward
protection, the pull-request rule, and required status checks. The pull-request
rule requires review-thread resolution, requires zero approving reviews, does
not dismiss or require code-owner/last-push approval, has no required reviewers,
and allows merge, squash, and rebase. The required-status-check rule has
`do_not_enforce_on_create: false`, requires GitHub Actions integration `15368`
contexts `test (3.12)` and `test (3.13)`, and has
`strict_required_status_checks_policy: true`. These values, including array

## One-shot controller transaction

This is one bounded transaction, not a reusable relaxed-gate mode. GitHub
provides no documented unsafe-write precondition contract for the
repository-ruleset update endpoint. Enforced writer exclusion plus complete
semantic readback before and after every write is the executable concurrency
mechanism; this addendum promises no unsupported GitHub primitive.

Before preflight, the approved repository owner must establish a bounded
repository-authority maintenance lease. A fresh access and automation inventory
must prove that no unquiesced actor, GitHub App, workflow, bot, token, or other
automation can write Administration settings. Authoritative AO and controller
readback must prove every other writer quiesced. For the lease window, the owner
freezes every UI and API ruleset change and every action that opens, retargets,
arms auto-merge on, or merges a `main`-target PR. The only exceptions are the
locked authorized controller's exact step 3 strictness relaxation, the
controller or recovery service's exact step 5 strictness restoration, the
controller's step 4 native operation on PR #31 at its guarded head, and GitHub's
resulting native PR #41 automatic retarget. A host-global `flock` on node4 serializes that controller,
and platform readback must prove PR #31 is the only PR targeting `main`. The
lease begins before the first ruleset write. An absolute 120-second deadline
starts restoration; if GitHub is unavailable, the freeze and lease persist
until strictness is verified `true`. The lease releases only after restoration
readback. If any
inventory, quiescence, freeze, lock, sole-PR, deadline, owner-authority, or
single-operation exception fact cannot be proved, stop before mutation.

Before strictness changes, the controller must install a temporary persistent
recovery guard on node4 under the `fqzhang` user. Authoritative host readback
must prove `Linger=yes`. A mode-0700 directory under `/home/fqzhang/tmp` stores
the baseline and relaxed payload hashes, phase, absolute 120-second deadline,
PR number and exact head, and ruleset ID. An enabled `Persistent=true` user systemd timer
invokes a restartable user service that uses `fqzhang`'s existing `gh`
credential independently of the interactive controller. At the deadline, or
after controller, runner, service, or host restart/reboot, the service reads
fresh GitHub state, restores strictness, and verifies it before lease release.
It also reads PR #31 and disables any armed auto-merge request when the PR is
still open, then persistently verifies that no request remains before release.
If GitHub is unavailable or a transient failure prevents verification, the
timer persistently reschedules the service with bounded backoff and continues
until authoritative readback proves strictness `true`; restoration attempts do
not expire. This persistence never retries or re-arms the merge transaction.
Arm the units, read back their enabled/active state and persisted data, and run
a no-write recovery rehearsal before relaxation. Remove the temporary units
and state only after final baseline semantic equality is proved. This is
delivery-only host machinery and creates no SeqEvi product, runtime, deployment,
or domain-model coupling.

The interactive restoration handler is installed before step 3, but runs only
after step 4 reaches authoritative `MERGED`, explicit rejection, or
expiration/interruption of the finite wait. The persistent guard covers loss of
that process and independently enforces the same hard deadline.

### 2. Semantic snapshot and hash

Before mutation, save the complete GET response for audit and derive a semantic
snapshot containing exactly the mutable ruleset representation: `name`,
`target`, `enforcement`, `conditions`, `rules`, and `bypass_actors`. Serialize
that object as UTF-8 canonical JSON with recursively sorted object keys and
compact separators while preserving array order, then record its SHA-256 hash.
The snapshot must equal the baseline described above before proceeding. Persist
the baseline hash and complete payload for the recovery guard.

Derive a second payload from that snapshot by changing only
`rules[type=required_status_checks].parameters.strict_required_status_checks_policy`
from `true` to `false`. A structural diff must prove that this boolean is the
only semantic difference. Do not construct a partial or hand-recalled ruleset.

### 3. Relax only strict freshness

Submit the complete derived ruleset payload to ruleset `19322798`.

Read the ruleset back immediately after the write. Canonicalize it by the same
projection and algorithm. It must equal the derived snapshot and differ from
the baseline snapshot only at the strict boolean, now `false`. If equality
cannot be proved, enter restoration immediately and do not request merge.

The allowed write is precisely `strict=true` to `strict=false`. Required check
names and integration IDs, pull-request requirements, allowed merge methods,
conditions, enforcement, bypass actors, and every other field remain unchanged.

### 4. Native squash auto-merge with exact-head guard

After repeating the current-main pin, PR #31 head, CI, review/thread,
sole-main-target, PR #41 preliminary gate, AO owner, maintenance-lease,
recovery-guard/lease, and no-existing-auto-merge preconditions, request GitHub
native squash auto-merge only, with GitHub's supported exact-head guard:

```text
gh pr merge 31 --repo FuqingZh/seqevi --auto --squash \
  --match-head-commit 0ba6e155c64d311c77a35ef3f187b99de7a56c31
```

Do not substitute `--admin`, a direct merge API, a local merge/push, update
branch, rebase, or a different merge method. Poll with a finite deadline and
backoff for GitHub to report PR #31 merged. While this bounded wait is in
progress, do not restore strictness: doing so could reapply the `BEHIND` block
after auto-merge is armed but before GitHub completes it. The success path first
requires authoritative `MERGED` readback proving that the merged PR head remains
the exact guarded head and that the resulting main advance is GitHub's native
squash merge of that PR. Explicit rejection, deadline expiry, or interruption
ends the wait as failure. The persistent guard independently enforces that same
absolute 120-second deadline; controller or host loss activates recovery. A
timeout or ambiguous request outcome is handled by readback and deduplication,
never by blindly issuing a second merge request.

### 5. Unconditional immediate strict restore

Restoration is a `finally` action installed before step 3. It runs immediately
after step 4 reaches authoritative `MERGED`, explicit rejection, finite-wait
timeout, interruption, or any other terminal failure. It does not run merely
because the merge request has been accepted or auto-merge has been armed, and
must not run during the bounded wait for `MERGED`. Submit the original complete
semantic snapshot, restoring `strict_required_status_checks_policy: true`. Do
not wait for downstream AO teardown or final verification before restoring.

Immediately before restoration, read the complete semantic state again. If it
is exactly the recorded relaxed payload, submit the original complete baseline
payload and verify byte-for-byte semantic equality and its SHA-256 hash. If
strictness is already `true`, treat restoration as an idempotent continuation:
verify baseline equality, or preserve a safe drifted state whose only required
safety fact is strictness `true`, then continue the remaining auto-merge and PR
readbacks. If strictness is `false` with unexpected drift, do not overwrite it
with the baseline: preserve the fresh payload and evidence, derive a complete
payload from that fresh state by changing only strictness to `true`, submit and
verify that safety restoration, then stop and escalate. Drift is a transaction
failure even when strictness is safely restored, and baseline equality must not
be claimed. The persistent recovery service follows the same restart-safe
fresh-readback branches.

Restore and verify strictness first without waiting for PR #41 to retarget.
Strictness must never be relaxed again to facilitate or retry that base
transition. After strictness is authoritatively `true`, keep the maintenance
freeze and poll with a finite deadline and bounded backoff for GitHub's native
PR #41 retarget. PR #41 must remain open with exact head
`9f9ca3645b4cd0ca91ef78a13e72c25f86ea6a12`, the same head branch, owner, body,
and authored commits; its base must now be `main`; and auto-merge must remain
null. Its computed comparison, diff/files, review state, mergeability, and
complete #39 preliminary gate may change because the base changed and must be
read back in full. The maintenance freeze prohibits merging or otherwise
advancing PR #41. Any head, head-branch, owner, body, authored-commit, or
auto-merge change, any non-native retarget, or incomplete readback is a critical
stop. If the native retarget does not complete before the deadline, retain the
freeze and evidence and escalate without changing strictness. The later PR #41
rebase and final gate remain owned by v1.2 step 5.

If PR #31 has not merged, first disable any auto-merge request that readback
shows was armed, then restore strictness. If merge outcome is unknown, restore
strictness first, authoritatively read back PR state, and disable auto-merge if
the PR remains open and armed. No failure path may leave auto-merge armed or
strictness false.

Read the ruleset back, apply the same semantic projection and canonicalization,
and require byte-for-byte semantic equality and the same SHA-256 hash as the
baseline snapshot. Server-owned timestamps may change; no semantic field may.
Failure to restore or prove equality is a critical stop: preserve evidence,
make no further repository or PR write except the narrowly necessary retry of
the applicable fresh-readback restoration path, and escalate to repository
authority.
Release the maintenance lease only after strictness is `true`, no auto-merge
remains armed, the bounded PR #41 retarget state is proved, and the applicable
equality or drift-preserving failure readback is durably recorded. Do not remove
the temporary service, timer, or state until baseline restoration is proved;
unexpected drift leaves them
and all evidence preserved for repository-authority escalation.
