## Settled Release And Compatibility Boundary

The target is SeqEvi 0.3.1, not 0.2.0 or the incomplete 0.3.0 release set. Production publication originally ended at
0.2.0, while post-0.2.0 `main` contains ClaimSession, schema revision
`0004_claim_sessions`, and an intentional incompatibility with released Python
source: removal of the released `HttpEvidenceStore(..., client=...)` injection
parameter. Target-Store mutation must therefore wait for a single named release
identity that contains the deployed schema and client behavior. Candidate
source, an editable checkout, and an unreleased wheel are not target execution
identities.

SeqEvi 0.3.1 must preserve the managed dbCAN behavior offered by 0.2.0. Before
tagging or publishing 0.3.1, corrective release preparation must:

1. build, validate, and publish the matching first-party dbCAN runtime image at
   an immutable manifest digest;
2. update the bundled `src/seqevi/kits/dbcan-cazyme.toml` image reference to
   that published digest and verify the built wheel contains the updated kit;
3. run the release checks that prove managed dbCAN planning and execution still
   resolve through the supported digest-pinned kit; and
4. publish/tag only after the Python artifacts and runtime image form one
   recorded release set.

No eggNOG or InterPro managed setup is added. Both continue to use their
supported explicit or named-profile runtimes and caller-owned, read-only
resources.

### Mechanism-equivalence reuse gate

The accepted fresh-Store concurrency evidence may be reused only when every
change from its protected lineage through the exact released 0.3.1 source is
classified as packaging, version metadata, documentation, or bundled-kit-only,
and a retained diff record proves there is no relevant semantic change to:

- runner launch, cancellation, containment, or cleanup;
- annotate lookup, claim, compute, commit, replay, or identity behavior;
- Store schema, persistence, client, service, or migration behavior;
- HTTP routes, transport, deadlines, retry, reconciliation, or capability
  selection;
- eggNOG adapter execution, parsing, parameters, profile, runtime identity, or
  result production; or
- either C2 or pressure harness, including inputs, barriers, assertions,
  readback, and cleanup.

The record must name the accepted candidate/tree, released tag and commit,
built wheel/sdist digests, protected file blobs, changed paths, classification
for every changed path, reviewer, and decision. Package contents must be
compared with the release source so an omitted or substituted runtime file
cannot pass as packaging-only.

Any relevant or unclassified change fails equivalence and requires a new
fresh-Store eggNOG C2 run, with the master plan's cold/replay mechanics and a
new benchmark record, before target mutation. A failed released target
integration stops target execution for diagnosis; it does not by itself revoke
accepted mechanism equivalence or require a fresh C2. Revoke reuse and require
a fresh-Store C2 only when diagnosis attributes the failure to a protected
runtime or harness semantic change, a defect in the equivalence
classification, or the accepted mechanism itself. This plan supersedes the old
requirement to repeat concurrency mechanics at the target physical Store only
when both the recorded mechanism-equivalence gate and the released target
integration/replay gate below pass; otherwise target execution remains stopped,
and the old cold C2 is required only when the diagnosed cause invalidates
mechanism reuse.

## Execution Graph And Review Units

```text
Review unit 1: 0.3.1 corrective release set -> target deployment/migration -> readback
  -> mechanism-equivalence decision
Review unit 2: read-only Preflight -> serial sanity/replay/capacity -> C1
  -> layered C2 closeout -> benchmark record -> InterPro Preflight handoff
```

The release/deployment prerequisite is reviewed independently from eggNOG
execution and evidence. No Store-mutating step from review unit 2 begins until
review unit 1 is accepted.

## Review Unit 1: Release And Deployment Prerequisite

### Release set

Prepare 0.3.1 from the accepted corrective release source. Record the tag/commit, clean
tree, version metadata, wheel and sdist digests, Python compatibility checks,
dbCAN image manifest digest, updated bundled-kit bytes, package-content audit,
and repository/release gates. Verify that production artifact indexes return
the exact 0.3.1 distributions and that a clean environment installs and reports
that version. Do not tag or publish if the matching dbCAN image or bundled kit
is absent, mutable, inconsistent, or unverified.

### Exact target deployment and schema maintenance

Quiesce every target Store service and writer and follow the approved
[ClaimSession Store maintenance
runbook](../operations/20260818-v1.2-claim-session-store-maintenance.md). Use the
exact released 0.3.1 service and client distributions, not source imports, for
the target loopback Store at `http://127.0.0.1:18081`.
Record canonical redacted database identity, the single-use revision
acknowledgement, pre-maintenance revision, terminal row counts and digests, and
the released executable/package digests.

If Preflight finds `0002_artifact_byte_size_bigint`, first use the runbook's
acknowledgement-bound preparation command and prove its 0003 readback before
issuing a fresh 0003 acknowledgement. Then run the fenced
`0003_evidence_claim_leases` to `0004_claim_sessions` upgrade; ordinary startup
is not a migration mechanism. Read back revision
`0004_claim_sessions`, all six coordination tables, absence of
`evidence_claim`, unchanged terminal sequence/evidence/artifact counts and
digests, one restarted service's `/health` response and ClaimSession
capabilities, and the exact 0.3.1 client-to-service path.

Any identity error, live writer, timeout, uncertain commit, unexpected schema,
terminal-data drift, or failed fresh readback is fail-closed. Keep writers
quiesced and classify state from a fresh connection. If downgrade is selected,
use the runbook's fenced 0004-to-0003 rollback and verify unchanged terminal
data. Do not resume seeding clients until the final selected revision and
service identity are proven.

### Released target integration gate

Before corpus mutation, use read-only health, capability, lookup, artifact
fetch, and representative pre-existing-key replay paths to prove the released
0.3.1 client and service operate against the target Store. This gate must
record package/tag identities, Store revision, HTTP observations, EvidenceKey,
payload and artifact digests, ToolRuntimeDigest, ResourceID, semantic
parameters, and zero-compute replay. It cannot be inherited from a fresh Store
or candidate-source run.

Acceptance requires the release set, migration readback, released target
integration, and either mechanism equivalence or a new accepted fresh-Store C2.

## Review Unit 2: eggNOG Execution And Evidence

### Read-only Preflight and key-state branch

Run the master plan's manifest, input, profile/resource, Store health, capacity,
output-isolation, timeout, containment, and applicable backup/export checks
with released 0.3.1. Inventory every frozen sanity, C1, and C2 EvidenceKey
against the exact eggNOG identity before mutation and retain the key-state
manifest and query/result digests.

The target remains a test/cache-seeding Store. Existing historical
export/readback evidence may be cited only by its recorded identity; this plan
does not require a fresh production backup. If the Store is promoted to
production authority, mutation remains fail-closed until a coordinated
PostgreSQL/artifact backup completes and its identities are read back.

Preflight chooses one branch per frozen set:

- When every key is missing, execute the old frozen cold set unchanged.
- When every key is present, prove exact EvidenceKey identity, payload
  equality, artifact references and file digests, ToolRuntimeDigest,
  ResourceID, semantic parameters, output mapping, and zero-compute replay.
- When the frozen set is partially cached, inventory and digest its disjoint
  present and missing subsets. Prove the same exact identity, payload,
  artifact, and replay properties for the present subset, then run the
  unchanged frozen input set so only the Preflight-missing union computes.
  Reconcile expected computed and cache-hit counts against both subsets,
  including input overlap and ClaimSession winner/waiter behavior, and require
  a zero-compute independent replay of the complete unchanged frozen set.
  Record this as a partially cached run, never as a cold run.
- Only when a later capacity gate actually requires new growth evidence may
  Preflight derive missing keys from the previously frozen corpus. Selection
  must be deterministic, identity-disjoint from reserved sets, bounded to the
  minimum defensible scale, and recorded as a derived manifest with algorithm,
  ordered inputs/keys, digests, relationship to the frozen corpus, missing-key
  proof, and approval before mutation. It is not a replacement C2 identity.

Do not delete, reset, hide, or overwrite immutable cache to manufacture cold
keys. A legitimate, fully reconciled partial state may proceed. Only
unexplained, unequal, or incompletely auditable mixed state stops the lane.

### Serial sanity, independent replay, and capacity

Run the master plan's unchanged frozen serial-sanity input for an all-missing or
partially cached set; for a partial set, only the Preflight-missing union may
compute and every present key must reconcile as a cache hit. For an all-present
set, use the complete proof/replay branch above. Follow every mutating branch
with an independent released 0.3.1 replay of the unchanged input. Accept only
the Preflight-predicted computed/cache-hit counts, complete adapter-native
output, exact input mapping, zero replay computation, reconciled Store/artifact
deltas, no temporary residue, and recorded PostgreSQL, artifact-filesystem,
retained-result, and peak-scratch measurements. A partially cached result is
not cold evidence.

Capacity projections retain the master's conservative rates, 2x successor
headroom, and final-reserve gates. If pre-existing keys prevent measurement and
new growth evidence is necessary, use only the approved deterministic derived
manifest. Do not infer cold growth from replay or the accepted fresh-Store C2.

### C1 and layered C2 closeout

Run C1 with the master plan's unchanged frozen disjoint inputs when their keys
are all missing or partially cached. For each partial set, retain its present
and missing inventory, prove the present subset, and require only its
Preflight-missing union to compute. Reconcile each process's expected computed
and cache-hit counts and the combined Store delta; then require zero-compute
independent replay of both complete frozen inputs. For all-present keys, apply
the exact proof/replay branch. Use a derived missing set only for genuinely
required capacity evidence, never to claim the frozen C1 ran cold. Preserve
two-process output isolation, Store and artifact reconciliation, finite
deadlines, containment cleanup, and capacity gates.

C2 closeout is layered:

1. **Mechanism layer:** retain the accepted fresh-Store 64-thread C2 only if
   mechanism equivalence passed; otherwise accept a new fresh-Store cold C2.
2. **Released target integration layer:** prove released 0.3.1 target health,
   schema/capability identity, exact frozen-set inventory, payload/artifact and
   evidence-identity readback, independent replay, and capacity. Execute the
   unchanged frozen target C2 inputs when their keys are all missing or
   partially cached. For a partial set, prove the present subset first; require
   Store growth to equal only the Preflight-missing overlapping union; and
   reconcile per-process computed/cache-hit counts, overlap, claim winners,
   waiters, and later cache visibility before zero-compute independent replay
   of both complete inputs. When all keys pre-exist, use the proof/replay
   branch. Never label a partial or all-present target run as cold same-key
   contention.
3. **Closeout layer:** reconcile mechanism and target records without merging
   their execution identities. State exactly which physical Store, package,
   input, key state, concurrency, mutation, and replay each record proves.

Target-Store integration and replay under released 0.3.1 are mandatory in all
branches. Reused mechanism evidence never supplies target capacity, deployment,
payload, artifact, or replay acceptance.

## Rollback, Cleanup, And Stop Conditions

The master plan's stop, timeout, backup/export, capacity, output, artifact,
cleanup, and forward-only immutable-Store rules remain unchanged. In addition,
stop before mutation on an incomplete release set, non-0.3.1 process, failed
package-content audit, unclassified protected diff, failed equivalence without
a replacement fresh C2, uncertain 0004 state, failed released target
integration, or incomplete key inventory.

Stop during execution on identity drift, unexpected computation in replay,
payload/artifact inequality, unexplained Store delta, lost capacity headroom,
HTTP/commit error, timeout, or non-empty containment boundary. Preserve all
observable state and evidence. Never delete valid cache rows or CAS artifacts
to retry; refresh inventory and resume only through a reviewed branch. Schema
rollback uses only the maintenance runbook and remains fail-closed.

## Completion And Handoff

eggNOG target-Store closeout is complete only when both review units pass and a
versioned benchmark record makes the release, service/client, schema, input,
EvidenceKey state, mechanism evidence, target Store, mutation, capacity,
payload/artifact reconciliation, output, replay, exclusions, and stop decisions
auditable without conflating execution identities.

That accepted record hands control to InterPro Preflight under the still-active
master safeguards. It neither accepts InterPro nor plans its execution details.
