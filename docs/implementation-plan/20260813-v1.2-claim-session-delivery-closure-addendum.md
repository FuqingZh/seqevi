## Minimal branch and merge topology

The approved topology is finite and minimal:

1. This #38 addendum merges to `main` and becomes current delivery authority.
2. The #39 PR may be developed and tested as a stack whose base is frozen PR
   #31 at `0ba6e155c64d311c77a35ef3f187b99de7a56c31`. It must remain a separate
   branch and PR. It must never merge into, transfer commits through, amend,
   rebase, or otherwise rewrite PR #31.
3. Before PR #31 may merge, #39 must reach a ready, passing preliminary state
   on that stack: all four findings implemented together; focused SQLite and
   PostgreSQL tests passing as applicable; PostgreSQL 17 and SQLite validation
   passing; `pdm run check` passing; preliminary exact-head CI passing; required
   architecture/runbook drafts present; and the preliminary head ready for
   platform review. This gate establishes credible closure, not permission to
   merge #39 into PR #31.
4. The existing PR #31 owner may then reply to the four ledger threads with
   the #39 preliminary evidence and resolve them. This is the only permitted
   PR #31 activity: it changes neither branch, exact head, PR body, nor files.
   Platform readback must prove zero unresolved PR #31 threads before PR #31
   merges unchanged to `main`. Any other PR #31 write or any head change stops
   this topology.
5. After PR #31 merges, #39 retargets and rebases to the then-current `main`.
   It reruns the complete final gate on its new exact head and merges
   independently to `main` before #33, #34, or #35.
6. Issues #33, #34, and #35 remain independent frozen delivery units and merge
   only after #39. Their ordering relative to one another remains unconstrained
   unless a newly discovered real dependency triggers the stop rule.
7. Issue #37 starts final acceptance only after PR #31, #39, #33, #34, and #35
   are on current `main`; it retargets/rebases, validates current `main`, and
   merges last.

No merge in this sequence authorizes deployment or product release.

## Finite review-order rule

For #38, #39, #33, #34, #35, and #37, the repository's automatic GitHub review
is the first review phase for a ready exact head. Allow it to settle, record
each thread once, classify it as duplicate, in-contract blocker, or separately
owned follow-up, and resolve every actionable in-contract thread before
triggering the designated final AO review.

This rule applies to each delivery unit's own PR threads. It does not transfer
the four ledger threads from PR #31 to #39: #39's owner resolves only threads
on the #39 PR, while the existing PR #31 owner performs the evidence-only
reply and resolution described above.

Exactly one designated contract-scoped AO review is last for that exact head.
Do not run the automatic and designated reviews as an open-ended alternating
loop. A head change invalidates review acceptance and restarts the finite order
on the new head. Any thread arriving after the designated review still blocks
merge and must be classified; it does not silently expand the frozen scope.
An in-contract fix creates a new head and repeats automatic-review settlement
before a new designated final review. An out-of-contract finding follows the
stop rule instead of being absorbed into the PR.

## Compatibility and release gates

The v1.0 technical design and v1.1 settled public/private boundaries remain
unchanged. Issue #39 adds no public API, CLI, profile, asynchronous transport
surface, deployment component, Store location, or user timing knob. Relative
to v0.2.0, released Store constructor parameters, synchronous method behavior,
health/lookup/fetch/artifact/download/legacy-commit wire behavior, immutable
`EvidenceKey`, evidence/artifact data, and result schemas remain compatible.
The already authorized removal of `HttpEvidenceStore(..., client=...)` remains
the sole released Python source break; unreleased per-key claim APIs remain
removed without aliases. The `/authority` correction is internal and
capability-gated.

Product release remains blocked until #39 has merged after unchanged PR #31,
then #33, #34, and #35 have merged independently, and #37 has completed final
acceptance on current `main` and merged last. Release readback must confirm the
then-current approved architecture and runbook successors, all exact-head
validation/CI/review gates, and zero unresolved review threads for every unit.
Production deployment still requires separate authority.

## Stop and rollback conditions

Stop the affected merge path, preserve every branch and exact head, and request
a new explicit delivery decision if:

- PR #31 changes from `0ba6e155c64d311c77a35ef3f187b99de7a56c31` for any
  reason, or any code, test, CI, documentation, merge, sync, or rebase is
  proposed on its branch, the #39 owner writes PR #31, or PR #31 merges before
  its existing owner has resolved the four ledger threads and platform readback
  proves zero unresolved PR #31 threads;
- #39 is split, omits a ledger finding, merges into or rewrites PR #31, fails to
  reach the preliminary gate before PR #31 merges, or attempts final merge
  without the post-PR-#31 current-`main` rebase and complete rerun;
- #33, #34, or #35 merges before #39, absorbs another unit, or ceases to be
  independently reviewable;
- #37 starts final acceptance early, omits its current-`main` PostgreSQL
  pressure or real C2 gate, or does not merge last;
- a finding requires a public compatibility change, architecture or runbook
  authority owned by another unit, or any expansion beyond a frozen row;
- automatic review has not settled before the designated final AO review, a
  later thread is ignored, review is accepted from an older head, exact-head
  CI is not passing, or zero unresolved threads cannot be proved; or
- any release or deployment gate would be bypassed.

Before this #38 addendum merges, rollback is to close its PR and preserve PR
#31, #39, and the v1.1 authority without mutation. After it merges, do not edit
history or fall back to the exhausted PR #31 repair loop. If no downstream work
has relied on this addendum, a reviewed revert may restore v1.1 while keeping
PR #31 frozen; otherwise publish a new dated superseding addendum recording the
preserved heads, relied-on branch state, revised disposition, compatibility,
and acceptance authority. Product rollback never restores mixed per-key and
ClaimSession protocols, bypasses maintenance fencing, or changes terminal
evidence/artifacts.
