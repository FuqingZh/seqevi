# Modern Single-Invocation Progress Presentation Implementation Plan

Version: v1.0

Date: 2026-08-24

Status: implemented; required repository gate passed

## Goal

Make one interactive `seqevi annotate` invocation immediately understandable
without claiming progress that SeqEvi cannot measure. The successor display
must answer:

1. what the invocation is doing now;
2. how many unique input sequences have terminal evidence;
3. what fraction and percentage of that exact work is ready; and
4. how long the complete invocation has been running.

Representative local execution is:

```text
⣹ Running eggNOG batch 3                         13m21s elapsed
  Unique sequences  ━━━━━━━━━━━━━╺━━━━━  1,920/2,729  70%
```

When terminal evidence reaches 100% but result publication is still active,
the completed bar is removed and the active phase replaces it:

```text
⣹ Writing result                                 13m24s elapsed
```

On success, the transient display is cleared and the existing final summary is
retained with total invocation time:

```text
✓ Annotated 2,729 unique sequences in 13m27s (1,920 cached, 809 computed); output: RESULT
```

## Authority And Compatibility Baseline

The implemented
[progress contract v1.1](../architecture/20260824-v1.1-progress-observability-contract.md)
is the authoritative single-invocation successor to v1.0. It changes two human
CLI behaviors:

- progress becomes automatic on a capable interactive stderr instead of
  requiring opt-in; and
- the transient single line becomes a Rich-rendered, width-aware live display.

It preserves the private event boundary, one-document `--json` guarantee,
scientific results, upstream logs, Store behavior and public Python API.

The architecture v1.1 and validation-strategy v1.3 successors were approved
with implementation. This plan records delivery order; it is not runtime
authority.

## Accepted Product Decisions

### 1. One invocation, not an input scheduler

SeqEvi continues to accept and annotate one FASTA per invocation. It may use
adapter threads and existing bounded batches internally, but it does not add a
manifest runner, multi-input queue, concurrency controller or dashboard.
External shell, workflow or service orchestration remains responsible for
starting and observing several invocations.

The following are explicitly deferred until a concrete external consumer
exists:

- `seqevi progress watch`;
- JSONL progress files or another public progress protocol;
- heartbeat and stale-process classification;
- cross-process aggregation, sorting or directory watching; and
- queued, retry or cancellation controls.

### 2. Automatic human progress with an explicit off switch

The CLI surface becomes:

```text
seqevi annotate ...                # automatic on capable interactive stderr
seqevi annotate ... --progress     # retained spelling and explicit enablement
seqevi annotate ... --no-progress  # explicit disablement
seqevi annotate ... --json         # always disables human progress
```

The renderer is enabled only when all of these are true:

- progress has not been disabled;
- stderr is an interactive terminal with dynamic rendering capability;
- `TERM` is not `dumb`; and
- `--json` is absent.

Non-TTY execution remains progress-free. It does not emit periodic plain-text
heartbeats or ANSI cursor movement. Existing automation therefore gains no new
default stream content. `--progress` remains accepted for compatibility; it
does not force dynamic output into an incapable stream.

### 3. The ratio is terminal evidence for unique sequences

The only invocation-level ratio is:

```text
unique sequences with terminal evidence / unique input sequences
```

The user-facing label is `Unique sequences`. It deliberately matches the
existing final summary and distinguishes evidence work from FASTA record count.
Multiple input records with identical sequence content share one evidence
identity and therefore one unit in the denominator.

A unique sequence becomes ready only when either:

- Store lookup establishes an existing terminal evidence record; or
- a local or peer computation has been finalized to the Store.

Looking up a miss, acquiring a claim, observing an upstream process exit or
parsing an uncommitted adapter result does not advance the ratio. The count is
monotonic, never exceeds its denominator and counts each SequenceID once.

### 4. Exact count and percentage remain visible together

When the ratio is known and the terminal is wide enough, the view contains:

- the visual bar;
- formatted `completed/total` counts; and
- an integer percentage derived from the same exact values.

When the full view does not fit without wrapping, it degrades to one stable
line that preserves active work, `completed/total`, percentage and total
elapsed time while dropping the visual bar first:

```text
Running eggNOG batch 3 · 1,920/2,729 unique sequences · 70% · 13m21s
```

Color is optional and never carries the only state signal. Width behavior is
based on Rich measurement of the actual console rather than a separate manual
ANSI layout engine.

### 5. Tool batches remain indeterminate

The display may name the adapter, current batch number and exact batch size
when SeqEvi owns those values. It does not show a percentage, throughput or ETA
for an active eggNOG-mapper, dbCAN or InterProScan/Pfam subprocess. A batch may
advance the unique-sequence ratio only after terminal Store finalization.

No adapter log parser, residue-based inference, batch-size change or upstream
instrumentation is introduced to make the bar move more smoothly. A long tool
batch may therefore leave the bar unchanged while the spinner and elapsed time
continue to update.

### 6. Show total invocation time only

The live display carries one monotonic duration from application start through
configuration resolution, annotation, Store teardown, result publication and
result validation. It does not show a second phase duration.

No ETA is shown. Sequence count is not a valid duration model across supported
adapters, residue-length distributions, runtime and resource identities,
thread counts and execution environments. ETA requires a separately accepted,
representative benchmark contract.

### 7. Completed work becomes a result, not a retained 100% bar

The live display is transient. When unique-sequence readiness reaches 100% but
the invocation is still packaging, closing the Store or validating the result,
the completed bar is cleared and replaced by the current indeterminate phase.

On success the whole live region is cleared before the durable human summary
is written. The summary preserves unique-sequence, cache/computation and output
path information and adds total invocation time.

On typed failure, untyped failure or interruption, the live region is cleared
and terminal state is restored. The existing CLI error presenter and exit code
remain the only durable failure authority; the progress renderer does not emit
a second failed or cancelled summary.

### 8. Managed OCI remains an outer liveness envelope

Local annotation can expose exact readiness because the parent process owns
FASTA staging, Store transitions and batch orchestration. Managed OCI currently
exposes only outer process liveness, so it renders:

```text
⣹ Running managed annotation                    13m21s elapsed
```

It never shows an internal ratio. The final validated managed result may still
produce the normal durable success summary. Container log parsing, sidecar
files and inner-event forwarding remain separate compatibility decisions.

## Internal Contract Shape

Evolve the existing private event model so the cumulative measure and batch
metadata are explicit rather than overloading one phase-local ratio:

```python
@dataclass(frozen=True, slots=True)
class WorkProgress:
    completed: int
    total: int
    unit: ProgressUnit


@dataclass(frozen=True, slots=True)
class BatchProgress:
    number: int
    size: int


@dataclass(frozen=True, slots=True)
class ProgressEvent:
    phase: ProgressPhase
    state: ProgressState
    message: str
    evidence_ready: WorkProgress | None = None
    batch: BatchProgress | None = None
```

Construction rejects negative, partial, unitless or over-complete work. The
annotation path emits semantic state only; it does not own clocks, terminal
width, Rich objects or formatting. The application/CLI boundary owns one
monotonic invocation clock and presentation lifecycle.

The model stays private: no package export, public callback or serialization
schema is added. Presentation failure remains guarded and cannot change
scientific or cleanup behavior.

## Component Ownership

| Component | Responsibility |
| --- | --- |
| `src/seqevi/progress.py` | Private exact work and batch values, event invariants, sink and guarded emission. |
| `src/seqevi/annotate.py` | Maintain cumulative terminal-evidence identity set and emit truthful batch metadata at existing orchestration boundaries. |
| `src/seqevi/api.py` | Preserve application finalization boundary and managed outer liveness; no public API change. |
| `src/seqevi/cli.py` | Resolve automatic progress eligibility, own the monotonic run clock, render/clear the Rich live display and retain final/error channel contracts. |
| `pyproject.toml`, `pdm.lock` | Declare Rich directly as `rich>=15,<16` and update the lock without relying on Typer's transitive dependency. |
| `tests/test_progress.py` | Event invariants, deterministic clocks, full/compact rendering and cleanup. |
| `tests/test_annotate.py` | Exact cumulative readiness across cache, local and peer-finalized paths. |
| `tests/test_cli.py` | Auto/disable/TTY/JSON behavior, width degradation and durable summaries. |
| `tests/test_api.py`, `tests/test_oci.py` | Finalization lifecycle and managed indeterminate behavior. |
| architecture and testing successors | Approve the changed human CLI and validation contract with implementation. |

No new `progress_io.py`, `progress_view.py`, background heartbeat publisher or
observer command is created. Rich remains a presentation dependency of the CLI
boundary and is not imported by annotation, adapter, Store or result modules.

## Execution Graph

```text
Slice P1 cumulative evidence semantics
    └── Slice P2 Rich single-invocation presentation
            └── Slice P3 contract and verification closeout
```

### Slice P1: Cumulative terminal-evidence semantics

Predecessor: implemented progress contract v1.0.

Work:

- add explicit immutable work and batch metadata values;
- derive the unique-sequence denominator from completed FASTA staging;
- maintain monotonic readiness from cache hits, local finalization and
  peer-finalized evidence without changing lookup or batching order;
- preserve the readiness count across fetch, packaging and finalization; and
- keep active tool batches indeterminate.

Invariants and non-goals:

- no SequenceID is counted more than once;
- terminal evidence is required before increment;
- Store, evidence identity, batch size and bounded-memory order are unchanged;
- no clocks, renderer or public protocol enter annotation orchestration.

Verification:

- all-cache, all-miss, mixed-cache, duplicate-content and multi-batch fixtures;
- local-finalize and peer-winner/claim-wait event sequences;
- no regression, duplication or value above total; and
- unchanged summaries, Store evidence and DuckDB results.

Acceptance: every local invocation exposes one truthful cumulative readiness
measure without changing scientific execution.

### Slice P2: Rich single-invocation presentation

Predecessor: P1.

Work:

- declare Rich as a direct runtime dependency and update the lock;
- replace the manual carriage-return renderer with a context-managed Rich live
  display;
- change the existing CLI option to the paired `--progress/--no-progress`
  surface with automatic interactive display;
- render full and compact layouts from the same semantic state;
- use one injected monotonic application clock for live and final human time;
- clear completed bars while later finalization remains active; and
- clear and restore the terminal before success, error or interruption output.

Invariants and non-goals:

- stdout remains free of live progress;
- `--json` and non-TTY paths remain progress-free;
- the existing typed error and one-document JSON contracts are unchanged;
- the human final summary retains counts and output path;
- no phase clock, ETA, machine protocol or adapter log parsing is added.

Verification:

- capable TTY default, explicit enable, `--no-progress`, non-TTY,
  `TERM=dumb` and every `--json` path;
- deterministic full and compact snapshots at representative wide and narrow
  widths, including ASCII/no-color capability fallback;
- all-cache fast completion and long blocking-adapter liveness;
- 100%-then-package transition without a retained completed bar;
- success, typed failure, untyped failure and interruption cleanup; and
- managed OCI displays liveness without a ratio.

Acceptance: an interactive local invocation gives a stable, truthful and
width-safe view while all machine and failure channels retain their contracts.

### Slice P3: Contract and verification closeout

Predecessor: P2.

Work:

- approve an architecture v1.1 successor covering auto progress, Rich,
  cumulative readiness and managed-mode limits;
- approve a validation-strategy successor covering the new CLI default and
  renderer dependency;
- update the documentation index from proposed to implemented only after the
  code and required gates pass; and
- review the final diff for scientific isolation and public CLI compatibility.

Verification:

- run focused progress, annotation, API, CLI, OCI, cancellation and cleanup
  tests using repository-owned fixtures;
- verify `annotate --help` exposes both option spellings;
- verify final human and JSON outputs directly; and
- run the repository-required `pdm run check` gate.

Acceptance: documentation, tests and runtime behavior agree at the exact final
source state. No real eggNOG, dbCAN or InterProScan run is required unless a
focused test reveals a change outside the presentation boundary.

## Compatibility And Migration

- Commands already passing `--progress` remain valid.
- Commands passing `--json`, commands with non-interactive stderr and normal
  pipelines remain progress-free.
- Direct terminal invocations gain automatic transient stderr output. Users can
  recover the previous quiet behavior with `--no-progress`.
- Human progress and final-summary text are not parseable stable formats.
  Existing machine consumers must continue to use `--json`.
- The JSON success/error documents, JSON metric meanings, public Python API,
  adapter commands, Store and evidence contracts, DuckDB schema and output
  artifacts are unchanged.
- Rich is a declared runtime dependency because SeqEvi imports it directly;
  Typer's current transitive dependency is not treated as an ownership
  contract.

## Risks And Containment

| Risk | Containment |
| --- | --- |
| Readiness double-counts a cache/claim transition | identity-based cumulative state and focused cache/local/peer fixtures |
| Users read 100% as a completed result | remove the bar and keep the active finalization phase until validated success |
| Automatic progress surprises interactive users | TTY-only stderr scope plus `--no-progress` |
| Narrow terminals wrap or corrupt the display | Rich measurement, compact fallback and deterministic width tests |
| Renderer failure affects annotation | guarded sink and unconditional presentation cleanup |
| Rich becomes cross-layer dependency debt | direct CLI-only import; deletion test remains satisfied by removing manual cursor/width lifecycle code |
| Managed OCI appears to have local detail | explicit indeterminate view and no fabricated ratio |

## Rollback And Stop Conditions

Before public release, P2 can be rolled back to the implemented v1.0 renderer
without removing P1's private cumulative semantics. The Rich dependency can be
removed with that renderer. No Store migration or result cleanup is required.

Stop and reopen design instead of expanding this plan if implementation needs:

- input scheduling or multi-process observation;
- a public progress file, callback or schema;
- adapter-native log parsing or batch-progress inference;
- managed OCI inner-event transport;
- Store, evidence identity, batch-size or result-schema changes; or
- an ETA model without representative benchmark evidence.

## Final Verification And Review Split

Implementation completion requires:

1. focused P1 semantic review and tests;
2. focused P2 CLI/presentation/dependency review and tests;
3. approved architecture and validation successors;
4. `pdm run check` against the exact final tree; and
5. final review of JSON purity, count correctness, terminal cleanup and
   dependency ownership.

The implementation may be reviewed in the three slices above. Editing this
plan alone requires only documentation link and content checks; it does not
require the runtime repository gate.

## External Design Precedents

- [uv CLI](https://docs.astral.sh/uv/reference/cli/): progress is normally
  available and `--no-progress` suppresses spinners and bars.
- [PDM terminal UI](https://github.com/pdm-project/pdm/blob/324f00e2/src/pdm/termui.py):
  Rich-backed interactive status with terminal capability detection.
- [pip install](https://pip.pypa.io/en/stable/cli/pip_install/):
  `--progress-bar=auto` is the default.
- [Cargo configuration](https://doc.rust-lang.org/cargo/reference/config.html#termprogresswhen):
  terminal progress defaults to `auto` with explicit overrides.
- [Command Line Interface Guidelines](https://clig.dev/#progress): long-running
  commands should remain observable without emitting animations to
  non-interactive output.
