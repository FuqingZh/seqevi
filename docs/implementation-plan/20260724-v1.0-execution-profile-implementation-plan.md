# Adapter Execution Profile Implementation Plan

> Status: in progress
> Date: 2026-07-24
> Target: high-frequency `eggnog` and `interpro-pfam` CLI use

## Outcome

Make the common annotation command describe the biological job rather than
repeat machine setup:

```bash
seqevi annotate \
  --profile interpro-pfam-38.1 \
  --fasta proteins.fasta \
  --output results/pfam
```

The same profile mechanism must work for all explicit first-party adapters
without coupling SeqEvi to resource acquisition.

## External Convention Review

The implementation follows the stable design pattern shared by mature CLI
tools, while avoiding features that do not fit SeqEvi:

| Tool | Current convention | SeqEvi consequence |
| --- | --- | --- |
| Cargo | TOML, user and directory-local layers, environment and `--config` overrides | Keep TOML and explicit one-run overrides; do not copy Cargo's full directory-tree merge |
| rustfmt | Project/ancestor TOML discovery and a command that prints default or minimal configuration | Provide a complete adapter-specific example, but keep profile selection explicit |
| Codex | User TOML, trusted project layers, CLI overrides and separately selected profile configuration | Use a clear named-profile selector and keep each reusable profile independently inspectable |
| Claude Code | JSON rather than TOML; user, project, local, managed and CLI layers; schema-backed validation | File format is not the universal rule; explicit scope, precedence and validation are |

Primary references:

- [Cargo configuration](https://doc.rust-lang.org/cargo/reference/config.html)
- [rustfmt configuration](https://rust-lang.github.io/rustfmt/)
- [Codex configuration basics](https://learn.chatgpt.com/docs/config-file/config-basic)
- [Claude Code settings](https://code.claude.com/docs/en/settings)
- [Claude Code CLI reference](https://code.claude.com/docs/en/cli-usage)

The review supports the optimized direction with two refinements:

1. use separate complete profile files rather than dynamic nested profile
   tables in one TOML document;
2. make templates and validation first-class, but do not generate hidden
   defaults or auto-discover repository configuration.

## Contract Decisions

- Named profiles live under the XDG user configuration directory.
- `--config PATH` selects the same schema from an exact caller-supplied path.
- Named profile, exact config and complete explicit identity are mutually
  exclusive.
- `--resource` replaces `--database` without an alias.
- Profile operational defaults may be overridden per run.
- Adapter scientific parameters remain code-owned and contract-versioned.
- External environment overlays apply to probes and execution.
- Unknown configuration is an error.

The authoritative behavior is defined in the
[execution profile contract](../architecture/20260724-v1.0-execution-profile-contract.md).

## Acceptance Criteria

1. A high-frequency user can run either official adapter using only profile
   name, FASTA, output and optional operational overrides.
2. An automation caller can select an exact TOML with `--config`.
3. Explicit mode remains available and auditable.
4. Invalid or ambiguous configuration fails before Store access or tool launch.
5. Runtime environment selection is consistent across probe and execution.
6. Scientific evidence identity is unchanged between profile and explicit
   invocation with the same resolved inputs.
7. Help, docs, focused tests and `pdm run check` agree.
