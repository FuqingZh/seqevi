## Goal And Decision

Prevent a completed annotation batch from failing solely because artifact
transfer shares the short ClaimSession metadata-finalization budget.

Use ORAS CLI with an unmodified zot Registry for shared artifact transfer and
storage, with standard OCI artifact manifests and stable tags retaining blobs.
SeqEvi continues to own scientific evidence, media-type consistency,
ClaimSession authority, and evidence finalization. Reusing an implementation,
not merely copying OCI route names into a new upload server, is the preferred
way to remove upload-engine complexity.

This revision includes shared Registry integration, new-client legacy reads,
and bounded OCI Image Layout interoperability verification. Historical-data
migration and complete offline-cache export/import are deferred. It does not authorize deployment,
production writes, migration, release, or deletion. Current runtime contracts
remain authoritative until tested successors are delivered with code.

R1 below remains independent of Registry selection.
Unit 0 has qualified the native route and delivered an integration
specification, accepted on 2026-08-31 for Unit 1 (R2) implementation.
A failed qualification returns to design review; it does not authorize a
custom protocol or Registry fork. The decisions below explicitly replace the
earlier stronger recovery, capacity, and compatibility requirements.

### Confirmed simplification decisions — 2026-08-31

- Local directory annotation keeps SQLite and POSIX CAS, with no ORAS or zot
  dependency. Do not turn OCI Image Layout into a third live evidence Store.
- OCI-enabled shared clients invoke ORAS directly. Reuse standard installation
  and Registry login/credential mechanisms; do not build a SeqEvi installer,
  credential vault, login proxy, or custom transfer-recovery engine.
- Enabling OCI is an explicit client-upgrade boundary. Preserve legacy data
  reads in upgraded clients, not an OCI-to-old-client byte relay.
- New artifacts use OCI; existing POSIX artifacts remain readable and are not
  bulk-migrated or deleted in this delivery.
- Use native client/Registry transfer recovery and cleanup. No additional
  byte-offset persistence, power-loss resume guarantee, reservation ledger,
  exact expiry policy, or SeqEvi cross-store garbage collector is required.
- Publish ordinary tagged OCI artifacts and do not auto-expire their tags.
  Registry GC owns storage garbage, not SeqEvi evidence lifecycle. A published
  artifact with no successful evidence registration may remain stored.
- A later annotation with no evidence record may recompute. Identical complete
  blobs can be reused by digest, but that does not imply annotation-cache reuse
  or automatic recovery of an interrupted SeqEvi invocation.
- Layout work is limited to standard artifact round trips. Full cache migration
  additionally needs evidence metadata and is not a first-delivery promise.

## Triggering Evidence

The 2026-08-29 eggNOG invocation completed an external-tool batch after about
4 hours 48 minutes, then failed while displaying `Saving batch 3` with
`ClaimSession artifact upload failed`. The controller observed temporary Store
unavailability. The failed batch retained a 1,174,075-byte normalized artifact
and a 1,357,169-byte raw artifact: together about 2.41 MiB, not near 512 MiB.
The retained error lacks its transport exception chain. Service journals were
not accessible to the diagnostic caller; the initiating network/service/I/O
failure remains unproven. The structural defects below are not proof that
either one caused this particular incident.

The pre-R1 client limited one `finalize_many()` operation to at most 30 seconds
and cut off uploads one second earlier to reserve reconciliation time. The
incident exposes the risk of putting bulk transfer inside that control-plane
window; it does not by itself identify the underlying Store interruption.

Retained artifacts may reproduce the transfer without rerunning eggNOG only
when input, digest, byte size, ToolRuntimeDigest, ResourceID, semantic
parameters, and harness lineage are mechanically identifiable.

## Accepted OCI / R2 Boundaries

### Responsibility split

| Owner | Responsibility |
| --- | --- |
| ORAS and Registry | Native transfer/recovery behavior, blob integrity, storage, retrieval, and storage-level cleanup |
| OCI artifact manifest | Storage reference retaining a blob; standard descriptor metadata |
| SeqEvi | Evidence identity, media-type consistency, ClaimSession leases and fencing, finalization, and evidence readback |
| Deployment/operator | Registry configuration, access boundary, capacity monitoring, native GC/retention, and backup policy |

No container image is created from the annotation data. The exact artifact
bytes and their existing SHA-256 identity remain unchanged. A manifest digest
is a separate storage-reference identity and must never replace an artifact
digest in an EvidenceKey or scientific result.

Use supported Registry APIs, not Registry-private filesystem layouts. Keep
Registry mechanics at the shared-Store boundary; local POSIX Store operation
must not acquire a mandatory Registry dependency. CephFS is a target
deployment acceptance environment, not a domain-model dependency.

### Client setup and distribution

The ordinary annotation command continues to accept one Store path or URL.
The shared service advertises its configured Registry through a typed discovery
seam; the Registry itself does not discover SeqEvi configuration. Discovery
provides endpoint/reference information, not reusable Store secrets.

Native OCI clients install a pinned ORAS release using its standard supported
installation methods and log in to the Registry only when required. Reuse
standard Registry credentials or credential helpers; credential presence alone
does not prove read/write permission. Missing ORAS or unsupported configuration
must be reported before expensive annotation starts, with actionable setup
guidance, no automatic installation, and no silent switch to another Store.

Managed OCI execution needs a newly published digest-pinned runtime containing
ORAS. Existing kit images are not silently upgraded. The actual inner execution
environment must have Registry network access and explicitly supplied scoped
credentials/CA configuration; host login is not automatically container login.
Do not mount an entire host credential store by default. Unit 0 freezes and
tests this configuration seam using standard ORAS options, not new authentication
semantics. Preserve the existing supported platform matrix.

Registry authentication does not provide authentication for `seqevi serve`.
The current private-network Store boundary remains; public exposure is out of
scope. No cluster-specific address, mount, or credential is a package default.

### Staging precedes authority-sensitive finalization

The successor `finalize_many()` flow is:

1. Validate proposed commits and deduplicate exact artifact identities.
2. Ensure each blob is uploaded, verified, and retained by a confirmed OCI
   artifact manifest, or resolve an already retained legacy artifact.
3. Re-check local session-loss state and capture fresh ClaimSession authority.
4. Start one short metadata deadline, bounded by 30 seconds and the applicable
   authority deadline, preserving reconciliation runway.
5. Finalize all split metadata batches and reconcile ambiguous outcomes
   within that same deadline.

Upload completion and manifest publication are not evidence publication.
Authority loss prevents finalization even if storage staging succeeded.
Retained but unreferenced artifacts may remain after failure; their existence
is never reported as a completed annotation.

Full artifact SHA-256 verification belongs to byte ingestion/completion and
verified download, not to metadata finalize. Finalize checks trusted retained
storage references, digest/size metadata, media-type consistency, and authority
without reading the entire artifact. HEAD proves byte identity/size at the
trusted storage boundary, not SeqEvi's authoritative media-type registration.

### Prefer standard wire behavior

Follow returned `Location` values, including opaque query parameters, and
standard OCI range/completion semantics. Do not reconstruct upload URLs.
Validate discovered destinations against the configured trust boundary;
redirects must not leak credentials.

Remove the proposed custom `artifact-upload-v1` protocol and
`/v1/artifact-uploads/*` session API from the preferred route. Do not require
a non-standard chunk checksum, total-size declaration at OCI initiate, or
custom offset headers.

Keep existing direct-CAS APIs for non-OCI deployments and legacy artifact reads.
Enabling OCI requires upgraded clients and a pre-compute compatibility check;
an unsupported client must fail clearly rather than compute and then fail at
upload. Do not build a zot-to-old-client byte relay. Unit 0 freezes how service
mode and minimum client capability are enforced, without treating a silent old
client as OCI-capable. Leave `/health` unchanged and use a separate discovery
seam. No transparent fallback may conceal OCI configuration or auth failures.

### Supported transfer envelope

| Property | Accepted target |
| --- | --- |
| Representative artifact | Verify 512 MiB transfer and exact downloaded bytes; no guaranteed recovery at every link speed |
| Per-artifact staging budget | Preserve the 900-second outer budget, including native retries and manifest publication/readback |
| Request timing/recovery | Use pinned ORAS/Registry native behavior; document actual limits rather than recreating HTTPX phase controls |
| Interruption or restart | Native support only; no additional partial-upload or power-loss resume contract |
| Completed content | Reuse complete blobs that still exist and are accessible by digest |

Use one monotonic absolute budget; no chunk, retry, or Store restart resets it.
Preserve active cancellation and exact reader/HTTP-task cleanup ownership.
Never abandon background work to claim a deadline was met.

Leave HTTP retries, backoff, range recovery, and chunk selection to the selected
client. Do not add a second retry/resume state machine around it. SeqEvi owns
the outer deadline, cancellation, sanitized diagnostics, and evidence authority.
If publication outcome is uncertain, standard digest/reference readback may
establish completion; otherwise report failure without finalizing evidence.
Do not blindly relaunch on auth, permission, integrity, cancellation, authority
loss, or exhausted-budget failures. Retransmission may start a blob over.

The earlier 1 MiB/s guaranteed-recovery envelope, one-interruption success
requirement, server-restart resume gate, and chunk-size comparison matrix are
withdrawn. Do not add persistence/recovery machinery for generated annotation
output across SeqEvi process or machine restarts; such reuse is not promised.

### Capacity, expiry, and durability qualification

Use native Registry upload cleanup, retention, and GC configuration, with
operator-owned capacity monitoring and applicable filesystem/storage quotas.
No exact 4 GiB reservation ledger, eight-session admission requirement,
durable-byte-refreshed one-hour idle expiry, or 24-hour absolute expiry remains.
Do not claim the native policies are equivalent to those withdrawn requirements.

Do not require each PATCH acknowledgment to survive power loss, or add offset
journals, sync-error qualification matrices, or full-prefix recovery machinery.
Final content integrity and no false evidence completion remain required.
Successful hashes, normal process restart, and HTTP success do not by themselves
prove power-loss durability; report the actual native storage/configuration
boundary without adding a stronger SeqEvi guarantee.

Initial qualification uses a single Registry instance. The earlier proposed
lock in `seqevi serve` is not a substitute for the Registry's storage ownership
model. Multi-instance/shared-root behavior requires separate evidence.

### Manifest retention and GC

Upload bytes, confirm the retaining manifest, then finalize evidence.
Use standard OCI artifact descriptors; do not place evidence authority or
ClaimSession state in manifests.

A naked completed blob is not sufficient retention proof. Registry GC can
collect it even if PostgreSQL references its digest. Unit 0 must freeze:

- deterministic repository/reference and manifest construction rules;
- the mapping between existing artifact identity and retaining manifest;
- idempotent retention/readback under lost responses and concurrent clients;
- handling of media-type conflicts without changing byte identity;
- retention rules that protect all finalized evidence.

The qualified specification derives stable tags from the canonical manifest
digest, not only the raw blob digest, so metadata differences cannot move an
older manifest's retaining tag. Raw scientific identity remains unchanged.
Publish ordinary OCI artifacts with those stable content-derived tags. Do not enable
tag auto-expiration for SeqEvi artifacts. Use zot native GC and its protection
delay; do not add a SeqEvi cleanup schedule, reconciliation scanner, orphan
collector, or database-to-Registry reference-counting service.

Registry reachability is not business reachability. A tagged artifact whose
evidence registration failed stays retained; the Registry cannot infer that
failure from SeqEvi metadata. Accept this space overhead. A later invocation
without a completed evidence record may rerun annotation; identical complete
blobs can save retransmission/storage, not establish a scientific cache hit.
Within a still-live invocation, retained output may be used only while ordinary
authority and deadline rules permit it. No cross-restart recovery is implied.

### OCI Image Layout scope

Use ORAS standard copy for a bounded Registry-to-Layout-to-Registry round trip,
verifying manifest and blob identities. Each validation/export directory has
one writer and is not a shared live cache. No custom archive format, global
concurrent `index.json` writer, or third EvidenceStore backend is introduced.

Layout contains OCI artifacts, not the complete SeqEvi evidence database.
Importing it does not publish completed evidence or guarantee offline cache
hits. User-facing full-cache export/import, coordinated metadata snapshots,
historical-data migration, and their restore workflow are deferred.

## Non-Goals And Superseded Proposals

- No extension of the metadata-finalize deadline to accommodate transfer.
- No scientific schema, EvidenceKey, lease, or generation-fencing changes.
- No download or redistribution of caller-owned annotation databases.
- No self-written OCI server, custom resume protocol, Registry fork, custom
  checksum extension, wrapper-level retry engine, or custom chunk scheduling.
- No mandatory Registry for the local Store or coupling of domain objects to
  Docker, Kubernetes, or CephFS.
- No new annotation progress/ETA/multi-input scheduler work.
- No expensive annotation rerun for validation when frozen output bytes suffice;
  this does not promise recovery of an unregistered artifact on later runs.
- No custom upload quota/expiry ledger, cleanup schedule, or orphan adoption.
- No historical-data migration or full offline-cache import/export in this delivery.
- No automatic production migration, rollout, release, or GC authorization.

R1 restores a bounded direct-PUT repair without reviving the earlier custom
resumable-upload proposal. The OCI direction supersedes the blanket prohibition
on a Registry dependency. Existing-data migration is not needed to enable new
OCI writes while preserving legacy reads. Earlier custom wire error codes,
sidecar layout, and capabilities are not requirements for the selected Registry.

## Delivery Units

### R1 — Immediate direct-CAS repair (authorized)

No Registry qualification dependency. One owning integrator writes the workspace;
subagents review design and tests read-only. Preserve the existing qualification
records. This slice delivers code, tests, and successor storage authority
together; no deploy, migration, release, or additional fault-injection probes.

1. Validate duplicate evidence keys, exact claims, and conflicting digest/size/
   media-type metadata before staging. Stage all artifacts before capturing a
   fresh authority snapshot and the existing 30-second metadata deadline.
2. Each unique artifact has one 900-second monotonic total deadline. HTTP
   connect/read/write/pool operations have a 60-second phase timeout, clamped
   to remaining total time. This is HTTPX phase timing, not a guaranteed
   minimum-throughput watchdog. Multiple sequential artifacts do not share a
   900-second call-wide budget; heartbeat continues during staging.
3. Preserve one deadline across split metadata batches and reconciliation.
   Session loss before/after staging prevents metadata finalization. Retain
   existing reader, HTTP-task, and Store-close cleanup ownership.
4. Keep existing PUT wire behavior, no automatic PUT retry and no partial
   resume. A later invocation may safely PUT the same digest; this is not
   evidence publication or a same-invocation recovery guarantee.
5. Report upload phase, digest, size, elapsed/remaining time, request ID, and
   exception type chain in errors; preserve the actual cause internally.
   Reuse service JSON logging, correlate a validated request ID, and never
   include credentials, arbitrary exception URLs, or body bytes in the normal
   CLI summary or service record. Raw programmatic causes remain available;
   library callers must redact them before publishing full tracebacks.
6. Move upload filesystem/hash operations off the service event loop. Bound
   active file writers and pending I/O; await admitted work and temporary-file
   cleanup before propagating cancellation. An uninterruptible filesystem
   operation may delay cancellation; do not claim a hard wall-clock bound or
   release a worker slot early. This is not Registry disk-quota admission or a
   guarantee against arbitrary slow clients holding all upload slots.
7. Keep full-file verification on finalize, existing artifacts, and downloads
   in R1. Removing finalize rehash requires a trusted verified-storage record
   and an immutable-CAS boundary; filename/size alone is insufficient. That
   optimization belongs to R2 and must not grow a second upload engine here.

Acceptance: regression showing staging exceeding the old 29-second window
while metadata gets a fresh deadline; staging/authority failure cannot finalize;
HTTP timeout and cleanup coverage; event-loop responsiveness and cancellation
ownership tests; unchanged corruption rejection; SQLite/PostgreSQL seams;
representative synthetic artifact transfer; `pdm run check` and Markdown links.
No expensive annotation rerun is required. A missing PostgreSQL or scale result
is reported as an evidence gap, not a pass.

Limits: R1 does not establish the former 512 MiB/1 MiB/s interruption/restart
recovery envelope, O(1) finalize, machine-crash durability, or production repair.
That stronger recovery envelope is no longer an R2 requirement either.
R2 remains gated on Unit 0 or a separately accepted immutable-storage design.

### Assignment and writing ownership

Before dispatch, the coordinator records each task's prerequisites, bounded
question or deliverable, exact read/write paths, input revisions/digests,
resource allocation, fault permissions, deadline, and expected evidence.
Return a small result with pass/fail/not-tested status, reproduction command,
observed outputs, limitations, and any proposed patch. Do not put agent
transcripts in project documentation.

Keep one writer per workspace and one owning integrator for the delivery.
In an AO-owned workspace, that integrator is the owning worker; the controller
remains read-only. Read-only subagents do not patch, stage, commit, or push.
Patch-producing contributors require an authorized isolated-workspace mechanism
and non-overlapping assigned files; they return changes for owner integration
and do not independently publish or merge the delivery branch. Without that
mechanism, serialize edits under the owner.

The owner retains shared files such as `src/seqevi/store/transport.py`,
`tests/test_shared_store.py`, dependency configuration, and architecture/index
documents unless a task explicitly reassigns one. Assignments use full
repository paths. Client and service lanes may propose interface changes, but
must not concurrently edit shared models or fixtures. Verification agents are
read-only by default. Tell every contributor that other work may exist and
that unrelated edits must be preserved; never revert another contributor's
changes to make a local check pass.

### Probe isolation and resource scheduling

- Give each mutating probe its own Registry instance, port, storage root,
  database, and fixture namespace within the approved task boundary. Separate
  directories on one disk are not performance isolation.
- Serialize representative transfer checks on shared storage unless resource
  independence is demonstrated and recorded. Record contention/environment
  conditions with each measurement; do not pool incompatible measurements.
- Fault injection, process termination, GC, capacity exhaustion, and cleanup
  may target only that lane's explicitly identified resources. Shared service
  restart, host-wide cache manipulation, and production-path mutation are not
  implied by a subagent assignment.
- The coordinator sets aggregate CPU, memory, disk, connection, and concurrency
  budgets before launch. A subagent cannot expand its test matrix or create
  nested agents beyond that allocation without renewed coordination.
- Cancellation or a failed prerequisite stops dependent work. Each lane must
  stop and reap its processes, reconcile ambiguous writes, and report leftover
  resources. A finished agent or disappeared terminal does not prove cleanup.

At each join, compare the exact candidate, code, configuration, input, and
fault-schedule identities. Conflicting findings or changed shared interfaces
invalidate the dependent result until reconciled; they are not resolved by
majority vote or by selecting the fastest passing run. Run integrated checks
on the assembled candidate even when every lane's focused checks passed, while
reusing expensive acceptance only under the frozen-lineage rule below.

## Compatibility And Verification

| Combination | Required result |
| --- | --- |
| Old client / non-OCI service | Existing PUT/GET and finalize semantics remain usable |
| Old client / OCI-enabled service | Explicit incompatibility rejection before expensive annotation; no OCI relay |
| New client / old non-OCI service | Existing direct transfer remains safe; no false claim of OCI capability |
| New client / qualified OCI service | Native ORAS transfer and tagged retention before evidence finalize |
| Legacy CAS / OCI-enabled shared Store | Upgraded clients read legacy and OCI references; new writes use OCI; no bulk migration/deletion |
| Local POSIX Store | No mandatory ORAS or Registry dependency |
| OCI Image Layout | Exact artifact round trip only; no completed-evidence or offline-cache import claim |

Unsupported additive discovery may fall back only on the documented
unsupported response. Authentication, malformed responses, and service outages
are not interpreted as old-service capability absence. Old configurations
cannot inherit an unverified 512 MiB recovery guarantee.

Focused coverage includes fresh authority after staging, authority loss
preventing finalize, one deadline across metadata batches, duplicate and
conflicting artifacts, ambiguous writes, Registry outage, digest-verified
downloads, cleanup failures, GC retention, compatibility, and safe diagnostics.
Redact credentials and upload capability URLs.

For this plan-only revision, use diff and repository Markdown-link checks.
It changes no runtime authority and requires no full package gate by itself.

R1 runtime delivery requires its slice-local checks above. Registry runtime
delivery additionally requires representative Registry/target-filesystem

Expensive evidence reuse requires unchanged, mechanically identifiable code,
Registry binary/image, harness, inputs, configuration, filesystem/environment,

applicable. Changed lineage invalidates reuse.

## Rollback, Risks, And Stop Conditions

- Keep legacy CAS and production metadata intact until separately approved
  cutover and retention policy allow otherwise.
- Reconcile unknown blob, manifest, and evidence writes before retry,
  cleanup, or rollback. Deleting a manifest can remove a GC root.
- Do not point an older client/service at a new storage layout without the
  proven compatibility path.
- Registry liveness, a HEAD response, and successful upload are not evidence
  finalization or complete durability proof.
- Stop if restore/rollback loses new writes, retained manifests fail to protect
  evidence, short finalize requires bulk hashing/copying, or native integration
  requires recovery or cleanup mechanisms outside the accepted scope.
- Stop if implementation requires new external coordination, authentication
  scope, a second custom stateful upload layer, or a Registry fork not approved
  in Unit 0.

## Completion

Plan revision completion means the agreed direction and gated work are
documented, not that Registry integration is production-ready. Runtime
completion requires matching contracts/code, verified mode/version admission,
legacy reads, integrity, representative native transfer, process cleanup,
portable setup and required repository gates. Deferred migration and full-cache
restore are not adapter acceptance gates. It does not establish that the failed batch can already
resume, nor authorize production cutover or a release.
