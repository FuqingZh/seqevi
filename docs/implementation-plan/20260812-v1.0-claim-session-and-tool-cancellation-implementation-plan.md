# ClaimSession and Tool Cancellation Implementation Plan

Version: v1.0

Date: 2026-08-12

Status: approved implementation plan; implementation not started

Target: post-0.2.0 shared Store claim hardening

Issue: [#28](https://github.com/FuqingZh/seqevi/issues/28)

Supersedes: [shared Store claim contention hardening plan](20260811-v1.0-shared-store-claim-contention-hardening.md)

## Goal

Replace per-key lease renewal with one `ClaimSession` per `annotate` invocation,
while retaining exact `EvidenceKey` claims and generation fencing. A session has
one O(1) heartbeat regardless of its key count. Loss of that session must cancel
an active external tool promptly and reap the complete process group.

The implementation is delivered in two dependent pull requests:

- **PR A: end-to-end session protocol and persistence** replaces the ephemeral
  0003 schema, per-key transport, row-by-row hot paths, and annotate-side
  per-key coordination with one functional session path and set-based
  persistence with SQLite/PostgreSQL parity.
- **PR B: cancellation and acceptance** adds generic `ToolRunner` cancellation,
  connects lease loss to that cancellation boundary, and proves the PostgreSQL
  pressure, fault-injection, and real C2 gates.

PR B is based on PR A and targets PR A until PR A merges. Neither PR may claim
release readiness before its own gates pass; the session design is accepted
only after both merge and the real C2 record is committed.

## Evidence and reason for replacement

Merged C2 evidence exercised 9,116 claims. The current client renews in chunks
of 250, while PostgreSQL renewal remains a per-key read/update loop followed by
a bulk tail refresh. One heartbeat wave therefore caused approximately 27,386
SQL executions. Four renew requests reached the approximately 25-second whole-
transaction limit and returned retryable `503` responses. Once the lease runway
was exhausted, the following ownership check correctly returned `412`.

That result proves the generation fence but rejects the current scaling unit:
heartbeat work grows with the number of evidence keys and competes with claim
acquire/finalize transactions. It also exposes a cancellation gap:
`ToolRunner.run()` waits for the external process and cannot currently react to
renewal failure, so adapter work can continue after ownership is lost.

The replacement changes the lease unit, not evidence identity. Exact-key claims
remain necessary to suppress duplicate computation and fence finalization.

## Decisions

### Session and key model

Each claim-capable `annotate` invocation opens exactly one `ClaimSession` before
its first claim acquire and closes it during structured cleanup. The session is
identified by a server-generated opaque `session_id` and a server-generated
secret `owner_token`. It owns one lease row with `generation`, `expires_at`, and
timestamps. The token is never logged or stored in result metadata.

Exact claims are separate rows keyed by the full existing `EvidenceKey` and
reference the owning session. Each row retains a positive, monotonically
increasing claim `generation`. Acquire returns cached, acquired, or busy in the
unique request order. Finalize succeeds only when all of these are true in the
same transaction:

1. the session ID and owner token identify the live session;
2. the session generation supplied by the client is current and unexpired;
3. the exact `EvidenceKey`, claim generation, and session ID match; and
4. immutable evidence is absent or is already byte-for-byte compatible under
   the existing terminal convergence contract.

Closing or expiring a session invalidates all of its unfinished exact-key
claims. A later acquire may reuse those keys with a strictly newer generation.
Terminal evidence and artifacts never depend on session lifetime.

### Timing and failure policy

Initial internal constants are a 120-second lease, a nominal 30-second jittered
heartbeat cadence, and a 90-second monotonic renewal budget. For every open or
renew attempt, the client captures `request_started` before transport. A
successful response sets the next monotonic renew deadline no later than
`request_started + 90 seconds`, not 90 seconds after receipt. The client also
conservatively maps the returned server `expires_at` into its monotonic clock
at receipt and clamps the deadline earlier by the required authority safety
runway. Server `expires_at` remains the authoritative fence; local monotonic
time only ensures the client stops before that authority can expire. Response
latency therefore consumes, and can never extend, the 90-second budget.

Retryable renew failures use a 1-to-5-second jittered delay, clamped to the
remaining deadline and honoring a larger valid `Retry-After` only when it still
fits. Jitter is per session and must not permit a heartbeat later than either
the conservative monotonic deadline or server authority.

These are internal safety constants, not user-facing lease knobs. A renew `503`
or transport failure is transient: retry within the same deadline while the
tool continues. A `412` means the generation/ownership fence is already lost
and triggers immediate cancellation without retry. Exhausting the 90-second
deadline, receiving malformed authority, or receiving a non-retryable renew
failure also marks the session lost and triggers cancellation.

### O(1) heartbeat and set-based persistence

`renew` locks and updates only the one session row and returns its refreshed
authority. It does not enumerate, lock, validate, or update claim-key rows, so
its database statement count and lock footprint are O(1) in session key count.

Acquire and finalize are set-based. PostgreSQL uses values/CTE/upsert/delete-
returning operations in canonical `EvidenceKey` order rather than Python
per-key `SELECT ... FOR UPDATE` and update loops. SQLite implements the same
observable transaction, ordering, generation, expiry, and result-alignment
contract using dialect-appropriate set operations. No backend may weaken the
exact-key fence to obtain parity.

### Internal HTTP protocol

The new routes are internal, versioned, and claim-capability gated:

- `POST /v1/internal/claim-sessions/open` creates one session and returns
  `session_id`, `owner_token`, `generation`, `expires_at`,
  `heartbeat_after_seconds`, and `renew_deadline_seconds`;
- `POST /v1/internal/claim-sessions/renew` accepts the exact session authority
  and returns refreshed authority; success is O(1);
- `POST /v1/internal/claim-sessions/close` accepts the exact session authority,
  invalidates unfinished claims idempotently for that authority, and returns a
  closed acknowledgement;
- `POST /v1/internal/claim-sessions/acquire` accepts session authority plus
  unique `EvidenceQuery` values and returns aligned cached/acquired/busy
  results with exact-key generations; and
- `POST /v1/internal/claim-sessions/finalize` accepts session authority plus
  exact-key generation-fenced commits and atomically consumes matching claims
  while preserving existing immutable evidence/artifact behavior.

`503` remains retryable service backpressure and includes `Retry-After`; `412`
means stale, expired, closed, or otherwise lost session/claim authority. `409`
and `422` preserve the current evidence-conflict and validation meanings.
Capability discovery advertises this protocol as one atomic capability; the
client never mixes session and per-key claim routes in one invocation.

There is no compatibility alias for the unreleased
`/v1/evidence/claims/{acquire,renew,release,finalize}` endpoints. They and their
per-key transport models are removed when the session routes land.

### Client context and legacy fallback

`ClaimSession` is a context-managed client API owned by the Store layer:

```python
with store.claim_session() as session:
    results = session.acquire_many(queries)
    outcomes = session.finalize_many(commits)
```

The context opens once, owns the heartbeat thread and cancellation state,
exposes `raise_if_lost()` and a cancellation signal, and closes once with
best-effort bounded cleanup. It does not expose owner tokens to `annotate`.
`annotate` uses one context around all batches and adapters in the invocation.

For a v0.2.0 service that does not advertise the session capability, the client
uses the existing legacy `EvidenceStore` lookup/commit path with no duplicate-
suppression claim guarantee. It does not fall back to the unreleased per-key
claim endpoints. Authentication, malformed capability, and server errors do
not silently select legacy behavior.

### Tool cancellation

`ToolRunner.run()` gains a generic cancellation input independent of claims,
adapters, HTTP, and Store types. It periodically waits for either process exit,
timeout, or cancellation without busy-spinning. Cancellation raises a distinct
structured runner error whose result records cancellation separately from
timeout.

On cancellation or timeout, the runner records the process-group ID, sends
`SIGTERM` to that group, and allows exactly a 5-second grace period. At the end
of the grace it probes process-group existence independently of the original
group leader. If any member remains, it sends `SIGKILL` to the group even when
the leader already exited, tolerates the probe/signal disappearance race, waits
the direct child to reap it, and does not return until the process group is
confirmed absent. Existing `start_new_session=True`, argument arrays,
`shell=False`, stdout/stderr paths, and process-group cleanup on exceptional
exit remain invariant. `annotate` maps session loss back to
`EvidenceClaimLostError` only after termination, group-absence confirmation,
and reap complete.

## Migration 0004 and upgrade contract

`0004_claim_sessions` replaces the ephemeral 0003 `evidence_claim` layout with
session and exact-key session-claim tables. The migration does not attempt to
translate live 0003 leases: a supported upgrade first quiesces all Store
services and claim-capable clients, then 0004 drops/invalidates every ephemeral
0003 claim and installs the new schema.

The existing automatic startup migration and database migration lock are not
proof that 0003 clients are quiesced. PR A therefore adds a fail-closed 0004
maintenance preflight. Ordinary service startup may migrate only through 0003;
if the database is at 0003, startup refuses to apply 0004 and reports the
documented maintenance command. An operator must stop every old service and
client, verify the deployment's writer/process readback is empty, and invoke
the explicit 0004 upgrade command with a single-use maintenance acknowledgement
bound to the target database and expected current revision. Under the existing
exclusive migration lock, the command rechecks revision and rejects new Store
traffic, verifies no live/unexpired 0003 claims remain after the quiescence
window (or explicitly invalidates expired rows), applies 0004, and records
successful completion before new services start. An acknowledgement never
causes normal startup to skip this preflight and cannot authorize a different
database/revision. Failure or uncertainty aborts before destructive DDL.

PR A updates the checked-in Store operations runbook with stop, writer/process
readback, maintenance command, schema verification, restart, and rollback
steps. It also tests automatic-startup refusal, missing/stale/wrong-target
acknowledgement, live 0003 claim refusal, lock serialization, pre-DDL failure,
and the accepted quiesced upgrade on SQLite and PostgreSQL. No production
deployment is performed by these documentation or implementation slices.

Only ephemeral claim coordination is invalidated. The `sequence`, `evidence`,
artifact metadata, artifact bytes, and DuckDB result schema remain untouched.
Downgrade removes session coordination and recreates an empty 0003-compatible
claim table; it never reconstructs expired ownership. Rollback therefore
requires the same quiescence and returns clients to legacy or 0003 behavior
without changing terminal evidence/artifacts.

## Preconditions and invariants

PR A starts from the exact current `main` containing PRs #25-#27. PR B starts
from PR A. Before migration or real acceptance, operators must prove all old
claim writers quiesced. The PostgreSQL pressure harness and real C2 inputs,
runtime images, caller-owned databases, and credentials must be available but
remain external to SeqEvi.

Both slices preserve these invariants:

- evidence identity is the unchanged immutable `EvidenceKey`;
- a current exact key generation is required for finalization;
- terminal evidence is immutable and wins convergence races;
- artifacts are caller-read-only and content-addressed;
- heartbeat work is O(1) per session, independent of key count;
- acquire/finalize do not use per-key SQL execution loops;
- requests reject duplicate keys and preserve aligned unique input order;
- SQLite and PostgreSQL expose identical lifecycle and failure semantics;
- no external process remains running or unreaped after cancellation returns;
- the public `annotate` CLI and profiles do not expose session machinery.

## Delivery slices

### PR A: end-to-end session protocol and persistence

Predecessor: merged PRs #25-#27 and this approved plan.

1. Add 0004 and schema/value objects. Prove a quiesced upgrade discards 0003
   claims while preserving all evidence and artifact rows/references.
2. Add the fail-closed 0004 maintenance preflight and PR A runbook. Prove normal
   automatic startup cannot cross 0003, uncertain/live writers abort before
   DDL, and the explicit database/revision-bound quiesced path is serialized.
3. Implement backend-neutral persistence behavior with PostgreSQL set-based
   acquire/finalize and one-row renew; implement matching SQLite semantics.
4. Add the internal session routes and update capability discovery while the
   old implementation remains available only inside the branch transition.
5. Implement the Store `ClaimSession` context, heartbeat retry policy, exact
   `503`/`412` handling, close cleanup, and v0.2.0 legacy fallback.
6. Convert `annotate` to open exactly one context per invocation and route all
   claim acquire/finalize and cleanup through it. Prove real in-process and HTTP
   claim-capable annotation plus legacy fallback before deleting anything.
7. Remove annotate-side per-key renewal and the unreleased per-key endpoint,
   transport, and scheduler code only after the end-to-end session path passes;
   do not retain aliases or a dual protocol at the PR A head.

PR A non-goals are lease-loss cancellation of a running external process,
fault-injection acceptance, real C2 execution, and release acceptance. It is
accepted when fail-closed migration preflight/runbook, protocol, set-based
behavior, O(1) SQL-count assertions, client timing/fallback, end-to-end
claim-capable annotation, and SQLite/PostgreSQL parity tests pass, plus
`pdm run check` with PostgreSQL. Its exact head is functional without any
per-key claim path, even before PR B adds prompt cancellation after asynchronous
lease loss.

### PR B: cancellation and acceptance

Predecessor: PR A exact accepted head.

1. Add generic runner cancellation, structured cancelled results/errors, and
   deterministic process-group termination tests using the 5-second grace.
2. Connect the PR A session's monotonic loss signal to every external tool
   execution without changing acquire/finalize, public CLI, or adapter behavior.
3. Inject renew `503`, `412`, timeout, close failure, and process termination
   races. Prove transient retry, immediate/exhausted cancellation, reap, and no
   unauthorized finalize.
4. Run the PostgreSQL pressure matrix and real C2 acceptance below; preserve
   secret-free logs and database readback as durable benchmark evidence.
5. Update the authoritative architecture/validation/operations documents from
   measured final behavior and replace this plan's “implementation not started”
   status only after all gates pass.

PR B has no license to revise scientific parameters, concurrency defaults, or
adapter/runtime behavior to make C2 pass. A resource ceiling is reported, not
hidden by reducing the required 64-thread gate.

## Verification and acceptance

### Focused automated tests

- migration upgrade/downgrade on SQLite and PostgreSQL, including non-empty
  0003 claims and unchanged evidence/artifact digests and counts;
- automatic startup refusal at 0003, maintenance acknowledgement binding,
  live-writer/claim refusal before DDL, migration-lock serialization, and
  runbook command/readback coverage on SQLite and PostgreSQL;
- open/renew/close lifecycle, token redaction, stale generation, expiry,
  idempotent close, duplicate keys, aligned results, terminal convergence, and
  concurrent acquire/finalize races on both databases;
- SQL instrumentation proving session renew has constant statement count at 0,
  1, 250, 1,000, and 9,116 claims and proving acquire/finalize do not issue a
  statement per key;
- HTTP route/model/status/capability tests, including retryable `503`, immediate
  `412`, invalid `Retry-After`, bounded jitter/deadline, delayed successful
  responses consuming the budget, clamp to server `expires_at`, and no silent
  fallback on authentication/server/protocol errors;
- v0.2.0 health/capability absence selecting only legacy lookup/commit;
- PR A end-to-end local and HTTP annotation using one context across batches,
  close on every exit path, exact-key generations passed to finalize, and no
  surviving per-key client/service route;
- runner exit-before-cancel, cancel-before-exit, cancel-during-wait, timeout,
  `SIGTERM` success, forced `SIGKILL` after five seconds, group disappearance,
  and guaranteed direct-child reap, including the case where the leader exits
  but only a descendant ignores `SIGTERM`.

### PostgreSQL pressure gates

Run the repository-owned pressure harness at 100, 1,000, 3,000, and 9,116 exact
claims with concurrent acquire, heartbeat, and finalize traffic. Record input,
PostgreSQL version/settings, client concurrency, SQL execution counts,
transactions, p50/p95/p99 latency, `503`/`412` counts, pool wait, lock wait,
`pg_stat_activity`, residual sessions/claims, and terminal evidence counts.

Acceptance requires heartbeat SQL and latency not to scale with key count; no
heartbeat transaction may approach the configured transaction deadline; no
ownership loss may occur without injected expiry/fencing; set-based
acquire/finalize must remain within bounded statement counts; and all session
and claim rows must be absent after clean completion.

### Fault injection

Inject consecutive renew `503` responses both shorter and longer than the
90-second deadline, an immediate `412`, a successful response delayed after
server commit, delayed/malformed failures, database pool/lock pressure, client
interruption during acquire/finalize/close, a tool leader that exits on
`SIGTERM` while its descendant ignores it, and terminal evidence appearing
during a retry race. Verify the documented retry/cancel decision, request-start
deadline and server-expiry clamp, exact fencing, immutable convergence,
leader-independent process-group kill/absence, direct-child reap, and cleanup
readback for every case.

### Real C2 gate

Use the real C2 two-process run at 64 annotation threads per process over 9,116
evidence identities with 9,115 overlapping identities. Both processes must exit
0, terminal evidence count must be exactly 9,116, and the later replay must
report exactly 9,115 cache hits and zero recomputed overlap records. No claim
session may be lost, no external tool may outlive its authority, no residual
session/claim rows may remain, and artifact/evidence integrity readback must
match the input contract.

The 64-thread gate is acceptance, not a tuning suggestion. Lower-concurrency
runs may diagnose a failure but cannot replace it. Preserve commands,
environment, exact revisions, secret-free logs, database readback, timing, and
result counts in a benchmark record.

Each PR runs focused tests first and the repository canonical gate last:

```text
SEQEVI_TEST_POSTGRES_URL=<configured PostgreSQL URL> pdm run check
```

Final documentation validation checks every changed relative link, status and
supersession edge, and confirms `docs/README.md` names the active plan.

## Non-goals

No Redis, etcd, Consul, scheduler, or other coordination service is introduced.
No public CLI/profile change, adapter behavior change, `EvidenceKey` change,
DuckDB schema change, scientific parameter change, production deployment, or
user-facing lease/timing knob is in scope. SeqEvi does not acquire or distribute
caller-owned databases/resources, install packages, or expose a container
engine. General adapter cancellation APIs beyond the generic runner signal and
the existing official adapters are also outside this plan.

## Risks and mitigations

- **Set-based SQL differs by dialect.** Keep one behavioral suite for both
  backends and add real PostgreSQL race/plan evidence; do not emulate parity
  with per-key loops.
- **A session is a larger failure domain.** One lost heartbeat cancels the
  invocation by design; exact-key generations prevent a stale invocation from
  finalizing any subset after loss.
- **Cancellation races with normal exit/finalize or leader exit.** Make loss
  monotonic, make runner termination idempotent, probe the group rather than
  only the leader, confirm group absence and reap before propagation, and
  revalidate exact authority inside finalization.
- **Quiescence is violated during 0004.** Refuse a rolling mixed-protocol
  upgrade and ordinary automatic 0004 startup; require the database/revision-
  bound maintenance preflight, stop clients/services, verify no writers, apply
  under the migration lock, verify schema, then restart.
- **Jitter, response delay, or retry masks deadline exhaustion.** Start the
  monotonic budget before transport, clamp it to server `expires_at` with a
  safety runway, and use deterministic clock/random injection in tests.
- **C2 passes while SQL pressure remains hidden.** Require statement/lock/pool
  evidence as a separate gate, not only successful process exits.

## Rollback

Before either rollout or rollback, follow the PR A maintenance runbook: stop
every Store writer, verify the writer/process boundary empty, and acquire the
exclusive migration lock. Application rollback before 0004 simply restores the
previous release. After 0004, the explicit downgrade preflight requires a fresh
target/revision-bound acknowledgement and recreates empty ephemeral 0003 claim
state; all in-flight session/key authority is deliberately lost and clients
must restart. Evidence rows, artifact metadata/bytes, DuckDB outputs, and caller
resources remain untouched and are verified by count/digest readback before
restart. If PR B cancellation fails acceptance, rolling back to PR A retains a
complete one-session annotate/acquire/finalize path with no per-key protocol,
but asynchronous lease loss cannot yet stop an active external tool promptly;
do not advertise full claim hardening or deploy that intermediate head for
long-running shared-Store annotation. Never restore mixed per-key/session
clients or bypass the maintenance fence as a rollback mechanism.
