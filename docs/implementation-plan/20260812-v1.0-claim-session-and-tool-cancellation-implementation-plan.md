## Goal

Replace per-key lease renewal with one `ClaimSession` per `annotate` invocation,
while retaining exact `EvidenceKey` claims and generation fencing. A session has
one O(1) heartbeat regardless of its key count. Loss of that session must cancel
an active external tool promptly and reap the complete process group.

The implementation is delivered in two dependent pull requests:

- **PR A: end-to-end session protocol and persistence** replaces the ephemeral
  0003 schema, per-key transport, row-by-row hot paths, and annotate-side
  per-key coordination with one functional session path and set-based
  persistence with SQLite/PostgreSQL parity.
- **PR B: cancellation and acceptance** adds generic `ToolRunner` cancellation,
  connects lease loss to that cancellation boundary, and proves the PostgreSQL
  pressure, fault-injection, and real C2 gates.

PR B is based on PR A and targets PR A until PR A merges. Neither PR may claim
release readiness before its own gates pass; the session design is accepted
only after both merge and the real C2 record is committed.

## Evidence and reason for replacement

Merged C2 evidence exercised 9,116 claims. The current client renews in chunks
of 250, while PostgreSQL renewal remains a per-key read/update loop followed by
a bulk tail refresh. One heartbeat wave therefore caused approximately 27,386
SQL executions. Four renew requests reached the approximately 25-second whole-
transaction limit and returned retryable `503` responses. Once the lease runway
was exhausted, the following ownership check correctly returned `412`.

That result proves the generation fence but rejects the current scaling unit:
heartbeat work grows with the number of evidence keys and competes with claim
acquire/finalize transactions. It also exposes a cancellation gap:
`ToolRunner.run()` waits for the external process and cannot currently react to
renewal failure, so adapter work can continue after ownership is lost.

The replacement changes the lease unit, not evidence identity. Exact-key claims
remain necessary to suppress duplicate computation and fence finalization.

## Decisions

### Session and key model

Each claim-capable `annotate` invocation opens exactly one `ClaimSession` before
its first claim acquire and closes it during structured cleanup. The session is
identified by a server-generated opaque `session_id` and a server-generated
secret `owner_token`. It owns one lease row with `generation`, `expires_at`, and
timestamps. The token is never logged or stored in result metadata.

Exact claims are separate rows keyed by the full existing `EvidenceKey` and
reference the owning session. Each row retains a positive, monotonically
increasing claim `generation`. A separate durable per-`EvidenceKey` generation
high-water row is the allocator and survives claim/session reclamation. Acquire
atomically locks/upserts that row and allocates `high_water + 1` only when
ownership transfers to a different session; same-session replay never advances
it. High-water rows are coordination tombstones, contain no owner/lease data,
and are not removed by the expired-session sweeper. Acquire returns cached,
acquired, or busy in unique request order. Finalize succeeds only when all of
these are true in the same transaction:

1. the session ID and owner token identify the live session;
2. the session generation supplied by the client is current and unexpired;
3. the exact `EvidenceKey`, claim generation, and session ID match; and
4. immutable evidence is absent or is already byte-for-byte compatible under
   the existing terminal convergence contract.

Closing or expiring a session invalidates all of its unfinished exact-key
claims. A later acquire may reuse those keys with a strictly newer generation.
Terminal evidence and artifacts never depend on session lifetime.

Expired coordination is reclaimed independently of client close. Every
open/acquire/finalize transaction performs at most one claim-row cleanup chunk:
lock and delete no more than 1,000 expired claim rows in canonical
`EvidenceKey` order, irrespective of how many sessions they belong to. A
separate statement deletes no more than 1,000 expired sessions whose candidate
predicate proves zero remaining claim rows, zero acquire-receipt headers, and
zero acquire-receipt item rows. The shared service's periodic sweeper and the
SQLite `LocalStore` lifecycle owner repeat these one-chunk transactions until
both chunks are empty. Thus one expired 9,116-key session is
cleaned across at least ten transactions rather than one unbounded transaction;
zero-claim cached-only/busy-only sessions first drain their receipts and are
then reclaimed rather than repeatedly violating restricted foreign keys.
Cleanup never deletes durable
generation high-water rows, uses the claim mutation lock order, is idempotent,
never deletes live sessions/evidence/artifacts, and has SQLite/PostgreSQL
parity. Close is an eager optimization, not the reclamation guarantee.

### Timing and failure policy

Initial internal constants are a 120-second lease, a nominal 30-second jittered
heartbeat cadence, and a 90-second monotonic renewal budget. For every open or
renew attempt, the client captures `request_started` before transport. A
successful response sets the next monotonic renew deadline no later than
`request_started + 90 seconds`, not 90 seconds after receipt. The client also
uses the server-relative `remaining_lease_seconds` returned by open/renew and
clamps the deadline to no later than
`request_started + remaining_lease_seconds - authority_safety_runway`. Anchoring
both limits at request start deliberately overcounts request and response
latency, needs no cross-machine wall-clock comparison, and cannot extend server
authority. The returned absolute `expires_at` remains the authoritative
generation fence and diagnostic timestamp, but is not converted into client
monotonic time. Response latency therefore consumes, and can never extend, the
90-second budget or the server-reported remaining lease budget.

Capability discovery is an authority-free probe with its own bounded transport
deadline. No session, receipt, claim, generation, or lease exists during that
probe; timeout or a response arriving after its probe deadline is terminal and
cannot be used to open. A valid timely capability response starts a distinct
30-second monotonic open-operation budget at client receipt. Immediately before
capability response serialization the service reads `server_time` from the
authorizing database. The client sends immediately with
`open_not_after = server_time + 30 seconds` and enforces its new local 30-second
open deadline independently. Response transport consumes the server admission
window exactly once: a response received about 20 seconds after serialization
leaves about 10 seconds before `open_not_after`; the client does not subtract
those 20 seconds again. Pre-handler capability queueing creates or extends no
authority because no open exists, and a valid response begins only the bounded
open phase. The client wall clock remains irrelevant, and it does not refetch
capability within one open attempt.

The client creates one opaque `open_request_id` and sends both admission anchor
fields. In the `/open` transaction, the service first looks up and locks that
request ID's existing receipt/tombstone. If present, it serializes and returns
the committed live or terminal result before inspecting the current
`server_time`/`open_not_after`. These admission anchors are non-semantic
transport fields excluded from the same-ID compatibility digest; every other
incompatible semantic open field remains `409`. Only when the ID is absent does
the transaction read current database time and validate that capability
`server_time` and `open_not_after` are present/canonical, `server_time` is not
after current database time, `open_not_after` is not expired, and the interval
between them is no more than 30 seconds. Any
missing, malformed, expired, or future-beyond-maximum deadline returns
pre-mutation `408` with stable wire code `open_request_expired`. Consequently a
request delayed in a proxy/server queue beyond `open_not_after` can never create
a session, including after an earlier tombstone has been swept. For an absent
ID, the conditional session-plus-receipt insert itself re-evaluates
`current_database_time <= open_not_after` at its linearization point, after all
lock waits, using PostgreSQL `clock_timestamp()` and a SQLite statement-time UTC
expression rather than a transaction-start timestamp. If the deadline crossed
while waiting, the conditional insert affects zero rows and the transaction
returns pre-mutation `408/open_request_expired`; no session or receipt exists.
Otherwise creation plus receipt commits atomically.
Repeating the same ID returns the identical `session_id`,
owner token, generation, and absolute expiry without creating another session,
but recomputes `remaining_lease_seconds` from current database time on every
replay and rejects expired/closing authority. The separately keyed open receipt
survives session close/deletion for 120 seconds—longer than the maximum open
request/in-flight horizon—and then is removed in the same row-bounded
sweeper. A replay of a closed/deleted session returns a terminal closed result
and never creates a replacement. Reuse with incompatible open fields is `409`.
`open_request_expired` is terminal for this open invocation; it cannot trigger
a capability refetch or a new anchor. Retryable `503` and transport
failures use 1-to-5-second jitter; a valid `Retry-After` is a minimum delay only
when it fits the remaining open budget, otherwise open fails. Every transport
timeout and sleep is clamped to the same deadline. Exhaustion, non-retryable
response, or malformed success fails the invocation before any adapter or
external tool starts; no session heartbeat exists until one open succeeds.

Retryable renew failures use a 1-to-5-second jittered delay, clamped to the
remaining deadline and honoring a larger valid `Retry-After` only when it still
fits. Jitter is per session and must not permit a heartbeat later than either
the conservative monotonic deadline or server authority.

These are internal safety constants, not user-facing lease knobs. A renew `503`
or transport failure is transient: retry within the same deadline while the
tool continues. A `412` means the generation/ownership fence is already lost
and triggers immediate cancellation without retry. Exhausting the 90-second
deadline, receiving malformed authority, or receiving a non-retryable renew
failure also marks the session lost and triggers cancellation.

Acquire has one 30-second monotonic operation budget starting before its first
request and clamped to current session authority. Each logical call creates an
opaque `acquire_request_id` and sends the ordered-query digest. Before receipt
lookup or mutation, the service canonically serializes the actual submitted
ordered query array and recomputes SHA-256. Canonical bytes are UTF-8 JSON with
array order preserved, object keys sorted, no insignificant whitespace, and
each `EvidenceQuery` represented by its complete validated transport fields;
duplicate-query rejection occurs before hashing. The recomputed digest must
equal the wire digest. In the same
transaction as acquire, the service stores a session-scoped receipt keyed by
`(session_id, acquire_request_id)` containing that digest and the complete
aligned cached/acquired/busy response. On replay, the recomputed digest must
equal both the wire digest and stored digest before outcomes are reconstructed
against the submitted queries. Any mismatch is `409` without receipt, claim,
generation, evidence, or reconstruction mutation. Thus the same ID plus an old
claimed digest and changed query content or order is rejected. A valid replay
reconstructs the identical response without new generations or mutations.
Independently, encountering a claim
already owned by the same live session returns acquired with its identical
generation. Therefore response loss after a committed mixed batch is safely
replayable.

Acquire receipts are normalized rather than storing duplicate key/record JSON.
One header stores request ID/digest; fixed-shape item rows store input index,
outcome, generation or busy expiry, and immutable evidence identity. Replay
reconstructs keys from the identical request and cached records from immutable
evidence. Neither table stores `EvidenceKey`, record JSON, or another
variable-width response copy. The request itself is bounded by the advertised
1,000-key batch maximum, and each logical batch retains one request ID/digest
through mutation and replay.

Receipt retention is independent of session lifetime. A receipt is protected
from deletion for 60 seconds from database `created_at`, covering the complete
30-second acquire/retry budget plus runway. After that age it is eligible for
set-based deletion even while the session remains live. Each session has a hard
limit of 1,000 receipt headers and 32,000 normalized item rows. Before accepting
a new request ID, the service transaction deletes one eligible item/header
chunk and checks both physical caps. If either cap would be exceeded, it returns
an explicit `503` with `Retry-After` and stable internal wire error code
`claim_receipt_capacity`; that code alone guarantees pre-mutation execution and
that no header, item, claim, or generation was created. The client may discard
the provisional operation start only for that exact code, wait before starting
a fresh 30-second mutation/replay budget, keep the heartbeat running, and bound
this admission wait only by live session authority minus runway. A generic
`503`, unknown error code, transport failure, or malformed response is
ambiguous and remains inside the already-started 30-second budget. Replays of
an existing ID remain available during their protected window and do not count
as new receipts.

Foreground cleanup deletes at most 1,000 normalized item rows per transaction in
`(created_at, session_id, request_id, input_index)` order; it then deletes at
most 1,000 now-childless headers in a separately bounded statement. Foreign
keys use restricted deletion, not cascading deletion. The periodic sweeper uses
these identical item/header bounds.
Empty-session cleanup never cascades an unbounded receipt set: it deletes a
session only after bounded item cleanup and childless-header cleanup have
removed every receipt, otherwise leaves it for a later chunk. Open-receipt
tombstones are separately deleted at most 1,000 rows per transaction. Receipt deletion never changes
claims, generation high-water, evidence, or artifacts and has identical
SQLite/PostgreSQL behavior.

Clean close performs exactly one transaction: it locks only the one session
row, atomically changes authority to irreversible `closing`, commits, and
immediately acknowledges. It never enumerates or locks exact keys and never
runs a reclamation chunk in the request. Every late
acquire/finalize/replay observes `closing` and fails without claim, generation,
evidence, artifact, or receipt mutation. In shared mode the service-owned
periodic sweeper exclusively performs subsequent transactions that reclaim at
most 1,000 `session_claims` rows each in canonical key order, then at most 1,000
receipt item rows, then at most 1,000 childless headers, and then at most 1,000
eligible open tombstones. An open receipt younger than 120 seconds is protected,
survives session deletion, and makes delayed replay return terminal closed; clean
close never deletes it merely to achieve an immediate zero-row readback. Header
and session foreign keys remain restricted, not cascading. The final transaction
deletes the session only after a locked zero-claim/zero-acquire-receipt readback;
the separately keyed protected open receipt is not part of that predicate. The
close request never waits for reclamation, and the sweeper eventually converges
the `closing` session.

SQLite has the same request semantics but an explicit in-process cleanup
owner. `ClaimSession.close()` still performs only the one O(1) invalidation and
returns; it wakes a `LocalStore`-owned sweeper. Before the outer `LocalStore`
context disposes its connection/engine, teardown joins that owner and drains
eligible coordination rows to a clean fixed point using only the same bounded
transactions. A protected open receipt remains until its 120-second retention
expires, so clean fixed point means no eligible claims, acquire receipts, or
sessions rather than deletion of a protected replay tombstone. If the process
crashes or teardown is interrupted, the next `LocalStore.open()` performs this
bounded startup drain before admitting a new annotation. No cleanup is moved
into the close request, and every transaction retains the PostgreSQL/SQLite
row limits. Crash/partition/expiry uses the same row-bounded sweeper order.

Retryable `503`, `Retry-After`, and transport
failures reuse the same request ID within the same budget while heartbeat
continues; `412` cancels immediately. Finalize starts with
`min(30 seconds, session authority remaining - safety runway)` and never retries
beyond the exact session/key generations. Only a result the service contract
explicitly guarantees occurred before transaction execution may be interpreted
directly. Every other non-definitive first result enters unknown-outcome:
timeout, disconnect, lost response, malformed/incomplete success, post-commit
`5xx`, response serialization/validation failure, or any unclassified result
that cannot prove non-execution. Terminal evidence is read back before
interpretation or retry. Matching immutable evidence is converged success;
conflicting
evidence raises the existing conflict; absence permits retry only while the same
authority remains live. Once any finalize attempt enters unknown-outcome state,
**every** later response or transport result—including `412`, `503`, timeout,
disconnect, and apparent success—is followed by terminal-evidence readback
before interpretation. Matching is success, conflict is conflict, absence with
live exact authority may continue within budget, and absence after authority
loss is failure. Mixed batches exclude converged keys from retry. In particular,
if the original transaction commits after an absent readback and a retry then
receives `412`, the mandatory second readback observes matching evidence and
reports success rather than false lease loss.

An initial batch finalize `412` is also always reconciled key by key before
reporting authority loss, because a v0.2.0 legacy commit may have won and
retired only a subset of the claims. Matching terminal evidence removes that
key from the pending batch as converged success; conflicting evidence fails the
batch. For every absent key, the client reads back the same session generation
and exact claim generation: lost/expired session or claim authority fails,
while absent keys whose exact authority remains live are retried as the reduced
batch under the original finalize request identity and unchanged monotonic
retry budget. No key that already converged is resubmitted. This is the same
per-key reconciliation rule used after an unknown outcome, not a blanket rule
that every initial `412` means every claim was lost.

### O(1) heartbeat and set-based persistence

`renew` locks and updates only the one session row and returns its refreshed
authority. It does not enumerate, lock, validate, or update claim-key rows, so
its database statement count and lock footprint are O(1) in session key count.

Acquire and finalize are set-based. PostgreSQL uses values/CTE/upsert/delete-
returning operations rather than Python per-key `SELECT ... FOR UPDATE` and
update loops. PostgreSQL acquire first derives the existing signed 64-bit
transaction advisory-lock ID for every requested `EvidenceKey`, deduplicates
the actual IDs, sorts them by signed numeric ID, and acquires them in that order.
It never orders advisory acquisition by `EvidenceKey`; multiple keys that
collide intentionally share one acquired ID. While retaining those locks, it discovers the requester and all
current owner session IDs without retaining session-row locks, then locks that
complete session set in one canonical phase sorted by stable opaque
`session_id`. It finally re-reads terminal evidence and claims in canonical
`EvidenceKey` order before deciding cached/acquired/busy, takeover, or
allocation. If the re-read discovers a different owner-session set, the
transaction rolls back and performs a bounded retry under the same acquire
request identity, monotonic operation budget, and authority clamp. It never
locks the requester and then acquires discovered owners in input or discovery
order. The key lock serializes empty-key claim creation with v0.2.0 legacy
publication, and the terminal recheck prevents returning `acquired` after
evidence becomes immutable. SQLite's database serialization preserves the same
terminal-evidence/claim recheck and observable result without weakening the
fence.

This key-before-session hierarchy applies to every PostgreSQL path that touches
both resource classes, including finalize: derive/deduplicate/sort actual signed
key advisory IDs and acquire them first, then lock all required session rows in
stable `session_id` order, then revalidate session generation/expiry, terminal
evidence, and exact claims before mutation. No finalize path may lock its session
row and later request a key lock. Acquire and finalize therefore cannot form a
`key K -> session S` / `session S -> key K` cycle. SQLite uses its existing
database serialization and performs the equivalent post-serialization authority,
terminal-evidence, and claim revalidation. No backend may weaken exact-key
authority to obtain parity.

### Internal HTTP protocol

The new routes are internal, versioned, and claim-capability gated:

- `GET /v1/internal/claim-sessions/capabilities` returns the strict model
  `{protocol: "claim-session-v1", maximum_batch_size,
  retention_seconds: 60,
  maximum_session_receipt_headers: 1000,
  maximum_session_receipt_items: 32000, server_time}` where `server_time` is
  read from the database that will authorize `/open` immediately before
  capability response serialization, after preceding service-side queue and
  handler delay. These fields validate protocol shape
  and diagnose server admission; the client does not use retention or
  session-cap values to predict capacity. The service sets
  `maximum_batch_size = min(configured_maximum_batch_size, 1000)`, preserving
  the existing public `--maximum-batch-size` range while enforcing the internal
  session-protocol ceiling; the client accepts values from 1 through 1,000 and
  chunks to the advertised value. Missing, unknown, inconsistent, or unsupported
  values fail capability selection before open;

- `POST /v1/internal/claim-sessions/open` accepts `open_request_id`, capability
  `server_time`, and `open_not_after`; under the request-ID lock it replays an
  existing receipt before inspecting these non-semantic admission anchors. For
  an absent ID it rejects deadline violations as pre-mutation
  `408/open_request_expired`, otherwise atomically creates one session/receipt and returns
  `session_id`, `owner_token`, `generation`, `expires_at`,
  `remaining_lease_seconds`, `heartbeat_after_seconds`, and
  `renew_deadline_seconds`;
- `POST /v1/internal/claim-sessions/renew` accepts the exact session authority
  and returns refreshed authority including `expires_at` and a server-relative
  `remaining_lease_seconds` computed from the same database time/transaction
  that established the lease; success is O(1);
- `POST /v1/internal/claim-sessions/close` accepts the exact session authority,
  performs exactly one O(1) session-row invalidation transaction and immediately
  returns a closed acknowledgement; only the service sweeper later reclaims
  claim/receipt/tombstone rows;
- `POST /v1/internal/claim-sessions/acquire` accepts session authority plus
  unique ordered `EvidenceQuery` values plus their claimed digest, recomputes
  the canonical digest from the actual array before receipt lookup/mutation,
  takes deduplicated signed-ID-sorted exact-key locks, then locks the canonical requester/owner session
  set before terminal-evidence and claim revalidation,
  and returns aligned cached/acquired/busy results with exact-key generations;
- `POST /v1/internal/claim-sessions/finalize` accepts session authority plus
  exact-key generation-fenced commits, follows the same signed-ID key-before-
  session lock hierarchy, revalidates authority/evidence/claims, and atomically consumes matching claims
  while preserving existing immutable evidence/artifact behavior; a batch
  `412` is reconciled per key and retries only still-absent keys whose exact
  authority remains live under the original request identity and budget.

`503` remains retryable service backpressure and includes `Retry-After`. Only
`503` with wire code `claim_receipt_capacity` certifies pre-mutation receipt-cap
admission; generic or unknown-code `503` has no such meaning. `412` means stale,
expired, closed, or otherwise lost session/claim authority. `409` and `422`
preserve the current evidence-conflict and validation meanings.
This distinct capability route advertises the protocol atomically; the released
`GET /v1/evidence/claims/capabilities` remains `404`, and `/health` retains its
v0.2.0 shape. The
client never mixes session and per-key claim routes in one invocation.

There is no compatibility alias for the unreleased
`/v1/evidence/claims/{acquire,renew,release,finalize}` endpoints. They and their
per-key transport models are removed when the session routes land.

### Client context and legacy fallback

`ClaimSession` is a context-managed client API owned by the Store layer:

```python
with store.claim_session() as session:
    results = session.acquire_many(queries)
    outcomes = session.finalize_many(commits)
```

The context opens once, owns the heartbeat thread and cancellation state,
exposes `raise_if_lost()` and a cancellation signal, and closes once with
best-effort bounded cleanup. It does not expose owner tokens to `annotate`.
`annotate` uses one context around all batches and adapters in the invocation.

For a v0.2.0 service that does not advertise the session capability, the client
uses the existing legacy `EvidenceStore` lookup/commit path with no duplicate-
suppression claim guarantee. It does not fall back to the unreleased per-key
claim endpoints. Authentication, malformed capability, and server errors do
not silently select legacy behavior.

PR A also preserves the exact reverse compatibility direction. An unmodified
v0.2.0 client uses the unchanged `/health`, legacy lookup, fetch, artifact, and
commit endpoints on the new session service. The unreleased per-key claim
endpoints remain removed and return `404`; no alias is added. Because the old
client cannot join a `ClaimSession`, its calculation may duplicate active
session work, but its legacy commit takes the same canonical exact-key locks as
session finalize and preserves immutable convergence. If legacy commit wins, it
retires the matching session claim in that same locked transaction, and
session finalize returns the matching terminal record as converged success; if
session finalize wins, legacy commit returns the existing matching record. A
scientifically conflicting payload remains `409` under the existing integrity
contract. Session finalize never consumes legacy authority; legacy commit does
retire the matching session claim as required by the governing v1.2 contract.
Neither path overwrites evidence or corrupts artifacts.

### Tool cancellation

`ToolRunner.run()` gains a generic cancellation input independent of claims,
adapters, HTTP, and Store types. Session loss publishes a monotonic cancellation
signal that directly wakes the runner's process/timeout wait; polling-only
“periodically waits” is not conforming. From signal publication to
`killpg(..., SIGTERM)` is at most one second under acceptance load. Forced
termination sends `killpg(..., SIGKILL)` no later than six seconds after signal
publication. Internal `authority_safety_runway` is strictly greater than six
seconds so the forced signal is issued before authority can expire; it is not a
promise that the kernel has removed every process. Cancellation raises a distinct
structured runner error whose result records cancellation separately from
timeout.

On cancellation or timeout, one runner-owned Linux wait state machine records
the process-group ID, sends `SIGTERM` to that group, and allows exactly a
5-second grace period. It observes leader exit with `waitid(..., WNOWAIT)` and
does not call `wait()`, `poll()`, or another reaping operation while cleanup is
in progress. The unreaped leader keeps its PID, and therefore its PGID, reserved
against reuse. The cleanup condition is explicitly **not** process-group
absence: the retained zombie leader is still a group member, so `killpg(pgid,
0)` cannot become the completion signal.

Instead, the Linux runner enumerates numeric `/proc/<pid>/stat` entries, parses
PID, state, and process-group ID, and builds the set of members whose PGID is the
reserved PGID, whose PID is not the leader PID, and whose state is neither
zombie nor dead. A process disappearing between enumeration and read is a
benign retry; a malformed, permission-denied, or otherwise ambiguous snapshot
is not treated as empty. At the end of the grace, the runner also observes the
leader through `waitid(..., WNOWAIT | WNOHANG)`. A leader still reported live
**or** any live non-leader member causes `SIGKILL` to the still-reserved group.
The runner repeats leader checks and full snapshots, tolerating disappearance
races and reissuing `SIGKILL` while either condition is live, until the leader
is observably exited and two consecutive snapshots separated by a scheduler
yield contain no live non-leader members. Retaining the exited leader prevents
PGID reuse during every scan/signal race; repeated snapshots catch a child
created during enumeration. Non-leader zombies contain no running work and do
not block completion.

The two clean snapshots are necessary but not sufficient. While the unreaped
leader still reserves its PID/PGID, the unified state machine on every exit path
(including observed normal leader exit) issues one final
group-wide `killpg(pgid, SIGKILL)` as a kernel membership fence before any
leader reap, even when both snapshots appeared empty. It then repeats complete
post-signal `/proc` scans and leader observation; only unambiguous scans with no
live non-leader may proceed to adopted-zombie cleanup and final leader reap. A
rotating fork handoff therefore receives the group signal before PGID release
and cannot escape behind the finite snapshot rule. When `waitid(..., WNOWAIT)`
has already observed the leader exited and that unreaped leader still reserves
the PGID, `ESRCH` from this final `killpg` is a successful membership-fence
outcome meaning no signalable process group; the required post-signal scans must
still prove no live or ambiguous non-leader before reap. `EPERM`, any other
signal error, or an ambiguous scan is fail-closed: the runner records it, enters
or retains `cleanup_stuck`, keeps the leader unreaped, and continues
scan/signal/wait handling until clean membership is proven. A live or `D`-state
post-signal member likewise keeps `run()` blocked under the existing cleanup
ownership contract.

Two seconds after `SIGKILL`, any live member, ambiguous snapshot, or member in
Linux uninterruptible `D` state transitions the invocation to observable
`cleanup_stuck`. The synchronous `ToolRunner.run()` does **not** unwind at that
transition. It records PGID/PIDs/states through its injected observability
callback plus structured log/metric, remains blocked as the sole cleanup owner,
retains the unreaped leader, and continues bounded wait/snapshot/exact-reap
iterations. Shutdown joins every active runner and refuses clean process exit
while its containment is non-empty; there is no daemon/background handoff that
could be abandoned. `cleanup_stuck` is never raised or returned to the caller.
Only after clean snapshots and final reap may `run()` raise its final structured
cancellation or timeout error. It never finalizes evidence, reports tool
success, or writes a tool result to the Store.
There is deliberately no eight-second no-live/reap guarantee: `SIGKILL` can
remain pending for uninterruptible kernel sleep, and cleanup completes only
after later clean snapshots and reap make that fact observable.

Normal leader exit and cancellation use this same single-owner state machine.
An observed normal exit is held with `WNOWAIT`; before selecting normal
completion, the runner atomically samples cancellation and scans for live group
descendants while the leader PID/PGID remains reserved. If cancellation is set
or any live descendant exists, cleanup wins and runs the same group
`SIGTERM`/five-second grace/`SIGKILL`/clean-snapshot sequence. Only after no
cancellation is pending and the leader is exited with two no-live-nonleader
snapshots may reaping begin. On Linux when SeqEvi is PID 1 or has child-subreaper
status, while the leader remains held by `waitid(..., WNOWAIT)` and its PID/PGID
remains reserved, the runner
rescans `/proc/<pid>/stat` and `/proc/<pid>/status`. It may reap an adopted
descendant only when all attributes are confirmed in the same stable snapshot:
the PID is not the leader, its PGID equals this runner's still-reserved PGID,
its state is zombie/dead, and its current `PPid` is the SeqEvi process. It calls
only exact `waitpid(pid, WNOHANG)` for those confirmed PIDs, tolerating `ECHILD`
or disappearance races, and repeats until no attributable waitable PID remains.
`waitpid(-1, ...)` and other global child waits are forbidden. Each parallel
runner owns a distinct PGID and may not reap a child attributed to another
group. Ambiguous `/proc` reads are retried/fail cleanup rather than broadening
the reap target. Stable scan plus exact-PID reap repeats until no attributable
adopted zombie remains. Only then does the runner call `wait()` once to reap the
leader last, and only if the final membership-fence signal and its post-signal
scans succeeded. No PGID-based scan or signal occurs after that reap.
Cancellation, normal exit, and timeout cannot race a separate waiter that might
reap early. The state transition makes cancellation/cleanup win an
exit-before-cancel boundary whenever descendants remain. Existing
`start_new_session=True`, argument
arrays, `shell=False`, stdout/stderr paths, and process-group cleanup on
exceptional exit remain invariant. `annotate` maps session loss back to
`EvidenceClaimLostError` only after termination, the two clean snapshots, and
final reap complete. A `cleanup_stuck` transition is reported only out of band
while the same `run()` call remains blocked; after that owner completes cleanup,
the caller receives the final cancellation/timeout error, never a stuck-state
exception. Neither path can reach finalize or Store result persistence after
loss.

## Migration 0004 and upgrade contract

`0004_claim_sessions` replaces the ephemeral 0003 `evidence_claim` layout with
session and exact-key session-claim tables and physically names the new
coordination tables `claim_sessions`, `session_claims`,
`evidence_claim_generations`, `claim_session_open_receipts`,
`claim_session_acquire_receipts`, and `claim_session_acquire_receipt_items`.
The migration does not attempt to
translate live 0003 leases: a supported upgrade first quiesces all Store
services and claim-capable clients, then 0004 drops/invalidates every ephemeral
0003 claim and installs the new schema.

The existing automatic startup migration and migration-caller lock are not
proof that 0003 clients are quiesced and do not fence persistence traffic. PR A
therefore adds a fail-closed 0004 maintenance preflight for an **existing**
pre-0004 Store. Ordinary startup distinguishes a pristine target from an
existing Store while holding a bootstrap fence:

- for SQLite, an exclusive database transaction serializes creators and the
  target is pristine only when it has no Alembic revision or Store user tables;
- for PostgreSQL, the new path first acquires the existing fixed
  `_POSTGRES_MIGRATION_LOCK_ID` advisory lock used by v0.2.0, then a schema-keyed
  transaction lock, and holds both through commit. The fixed lock makes old/new
  creators conflict; the schema is pristine only with no revision or Store
  tables.

The process rechecks pristine state after acquiring the fence. A pristine Store
has no legacy persistence traffic to quiesce, so first-run startup applies the
complete schema directly through 0004 while retaining the fence through commit,
then performs ordinary annotation without a maintenance acknowledgement. An
unversioned but non-empty/ambiguous target fails closed rather than being
classified as pristine. Concurrent first-run creators serialize and the loser
observes an already-0004 Store after the winner commits. A mixed v0.2.0/PR A
creator race serializes on the legacy fixed lock: if old wins, PR A observes an
existing 0003 Store and refuses; if PR A wins, old observes a newer revision and
fails rather than racing DDL.

For an existing Store, ordinary startup has an explicit automatic target of
0003: revision 0001, 0002, or any earlier supported non-empty revision upgrades
only through 0003, then refuses to cross into 0004 and reports the documented
maintenance command. Revision 0003 refuses immediately. Revision 0004 opens
normally and idempotently without maintenance. Existing-Store startup never
invokes an unbounded Alembic `head` upgrade while 0004 is head.

An operator must stop every old service and client, verify the deployment's
writer/process readback is empty, and invoke the explicit 0004 upgrade command
with a single-use maintenance acknowledgement bound to the target database and
expected current revision. Before attempting the PostgreSQL migration-caller
lock, the command starts the same fixed 60-second monotonic maintenance
deadline used by all later fence work. It replaces indefinite
`pg_advisory_lock(_POSTGRES_MIGRATION_LOCK_ID)` with bounded polling of
`pg_try_advisory_lock(_POSTGRES_MIGRATION_LOCK_ID)`: each miss sleeps with
1-to-5-second jitter clamped to positive remaining budget. Exhaustion before
caller-lock acquisition returns a clean pre-readback/pre-DDL failure. Once
acquired, the command retains the advisory lock across every complete-fence
retry and the successful fenced transaction/commit, and releases it in a
`finally` block on success, deadline, cancellation, or error.

SQLite starts that same fixed 60-second monotonic maintenance deadline before
attempting the outer `.migration.lock`. It replaces blocking `flock(LOCK_EX)`
with `flock(LOCK_EX | LOCK_NB)` polling; every 1-to-5-second jittered sleep is
clamped to the positive remaining budget. After the file lock is held, acquiring
`BEGIN EXCLUSIVE` uses a `busy_timeout` no greater than the current positive
remainder plus nonblocking/busy retry whose sleeps are clamped to that same
deadline. Exhaustion before either lock returns a clean pre-readback/pre-DDL
failure. The command retains both file and database locks through fenced
validation, DDL, revision write, and commit, and releases them in `finally` on
every success or failure path. Near-deadline acquisition leaves only the actual
remainder for validation and the existing immediate pre-DDL/pre-commit checks;
neither lock starts a new budget. Once `BEGIN EXCLUSIVE` succeeds, the command
installs a SQLite progress handler whose callback compares the same monotonic
deadline at a fixed VM-opcode interval throughout fenced validation, migration
DDL, and revision writes. Deadline expiry returns nonzero to interrupt the
running statement; the command rolls the exclusive transaction back and fails
without commit. The handler is removed in `finally`. This execution fence is in
addition to, not a replacement for, the immediate pre-DDL and pre-commit checks.

After the migration-caller lock but before revision, claim, or writer
validation, the command acquires a database-level persistence
traffic fence that every old and new persistence mutation conflicts with:
PostgreSQL attempts one complete `ACCESS EXCLUSIVE` fence over the exact 0003
physical tables `sequence`, `evidence_claim`, `artifact`, and `evidence` inside
one transaction. Immediately before each attempt, the command computes
positive remaining monotonic time. Any preliminary autocommit setup/readback is
itself clamped to the same absolute maintenance deadline. After that readback,
the command recomputes the positive remainder; exhaustion aborts before
transaction start. In explicit DBAPI autocommit it then sends one server round
trip containing session `SET transaction_timeout` to that recomputed remainder,
followed by a PostgreSQL protocol `Sync`/commit boundary, and only then a
separate `BEGIN`. The driver may pipeline these protocol operations to avoid a
client response wait, but must not encode `SET; BEGIN` as one multi-statement
simple Query: the `SET` must be durably effective before PostgreSQL executes
`StartTransaction` for the fence. A monotonic deadline watchdog
also owns/cancels the connection from before setup through the active pre-commit
transaction, making delayed setup/readback or an ambiguous SET/Sync/BEGIN
pipeline fail closed. Only after the Sync-confirmed SET and separate BEGIN succeed does it set
`SET LOCAL lock_timeout = min(5 seconds, remaining)`. Zero/non-positive
remaining aborts before transaction start. The session-level value is reset in
`finally` using explicit DBAPI autocommit, followed by authoritative
`SHOW transaction_timeout` readback in autocommit proving the connection's
durably configured default/zero value before pool check-in. Neither setup nor
cleanup relies on SQLAlchemy autobegin or an implicit transaction that pool
rollback could undo. If reset, readback, autocommit restoration, or their
transport outcome fails or is uncertain, the command marks
the physical SQLAlchemy connection invalid and closes/discards it; that
connection is never returned to the pool. Cleanup preserves the primary
migration/commit exception and attaches reset/invalidation failure as secondary
diagnostic context rather than masking it. Retry jitter is 1-to-5 seconds, and every lock wait/
sleep is clamped to the then-remaining deadline. Legacy
acquire takes
`sequence` before `evidence_claim`, while legacy finalize/commit takes
`evidence_claim` before `sequence`, `artifact`, and `evidence`; the plan does not
claim that one fence order matches both legacy paths. Instead, the complete
fence transaction is the bounded retry unit: SQLSTATE `40P01` or `55P03` rolls
back the whole transaction, releases every partial table lock, jitters, and
retries from a new transaction within one fixed maintenance monotonic deadline.
After one attempt acquires the complete fence, it rechecks the monotonic
deadline before revision/claim/writer readback; expiration rolls back all locks
and aborts. Because `transaction_timeout` was armed before `BEGIN`, its
cumulative timer covers complete-fence locking, fenced validation, and every
subsequent Alembic DDL/revision statement up to the commit call; it does not
reset per statement. After fenced validation and immediately before the first
upgrade DDL statement, the command still recomputes positive remaining time and
aborts if none remains, but does not attempt to arm or restart the active
transaction's timeout there.
Tighter per-statement caps may remain, but `statement_timeout` is not the
maintenance-deadline mechanism. Immediately before commit, the command
recomputes the monotonic remainder and rolls back instead if it is not positive.
PostgreSQL disables `transaction_timeout` during `CommitTransaction()`, so the
plan does not claim that the timer bounds durable WAL/synchronous commit or can
roll back a commit after that boundary. No validation, Alembic revision
mutation, or DDL occurs until the complete fence is held and the post-lock check
succeeds, and no DDL starts without the second pre-DDL check and cumulative
pre-commit timeout. SQLite
performs the same immediate pre-DDL monotonic recheck inside one exclusive
database transaction, keeps its deadline-driven progress handler active through
validation/DDL/revision execution, and holds the transaction through commit.
An interrupted statement rolls the entire migration back. Operator quiescence remains mandatory;
retry handles a late/incorrect writer safely rather than authorizing rolling
upgrade.

Only after that fence is held does the command recheck the exact revision,
verify no live/unexpired 0003 claims remain after the quiescence window (or
explicitly invalidate expired rows), apply 0004 in the same fenced transaction,
and record successful completion before new services start. A persistence
writer that arrives after the operator's initial readback either causes a
whole-fence retry before validation or blocks behind the successfully acquired
complete fence and, after commit, fails/reconnects against the new protocol; it
cannot write between validation and destructive DDL. An acknowledgement never causes
normal startup to skip this preflight and cannot authorize another
database/revision. Failure or uncertainty aborts before destructive DDL.

After the PostgreSQL commit call, the command performs authoritative revision
and exact expected-schema readback before reporting success. A slow commit that
returns after the monotonic deadline is reported as committed-late only when
that readback proves the complete 0004 revision/schema. If commit transport is
lost or its outcome is otherwise ambiguous, the command does not rerun DDL: it
opens a fresh connection, performs read-only revision/schema readback, and
classifies complete target schema as success, unchanged source schema as a safe
failed attempt, and any mixed/unexpected state as fail-closed manual recovery.
The maintenance runbook keeps writers quiesced throughout this reconciliation.

PR A updates the checked-in Store operations runbook with stop, writer/process
readback, database-fence acquisition, maintenance command, schema verification,
restart, and rollback steps. It also tests fenced pristine bootstrap directly to
0004 and first local annotation; concurrent fresh SQLite and PostgreSQL
creation; normal already-0004 restart; automatic 0001/0002-to-0003 refusal and
0003 refusal on both backends; ambiguous non-empty unversioned refusal;
missing/stale/wrong-target acknowledgement; live 0003 claim refusal; a writer
arriving after initial readback; database-fence serialization and timeout;
pre-DDL failure; and the accepted quiesced upgrade on SQLite and PostgreSQL. No
production deployment is performed by these documentation or implementation
slices.

Only ephemeral claim coordination is invalidated. The `sequence`, `evidence`,
artifact metadata, artifact bytes, and DuckDB result schema remain untouched.
Downgrade removes session coordination and recreates an empty 0003-compatible
claim table; it never reconstructs expired ownership. Rollback therefore
requires the same quiescence and returns clients to legacy or 0003 behavior
without changing terminal evidence/artifacts.

## Preconditions and invariants

PR A starts from the exact current `main` containing PRs #25-#27. PR B starts
from PR A. Before migration or real acceptance, operators must prove all old
claim writers quiesced. The PostgreSQL pressure harness and real C2 inputs,
runtime images, caller-owned databases, and credentials must be available but
remain external to SeqEvi.

Both slices preserve these invariants:

- evidence identity is the unchanged immutable `EvidenceKey`;
- a current exact key generation is required for finalization;
- terminal evidence is immutable and wins convergence races;
- artifacts are caller-read-only and content-addressed;
- heartbeat work is O(1) per session, independent of key count;
- acquire/finalize do not use per-key SQL execution loops;
- PostgreSQL acquire first takes deduplicated transaction-scoped exact-key
  advisory locks in signed numeric lock-ID order, then locks the canonical
  sorted union of requester and discovered owner
  sessions before canonical-key terminal-evidence/claim revalidation; owner-set
  drift retries under the same request identity and deadline;
- every PostgreSQL operation touching both exact keys and sessions, including
  finalize, takes signed-ID-sorted/deduplicated key locks before stable-ID-
  ordered session rows and revalidates authority/evidence/claims afterward;
- close performs exactly one O(1) session-row invalidation transaction and
  returns; only the shared-service or `LocalStore` lifecycle sweeper performs
  bounded claim/receipt reclamation;
- acquire recomputes the canonical digest from actual submitted ordered queries
  before replay or mutation and requires equality with wire/stored digests;
- requests reject duplicate keys and preserve aligned unique input order;
- SQLite and PostgreSQL expose identical lifecycle and failure semantics;
- no external process remains running or unreaped after cancellation returns;
- no cleanup path releases the reserved leader/PGID before a final group-wide
  SIGKILL and clean post-signal membership scans;
- an existing `open_request_id` receipt/tombstone is replayed before absent-ID
  deadline admission, and admission anchors never change same-ID semantics;
- capability discovery is authority-free and independently time-bounded; only
  timely valid receipt starts the separate 30-second open operation, whose
  server deadline is exactly response-boundary `server_time + 30 seconds`;
- expired-session deletion requires zero claims and zero acquire-receipt
  headers/items; restricted foreign keys are never used as candidate filtering;
- every PostgreSQL maintenance lock wait and retry sleep is clamped to positive
  remaining monotonic budget, followed by a post-fence deadline check;
- SQLite maintenance starts the same deadline before nonblocking file-lock
  polling and bounds `BEGIN EXCLUSIVE` busy/retry waits by its positive
  remainder; a progress handler interrupts validation/DDL/revision execution at
  that deadline, and both locks are retained through commit and finally released;
- before every PostgreSQL complete-fence transaction, session
  `transaction_timeout` is armed to the positive remaining maintenance budget
  after setup/readback and a fresh remainder calculation. A protocol Sync/commit
  boundary separates the autocommit SET from a distinct BEGIN; pipelining may
  remove client wait but never that boundary. One watchdog covers setup and active
  transaction. It is then reset plus readback-verified
  in autocommit before connection reuse; uncertain cleanup
  invalidates/discards the physical connection without masking a primary error.
  The timeout cumulatively covers lock acquisition,
  validation, and pre-commit statements. Pre-DDL and pre-commit deadline checks
  plus authoritative late/ambiguous commit readback remain required;
- the single PostgreSQL maintenance deadline begins before caller advisory-lock
  polling; the acquired lock spans fenced commit and is always finally released;
- the public `annotate` CLI and profiles do not expose session machinery.

## Non-goals

No Redis, etcd, Consul, scheduler, or other coordination service is introduced.

## Risks and mitigations

- **Set-based SQL differs by dialect.** Keep one behavioral suite for both
  backends and add real PostgreSQL race/plan evidence; do not emulate parity
  with per-key loops.
- **Crashed clients leak coordination rows.** Make reclamation owned by the
  shared service or the SQLite `LocalStore` teardown/next-open lifecycle,
  bounded by claim rows as well as empty sessions, set-based, and independent of
  close; retain durable generation high-water and require zero residual expired
  session/claim/receipt rows in pressure and C2 readback. Select an expired
  session for deletion only after zero claims and zero acquire header/item rows,
  so restricted foreign keys cannot create retry livelock.
- **A delayed `/open` arrives after its tombstone is swept.** Read capability
  `server_time` at the response boundary and set `open_not_after` to that anchor
  plus 30 seconds for the newly started open phase; reject
  every missing/malformed/expired/overlong deadline as pre-mutation
  `408/open_request_expired`; retain the 120-second tombstone for ordinary
  response-loss replay, not as the ingress-age fence.
- **Capability delay is subtracted twice or creates authority.** Keep discovery
  an independently bounded authority-free probe. Start the client open budget
  only on timely valid receipt, use exactly `server_time + 30 seconds`, and send
  immediately. Response transport consumes that server window once; late probe
  responses are terminal, and no capability refetch occurs within the attempt.
- **An absent-ID open crosses its deadline while blocked on a lock.** Put the
  current-database-time predicate in the conditional session/receipt insert at
  the linearization point; use `clock_timestamp()` rather than PostgreSQL's
  transaction timestamp and the SQLite statement-time equivalent.
- **A retried open anchor conflicts with a committed lost response.** Lock and
  replay an existing request-ID receipt before absent-ID deadline validation;
  exclude admission anchors from compatibility while retaining `409` for every
  incompatible semantic field.
- **Long live sessions accumulate acquire receipts while polling busy keys.**
  Protect receipts only through the replay budget, cap headers and fixed-width
  item rows per session, return explicit bounded backpressure before mutation at either cap,
  and delete child items then childless headers in independent age-ordered
  chunks so heartbeat stays O(1) and session deletion cannot cascade unbounded
  work.
- **A claimed acquire digest does not describe the submitted queries.**
  Canonically serialize and hash the actual validated ordered array on the
  service, compare recomputed/wire/stored values before replay or mutation, and
  reject changed content or order as `409`.
- **Reciprocal owners deadlock acquire or race renew/takeover.** Discover the
  complete requester/owner session set without retaining session-row locks,
  acquire that set once in stable session-ID order, then re-read claims in
  canonical key order. Roll back and bounded-retry owner-set drift under the
  original acquire identity/budget; SQLite provides the same outcome through
  database serialization.
- **Legacy publication races claim creation for an empty key.** Retain the
  transaction-scoped exact-key advisory locks before any
  PostgreSQL acquire decision, then take canonical session locks and re-read
  terminal evidence/claims. This shares the legacy commit lock boundary and
  forbids returning `acquired` for evidence that already became terminal;
  SQLite uses database serialization plus the same terminal recheck.
- **Hashed exact-key lock collisions reverse batch order.** Compute all actual
  signed 64-bit advisory IDs first, deduplicate them, and acquire them in signed
  numeric order exactly as the governing helper/legacy path does. Keep
  canonical `EvidenceKey` order only for the later evidence/claim re-read, and
  force collisions in the overlapping-batch deadlock tests.
- **Acquire key locks deadlock finalize session locks.** Use one global
  key-before-session hierarchy for every PostgreSQL path touching both: signed-
  ID-sorted/deduplicated advisory locks first, stable-ID session rows second,
  then full authority/evidence/claim revalidation. Finalize must never lock a
  session before requesting a key; deterministic acquire/finalize interleaving
  tests enforce the hierarchy.
- **Receipt cleanup recreates fan-out.** Store only fixed-width outcome
  references, forbid cascading header/session deletion, and cap every close/
  sweeper transaction independently by item rows then childless headers;
  measure both physical row counts under pressure.
- **Receipt-cap backpressure is confused with ambiguous service failure.** Give
  only the proven pre-mutation capacity response the stable
  `claim_receipt_capacity` code; every generic/unknown `503` and transport
  failure consumes the existing mutation/replay budget.
- **Close recreates a thousands-of-claims transaction.** Commit one-row
  `closing` authority and acknowledge in the one close transaction; run no
  cleanup chunk in the request. The shared-service sweeper or SQLite lifecycle
  sweeper alone reclaims claims/items/headers/tombstones in separate bounded
  transactions; SQLite teardown joins it, with next-open recovery after a crash.
  Preserve a protected open receipt through session deletion and remove it only
  after its 120-second retention window.
- **A session is a larger failure domain.** One lost heartbeat cancels the
  invocation by design; exact-key generations prevent a stale invocation from
  finalizing any subset after loss.
- **Cancellation races with normal exit/finalize, leader exit, or PGID reuse.**
  Make loss monotonic and runner termination single-owner/idempotent, observe
  and kill a still-live leader, observe exit without reaping, reserve the
  PID/PGID through group cleanup,
  require two unambiguous `/proc` snapshots with no live non-leader member (not
  group absence) before the one final reap, and revalidate exact authority
  inside finalization.
- **Fork handoff defeats finite `/proc` snapshots.** Before leader reap, always
  send final group-wide `SIGKILL` while PGID is reserved and require clean
  post-signal scans. With a WNOWAIT-observed-exited unreaped leader, `ESRCH` is
  a successful no-signalable-group fence result followed by those scans;
  `EPERM`, other errors, ambiguity, live members, and `D` state remain
  fail-closed under the existing synchronous cleanup owner.
- **`SIGKILL` cannot remove a task in uninterruptible kernel sleep.** Guarantee
  signal issuance, not physical disappearance: publish `cleanup_stuck` out of
  band after the two-second observation window, keep synchronous `run()`
  blocked, prohibit finalize/Store result writes, join it during shutdown, and
  deliver only the final cancellation/timeout error after single-runner cleanup
  reaches clean snapshots and exact reap.
- **Normal exit releases PGID before cancellation observes descendants.** Route
  normal exit and cancellation through one WNOWAIT state machine, resample
  cancellation and descendants before reap, let cleanup win when either is
  present, and forbid signaling after reap.
- **PID1/subreaper cleanup reaps another runner's child.** Require same-PGID,
  zombie/dead state, and current SeqEvi `PPid` attribution from `/proc`, use only
  exact-PID `waitpid(..., WNOHANG)`, forbid global waits, and test parallel group
  isolation.
- **A v0.2.0 client bypasses session duplicate suppression.** Accept possible
  duplicate calculation as the released compatibility tradeoff, but serialize
  legacy commit with session finalize under exact-key locks and immutable
  convergence; test both race winners and conflicts from the exact old contract.
- **Quiescence is violated during 0004.** Refuse a rolling mixed-protocol
  upgrade and cap every existing pre-0004 Store's automatic upgrade at 0003;
  bootstrap only a fence-verified pristine target directly to 0004; otherwise
  require the database/revision-bound maintenance preflight, acquire the
  persistence-conflicting PostgreSQL table locks or SQLite exclusive transaction
  before authoritative readback, hold through DDL/commit, verify schema, then
  restart. Because legacy acquire and finalize use opposing table orders, make
  the entire PostgreSQL fence transaction retryable on `40P01`/`55P03` under
  `SET LOCAL lock_timeout=min(5s, positive remaining budget)` and a fixed
  maintenance deadline; after full acquisition recheck the deadline, and never
  validate or run DDL after only a partial or over-budget fence. Recheck again
  after validation immediately before DDL; the session `transaction_timeout`
  configured from a post-setup remainder and committed across a protocol Sync
  before the distinct BEGIN already constrains the
  cumulative locks/validation/DDL/revision phase. Recheck before
  commit. A per-statement timeout alone is explicitly insufficient, and the
  transaction timeout is not represented as a durable-commit timer. Reconcile
  late/ambiguous commit by exact revision/schema readback without replaying DDL.
- **The migration caller lock blocks outside the maintenance budget.** Start the
  one 60-second monotonic deadline before `pg_try_advisory_lock` polling, clamp
  every poll sleep and later table wait to its positive remainder, fail before
  readback/DDL on exhaustion, retain the acquired lock through fenced commit,
  and release it in `finally` on every exit.
- **A maintenance timeout leaks through the connection pool.** Before check-in,
  use explicit DBAPI autocommit to reset session `transaction_timeout` and
  verify its durable default/zero value by autocommit readback, so SQLAlchemy
  autobegin/check-in rollback cannot restore the maintenance value. Any failed,
  mismatched, or ambiguous reset/readback/autocommit restoration invalidates and
  closes the physical connection; never return it to the pool, and preserve any
  primary migration/commit failure while reporting cleanup as secondary context.
- **Timeout setup consumes uncharged maintenance time.** Clamp setup/readback to
  the original deadline, recompute afterward, and send the final session
  `SET transaction_timeout`, cross a protocol Sync/commit boundary, then start
  a distinct BEGIN; pipeline if useful but never use one simple Query message.
  Keep an independent monotonic watchdog from setup through the active
  pre-commit transaction; exhaustion or ambiguity aborts/invalidate rather than
  applying a stale pre-setup duration.
- **SQLite blocks indefinitely before reaching its database fence.** Start the
  maintenance deadline before `.migration.lock`, poll `flock` nonblocking, and
  bound `BEGIN EXCLUSIVE` busy/retry by the same positive remainder. Exhaustion
  fails before readback/DDL; retain both locks through commit and release them
  in `finally`.
- **SQLite DDL runs past the maintenance deadline.** Keep a monotonic-deadline
  progress handler installed for fenced validation, DDL, and revision writes;
  interrupt and roll back the exclusive transaction on expiry, remove the
  handler in `finally`, and retain the pre-DDL/pre-commit point checks.
- **Durable PostgreSQL commit outlives the pre-commit timer or loses its
  response.** Do not claim `transaction_timeout` covers
  `CommitTransaction()`; recheck the monotonic budget immediately before
  commit, keep the deployment quiesced, and classify late/ambiguous completion
  by authoritative exact revision/schema readback. Never replay migration DDL
  when commit outcome is unknown; mixed state fails closed for manual recovery.
- **Downgrade deadlocks with late 0004 finalize or receipt cleanup.** Keep child
  receipt items before parent headers and terminal tables in writer order, and
  apply the same `40P01`/`55P03` whole-fence rollback/retry deadline as upgrade;
  exhaustion aborts before downgrade readback or DDL.
- **Jitter, wall-clock skew, response delay, or retry masks deadline
  exhaustion.** Start the monotonic budget before transport, clamp it to the
  server-relative remaining lease budget with a safety runway, retain absolute
  `expires_at` only as the authority fence/diagnostic, and inject deterministic
  monotonic/wall clocks and randomness in tests.
- **C2 passes while SQL pressure remains hidden.** Require statement/lock/pool
  evidence as a separate gate, not only successful process exits.

## Rollback

Before either rollout or rollback, follow the PR A maintenance runbook: stop
every Store writer, verify the writer/process boundary empty, and acquire the
database-level persistence fence before authoritative readback. Application
rollback before 0004 simply restores the previous release. After 0004, the
explicit downgrade preflight requires a fresh target/revision-bound
acknowledgement. Before downgrade readback or DDL, PostgreSQL takes canonical
`ACCESS EXCLUSIVE` locks, in this fixed canonical order, on
`claim_session_open_receipts`, `claim_sessions`,
`evidence_claim_generations`, `session_claims`,
`claim_session_acquire_receipt_items`, `claim_session_acquire_receipts`,
`sequence`, `artifact`, and `evidence` before readback and holds them through
commit. As with upgrade, this complete downgrade fence is one bounded retry
unit: immediately before each attempt it requires positive remaining monotonic
time, bounds setup/readback to the same deadline, recomputes the remainder, and
configures session `transaction_timeout` in autocommit, crosses a protocol
Sync/commit boundary, then issues a distinct `BEGIN` before setting
`SET LOCAL lock_timeout = min(5 seconds, remaining)`;
`40P01` or
`55P03` rolls back every partial lock and retries with clamped 1-to-5-second
jitter inside the same fixed 60-second monotonic maintenance deadline. After
complete fence acquisition it rechecks the deadline before readback; expiration
rolls back and aborts. No downgrade validation or DDL runs until the full fence
and post-lock deadline check both succeed. After readback and immediately before
downgrade DDL, it recomputes positive remaining time; exhaustion aborts pre-DDL,
while the timeout armed before transaction start already covers the cumulative
