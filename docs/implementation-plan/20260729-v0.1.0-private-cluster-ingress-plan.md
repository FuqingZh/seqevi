# SeqEvi 0.1.0 Private Cluster Ingress Plan

> Status: active implementation plan
> Date: 2026-07-29
> Issue: FUQ-22
> Scope: PR2 deployment boundary for the node4 HTTP Store

## Decision

Use the existing node4 Apache service as a plain HTTP reverse proxy on the
private `192.168.30.0/24` network. Apache listens only on
`192.168.30.205:18082`, accepts only the observed worker source ranges, and
forwards only to the existing SeqEvi loopback listener at
`http://127.0.0.1:18081`.

The allowed cluster CIDRs are the complete trust boundary for this increment.
There is no TLS, certificate, HTTP authentication, application authentication,
or worker secret. This choice is intentionally limited to a cluster whose
allowed nodes and workloads are trusted.

This is the smallest increment supported by runtime evidence:

- node4 already runs Apache with the required `proxy`, `proxy_http`,
  `authz_host`, and `headers` modules;
- the SeqEvi user service is healthy and bound only to `127.0.0.1:18081`;
- PostgreSQL is separately bound only to `127.0.0.1:15432`;
- observed Cromwell jobs use Docker bridge networking and can reach the node4
  private address; live inspection showed Apache receives that traffic from
  `172.17.0.10`;
- port `18080` is already bound on all host addresses by another service, while
  the dedicated private-address port `18082` is available;
- the requested outcome is cluster reachability, and the current cluster
  network is accepted as the authorization boundary.

SeqEvi application code and its public HTTP client contract remain unchanged.
In particular, PR2 adds no authentication parameter, environment variable,
secret-file format, Cromwell concept, or WDL concept.

## Boundary

```text
trusted worker container
  |
  | HTTP, source must be in an allowed cluster CIDR
  v
node4:192.168.30.205:18082 (Apache)
  |
  | HTTP over host loopback only
  v
127.0.0.1:18081 (seqevi serve)
  |
  +-- 127.0.0.1:15432 (PostgreSQL)
  +-- service-owned artifact directory
```

Only the HTTP Store API crosses the deployment boundary. PostgreSQL and the
artifact directory remain unreachable as independent network or filesystem
surfaces.

## Trust Consequence

The Store API is read-write: allowed clients can upload content-addressed
artifacts and commit immutable evidence, not only query cached results.
Therefore every process able to originate traffic from `172.17.0.0/16` or
`192.168.30.0/24` is trusted as a Store writer. Digest, schema, size, and
immutability validation still apply, but they are not client authentication.

If that network-level trust assumption stops being true, this ingress must be
replaced or fronted by an authenticated transport before admitting untrusted
workloads. That future change is not part of FUQ-22.

## Implementation

1. Add an auditable Apache configuration for the dedicated private HTTP
   listener.
2. Require the observed node4 Docker bridge range `172.17.0.0/16` or private
   LAN range `192.168.30.0/24`.
3. Strip client-supplied forwarding identity headers before proxying.
4. Keep the upstream literal, HTTP, and loopback-only.
5. Add deployment contract tests and an operator runbook.
6. Perform bounded acceptance with a temporary equivalent proxy and ordinary
   Docker bridge workers because installing the system Apache configuration
   requires privileged operator approval.

## Acceptance

- an ordinary allowed worker receives the SeqEvi `/health` response;
- an allowed worker can query an existing cache hit and download its artifacts;
- a worker outside the allowed CIDRs receives HTTP `403`;
- direct access from a worker to `192.168.30.205:18081` fails;
- node4 loopback health remains successful;
- PostgreSQL remains loopback-only and no direct artifact route exists;
- focused deployment tests and `pdm run check` pass.

## Explicit Exclusions

TLS, certificates, HTTP authentication, application users or tokens, secret
delivery, Kubernetes changes, Vault, Prometheus, backups, performance work,
and Cromwell/WDL integration are outside FUQ-22.
