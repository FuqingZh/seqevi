# SeqEvi 0.1.0 Private Cluster Ingress Plan

> Status: active implementation plan
> Date: 2026-07-29
> Issue: FUQ-22
> Scope: PR2 deployment boundary for the node4 HTTP Store

## Decision

Use the existing node4 Apache service as a TLS-terminating, authenticated
reverse proxy on the private `192.168.30.0/24` network. Apache forwards only to
the existing SeqEvi loopback listener at `http://127.0.0.1:18081`.

This is the smallest increment supported by runtime evidence:

- node4 already runs Apache and has the required `ssl`, `proxy`,
  `proxy_http`, `auth_basic`, `authn_file`, `authz_host`, and `headers` modules;
- the SeqEvi user service is healthy and bound only to `127.0.0.1:18081`;
- PostgreSQL is separately bound only to `127.0.0.1:15432`;
- observed Cromwell jobs use Docker bridge networking and can reach the node4
  private address; live acceptance showed Apache receives that traffic from
  `172.17.0.10`, while the inspected backend has no generic secret-injection
  runtime attribute;
- the installed node4 certificate is expired, names only
  `localhost.localdomain`, and is unsuitable for this ingress;
- node4 has no suitable private-cluster CA installed beyond unrelated platform
  trust, so FUQ-22 requires an externally issued certificate and explicit
  worker CA delivery.

SeqEvi needs no application authentication, TLS, Cromwell, or WDL code. The
generic HTTP client reads Basic-auth credentials from an owner-only file named
by `SEQEVI_HTTP_BASIC_AUTH_FILE`, rejects credentials embedded in Store URLs,
and honors the standard `SSL_CERT_FILE` trust override. The file has exactly
two non-empty UTF-8 lines: username, then password. Its path is not a secret;
its contents never enter a URL, profile, command line, WDL input, or log.

## Boundary

```text
worker container
  |
  | HTTPS + Basic auth, allowed bridge or private-LAN source
  v
node4:192.168.30.205:18443 (Apache)
  |
  | HTTP over host loopback only
  v
127.0.0.1:18081 (seqevi serve)
  |
  +-- 127.0.0.1:15432 (PostgreSQL)
  +-- service-owned artifact directory
```

Only the HTTP Store API crosses the deployment boundary. PostgreSQL and the
artifact directory remain unreachable as independent network or filesystem
surfaces.

## Implementation

1. Add an auditable Apache configuration for the dedicated private listener.
2. Require a certificate with a `node4.cluster.local` SAN, a separately
   delivered CA, and a mode-restricted `htpasswd` file.
3. Require both an allowed source (`172.17.0.0/16` for node4 Docker bridge
   workers or `192.168.30.0/24` for private-LAN workers) and valid Basic
   credentials.
4. Strip client-supplied forwarding identity headers before proxying.
5. Keep the upstream literal and loopback-only.
6. Add deployment contract tests and an operator runbook.
7. Add the smallest generic client boundary for an owner-only Basic-auth file.
8. Perform bounded acceptance with a temporary equivalent proxy and an
   ordinary Docker bridge worker because installing the system Apache
   configuration requires privileged operator approval.

## Acceptance

- unauthenticated HTTPS returns `401`;
- wrong credentials return `401`;
- correct credentials and the issued CA return the SeqEvi `/health` response;
- omitting the CA fails TLS verification;
- direct access from the worker to `192.168.30.205:18081` fails;
- node4 loopback health remains successful;
- PostgreSQL remains loopback-only and no artifact route exists;
- focused deployment tests and `pdm run check` pass.

## Explicit Exclusions

Kubernetes changes, Vault, Prometheus, backups, performance work, certificate
authority operation, secret rotation automation, and Cromwell/WDL integration
are outside FUQ-22.
