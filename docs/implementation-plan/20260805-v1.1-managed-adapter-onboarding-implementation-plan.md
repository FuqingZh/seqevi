## Goal

Give a new GitHub or PyPI user one supported path to a real dbCAN annotation
without installing dbCAN, DIAMOND or their Python environment by hand:

```bash
pipx install seqevi

seqevi setup dbcan-cazyme \
  --resource /path/to/dbcan/raw

seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

SeqEvi manages the fixed runtime image and durable profile. The caller manages
the annotation database and supplies its exact path once. Later annotations
reuse that profile without re-entering the resource path.

The target contracts are:

- [managed distribution architecture v1.2](../architecture/20260806-v1.2-managed-adapter-distribution-architecture.md);
- [execution profile contract v2.2](../architecture/20260806-v2.2-execution-profile-contract.md);
- [dbCAN runtime image release review v1.1](../architecture/20260805-v1.1-dbcan-runtime-image-release-review.md).

Slice A made strict v2 reading, kit-manifest validation and read-only setup
planning available. Slice B adds setup apply, digest pull-if-missing, resource

## Corrected Product Boundary

The following decisions supersede the earlier roadmap:

1. SeqEvi has one public user model. There is no cluster, institutional or
   workstation-specific setup path.
2. SeqEvi pulls a digest-pinned runtime image but does not download, copy,
   publish or redistribute annotation databases.
3. `--resource` identifies a caller-owned database root. Setup verifies it and
   writes the path into an ordinary named profile.
4. The public runtime package is
   `ghcr.io/fuqingzh/seqevi-dbcan@sha256:<digest>` and must be publicly
   pullable without authentication.
5. Internal Harbor is deployment-side caching only. It does not enter the
   public manifest, CLI, profile schema or evidence identity.
6. Smoke and annotation containers are ephemeral. Docker image layers,
   profiles, resources, Stores and outputs are the only durable state.
7. Setup does not claim success for an image-only state that cannot run an
   annotation.

SeqEvi remains independent of biofetch, workflow schedulers, shared filesystem
layout and generic deployment systems.

## Frozen P0 Scope

P0 supports exactly:

- Linux on `amd64`;
- Docker Engine supplied and accessible to the caller;
- `dbcan-cazyme`;
- dbCAN `5.2.9` and DIAMOND `2.1.15`;
- externally supplied resource release `db_v5-2-9_5-5-2026`;
- one public digest-pinned GHCR runtime image;
- local POSIX Store or an explicit HTTP(S) shared Store;
- one bundled tiny protein smoke fixture.

P0 does not promise Podman, Apptainer, ARM64, offline bundles, automatic
database acquisition, eggNOG, InterPro/Pfam, a registry-mirror API or a mutable
remote kit catalog.

Accordingly, SeqEvi 0.2.0 includes managed setup only for `dbcan-cazyme`.
eggNOG and InterPro/Pfam remain supported through the existing explicit and
profile runtime paths. Managed setup for those adapters is later feature work.

It does not contain the dbCAN database. It is distinct from the existing

```text

```

Release tags aid inspection, but the kit manifest records only a verified
digest reference. Do not publish or consume `latest` as an operational input.

### GitHub Publication

Add a repository-owned GitHub Actions workflow that:

1. checks out the exact release revision;
2. builds the Linux/amd64 dbCAN image from locked inputs;
3. runs the bundled smoke before publication;
4. generates and attaches an SBOM;
5. publishes with `packages: write` through `GITHUB_TOKEN`;
6. records the pushed digest and verifies it by pulling that digest;
7. links the package to `FuqingZh/seqevi` through OCI source labels.

The GHCR package must be made public before the public setup release gate.
TestPyPI/PyPI trusted publishing is a separate artifact path and grants no GHCR
permission.

### Compliance Record

The release record maps every bundled runtime component to:

- exact name and version;
- installed artifact or package;
- license and notice obligations;
- corresponding upstream source URL and checksum;
- image layer/build step that introduced it.

The source and notice record covers the runtime image only. The caller-owned
database is not listed as a redistributed image component.

## External Resource Contract

The supported database root contains:

```text
CAZy.dmnd
dbCAN.hmm
dbCAN-sub.hmm
fam-substrate-mapping.tsv
```

The bundled kit manifest declares the release name, canonical relative paths,
byte sizes and SHA-256 values. It contains no resource download URL or staging
destination.

Setup performs a full validation before smoke. It reuses the native
`seqevi.lock` contract:

- validate an existing lock and all required files;
- atomically create a lock when absent and the directory is writable;
- remain correct with a read-only unlocked directory by calculating identity
  without requiring a write;
- never refresh or overwrite a conflicting lock silently.

The resource remains at the caller-supplied path and is bind-mounted read-only
for each container invocation.

## CLI Contract

### `seqevi setup`

```bash
seqevi setup dbcan-cazyme --resource /data/dbcan/raw
seqevi setup dbcan-cazyme --resource /data/dbcan/raw --dry-run
seqevi setup dbcan-cazyme --resource /data/dbcan/raw --dry-run --json
seqevi setup dbcan-cazyme --resource /data/dbcan/raw --yes
seqevi setup dbcan-cazyme \
  --resource /data/dbcan/raw \
  --profile-name dbcan-cazyme-2026 \
  --yes
```

Public CLI exposes `--dry-run`, not an additional `--plan` synonym.

Resource resolution is:

1. use explicit `--resource`;
2. otherwise reuse the target profile's resource when that profile already
   exists;
3. otherwise prompt once for a path on an interactive terminal;
4. otherwise fail before Docker or filesystem mutation.

`--yes` is non-interactive. It cannot invent a first-run resource path and does
not weaken validation.

### Setup State Matrix

| Profile | Image | Resource input | Behavior |
| --- | --- | --- | --- |
| absent | absent | supplied/resolved | pull, verify, smoke, publish profile |
| absent | present | supplied/resolved | verify, smoke, publish profile |
| absent | either | unresolved | prompt interactively or fail without mutation |
| present and equal | absent | omitted or equal | pull exact digest, verify and finish as repair/no-op |
| present and equal | present | omitted or equal | verify readiness and finish as no-op |
| present but conflicting | either | different | fail; require an explicit new profile name |

There is no successful runtime-only state in P0.

### Confirmation

Setup calculates one typed plan before applying it. Human mode displays:

- adapter, dbCAN and DIAMOND versions;
- exact GHCR repository and digest;
- whether a pull is required;
- resolved resource and Store paths;
- resource validation work;
- profile name and destination;
- license/NOTICE summary;
- ordered actions.

Without `--yes`, it asks for one confirmation after the complete plan. It does
not ask separately before pulling and before mounting. A mount is created only
for the short-lived smoke or annotation process; it is not persistent state.

### `--dry-run`

Dry-run may inspect the kit, Docker daemon, image cache, resource metadata,
free space and existing profile. It must not:

- pull an image;
- create or update `seqevi.lock`;
- create directories or profiles;
- start a container;
- mutate Docker or SeqEvi state.

### `--json`

`--json` changes presentation only. It neither implies dry-run nor authorizes
mutation. Human and JSON modes render the same typed plan and outcome.

The initial JSON document includes:

```text
schema_version
adapter
kit_id
status
runtime
resource
profile
actions
smoke
next_command
```

Successful JSON output is one document on stdout. Structured failures go to
stderr with a non-zero exit status; Rich markup and progress output never mix
with JSON.

## Idempotency And Publication

Apply executes the already displayed plan:

1. validate platform, Docker access, path boundaries and local state;
2. pull the exact GHCR digest only when missing;
3. fully validate the caller-owned resource;
4. run the bundled smoke in an ephemeral container;
5. compare adapter, runtime, resource and result identities with the kit;
6. atomically publish the complete v2 profile;
7. print the exact next annotation command.

Repeating equal setup succeeds without rewriting the profile or re-pulling the
image. A failed smoke publishes no profile. Image layers may remain in Docker's
cache after failure; they are valid content-addressed cache, not a partial
SeqEvi installation.

Setup never overwrites a same-name profile with different effective content.
`--profile-name` is the explicit side-by-side path.

## Execution Profile And Later Reuse

V1 local profiles remain valid:

```toml
version = 1
adapter = "dbcan-cazyme"
executable = "/opt/dbcan/bin/run_dbcan"
resource = "/data/dbcan/raw"
```

Managed setup writes a v2 document:

```toml
version = 2
adapter = "dbcan-cazyme"
resource = "/data/dbcan/raw"
store = "/home/user/.local/share/seqevi/store"
threads = 8

[runtime]
kind = "oci"
kit_id = "dbcan-cazyme-5.2.9-db-2026.05.05"
engine = "docker"
image = "ghcr.io/fuqingzh/seqevi-dbcan@sha256:<digest>"
```

The default profile name is `dbcan-cazyme`. Profile selection remains explicit;
there is no mutable current profile, site inheritance or hidden project
discovery.

Days later, the same CLI and Python paths continue to work:

```bash
seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

```python
import seqevi

annotations = seqevi.annotate(
    "proteins.faa",
    profile="dbcan-cazyme",
    output="dbcan.duckdb",
)
```

If Docker's cache was cleaned, execution may pull the same pinned digest again.
If the recorded resource path is gone, SeqEvi reports that exact path and a
copyable repair command. It does not search other filesystems.

## OCI Delegation Boundary

OCI execution is dispatched at the application boundary so CLI and Python API
behavior stay equal. Adapter implementations remain unaware of Docker.

Every smoke or annotation uses one unique ephemeral container with:

- FASTA and resource read-only;
- only output, temporary work and an optional local Store narrowly writable;
- caller numeric UID/GID;
- no Docker socket, home-directory or whole-working-directory mount;
- `--network none` for local Store;
- network enabled only for an explicit shared HTTP(S) Store;
- redacted environment transfer for shared Store credentials;
- exact inspection and cleanup on success, failure, timeout and cancellation.

All subprocesses use argument arrays and `shell=False`.

## Acceptance Criteria

1. A supported user reaches a real dbCAN annotation without installing dbCAN,
   DIAMOND or a host Python environment for them.
2. The only unavoidable external prerequisite is the exact database path; the
   path is supplied once and persisted in a normal named profile.
3. Setup has one confirmation, a read-only dry-run, stable JSON, idempotent
   repair and atomic profile publication.
4. The public image is pullable from GHCR without login and is always selected
   by digest.
5. The image has auditable license, NOTICE, SBOM and source correspondence and
   contains no annotation database.
6. Later annotation works from CLI and Python without resource re-entry or a
   persistent container.
7. Direct and managed execution of the same candidate have equal runtime and
   scientific identity; separate installations may differ only in exact
   runtime fingerprint while preserving scientific identity and result.
8. Existing v1 profiles and explicit local mode continue unchanged.
9. SeqEvi contains no cluster-user branch, site profile, internal Harbor
   default, broad filesystem discovery or biofetch dependency.
