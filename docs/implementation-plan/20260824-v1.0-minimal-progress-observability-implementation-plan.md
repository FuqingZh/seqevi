# Minimal Annotation Progress Observability Implementation Plan

Version: v1.0

Date: 2026-08-24

Status: approved implementation plan; not implemented

## Goal

Give an interactive `seqevi annotate` user a truthful answer to three questions:

1. Which SeqEvi phase is active?
2. Is a long-running annotation invocation still active?
3. What exact work has completed when SeqEvi owns a meaningful count?

The first release is a small execution-observability skeleton shared by local
eggNOG-mapper, dbCAN and InterProScan/Pfam annotation. It is not a unified
parser for third-party console output and does not claim an upstream-tool
percentage or estimated completion time that SeqEvi cannot establish.

## Frozen Product Decisions

1. SeqEvi progress and upstream tool logs are separate channels. Existing
   adapter stdout and stderr files remain byte-preserving and authoritative.
2. The initial progress model is internal. It is not exported from the Python
   package and does not add a public callback to `seqevi.annotate()`.
3. The CLI adds only `--progress auto|off`. `auto` enables an interactive
   stderr presentation when stderr is a TTY and disables it otherwise.
4. `--json` always disables the initial interactive presentation. After Click
   has successfully parsed a syntactically valid invocation, successful stdout
   remains exactly one JSON document and the existing typed application-failure
   stderr remains exactly one JSON error document. Pre-callback Click usage and
   option-validation failures retain Click's existing human-readable contract;
   this plan does not add a top-level CLI error serializer.
5. Progress is best-effort presentation. A renderer failure is diagnosed but
   must not change evidence computation, Store mutation, result publication,
   cancellation, timeout or process cleanup.
6. SeqEvi reports a percentage only when both numerator and denominator are
   exact and refer to the same SeqEvi-owned unit. Activity and elapsed time are
   never converted into percentage or ETA.
7. Tool-batch totals are not predicted. The bounded-memory orchestration may
   execute misses while later Store lookup is still in progress, so the final
   number of tool batches is not always known at the first batch.
8. No dependency is added. The terminal presentation uses existing Python and
   Typer surfaces.

## Minimal Internal Contract

Add one immutable internal event value with only the fields needed by the
initial terminal renderer:

```python
@dataclass(frozen=True, slots=True)
class ProgressEvent:
    phase: ProgressPhase
    state: ProgressState
    message: str
    completed: int | None = None
    total: int | None = None
    unit: ProgressUnit | None = None
    elapsed_seconds: float | None = None
```

The internal sink is an optional callable. One guarded emission helper keeps
presentation failure outside the scientific and operational result contract.
`completed` and `total` may form a ratio only when both are present with one
typed `unit`; the event constructor rejects partial or unitless ratios. The
renderer never infers a unit from `message`. The initial phases are:

```text
annotation
staging
store_lookup
claim_wait
tool
store_commit
store_fetch
package
completed
```

The initial states are `started`, `running` and `completed`. Annotation errors
continue through the existing typed exception path; the renderer clears its
line before the existing CLI error presenter runs. A separate public failure
event contract is deliberately deferred.

## Presentation

The interactive renderer owns only the latest event and a monotonic display
clock. While any phase remains active, including staging, Store lookup,
claim-wait, tool execution, commit, fetch, packaging or managed OCI dispatch,
one small timer thread refreshes the same stderr line with elapsed time. It
does not inspect processes, files, CPU, Store state or upstream logs, and it
never owns cancellation or cleanup.

Representative output is:

```text
[seqevi] store lookup · 2,000/2,729 sequences
[seqevi] InterProScan/Pfam · tool batch 1 running · 12m34s
[seqevi] tool batch 1 completed · 2,729 sequences
[seqevi] packaging result · 20m41s
```

When an exact denominator is unavailable, the renderer omits a fraction and
percentage. The final existing human or JSON summary remains the invocation
result; progress never replaces it.

## Execution Slices

### Slice 1: Internal event boundary and exact orchestration events

- Add the internal event value, phase/state types, sink alias and guarded emit
  helper.
- Thread the optional internal sink through `_run_annotation_application()` and
  `run_annotation()` without changing the public Python API.
- Emit phase transitions at existing shallow orchestration boundaries.
- Emit exact Store lookup and tool-batch counts only where the current code
  already knows them without retaining additional sequence state or changing
  batching order.
- Emit an outer annotation-running state around managed OCI dispatch. Do not
  alter the inner managed command or its one-document `--json` contract.
- Keep the invocation active after `run_annotation()` returns. The application
  boundary alone emits terminal completion, after the local Store context has
  closed and the published result has been reopened and validated, or after the
  equivalent managed result scan has succeeded.

### Slice 2: Minimal CLI renderer

- Add `--progress auto|off` to `seqevi annotate`.
- Enable `auto` only for interactive stderr and only when `--json` is absent.
- Refresh one stderr line from the latest event and monotonic elapsed time.
- Stop and join the presentation thread from an unconditional `finally` path
  after every normal or exceptional exit; clear the transient line before the
  existing result or typed error output.
- Keep renderer timing injectable in focused tests so no test waits 30 seconds.

### Slice 3: Contract documentation and verification

- Add a focused approved progress-observability contract under
  `docs/architecture/` when implementation begins.
- Update the documentation index and validation strategy for the accepted CLI
  behavior.
- Run focused orchestration, CLI and application-boundary tests, then the
  repository-required canonical `pdm run check` gate.

## File-Level Modification Scope

| Path | Planned change |
| --- | --- |
| `src/seqevi/progress.py` | New private event value, types, sink and guarded emission boundary. No public export. |
| `src/seqevi/annotate.py` | Emit exact staging, lookup, claim-wait, tool-batch, commit, fetch and package transitions, but no terminal completion. Preserve batching and Store semantics. |
| `src/seqevi/api.py` | Pass the private sink through the shared application boundary, provide the outer managed-OCI running transition, and emit terminal completion only after Store teardown and result scan. Keep `annotate()` signature unchanged. |
| `src/seqevi/cli.py` | Add `--progress auto|off` and the interactive stderr renderer; preserve current final human/JSON output. |
| `tests/test_progress.py` | New deterministic unit coverage for rendering, monotonic elapsed display, shutdown and sink-failure containment. |
| `tests/test_annotate.py` | Verify event order and exact/unknown count semantics without changing annotation results. |
| `tests/test_cli.py` | Verify TTY auto/off selection, stderr-only presentation and exact `--json` purity. |
| `tests/test_api.py` | Verify local sink forwarding and the managed outer-envelope event without changing the public Python API. |
| `docs/architecture/20260824-v1.0-progress-observability-contract.md` | New focused authoritative contract created with the implementation. |
| `docs/testing/20260810-v1.1-validation-strategy.md` or a successor | Record the progress compatibility gates. Use a successor if the accepted validation contract changes materially. |
| `docs/README.md` | Link the active plan now and the implemented contract when accepted. |

The implementation must not change these surfaces:

- `src/seqevi/runner.py` process supervision and cleanup;
- `src/seqevi/adapters/` command construction or output parsing;
- Store, EvidenceKey, ToolRuntimeDigest, ResourceID or artifact contracts;
- annotation batch sizes or bounded-memory ordering;
- upstream stdout/stderr contents or successful-work-directory cleanup;
- DuckDB result schema, metrics or scientific result content;
- managed OCI inner stdout JSON protocol;
- dependencies in `pyproject.toml`.

## Deferred Work

The following features require evidence of need and are not part of this plan:

- adapter-specific parsing of eggNOG, dbCAN or InterProScan milestones;
- upstream-tool percentages or ETA;
- JSONL progress files or a public progress-event schema;
- a public Python callback;
- raw tool-log following or successful-run log retention;
- Rich dashboards, multiple simultaneous progress bars or a plugin framework;
- managed OCI inner-event forwarding;
- history-based duration prediction.

These additions may reuse the internal emission boundary later. They must not
be pre-built into the initial implementation.

## Verification And Acceptance

Focused tests must prove:

1. Event order follows the existing orchestration path for all-cache, local
   compute, no-hit, claim-wait and failure cases.
2. Counts and percentages appear only when exact `completed`, `total` and typed
   `unit` values are present on the same event; partial or unitless ratios are
   rejected, and an unknown tool-batch total remains unknown.
3. A blocking fake adapter continues to produce elapsed interactive display
   updates without reading or rewriting its logs.
4. Renderer or sink failure is diagnosed and does not change the annotation
   summary, result bytes, Store evidence or typed failure.
5. `--progress off`, non-TTY `auto` and every `--json` application path produce
   no progress text.
6. After successful Click parsing, JSON success stdout and typed application
   failure stderr remain individually parseable as one document; an invalid
   `--progress` value retains the existing Click usage-error shape.
7. Managed OCI preserves its existing inner command and result validation;
   only the outer invocation state is displayed.
8. The renderer refreshes elapsed time during claim-wait, Store and packaging
   phases as well as tool and managed OCI phases, and unconditional finalization
   stops its timer after ordinary untyped exceptions.
9. A delayed local Store close or result scan keeps the invocation active;
   terminal completion appears only after teardown and validated result open.
10. Cancellation, timeout and cleanup tests remain green without modification
   to `ToolRunner`.

Completion requires focused tests plus `pdm run check`. No real eggNOG,
dbCAN or InterProScan rerun is required for this presentation-only first slice
unless executable tests reveal a change outside the frozen modification scope.

## Stop Conditions

Stop and revise this plan rather than expanding implementation if any of the
following becomes necessary:

- changing process supervision or adapter command arguments;
- retaining or parsing successful upstream logs;
- changing the managed inner JSON protocol;
- restructuring lookup and tool batching to obtain a denominator;
- adding a dependency or a public event schema;
- changing Store, evidence identity or result content.
