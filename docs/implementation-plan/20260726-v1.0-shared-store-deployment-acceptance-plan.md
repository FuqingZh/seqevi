# Shared Store Deployment And Acceptance Plan

> Status: canary accepted; production promotion pending
> Date: 2026-07-26
> Issue: FUQ-11
> Target: real PostgreSQL/HTTP/POSIX shared Store acceptance

## Outcome

Deploy the already implemented Phase 5 shared Store on a real host and prove
that independent annotation clients reuse exact eggNOG and InterPro evidence
through HTTP.

This work validates the approved storage architecture. It does not redesign the
SQL schema, add annotation scheduling, expose PostgreSQL to compute clients, or
put SQLite on a shared filesystem.

## Acceptance Topology

The first acceptance deployment is deliberately private and single-service:

```text
independent SeqEvi clients
          |
          | HTTP on node4 loopback
          v
     seqevi serve
       /       \
      v         v
PostgreSQL 18   service-owned CephFS artifacts
```

Selected canary surfaces:

| Boundary | Selection |
| --- | --- |
| Compute and service host | `node4` |
| HTTP endpoint | loopback-only `127.0.0.1:18081` |
| PostgreSQL | dedicated PostgreSQL 18.4 container on loopback |
| PostgreSQL persistence | dedicated Docker volume |
| Artifact root | `database/bioinfo/stores/seqevi/artifacts` on CephFS |
| Annotation runtimes | existing accepted user execution profiles |

Loopback keeps the unauthenticated v1 service private during acceptance.
Multi-host exposure is a separate promotion gate requiring an authenticated
private ingress or equivalent network control.

## Evidence Rules

- Record exact source commit, service configuration without credentials,
  database and runtime versions, input identities, wall time and peak RSS.
- Keep passwords, raw logs and temporary outputs outside the repository.
- Retain stable commands, checksums, counts and conclusions in a benchmark
  document.
- Verify the final PostgreSQL rows and referenced artifact bytes, not only CLI
  exit codes.
- Mark a stage complete only from fresh evidence generated by this deployment.

## Execution Stages

### Stage 0: Environment And Boundary Selection

Status: complete.

- Confirm Docker and PostgreSQL 18.4 are available on `node4`.
- Confirm no existing SeqEvi service or dedicated shared Store exists.
- Select a dedicated PostgreSQL container, database and persistent volume.
- Select a service-owned artifact directory outside external resource trees.
- Keep the canary HTTP endpoint on loopback until security promotion.

### Stage 1: Deploy The Canary Store

Status: complete.

- Create the dedicated CephFS artifact root with a narrow write probe.
- Start PostgreSQL with a generated credential and loopback-only port.
- Start `seqevi serve` against the empty database and artifact root.
- Verify advisory-lock Alembic migration, schema head and `/health`.
- Restart the service and confirm migration and health are idempotent.

### Stage 2: PostgreSQL Contract Validation

Status: complete.

- Run all tests marked `requires_postgres` with
  `SEQEVI_TEST_POSTGRES_URL`.
- Verify bigint artifact sizes, commit/lookup/fetch and concurrent identical
  commits.
- Query terminal row counts and schema revision directly from PostgreSQL.
- Confirm clients cannot obtain database credentials from the service API.

### Stage 3: Shared HTTP Performance Baseline

Status: complete.

- Exercise new, cached and mixed fixture workloads through the HTTP Store.
- Measure lookup, artifact transfer, commit, fetch and materialization phases.
- Use at least 10,000 deterministic sequences unless measurement shows a
  smaller bound is sufficient to identify the bottleneck.
- Compare output values with local Store results.
- Record batch counts, wall time, throughput, peak RSS and stored bytes.

### Stage 4: Real Adapter Reuse

Status: complete.

- Refresh and validate the published eggNOG resource lock if required.
- Validate named profiles for eggNOG-mapper 2.1.13/DB 5.0.2 and
  InterProScan 5.77-108.0/Pfam 38.1.
- Run one cold annotation for each adapter through the HTTP Store.
- Run an independent second client and require a complete cache hit with zero
  external-tool execution.
- Compare evidence identity, normalized tables, no-hit tables and artifact
  digests between cold and cached packages.

### Stage 5: Recovery And Operational Acceptance

Status: complete.

- Restart the HTTP service and PostgreSQL container, then repeat cached reads.
- Verify identical concurrent commits are idempotent.
- Verify malformed, oversized, missing and corrupt artifacts fail loudly.
- Record the PostgreSQL plus artifact backup consistency boundary.
- Check directory ownership, service logs, container health and remaining
  temporary files.

### Stage 6: Closeout

Status: complete.

- Publish a versioned benchmark with the accepted and rejected claims.
- Update this plan with final stage status and residual risks.
- Run focused tests and `pdm run check`.
- Deliver a ready-for-review pull request linked to FUQ-11.

The stable evidence and promotion boundary are recorded in
[Shared Store deployment and acceptance](../benchmarks/20260726-v1.0-shared-store-deployment-acceptance.md).

## Acceptance Criteria

1. An empty PostgreSQL database migrates to the supported head under the
   advisory lock and restarts idempotently.
2. Only `seqevi serve` writes shared metadata and artifacts.
3. A second client reuses evidence committed by a first client without running
   the adapter.
4. eggNOG and InterPro each pass one real cold/cache HTTP Store smoke.
5. Local and shared Store packages are scientifically equivalent for the same
   evidence identity.
6. Concurrent identical commits are idempotent and conflicting payloads fail.
7. Performance claims include input scale, environment, outputs and resource
   use.
8. PostgreSQL integration tests and `pdm run check` pass.

## Promotion Gate

This canary does not authorize exposing the v1 unauthenticated service to other
hosts. Production promotion requires:

- a stable service package or immutable deployment image;
- private authenticated ingress and TLS policy;
- durable secret management;
- PostgreSQL and artifact backup/restore rehearsal;
- monitoring for health, storage capacity and integrity failures;
- a reviewed endpoint and ownership decision.
