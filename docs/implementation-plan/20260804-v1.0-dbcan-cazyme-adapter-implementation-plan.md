# dbCAN CAZyme Adapter Implementation Plan

Version: v1.0
Date: 2026-08-04
Status: complete for v1 local and shared Store acceptance; managed onboarding remains separate
Target adapter: `dbcan-cazyme`

## Goal

Add a third explicit official adapter for protein-level carbohydrate-active
enzyme annotation while preserving SeqEvi's per-sequence cache model and
adapter-native schemas.

The high-frequency invocation remains the same as the existing adapters:

```bash
seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

The adapter calls the official `run_dbcan` launcher. SeqEvi does not reimplement
DIAMOND, HMM matching, subfamily assignment or recommendation logic.

## Dependency On The Result Contract

This plan depends on the
[queryable result and Python API plan](20260804-v1.0-result-consumption-implementation-plan.md)
through its DuckDB writer acceptance gate. Implementing dbCAN directly against
the 0.1.0 Data Package output would create an avoidable second migration.

The dbCAN adapter itself does not depend on the later managed setup/OCI work. A
user-supplied local runtime and resource must work first.

## Installation And Onboarding Boundary

The scientific adapter and managed installation are separate acceptance
boundaries:

1. this plan first proves a user-supplied installation of the official
   `run_dbcan` launcher, dbCAN Python runtime and DIAMOND against the four-file
   resource through profile v1;
2. only after that direct/local parity gate may the
   [managed onboarding roadmap](20260804-v1.0-managed-adapter-onboarding-implementation-plan.md)
   package the accepted runtime into a SeqEvi-managed OCI image and introduce
   `seqevi setup` plus profile v2.

The future image is built from the official dbCAN release but is published and
supported by SeqEvi; it is not an upstream-official dbCAN image. The current CLI
does not install dbCAN, DIAMOND, Docker or the database resource.

## Scientific Model

dbCAN combines three evidence paths for the same protein input:

```text
protein sequence
  |-- DIAMOND       -> similarity to known CAZy proteins
  |-- dbCAN HMM     -> CAZy family/domain evidence
  `-- dbCAN-sub HMM -> subfamily, EC and substrate-associated evidence
                         |
                         `-> overview.tsv
```

The engines overlap with other adapters only at the implementation level.
dbCAN and eggNOG-mapper can both execute DIAMOND, but they search different
databases with different parameters and answer different scientific questions.
An eggNOG DIAMOND hit or transferred `CAZy` field cannot be reused as dbCAN
evidence.

## Frozen Adapter Contract

### Public And Internal Names

- public adapter family: `dbcan-cazyme`;
- initial internal adapter contract: `dbcan-cazyme/1`;
- upstream runtime: `dbcan==5.2.9` and DIAMOND `2.1.15`;
- supported input: protein FASTA;
- supported dbCAN command family: `CAZyme_annotation --mode protein`.

The qualified public name is intentional. SeqEvi does not support the complete
dbCAN product surface: CGC and PUL analyses depend on gene coordinates,
neighborhood and additional inputs that are not functions of one canonical
protein sequence.

Profiles continue to contain the adapter family, not the internal contract:

```toml
version = 1
adapter = "dbcan-cazyme"
executable = "/opt/dbcan-5.2.9/bin/run_dbcan"
resource = "/data/dbcan/db_v5-2-9_5-5-2026/raw"
store = "/data/seqevi-store"
threads = 8
```

SeqEvi probes the runtime and resource and binds the supported internal
contract. Ordinary users do not type `dbcan-cazyme/1`.

### Fixed Invocation Semantics

The adapter constructs an argument array equivalent to:

```text
run_dbcan CAZyme_annotation
  --input_raw_data <cache-miss.faa>
  --mode protein
  --output_dir <batch-work-dir>
  --db_dir <resource>
  --methods diamond,hmm,dbCANsub
  --threads <threads>
```

The initial semantic contract fixes all three methods and materializes every
result-affecting threshold in `SemanticParameters`, including:

| Method | Parameter | Initial value |
| --- | --- | --- |
| DIAMOND | E-value | `1e-102` |
| dbCAN HMM | coverage | `0.35` |
| dbCAN HMM | E-value | `1e-15` |
| dbCAN-sub HMM | coverage | `0.35` |
| dbCAN-sub HMM | E-value | `1e-15` |

The implementation must confirm the exact v5.2.9 launcher option names in a
Stage 0 probe and pass every value explicitly. An upstream default is not an
acceptable hidden part of the evidence identity.

`threads`, temporary paths, logs and retry behavior remain operational. A
1-thread versus multi-thread parity gate must show equal normalized scientific
content before threads are classified as non-semantic.

There is no arbitrary `--extra-args`, no public `--diamond` path, and no set of
`--dbcan-*` scientific switches on `seqevi annotate`. Changing methods or
thresholds requires an explicit adapter-contract decision.

## Resource Contract

The initial resource release is `db_v5-2-9_5-5-2026`. Its required
result-bearing files are:

```text
CAZy.dmnd
dbCAN.hmm
dbCAN-sub.hmm
fam-substrate-mapping.tsv
```

The adapter resource inventory, resource lock and `ResourceID` cover all four
files by canonical relative path, byte size and SHA-256. A mutable alias such
as `db_current` is never an identity.

The following resources are outside the protein-only contract and are not
required:

- `TCDB.dmnd`;
- `TF.hmm` and `TF.dmnd`;
- `STP.hmm`;
- `PUL.dmnd`, `dbCAN-PUL.xlsx` and the PUL directory;
- peptidase and SulfAtlas databases;
- SignalP or DeepTMHMM data.

SeqEvi remains independent of biofetch. A publisher may use biofetch to acquire
and lock the resource, but SeqEvi validates only its own native adapter resource
contract and `seqevi.lock`.

## Runtime Contract

Installing the small `dbcan` Python package is not sufficient by itself. The
runtime contains:

- the official `run_dbcan` launcher and installed `dbcan` package files;
- the resolved Python interpreter and result-bearing Python dependencies;
- `pyhmmer` used by dbCAN v5;
- a separately installed DIAMOND executable.

An external `hmmscan` executable is not required for this v5 contract.

`ToolRuntimeDigest` must be path-independent and cover the dbCAN distribution,
normalized dbCAN version, selected DIAMOND binary and normalized DIAMOND
version. Extract a private Python-runtime fingerprint helper only for the
component logic genuinely shared with eggNOG. Do not introduce a plugin or
generic arbitrary-runtime framework.

## Result Contract

### Normalized Evidence

The authoritative normalized source is `overview.tsv`. Preserve its
protein-level row grain, native columns and meanings, normalize only
scalar/null types, and add canonical `SequenceID` linkage.

The initial adapter schema includes the actual v5.2.9 overview fields observed
in Stage 0, including the concepts represented by:

```text
Gene ID
EC#
dbCAN_hmm
dbCAN_sub
DIAMOND
#ofTools
Recommend Results
Substrate
```

The Stage 0 direct probe freezes the exact spelling, order and types. The
official v5.2.9 launcher emits Substrate even when the value is a hyphen and
when no sequence has a hit. No field is renamed to create a cross-adapter
ontology.

Terminal status is determined as follows:

- a requested sequence represented in the validated overview is `hit`;
- a requested sequence absent after successful complete execution is `no_hit`;
- one-method support remains a hit;
- `#ofTools` and `Recommend Results` expose confidence for downstream policy;
- SeqEvi does not silently require two agreeing methods.

### Raw Evidence

The initial raw artifact is a deterministic compressed copy of the validated
primary `overview.tsv`, not a tarball of every detailed dbCAN output.

This is a deliberate MVP boundary. The current Store fetch path materializes
raw and normalized artifacts together, and the shared service enforces a
single-artifact size limit. Bundling `diamond.out` and both detailed HMM result
tables could substantially increase cached network I/O without benefiting the
common annotation result.

Retaining or fetching detailed method artifacts is a separate Store contract
decision after real size and demand measurements. It must not be hidden inside
this adapter implementation.

### DuckDB Exposure

The adapter supplies its native normalized schema to the shared result writer.
The public `main.annotations` view therefore begins with `InputID` and the
common sequence/status fields and then exposes the dbCAN overview columns.

The adapter does not create a dbCAN-specific result wrapper, a dbCAN top-level
CLI command, or a universal annotation table.

## Execution Slices

### Slice A: Stage 0 Runtime And Resource Probe — direct probe passed

Predecessor: accepted dbCAN 5.2.9 runtime and four-file resource snapshot are
available outside the repository.

Run the official launcher directly on a tiny fixture containing known hit and
no-hit candidates. Record:

- exact version probes and command options;
- required files opened by the protein-mode command;
- exact `overview.tsv` header, null markers and row ordering;
- behavior when no sequence has a hit;
- behavior for one-, two- and three-method support;
- detailed output sizes even though they are not retained in MVP;
- peak RSS and 1-thread/multi-thread value equality.

Evidence for this gate is retained in
[`20260804-v1.0-dbcan-runtime-validation.md`](../benchmarks/20260804-v1.0-dbcan-runtime-validation.md).
The official `dbcan==5.2.9` wheel and DIAMOND `2.1.15` release were installed
in an isolated temporary environment; reusable copies are retained under
`/home/fqzhang/pkgs`. The accepted four-file resource snapshot was verified
through its `seqevi.lock` and its publisher `manifest.lock` was read back.
The direct 50-record run accounted for all inputs: five overview hit rows and
45 absent rows that SeqEvi classified as terminal no-hits. The launcher opened
only the four contracted files; no CGC/PUL asset was required. The exact
v5.2.9 option names and defaults were frozen, including the eight-column
`overview.tsv` header. A four-thread direct rerun completed successfully with
the same scientific rows as the one-thread run.

### Slice B: Contract And Fixtures — implemented in working tree

Predecessor: Slice A evidence accepted.

Create a new versioned adapter-contract document or version the current adapter
contract so that dbCAN's command, identities, schema, status rule and exclusions
are normative. Add small native output fixtures covering hit, no-hit, malformed
header, unknown sequence ID, duplicate overview rows and invalid scalar values.

Acceptance gate: an implementer does not need to infer thresholds, result
grain, required files or hit policy from upstream defaults.

### Slice C: Adapter Implementation — implemented in working tree

Predecessor: Slice B merged and the DuckDB writer contract from the result plan
is accepted.

Implement the official adapter, resource lock inventory, runtime digest,
profile template and registry binding. Use subprocess argument arrays and the
existing runner. Stream or batch native parsing into file-backed Parquet; do
not build the complete result in Python objects.

Focused acceptance (fixture-backed locally):

- command array contains all fixed semantic parameters;
- runtime identity changes when dbCAN package or DIAMOND content changes;
- resource identity changes when any required resource changes;
- relocation of identical runtime/resource content does not change identity;
- malformed or incomplete output commits zero evidence for the failed batch;
- every requested sequence is classified exactly once;
- normalized schema and payload digests are deterministic.

### Slice D: Store And Incremental Reuse — local and shared Store complete

Predecessor: Slice C focused tests pass.

The local fixture validates:

- cold run commits hit and no-hit evidence;
- an exact rerun launches no dbCAN process;
- partial-overlap input computes only missing `SequenceID` values;
- changed runtime, resource or semantic contract does not reuse incompatible
  evidence;
- dbCAN evidence coexists with eggNOG and InterPro evidence for the same
  sequence in one local or shared Store without schema mixing.

The shared PostgreSQL Store contract suite passed with a configured
`SEQEVI_TEST_POSTGRES_URL`. An isolated PostgreSQL-backed HTTP replay also
served the already validated dbCAN evidence without launching the external
runtime; its `main.evidence` and `main.no_hits` relations were value-equal to
the local DuckDB result after deterministic sorting.

Run this slice against SQLite and PostgreSQL/shared Store paths.

### Slice E: Official Runtime Parity And Closeout — complete

Predecessor: Slice D passes.

Compare direct dbCAN and SeqEvi on the accepted real runtime/resource:

- overview schema and values;
- per-sequence hit/no-hit status;
- method counts and recommendation fields;
- cold, all-cached and partial-overlap behavior;
- final DuckDB `annotations`, `evidence`, provenance and row-grain metadata.

The 50-record cold and exact-cache replays passed, and the 51-record
partial-overlap replay reported 50 cached and one computed sequence while
preserving the prior five hits. The isolated shared PostgreSQL cache replay
preserved the same dbCAN evidence rows without invoking the launcher. The
shared PostgreSQL contract suite and the final repository gate also passed:

```bash
pdm run check
```

Record reproducible commands, versions, input digest, evidence identity and
result comparisons in a benchmark/runtime-validation document. Do not commit
large databases or raw runtime outputs.

## Acceptance Criteria

1. A user with a valid local profile invokes dbCAN through the same `annotate`
   interface used for eggNOG and InterPro/Pfam.
2. SeqEvi results match official dbCAN 5.2.9 protein-mode overview semantics.
3. DIAMOND, family HMM and subfamily HMM evidence are all enabled and
   identity-bearing.
4. One-method hits are preserved rather than silently filtered.
5. Exact reruns and partial-overlap runs demonstrate Store-based incremental
   reuse.
6. SQLite and shared PostgreSQL paths preserve identical scientific results.
7. The result is self-describing and consumable through `InputID` without a
   dbCAN-specific Python API.
8. `pdm run check` and the real-runtime parity gate pass.

## Non-Goals

- CGC, PUL, genome-neighborhood or GFF-dependent analysis.
- SignalP, DeepTMHMM or licensed optional topology tools.
- A generic adapter plugin system.
- Arbitrary upstream command templates or passthrough arguments.
- Reuse of eggNOG DIAMOND hits as dbCAN evidence.
- A multi-table detailed-method Store redesign.
- Runtime or resource download inside the scientific adapter.
- Cross-adapter result merging or CAZyme enrichment analysis.

## Intended Review Split

1. Stage 0 evidence plus versioned scientific contract.
2. Fixture-backed adapter, profile and resource/runtime identity.
3. SQLite/shared Store reuse and real-runtime parity acceptance.

The managed setup and OCI distribution work remains a separate plan and pull
request sequence.
