# Release Channel Modernization Implementation Plan

Version: v1.0

Date: 2026-09-01

Status: implemented and merged by PR #76 at
`f603424a7ded3fc45ab36cf1ce00842b6f43d57c`; post-merge nightly live canary
complete; no formal publication authorized

## Goal And Authority

Modernize SeqEvi's release channels so candidate validation, nightly package
testing, GitHub Release publication, PyPI publication, and manual dbCAN OCI
publication are distinct states with independent authority.

This plan implements the user-approved contract recorded on 2026-09-01. It
authorizes repository changes, validation, and one ready-for-review pull
request. It does not authorize creating or pushing a formal version tag,
publishing a GitHub Release, uploading to PyPI or TestPyPI, publishing an OCI
image, deploying, or migrating data.

## Release States

| State | Trigger | Effect | Explicit non-effect |
| --- | --- | --- | --- |
| CI | pull request or ordinary push | repository checks and selected build validation | no tag, release, package-index upload, or OCI publication |
| nightly | off-minute daily schedule or manual dispatch | validate exact clean `main`, build and smoke-test finite SHA-named artifacts retained for 14 days | no tag, GitHub Release, PyPI/TestPyPI/GHCR publication, deployment, or migration |
| tag candidate | canonical `vX.Y.Z` tag push | validate the immutable tagged source and its wheel/sdist | tag push alone never publishes |
| GitHub Release | a human publishes a non-prerelease release for an exact canonical `vX.Y.Z` tag | records the formal release before downstream publication begins | GitHub Release publication does not prove PyPI completion |
| PyPI | non-prerelease `release.published` event after fail-closed identity validation | publish the exact validated wheel/sdist through PyPI Trusted Publishing | no TestPyPI path and no repository code in the OIDC-bearing publish job |
| dbCAN OCI | independent manual workflow dispatch | publish revision-tagged, digest-read-back runtime image for the exact selected source | no coupling to Python tags, GitHub Releases, PyPI, nightly, or ordinary pushes |

The stable tag convention remains `vX.Y.Z`. Release candidates and
prereleases are deliberately unsupported in this revision.

## Version Identity

`pdm-backend` owns package version derivation from SCM. Project metadata uses a
dynamic version with only canonical `vX.Y.Z` tags admitted. An exact tagged
source builds final version `X.Y.Z`; an untagged source builds a PEP 440
development version containing source-distance/revision identity.

The installed distribution metadata is the single runtime authority.
`seqevi.__version__` reads that metadata, and `seqevi --version` reports the
same value. Stable installed releases therefore retain their public `X.Y.Z`
behavior without a source-level version duplicate. Source-tree test execution
must use an installed editable distribution so metadata remains available.

## Workflow Design

### Tag validation and PyPI

Retain `.github/workflows/publish.yml`. It listens only to canonical-looking
version-tag pushes and `release.published` events. Both paths check out the
event's exact tag with complete tag history and fail closed unless:

- the tag is exactly canonical `vX.Y.Z`;
- the tag resolves to the event commit;
- the checkout is clean;
- project, wheel, sdist, installed package, and CLI versions all equal `X.Y.Z`;
- wheel and sdist pass package metadata checks and isolated installation
  smoke tests.

The tag-push path stops after validation and finite artifact upload. Only a
published, non-draft, non-prerelease GitHub Release may reach the PyPI publish
job. Build/validation and publication are separate jobs. The `pypi`
environment and `id-token: write` exist only on the publish job. That job has
exactly two responsibilities: download the SHA-named artifact produced by the
successful validation job and invoke the pinned official PyPI publishing
action. It checks out no repository and executes no repository code.

PyPI completion is asynchronous relative to GitHub Release publication. A
future authorized release operator must read back the exact project version
and file identities from PyPI before claiming completion.

### Nightly

Add `.github/workflows/nightly.yml` with one off-minute daily schedule and
`workflow_dispatch`. It checks out exact `main` with full history and tags,
requires a clean checkout equal to `origin/main`, runs the canonical repository
gate, builds wheel and sdist, validates their shared development identity,
runs package checks, and smoke-installs both wheel and sdist in isolated
environments. It uploads one artifact named with the exact source SHA and
retains it for 14 days.

Nightly has read-only repository permissions and no OIDC or package-write
permission. It contains no tag, release, package-index, OCI, deployment, or
migration operation.

### dbCAN OCI

Keep `.github/workflows/publish-dbcan-image.yml` dispatch-only and independent.
Adapt checkout history and artifact selection only as needed for SCM-derived
versions. Revision tags continue to include both the derived package version
and exact source SHA; pushed digest and embedded revision/version are read back
before success. No Python release event or tag trigger is added.

All third-party Actions in changed or new publication workflows are pinned to
immutable commit SHAs with readable version comments. Workflow-level and job-
level permissions remain least privilege.

## Repository-Owned Contract Boundary

Add a small typed release-contract module under `scripts/` that:

- parses only canonical `vX.Y.Z` tags;
- derives the expected final version;
- validates wheel/sdist filenames and embedded metadata as one exact artifact
  set; and
- exposes a command used by workflows after builds.

Focused tests cover accepted/rejected tags, mismatched or incomplete artifact
sets, final and development identities, installed metadata/CLI agreement, and
workflow structure. Workflow tests mechanically reject tag-to-publication,
manual TestPyPI, prerelease publication, OIDC outside the publish job,
unbounded nightly artifacts, and Python-release coupling in dbCAN OCI.

## Documentation Decision

Update the current system architecture, documentation index, and root README
to name CI, nightly, tag candidate, GitHub Release, PyPI, and OCI as distinct
states. Historical release reviews and dated evidence remain unchanged.

## Verification

Completion claim: the pull request implements SCM-derived development/final
version identity; tag validation cannot publish; nightly performs no external
publication and retains one finite artifact; only a stable
`release.published` event can reach least-privilege PyPI Trusted Publishing;
wheel/sdist installs agree with metadata; and dbCAN OCI remains independently
manual with exact-source identities.

Required evidence:

1. focused parser, artifact-identity, installed-version, and workflow-contract
   tests, including a credible negative control;
2. an untagged source build whose PEP 440 development version is tied to the
   current source;
3. an isolated local exact-tag build without remote tag mutation;
4. YAML/workflow syntax validation through repository-owned checks and GitHub's
   pull-request workflow parsing;
5. `pdm run check` because packaging, public, and executable workflow contracts
   change;
6. wheel/sdist package checks and isolated installation smoke tests; and
7. exact-head GitHub CI, platform review, and zero unresolved review threads.

PostgreSQL and native OCI runtime acceptance are not repeated because this
change does not alter Store, scientific, migration, or OCI runtime behavior.
Any unavailable package-index or GitHub Release readback is an intentional
non-publication boundary, not evidence of completion.

## Stop Conditions

Stop rather than publish if validation requires a remote tag, GitHub Release,
package-index upload, OCI push, deployment, migration, admin bypass, or an
unreviewed permissions expansion. Stop and recalibrate if exact artifact
identity cannot cross the build/publish job boundary without repository code in
the OIDC-bearing job, or if feedback expands the accepted release contract.

## Completion

Implementation delivery completed when PR #76 merged at the reviewed head and
the post-merge nightly canary above succeeded. Formal release completion
remains a separate future operation requiring explicit authority for its tag,
GitHub Release, PyPI publication, and external readback stages. OCI publication
remains independently manual.
