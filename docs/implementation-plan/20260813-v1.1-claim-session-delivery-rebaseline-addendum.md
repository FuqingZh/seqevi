## Merge topology and release gate

The merge order and branch relationships are:

1. PR #36 merges to `main` first and becomes delivery authority.
2. Only after PR #36 merges, PR #31 may receive exactly one sync from `main`. That
   sync is base-only: it may incorporate the merged documentation and resolve
   base conflicts, but it must contain no functional change. PR #31 then
   receives exactly one designated, contract-scoped review against its exact
   resulting head.
3. PR #31 merges to `main` only after its frozen acceptance row is satisfied.
4. The #37 PR B cancellation/acceptance slice and the implementation PRs for
   #33, #34, and #35 remain independently reviewable and do not absorb one
   another's scope. For meaningful CI and review before PR #31 lands, each may
   initially target the frozen PR #31 branch. It must not merge into that
   branch or transfer commits through PR #31.
5. After PR #31 lands, every still-open dependent implementation PR is
   retargeted and rebased onto current `main`, reruns its own exact-head gates,
   and merges independently to `main`. Issues #33, #34, and #35 may merge in
   any order. Issue #37 does not enter final acceptance until PR #31 and all
   three are on current `main`; its PR is then retargeted and rebased to current
   `main`, reruns the exact-head PostgreSQL pressure matrix and real C2 64-thread
   acceptance, satisfies its frozen row, and merges last. Any other actual
   dependency triggers the stop condition rather than an implicit stack.

Merging PR #31 establishes implementation PR A only. Product release remains
blocked until #33, #34, and #35 have merged, then #37 has completed its
current-`main` final acceptance and merged last. No merge in this topology
authorizes a production deployment.

## Review governance

For PR #31, a repository maintainer records exactly one designated final
reviewer before the post-sync review starts. That reviewer examines the exact
current head only against PR A's declared contract, the frozen acceptance row,
and whether the base sync is non-functional. The review is not another
open-ended full-diff rediscovery cycle, and additional rolling reviewers do not
expand PR #31's contract.

Each new finding is recorded once and classified before action:

- **duplicate**: link the existing finding or disposition; make no new change;
- **in-contract blocker**: keep the affected PR unmerged until the blocker is
  resolved within that PR's frozen row and revalidated at its new exact head;
- **new follow-up**: open or link an independently owned issue and do not add it
  to the current PR.

For PR #31 specifically, an in-contract blocker cannot be repaired under the
single base-only-sync allowance; it activates the stop-and-rebaseline process.
Classification as a follow-up never weakens the product-release block when the
finding affects ClaimSession release safety. Classification also never closes
a thread by itself: every PR still requires passing CI at its exact current
head and zero unresolved review threads before merge. A review approval of an
older head is not acceptance of a newer head.

## Stop, rollback, and scope-expansion conditions

Stop the affected merge path, preserve its branch and exact head, and request a
new explicit delivery decision if any of these occurs:

- PR #31's permitted sync contains a functional product, test, or CI change;
- PR #31 needs a second base sync, any contract repair, or implementation from
  #33, #34, or #35;
- a designated exact-head review identifies an in-contract blocker on PR #31;
- a follow-up PR needs scope owned by another row, ceases to be independently
  reviewable, or reveals a genuine dependency that changes the topology;
- #37 is combined with another acceptance row, absorbs or loses scope, enters
  final acceptance before PR #31 and #33/#34/#35 are on current `main`, omits
  the post-rebase exact-head PostgreSQL pressure or real C2 gate, or does not
  merge last;
- a new finding would expand a frozen acceptance row or compatibility surface;
- exact-head CI, review authority, or actionable-thread state cannot be
  established; or
- the release gate would be bypassed before #33, #34, #35, and finally #37 have
  merged in the required order.

Before PR #36 merges, rollback is closing its PR and leaving the v1.0 plan's
delivery text unchanged. After PR #36 merges, do not silently edit history or
resume the exhausted review loop: publish a new dated superseding addendum that
records the preserved heads, the reason for reopening topology, the revised
disposition, and fresh acceptance authority. Reverting this addendum is safe
only while no downstream branch or review has relied on it; otherwise use a
superseding addendum so dependent work remains auditable.

Scope-expansion pressure is not resolved by moving code into PR #31, merging a
dependent PR into the frozen branch, adding unrestricted reviewers, or waiving
exact-head gates. Those actions are stop conditions, not rollback mechanisms.
