# Managed Adapter Onboarding And Distribution Implementation Plan

Version: v1.0
Date: 2026-08-04
Status: Slice A blocked on redistribution provenance/legal review; implementation not started
Initial vertical slice: `dbcan-cazyme`

## Goal

Give a new GitHub/PyPI user a supported path from an installed SeqEvi CLI to a
real annotation without asking them to assemble Python, DIAMOND, Java, PATH,
database files and TOML by hand.

The initial gold path is:

```bash
pipx install seqevi

seqevi setup dbcan-cazyme --yes

seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

The scientific evidence cache remains independent of Docker, download tools,
biofetch and any workflow scheduler. Managed onboarding is a product-edge
layer around the existing explicit adapter, profile, Store and result
contracts.

The target boundary is defined in the proposed
[managed distribution architecture](../architecture/20260804-v1.0-managed-adapter-distribution-architecture.md)
and
[profile v2 contract](../architecture/20260804-v2.0-execution-profile-contract.md).
Neither document describes currently available CLI behavior.

## Preconditions And Dependency Order

This plan starts after:

1. the
   [queryable result contract](20260804-v1.0-result-consumption-implementation-plan.md)
   is accepted; and
2. the
   [local dbCAN scientific adapter](20260804-v1.0-dbcan-cazyme-adapter-implementation-plan.md)
   passes direct runtime parity.

Public image work also requires a completed redistribution/license review for
dbCAN, DIAMOND and every bundled runtime dependency. These are hard entry gates,
not tasks to discover after implementing setup apply.

The technical review is recorded in the
[dbCAN redistribution and license review](../architecture/20260805-v1.0-dbcan-redistribution-license-review.md).
It found that the software component licenses are discoverable, but database
redistribution terms, DIAMOND notice/source materials and dbCAN wheel
provenance still require maintainer/legal sign-off. Therefore the gate remains
open and no profile-v2 or setup implementation is activated by this update.

The local profile and explicit CLI path are the scientific oracle. Managed OCI
execution must produce the same `EvidenceKey` and normalized result for the
same runtime/resource contract.

## Product Boundary Change

The current execution-profile contract says SeqEvi does not install or download
external runtimes and resources. This plan deliberately changes the user-facing
boundary, so implementation cannot begin by silently editing profile code.

This plan alone does not supersede the repository's current `AGENTS.md` product
boundary. Slice A must update that operational map together with the approved
versioned architecture. Until both changes are accepted, the controller and
workers must continue treating runtime/resource installation and distribution
as out of scope.

Before code, accept:

- the proposed versioned managed adapter distribution architecture;
- the proposed v2 execution-profile contract for OCI runtimes;
- a compatibility note that leaves v1 local profiles unchanged.

The revised boundary is:

- SeqEvi core still knows only adapter contracts, execution profiles, Stores
  and immutable result files;
- a separate first-party distribution module owns `setup`, fixed kit manifests,
  OCI delegation and resource staging;
- SeqEvi has no runtime dependency on biofetch and does not expose a biofetch
  command or data model;
- release automation may use biofetch or other publisher tooling to prepare and
  verify manifest inputs;
- databases remain outside wheels and container images.

## Frozen P0 Scope

P0 supports exactly:

- Linux on `amd64`;
- Docker Engine;
- the `dbcan-cazyme` adapter;
- one digest-pinned SeqEvi-managed dbCAN runtime image;
- the fixed `db_v5-2-9_5-5-2026` resource release;
- local POSIX Store or an explicit HTTP(S) shared Store;
- a bundled tiny protein smoke test.

P0 does not promise Podman, Apptainer, ARM64, offline bundles, eggNOG,
InterPro/Pfam or a mutable remote kit catalog.

## What Managed Installation Means

There are two supported concepts, and they must not be described as the same
installation path:

- current profile v1 users install the official `run_dbcan` launcher, its
  Python dependencies and DIAMOND themselves, then point SeqEvi at that host
  runtime and the four-file resource;
- the proposed managed path pulls a SeqEvi-managed image built from the
  supported official dbCAN release, downloads and verifies the separate
  resource, runs a smoke test, and publishes a profile v2 document.

The proposed setup command does not install Docker, modify operating-system
packages, invoke `sudo`, or place dbCAN and DIAMOND into the host Python
environment. A supported Docker Engine that the caller can access is a P0
precondition. The runtime image is a SeqEvi distribution artifact, not an
upstream-official dbCAN image.

## Runtime And Resource Distribution

### Runtime Image

The SeqEvi-managed dbCAN runtime image contains:

```text
the exact compatible SeqEvi version
dbcan 5.2.9
DIAMOND 2.1.15
Python and locked runtime dependencies
```

It does not contain the dbCAN database. The image is published by immutable OCI
digest, includes SBOM and license/NOTICE artifacts, and is never referenced by
`latest` in a kit manifest.

The image is built from the supported official dbCAN release; it is not an
upstream-official dbCAN image. The public default must be retrievable from a
public digest-addressable registry. An internal Harbor mirror may be configured
by deployment policy but is not embedded in SeqEvi's domain model or public
evidence identity.

An OCI image digest is a distribution and supply-chain identity. It does not
replace `ToolRuntimeDigest`; the latter is still calculated by the adapter from
the actual result-producing components inside the image.

### Resource

The resource stays in a separate versioned directory and is mounted read-only
for annotation. Setup downloads the four files required by the dbCAN adapter,
verifies declared byte sizes and SHA-256 values, generates the SeqEvi resource
lock, and atomically publishes the completed directory.

Large resources are never downloaded during `annotate`. Setup stages downloads
under a recognizable incomplete path and does not publish a profile that points
to that path. Interrupted setup is safe to retry; exact verified content is a
no-op, while conflicting content fails explicitly.

## First-Party Kit Manifest

P0 uses a bundled, strongly validated manifest for the supported vertical
slice. It includes at least:

```text
ManifestSchemaVersion
KitID
Adapter
SupportedPlatform
SeqEviVersion
ImageReference
ImageDigest
ContainerExecutable
RuntimeComponents
ResourceRelease
ResourceFiles
DownloadBytes
ExpandedBytes
Licenses
SmokeFixture
ExpectedSmokeContract
```

Every resource file entry includes canonical destination, URL, byte size and
SHA-256. The manifest also declares container-internal mount paths and the
expected adapter contract, runtime identity and result schema observed by the
smoke test.

There is no mutable remote `latest`, best-effort fallback, arbitrary command
template or third-party plugin manifest in P0. Updating runtime or resource
content creates a new `KitID` and manifest entry.

## CLI Contract

### `seqevi setup`

```bash
seqevi setup dbcan-cazyme
seqevi setup dbcan-cazyme --dry-run
seqevi setup dbcan-cazyme --dry-run --json
seqevi setup dbcan-cazyme --yes
seqevi setup dbcan-cazyme --profile-name dbcan-cazyme-2026 --yes
```

Public CLI uses only `--dry-run`; it does not also expose the near-synonym
`--plan`. Internally the command may create a typed `SetupPlan`.

`--dry-run` is strictly read-only. It may:

- read the bundled kit manifest and local setup state;
- check operating system, architecture, free disk and Docker daemon access;
- determine exact destination paths and whether work is already complete.

It must not:

- pull an image;
- download a resource;
- create directories, locks or profiles;
- run the smoke test;
- mutate Docker or SeqEvi state.

The plan reports runtime and database versions, image digest, expected download
and expanded size, destinations, Store path, profile name, licenses and the
ordered actions that apply would execute.

Without `--yes`, setup requests confirmation after showing the complete plan.
`--yes` makes the same plan non-interactive; it does not weaken validation.
The default profile name equals the adapter name. `--profile-name` provides an
explicit side-by-side upgrade path; setup never rewrites an existing profile
to a newer kit.

### `--json`

`--json` changes presentation only. It does not imply dry-run and does not
authorize changes.

Human mode uses concise progress and a final copyable annotation command. JSON
mode writes one versioned JSON document to stdout on success. Failures write a
structured error document to stderr and return non-zero. No Rich markup,
progress bars or unstructured text may be mixed into JSON output.

The initial setup JSON includes:

```text
schema_version
adapter
kit_id
status
runtime
resource
destinations
actions
smoke
next_command
```

### Idempotency And Publication

Setup follows plan/apply semantics internally:

1. validate platform, Docker access, destination boundaries and disk budget;
2. pull the exact OCI digest;
3. stream resource files into staging with digest verification;
4. build and fully verify `seqevi.lock`;
5. execute the bundled tiny smoke through the managed runtime;
6. compare the observed adapter, runtime, resource and result identities with
   the manifest;
7. atomically publish the resource and v2 profile;
8. print the exact next annotation command.

Repeating the exact setup succeeds without redownloading or rewriting. A
same-name profile with different effective content fails; setup never
overwrites it. A failed smoke leaves no published profile and no result that can
be mistaken for accepted setup. Pulled image layers may remain in Docker's
content cache.

## Execution Profile v2

V1 local profiles remain readable and unchanged. They continue to describe a
host executable:

```toml
version = 1
adapter = "dbcan-cazyme"
executable = "/opt/dbcan/bin/run_dbcan"
resource = "/data/dbcan/raw"
```

Managed setup writes a complete v2 profile:

```toml
version = 2
adapter = "dbcan-cazyme"
resource = "/home/user/.local/share/seqevi/resources/dbcan-cazyme/db_v5-2-9_5-5-2026"
store = "/home/user/.local/share/seqevi/store"
threads = 8

[runtime]
kind = "oci"
kit_id = "dbcan-cazyme-5.2.9-db-2026.05.05"
engine = "docker"
image = "<public-registry>/seqevi-dbcan@sha256:<digest>"
```

V2 is not automatically rewritten to a later kit. Profile selection remains
explicit; there is no mutable current profile or hidden project discovery.
`profile validate` remains static and does not pull an image or launch Docker.

## OCI Delegation Boundary

An OCI profile delegates the complete annotation invocation at the CLI or
application boundary to the compatible SeqEvi inside the adapter image. The
host does not pretend a container is a local executable and does not add Docker
branches to every adapter runner.

The delegated command uses the same adapter implementation and Store/result
contracts as local execution. A generated ephemeral inner profile identifies
the container executable, mounted resource, Store and operational values. The
host validates that the image's SeqEvi version and observed adapter contract
match the kit manifest before accepting the result.

Mount and process rules are fixed:

- FASTA and resource mounts are read-only;
- output, temporary work and a local Store mount are narrowly writable;
- run with the caller's UID/GID so outputs are not root-owned;
- do not mount Docker socket, the user's home directory or the whole working
  directory;
- use `--network none` for a local Store;
- enable network only for an explicit shared HTTP(S) Store;
- pass shared Store credentials through a redacted environment boundary, not
  image labels, profile literals, argv or logs;
- use a unique container name;
- on success, failure, timeout and cancellation, inspect and remove the exact
  container rather than relying only on `--rm`.

All Docker invocations use argument arrays and `shell=False`.

## Module Boundary

The initial implementation is intentionally small:

```text
src/seqevi/distribution/
  manifest.py   # typed first-party kit manifest
  setup.py      # read-only planning, apply, staging and publication
  oci.py        # Docker command, mounts, delegation and cleanup
```

CLI binding stays in `src/seqevi/cli.py`. V2 profile parsing stays in the
profile module. Adapter science remains in `src/seqevi/adapters/`.

Do not create a general package-manager abstraction, downloader plugin,
container-engine interface hierarchy or arbitrary kit SDK during the dbCAN
vertical slice. Extract a shared boundary only after a second managed adapter
demonstrates the same need.

## Execution Slices

### Slice A: Architecture Activation And Profile v2 Contract — blocked

Predecessors:

- accepted result and local dbCAN contracts;
- accepted direct parity against the supported official dbCAN 5.2.9 runtime;
- completed redistribution/license review for every public image component.

The proposed managed-distribution and profile-v2 documents are prepared for
review. After the predecessors pass, accept those documents, update the
documentation authority index, and update the repository `AGENTS.md`
product-boundary map in the same change that begins implementation. Do not
change the operational boundary earlier, because that would make an
unimplemented setup path appear authoritative.

The activated contracts freeze:

- setup command behavior;
- dry-run and JSON schemas;
- idempotency and conflict policy;
- staging, publication and recovery semantics;
- OCI delegation and mount/security policy;
- v1 profile compatibility;
- image/resource/runtime identity separation.

Acceptance gate: the two architecture documents no longer carry proposed
status, the repository guidance describes the same boundary, and no
implementation decision about writes, overwrite behavior, network, secrets or
version selection remains implicit.

### Slice B: Kit Manifest And Read-Only Setup Plan

Predecessor: Slice A merged.

Implement strict manifest parsing and `seqevi setup dbcan-cazyme --dry-run` in
human and JSON modes. Use fixture manifests/resources in normal CI.

Focused acceptance:

- unknown fields, unsupported platforms, non-digest images, path traversal,
  duplicate resources and invalid sizes/digests fail;
- dry-run performs zero filesystem and Docker mutation;
- repeated planning is deterministic for equal local state;
- human and JSON views represent the same typed plan;
- secrets and credential-bearing Store URLs are redacted.

### Slice C: Atomic Setup Apply

Predecessor: Slice B passes.

Implement digest-pinned image pull, streamed resource staging, full verification,
resource lock generation, smoke execution and atomic profile publication.

Inject failures after every state transition. Acceptance requires that no
failure publishes a usable-looking partial profile/resource and that exact
rerun safely resumes or no-ops according to the recorded state.

### Slice D: OCI Annotation Delegation

Predecessor: Slice C passes its fixture smoke.

Load profile v2 and delegate a real `annotate` invocation through the managed
image. Verify mount boundaries, UID/GID ownership, network policy, timeout and
cancellation cleanup, typed error translation and single-file DuckDB recovery.

Acceptance requires local-v1 versus managed-v2 equality for:

- adapter contract;
- `ToolRuntimeDigest`;
- `ResourceID`;
- semantic parameters;
- hit/no-hit classification;
- normalized values and public DuckDB schema.

### Slice E: Public Release Gate

Predecessor: Slice D passes.

In a clean supported Linux/amd64 environment:

1. install from the built wheel without cloning the repository;
2. run setup from only the root README instructions;
3. run the first real annotation without editing TOML or PATH;
4. rerun and prove an exact cache hit;
5. inspect the image digest, resource lock, runtime digest, profile and DuckDB
   provenance;
6. test paths containing spaces and Unicode;
7. test actionable failures for Docker unavailable, insufficient disk,
   unsupported architecture and resource corruption.

Run `pdm run check` and validate the published wheel, image, SBOM, manifest and
documentation together. A release canary repeats setup, cold annotation and
cached annotation on a schedule outside normal pull-request CI.

### Slice F: Generalization Only After dbCAN

Predecessor: public dbCAN release gate accepted.

Add managed eggNOG and InterPro/Pfam kits as independent vertical slices. Only
after at least two kits pass real setup and annotation should the implementation
extract common manifest/setup helpers or add reusable commands such as:

```bash
seqevi profile check NAME
seqevi profile test NAME
```

`check` is a quick runtime/resource/Store preflight. `test` launches a tiny
real annotation. Neither is required to prove the dbCAN setup MVP because setup
already performs its own mandatory smoke.

## Validation Matrix

| Layer | Normal PR | Release gate |
| --- | --- | --- |
| manifest and plan | fixture unit/property tests | inspect published manifest |
| OCI command and cleanup | tiny fixture image | digest-pinned public image |
| resource staging | tiny fixture files and fault injection | real dbCAN resource |
| annotation | fixture adapter/runtime | real dbCAN 5.2.9 cold and cached runs |
| Store | local fixture plus shared contract tests | local and shared PostgreSQL smoke |
| result | DuckDB contract fixtures | final public DuckDB inspection |
| packaging | wheel tests | fresh `pipx install` |

## Acceptance Criteria

1. A new supported-platform user reaches a real dbCAN annotation in three
   commands without editing TOML or configuring DIAMOND/PATH.
2. Setup is reviewable before execution, non-interactive when explicitly
   requested, idempotent and atomically published.
3. JSON output is stable and contains no mixed terminal prose.
4. Images and resources are immutable, checksum-verified and auditable.
5. Managed and local execution produce the same scientific identity and result.
6. Container mounts, network, credentials and cleanup satisfy the fixed
   boundary above.
7. Existing v1 local profiles and explicit mode continue to work unchanged.
8. SeqEvi core remains independent of biofetch and generic deployment systems.

## Non-Goals

- `setup all` or a three-adapter all-in-one image.
- Databases embedded in wheels or OCI images.
- Mutable `latest` tags, automatic upgrades or silent profile rewrites.
- A remote plugin marketplace or arbitrary third-party kit execution.
- Podman, Apptainer, Kubernetes, Slurm, WDL or Cromwell management in P0.
- Docker socket, broad home-directory or broad working-directory mounts.
- Secret storage inside SeqEvi.
- A generic package manager or downloader framework.
- Cross-adapter result merging.

## Intended Review Split

1. dbCAN parity and redistribution/license gate, then managed-distribution
   architecture/profile-v2 activation plus the repository boundary update.
2. Typed kit manifest plus read-only setup planning.
3. Atomic dbCAN setup apply and fixture smoke.
4. OCI delegation, security/lifecycle tests and real dbCAN acceptance.
5. Release packaging, public documentation and scheduled canary.

Managed eggNOG and InterPro/Pfam kits remain later independent pull requests.
