## Decision And Scope

managed dbCAN target-Store lane before InterPro. This dated plan supersedes
only that active next-lane ordering and the master plan's generic dbCAN gate.
It does not rewrite accepted eggNOG evidence, close global cache seeding, or
change any architecture, adapter, Store, evidence-identity, result-schema, or
managed-distribution contract. InterPro resumes only after dbCAN closeout.

The execution target is one managed dbCAN process with `64` adapter threads
for both the fixed 50-record target gate and the 2,729-record sizing run. There
is no `8/32/64` sweep. Real file concurrency starts and remains at one unless
the optional post-sizing two-file gate below is explicitly selected and its
measured headroom gate passes.

## Concurrency Vocabulary

These are independent axes and must not be reported as one undifferentiated
"concurrency" value:

- **per-adapter threads** are the `--threads` value passed to one dbCAN
  invocation. dbCAN passes the same value into DIAMOND and PyHMMER, but its
  three selected analyses execute sequentially;
- **simultaneous SeqEvi or file processes** are independent caller processes,
  each with its own project root, DuckDB result, managed container and thread
  allocation; and
- **ClaimSession same-key coordination** is Store-side coordination between
  callers requesting the same EvidenceKeys. A same-key gate may declare `64`
  threads for both callers while accepting only one external OCI computation:
  the claim winner launches dbCAN, and the waiter reuses the winner's committed
  evidence.

Consequently, `two callers at 64 threads` is not permission for two dbCAN
containers to compute the same key set. It is a coordination declaration whose
acceptance requires proof that exactly the winner launched external OCI work.

## Runtime Research And Sizing Rationale

The exact dbCAN 5.2.9 wheel is SHA-256
`daf39033e9921d116f46a374714f6095b71394eb6438035f1754354d7e20d8d2`.
PyPI attests tag `v5.2.9` to source commit
`36737a9b990645661be20a50edaadab481a95b17`; see the [dbCAN 5.2.9
release](https://pypi.org/project/dbcan/5.2.9/) and the exact
[`run_dbCAN_CAZyme_annotation`
source](https://github.com/bcb-unl/run_dbcan/blob/36737a9b990645661be20a50edaadab481a95b17/dbcan/core.py#L108-L165).
That released source invokes DIAMOND, dbCAN-HMM and dbCAN-sub-HMM in order,
then builds the overview. The command creates all three configurations from
one `threads` option; DIAMOND and both PyHMMER configurations therefore receive
the same value. It does not execute the three methods concurrently.

[PyHMMER's performance guide](https://pyhmmer.readthedocs.io/en/stable/guide/performance.html)
explains that target sequences are prefetched and shared across workers while
queries are distributed, but also that useful scaling depends on query and
target workload. It supports a measured gate, not an assumption of linear
64-thread scaling.

Existing [dbCAN runtime evidence](../benchmarks/20260804-v1.0-dbcan-runtime-validation.md)
proves scientific output equality at one and four threads and reports an
estimated 24.5 GB dbCAN-sub model footprint. It does not size 32 or 64 threads.
The [eggNOG full-proteome benchmark](../benchmarks/20260723-v1.0-eggnog-full-proteome-tuning.md)
found only about 12% improvement from 32 to 64 threads. That is comparison
evidence for avoiding an automatic thread sweep, not proof of dbCAN behavior.

The dated 2026-08-19 host snapshot reports 192 logical CPUs, 503 GiB RAM and
approximately 431 GiB available. It is planning evidence only. D1 must refresh
logical/physical CPU topology, total and available memory, scratch and result
filesystems, Ceph capacity/I/O state, Docker storage, Store/CAS capacity and
other active workload immediately before execution.

## Safety And Evidence Contract

Every mutating gate preserves:

- the exact released package, kit, image digest, profile, ResourceID,
  ToolRuntimeDigest, adapter contract, result schema and canonical semantic
  parameters;
- read-only FASTA and resource mounts, caller numeric UID/GID, no Docker socket
  mount, and no resource content, mode, owner, size or mtime change;
- one isolated project root, DuckDB output, JSON output, stderr/stdout capture
  and container name per caller;
- exact command argument arrays, start/end times, exit codes, configured
  internal OCI timeout, wall time, CPU, peak RSS, peak scratch and Ceph I/O;
- Store health and before/after sequence, evidence, artifact and coordination
  counts; PostgreSQL bytes; CAS inventory, bytes, digest reconciliation and
  temporary-residue scan;
- computed, cache-hit, hit and no-hit counts plus DuckDB metadata, native table
  schemas, row/input-map counts, semantic parameters and focused content
  checks; and
- independent later-process replay with zero external computation, followed by
  zero residual `seqevi-*` containers and cleanup evidence.

Write the supported setup and annotation result to JSON rather than parsing
Rich output. A concrete command skeleton is:

```bash
uvx --from seqevi==0.3.1 seqevi setup dbcan-cazyme \
  --resource /cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/dbcan/database/db_v5-2-9_5-5-2026/raw \
  --dry-run --json > setup-dry-run.json

uvx --from seqevi==0.3.1 seqevi setup dbcan-cazyme \
  --resource /cephfs_data/genostack_v3/genostack_php/public_file_data/database/bioinfo/resources/dbcan/database/db_v5-2-9_5-5-2026/raw \
  --yes --json > setup-apply.json

uvx --from seqevi==0.3.1 seqevi annotate \
  --profile dbcan-cazyme \
  --store http://192.168.30.205:18082 \
  --fasta <frozen-input> \
  --output <isolated-result.duckdb> \
  --threads 64 \
  --timeout-seconds <finite-preflight-value> \
  --json > <isolated-result.json>
```

The evidence wrapper records the arrays before launch and monitors resources;
it must not inject a hidden image, override the kit, use `shell=True`, or write
inside the Store artifact root.

For managed dbCAN, Docker is the OS-owned runtime boundary. Every annotation
has a finite SeqEvi OCI timeout. On success, failure, cancellation or timeout,
cleanup targets only the exact generated container name with `docker rm
--force`, waits for that removal to become authoritative, and verifies zero
residual `seqevi-*` containers. Generic systemd scopes and host process-group
hardening are not prerequisites for dbCAN because no adapter process is
launched outside that container boundary.

Store mutation is forward-only. Never delete valid evidence or CAS artifacts
to manufacture cold work or make a retry look clean.

## Key-State Branches

D1 inventories the 50-record and 2,729-record EvidenceKeys under the exact
frozen identity before D3. The fixed 50 may overlap the 2,729 input, so D3 must
take one of these honest branches:

- **all missing:** run the full 50-record managed target computation, then an
  independent later-process zero-compute replay;
- **partial:** compute only the missing keys through ordinary `annotate`,
  preserve the existing-key hits, and accept the exact computed/cache split;
  do not label this cold; or
- **all present:** accept only an independent later-process zero-compute replay
  and exact zero Store/CAS growth; do not launch dbCAN merely to repeat parity.

Apply the same inventory rule before D4 and every expansion input. Capacity
projections use actual missing-key counts. All-present branches reserve only
bounded result/scratch needs and require exact zero Store/CAS growth; missing
branches use measured growth and final-reserve headroom.

### D3: Fixed 50-Record Managed Target Gate

**Predecessor:** D2 accepted; fresh health, key-state and capacity readback.

Run one managed caller at 64 threads using the branch established in D1. For an
all-missing or partial input, only ordinary ClaimSession behavior determines
which keys compute. For an all-present input, run replay only. Follow with an
independent later process using a separate output and JSON file.

**Acceptance:** both outputs are complete, schema-correct and scientifically
consistent with the accepted native contract; the first run's computed/cache
split equals the refreshed missing/present inventory; replay reports 50 cache
hits and zero computed; Store growth equals the missing-key union; all
artifacts reconcile; mounts and UID/GID are correct; resource state is
unchanged; cleanup leaves zero containers. This is target execution and replay,
not repeated direct-versus-managed parity.

### D4: 2,729-Record One-Process Sizing

**Predecessor:** D3 accepted; refreshed live path/digest/key inventory and
capacity gate.

Run exactly one managed dbCAN process at 64 threads, followed by an independent
later-process replay. Do not run an 8/32/64 sweep. Measure phase-aware CPU,
peak RSS, scratch, Ceph read/write I/O, Store/CAS growth, DuckDB size and wall
time. Record enough timeline evidence to distinguish DIAMOND, dbCAN-HMM and
dbCAN-sub-HMM phases where logs permit without modifying the runtime.

**Acceptance:** computed/cache counts equal the pre-run inventory; native
DuckDB/JSON checks pass; replay is 2,729 cache hits and zero computation;
Store/CAS deltas and artifacts reconcile; no resource or container residue
remains. The measurement supplies the dbCAN-specific rates and two-process
headroom decision. Neither the 24.5 GB estimate nor eggNOG scaling substitutes
for this measurement.

### D5: Small Same-Key Managed Bridge

**Predecessor:** D4 accepted and a small key set is authoritatively reserved as
missing without deleting Store data. If no suitable naturally missing set
exists, record D5 as unavailable and do not manufacture one.

Replace a full per-adapter C1/C2 rerun with one small, bounded same-key managed
bridge. Launch two independent SeqEvi callers against the same reserved input,
each declaring 64 threads and its own project/output. Capture ClaimSession and
container timelines.

**Acceptance:** both callers complete; the claim winner alone launches the
external OCI dbCAN computation; the waiter launches no annotation container,
waits through ClaimSession and reuses the committed evidence; Store evidence
growth equals the missing-key union once; outputs/payloads agree; independent
replay is zero-compute; CAS and cleanup reconcile. If both callers launch
external dbCAN computation, this gate fails even if final Store rows deduplicate.

### Selected Expansion

**Predecessor:** D4 accepted; D5 accepted or explicitly unavailable for lack of
a naturally missing small set; exact selected manifest and missing-key
inventory frozen.

Start at file concurrency one. For each file, repeat fresh identity, health,
capacity and key-state checks; run one 64-thread managed process; validate
DuckDB/JSON and Store/CAS; then run an independent zero-compute replay.
Selection and progression are reviewed from measured record counts and D4
rates, never from an unrecorded directory glob.

A two-file expansion after sizing is optional:

- start with two simultaneous files at 32 threads each; and
- permit two at 64 threads only after measured combined CPU, peak RSS, scratch,
  Ceph I/O, Store/CAS health and complete two-process headroom all pass with the
  D1-frozen final reserves intact.

The optional gate proves different-file process concurrency only. It neither
replaces D5 same-key coordination nor changes the default file concurrency of
one. Failure or weak headroom returns execution to one file without deleting
accepted Store state.

## Stop, Cleanup And Recovery

Stop and preserve evidence on any package, image, kit, ResourceID,
ToolRuntimeDigest, semantic-parameter, input or schema drift; timeout; Store
health/commit error; unexplained row or byte delta; failed artifact
reconciliation; output defect; resource write; insufficient headroom; or
residual container. On timeout or cancellation, force-remove only the exact
owned container, verify its absence and then scan the bounded `seqevi-*`
namespace. An uncertain external write is read back and deduplicated before
any retry.

Retry only after authoritative Store, CAS, output and container readback shows
the intended state. Preserve valid partial progress and use the partial or
all-present branch on the next reviewed attempt. There is no destructive
rollback of immutable Store data.
