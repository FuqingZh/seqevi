# Annotate Runtime And Bounded-Memory Plan

> Status: implemented and validated
> Date: 2026-07-22

## Implementation Status

- Phase 6.1 resource locking and full verification: complete.
- Phase 6.2 path-independent runtime identity: complete.
- Phase 6.3 atomic FASTA staging and bounded Store/tool batches: complete.
- Phase 6.4 file-backed artifacts, batch fetch and lazy package materialization:
  complete.
- Phase 6.5 threads, minimal runtime, fixture performance, and staged real
  eggNOG validation: complete. The measured 100-record cost established the
  stop boundary for larger matrix variants.
- Phase 6.6 disk-backed large-FASTA indexes: not required by current 100k
  measurements.

## Objective

Harden `seqevi annotate` for reproducible resource identity, bounded-memory
materialization and practical external-tool performance without changing its
scientific result contract.

The target data flow is:

```text
seqevi.lock
  -> exact runtime identity
  -> streaming FASTA validation and staging
  -> bounded Store operations
  -> external tool files
  -> file-backed content-addressed artifacts
  -> Polars lazy scan and streaming sink
  -> Data Package
```

The goal is not an all-`LazyFrame` workflow. Polars lazy operations belong at
file-backed tabular boundaries. FASTA parsing, Store transactions and RPC, and
external process execution retain streaming, batched or process-native
abstractions.

## Initial Smoke Findings

The initial eggNOG-mapper 2.1.13 validation established direct/SeqEvi parity and
exposed the work addressed by this plan:

- adapter construction rehashes about 50 GB of eggNOG files per invocation;
- `ToolRuntimeDigest` does not yet cover the complete result-producing mapper
  package and DIAMOND binary;
- the 10-sequence smoke contained only hits and did not exercise real-tool
  no-hit caching;
- the cloned 289-package environment is a validation baseline, not a minimal
  production runtime;
- a small miss batch still pays the fixed DIAMOND database startup cost;
- external annotation reached about 4.6 GB peak RSS before SeqEvi's eager
  artifact and DataFrame materialization is considered;
- `--cpu 1` limits external-tool performance, but thread tuning must follow the
  streaming and lazy-dataflow work so it does not mask SeqEvi overhead.

Real-runtime validation already corrected database-aware version probing,
runtime `PATH` isolation and eggNOG-mapper v2 CLI flags. Those fixes remain part
of the frozen baseline.

## Compatibility Rules

- `seqevi.lock` is owned and interpreted only by SeqEvi. Biofetch, database
  publication tools and third-party annotation software have no SeqEvi-specific
  responsibility or dependency.
- The public `annotate` CLI, Data Package filenames, schemas and scientific
  parameters remain unchanged until the later additive operational `--threads`
  option.
- A resource lock caches the same component hashes and aggregate ResourceID
  algorithm used today, preserving existing eggNOG resource identity.
- Strengthening runtime identity intentionally creates a new
  `ToolRuntimeDigest`; evidence under the previous incomplete digest remains in
  the Store but is not silently reused.
- Scientific equality is defined by schema, values, hit/no-hit classification
  and canonical `payload_digest`, not Parquet physical bytes.
- Compression, row groups, writer metadata and Parquet file SHA may change
  without an adapter contract change when scientific content is identical.
- The shared HTTP API evolves additively; existing v1 endpoints remain valid.

## Atomic FASTA Contract

Streaming preserves whole-invocation input validation. SeqEvi does not access
the Store until every FASTA record is valid.

1. Stream source records through canonicalization and validation into temporary
   staging. During this pass calculate the input digest, preserve order, collect
   all errors and maintain compact duplicate `InputID` and `SequenceID` state.
2. Only after validation succeeds, read staging records in bounded batches for
   Store lookup, annotation and commit.

Invalid input produces zero Store lookup or commit. After input validation,
completed immutable evidence batches may remain committed if a later tool batch
fails; reruns reuse them. The invocation Data Package remains atomically all or
nothing.

For normal project sizes, duplicate and order state remains in `set`/`dict`
structures. Disk-backed indexes are measurement-driven rather than assumed.

## Phase 6.1: Resource Lock And Full Verification

### SeqEvi Lock

Each exact database root may contain a machine-generated `seqevi.lock` beside
the native files:

```text
expanded/
├── eggnog.db
├── eggnog.taxa.db
├── eggnog.taxa.db.traverse.pkl
├── eggnog_proteins.dmnd
└── seqevi.lock
```

The TOML lock records:

- lock schema version;
- resource name and version;
- named components with canonical relative paths;
- file sizes and SHA-256 values.

It contains no absolute path, executable identity, thread count or project
input. The lock file itself does not enter ResourceID. The lock inventories the
resource; each adapter contract selects its result-affecting components in a
fixed order when calculating ResourceID.

Resolution behavior:

1. With a valid lock, validate schema, path boundaries, required components,
   file existence and sizes, then derive ResourceID without reading large file
   contents.
2. Without a lock, hash required files once. Atomically create `seqevi.lock`
   when the database root is writable.
3. Without a lock in a read-only directory, calculate ResourceID for the current
   run but do not cache it; a later run repeats the hash.
4. A malformed lock, missing component, wrong size or concurrent conflicting
   lock fails loudly. SeqEvi never silently overwrites a conflicting lock.

V1 deliberately does not implement XDG resource caching, inode/mtime/ctime
fingerprint caching or cross-path cache reuse. Those form a possible later
second layer if public read-only database usage demonstrates the need.

The operational contract assumes a locked database snapshot is immutable.
Internal deployments initialize it with SeqEvi and then expose it read-only;
database acquisition remains outside SeqEvi.

### Full Verification Command

Add a SeqEvi-owned command:

```bash
seqevi resource verify \
  --adapter eggnog \
  --executable /path/to/emapper.py \
  --database /path/to/expanded
```

- without a lock, it fully hashes and creates one when writable;
- with a lock, it ignores cached hashes and compares every declared component;
- mismatch reports the exact component and exits non-zero;
- it does not refresh a conflicting lock automatically.

This command supports initialization, migration checks, release acceptance,
suspected corruption and scheduled audits. Database updates use a new versioned
directory rather than mutating an existing locked snapshot.

### Acceptance

- locked and freshly hashed resources produce the existing ResourceID;
- a valid lock causes zero content reads from large database files;
- mutating a locked component causes explicit verification to fail;
- publishing changed content in a new versioned resource root produces a new
  ResourceID;
- first-use lock creation is atomic under concurrency;
- read-only databases without a lock remain correct, though slower;
- Biofetch and third-party database schemas remain untouched.

## Phase 6.2: Runtime Identity

The eggNOG runtime identity covers:

- the launcher;
- installed eggNOG-mapper package code or an authoritative runtime lock;
- the selected DIAMOND executable;
- normalized mapper and DIAMOND versions.

A container image digest is preferred for an immutable container runtime. A
local Conda/Micromamba runtime hashes the relevant package and binary rather
than an unrelated complete environment. InterProScan declares its own launcher,
JAR and native execution components through the same shared identity boundary.

Acceptance:

- mapper package or DIAMOND content changes ToolRuntimeDigest;
- operational paths do not enter the digest;
- identical runtime content at another path produces the same digest;
- the intentional transition from the old digest is documented and tested.

## Phase 6.3: Low-Risk Streaming And Batching

- calculate FASTA and output-file SHA-256 incrementally instead of using
  `Path.read_bytes()`;
- write cache-miss FASTA records directly to the destination stream;
- bound Store lookup and commit operations by an internal batch size;
- deduplicate artifact digests before fetching or parsing artifacts;
- stream `sequence-map.tsv` rows in invocation order;
- retain file paths at orchestration boundaries when complete bytes are not
  required;
- add measurement hooks for peak RSS, request count, artifact reads and phase
  wall time.

This phase retained the previous artifact model and external-tool thread count
while removing straightforward whole-file materialization. Phase 6.4 then
replaced the artifact ownership boundary.

## Phase 6.4: File-Backed Artifacts And Lazy Parquet

Replace complete artifact byte ownership with a file/reference/stream contract
that includes path or stream access, media type, expected size, expected digest
and explicit lifetime ownership.

- adapters retain native output as files and write normalized Parquet files;
- Stores hash and copy/upload an artifact from one stable open source, avoiding
  hash-then-change time-of-check/time-of-use races;
- add `fetch_many` and fetch each unique artifact digest once;
- package materialization uses `pl.scan_parquet(...)`, lazy transformations and
  a streaming Parquet sink instead of eager `BytesIO` reads and concatenation;
- write requested SequenceIDs to temporary Parquet and use a lazy semi join,
  avoiding a large Python `is_in` list;
- use `scan_csv` only where the upstream TSV can be represented and validated
  faithfully; otherwise parse bounded rows into Parquet staging files;
- stream sequence-map and no-hit output while preserving schema checks.

LazyFrame is not used for FASTA validation, Store RPC/transactions or external
tool execution. Collection is limited to explicit small metadata boundaries.

Scientific compatibility tests compare schemas, values, null semantics,
hit/no-hit sets and canonical payload digests. They do not require equal
Parquet bytes, compression or file SHA. Artifact digests continue to verify the
integrity of each stored file. Duplicate concurrent computation may leave an
unreferenced content-addressed artifact; auditing that condition is separate
from scientific evidence conflict and automatic garbage collection remains out
of v1 scope.

The implemented shared API adds `POST /v1/evidence/fetch-many` while retaining
the original single-record fetch endpoint. Clients chunk metadata requests by
the configured batch size and download each unique artifact digest once.

## Phase 6.5: Threads And Real-Tool Performance

After streaming and lazy materialization are stable, add `--threads` as a
positive operational option and pass it to supported external tools. Preserve
the current default until parity is demonstrated. Threads never enter
EvidenceKey.

Build a minimal eggNOG runtime containing only eggNOG-mapper, DIAMOND, Python
and required dependencies. Keep the cloned 289-package environment as a frozen
historical baseline.

Use staged measurements instead of a full Cartesian product:

1. Fixture runs at 10,000 and 100,000 sequences measure SeqEvi itself.
2. Real eggNOG runs begin with 10, 100 and 1,000 sequences at 1 and 8 threads.
3. Inputs include true hit, true no-hit, mixed and A/B/C partial-overlap reuse.
4. Add 4-thread, 10,000-sequence, node-local storage or other variants only when
   initial evidence identifies a useful performance boundary.

Execution stopped after the 10-record 1/8-thread parity comparison and the
100-record 8-thread partial-reuse run. The latter required 93.6 minutes for 85
new unique sequences, so a 100-record 1-thread run and 1,000-record variants
would consume hours without changing a remaining contract decision. This is a
measurement-driven staged stop, not an unverified success claim. The completed
runs cover thread parity, exact cache reuse, partial overlap, true hits and true
no-hits; their evidence is recorded in the versioned benchmark report.

Record external-tool time separately from resource initialization, Store work
and package materialization. Record peak RSS, CPU, database bytes read, Store
requests and unique artifact opens. Do not flush shared host page caches merely
to manufacture a cold-cache benchmark.

Node-local database staging, short-window batch aggregation and a compute claim
protocol remain deferred until measured startup or duplicate computation cost
justifies their complexity.

## Phase 6.6: Optional Large-FASTA Indexes

Move global identity, duplicate and order indexes to SQLite or temporary
Parquet only if Phase 6.3 through 6.5 measurements show that compact FASTA
metadata is the remaining material memory limit. This phase is not a v1 release
prerequisite.

## Test Strategy

- lock schema, path traversal, duplicates, missing files, wrong sizes,
  concurrency and read-only behavior;
- locked versus freshly calculated ResourceID equality;
- full verification success and precise mismatch diagnostics;
- runtime digest sensitivity to mapper package and DIAMOND changes;
- invalid FASTA at the first, middle and last record causes zero Store access;
- completed batch reuse after a later valid-tool failure;
- exact duplicate identity handling and input order;
- local/shared Data Package semantic parity;
- scientific equality across eager and lazy writers without physical-byte
  equality requirements;
- true external-tool hit/no-hit and thread-count payload parity;
- batch requests scale with batches and unique artifact digests;
- failure injection cannot expose partial evidence or truncated artifacts;
- existing shared HTTP endpoints remain valid.

## Execution Strategy

Implement in separate semantic batches:

1. Freeze semantic compatibility, lock and benchmark test harnesses.
2. Implement `seqevi.lock` and `seqevi resource verify`.
3. Strengthen runtime identity and document the digest transition.
4. Apply low-risk streaming, hashing and Store batching; remeasure.
5. Introduce file-backed artifacts and additive `fetch_many` boundaries.
6. Switch package output and suitable adapters to lazy scan/join/sink.
7. Add `--threads`, the minimal runtime and staged real-tool benchmarks.
8. Decide whether disk-backed FASTA indexes are justified.
9. Run clean-install, PostgreSQL, local/shared and official-tool release gates.

Every batch runs targeted tests, the full fast suite, Ruff, type checking and
`git diff --check`. External-tool and performance batches retain commands,
inputs, runtime/resource identities, wall time and peak RSS in versioned
benchmark documents.

## Non-Goals

- converting every operation to LazyFrame;
- adding the deferred local resource-fingerprint cache in v1;
- introducing a workflow engine, queue, new storage backend or scheduler before
  measurements justify it;
- merging adapter schemas or changing scientific annotations;
- bundling or redistributing third-party databases;
- integrating SeqEvi into Proteomics during this standalone exploration.
