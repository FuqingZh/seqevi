# Queryable Annotation Result And Python API Implementation Plan

Version: v1.0
Date: 2026-08-04
Status: Slice E accepted for the v1.0 runtime gate
Target release: SeqEvi 0.2.0

## Goal

Make one annotation invocation produce one self-describing, immutable DuckDB
file that is straightforward to consume from Python, SQL, R, notebooks, and
external workflow engines.

The common Python path becomes:

```python
import seqevi

annotations = seqevi.annotate(
    "proteins.faa",
    profile="interpro-pfam",
    output="interpro.duckdb",
)

print(annotations.columns)

pfam = annotations.select(
    "InputID",
    "SignatureAccession",
    "SignatureDescription",
)
```

Opening an existing result uses the same native return type:

```python
annotations = seqevi.scan_annotations("interpro.duckdb")
```

Both functions return `duckdb.DuckDBPyRelation` for the public
`main.annotations` view. SeqEvi does not add a result wrapper or a parallel
column-constant API.

## Why This Changes The Current Output

The existing Data Package v2 output is technically valid. It was selected to
avoid inventing a manifest for `evidence.parquet`, `sequence-map.tsv`,
`no-hits.parquet`, their schemas and provenance. The implementation generates
and validates the descriptor with `dplib-py`.

The missing contract is consumption. A caller still has to know the four file
names, parse two formats, understand `InputID` versus `SequenceID`, perform the
common join, and account for adapter-specific row grain. No production caller
in this repository consumes the package through the Data Package API.

DuckDB now earns its dependency because it removes that complete boundary at
once: one file can carry the tables, views, schemas, provenance, row-grain
metadata and native lazy query interface. This is not a claim that DuckDB
replaces Parquet generally. Adapter artifacts in the Store remain Parquet;
only the invocation delivery format changes.

## Frozen Decisions

1. One successful invocation produces one new `.duckdb` file.
2. An invocation still runs exactly one adapter. eggNOG, InterPro/Pfam and
   dbCAN results are never merged into a universal table.
3. SQLite/POSIX and PostgreSQL/POSIX Stores remain the incremental evidence
   layer. DuckDB is not a Store backend.
4. Every result DuckDB is a complete, immutable snapshot of the current
   invocation. SeqEvi does not append to or update an older result file.
5. `seqevi.annotate(...)` is eager because it launches external tools, commits
   evidence and publishes a file. Querying its returned relation is lazy.
6. `seqevi.annotate(...)` and `seqevi.scan_annotations(...)` return the native
   `duckdb.DuckDBPyRelation`; there is no `AnnotationResult` class.
7. There is no `seqevi.columns` package. The result catalog is the only source
   of column truth.
8. `InputID` is the normal downstream protein join key. `SequenceID` remains
   the content identity used for cache reuse, deduplication and audit.
9. The Data Package directory is removed as the default and as a compatibility
   output mode. SeqEvi is pre-1.0; maintaining two canonical result formats
   would create more risk than a documented 0.2.0 cutover.
10. A DuckDB result never enters `EvidenceKey`. Rewriting a result does not
    alter cached scientific evidence.

## Incremental Annotation Boundary

The existing incremental flow remains authoritative:

```text
FASTA
  -> canonical SequenceID and exact EvidenceKey
  -> Store lookup
  -> run one adapter only for cache misses
  -> commit new immutable evidence
  -> fetch cached plus newly committed evidence
  -> materialize the complete invocation DuckDB
```

For example, after a 2,000-sequence run, an invocation containing 1,000 old
sequences and 500 new sequences computes only the 500 misses. It still writes a
complete DuckDB for all 1,500 requested inputs. Compute is incremental; result
materialization remains proportional to the current result size.

SeqEvi must not copy an earlier DuckDB and mutate it in place. Input removal,
input order, repeated sequence content under different IDs, and changed
runtime/resource identity make that optimization unsafe.

## DuckDB Result Contract

### Public Relations

The `main` schema contains four public relations:

| Relation | Kind | Row grain |
| --- | --- | --- |
| `annotations` | view | one row per input record and evidence row; one null-evidence row for an input with `no_hit` |
| `sequence_map` | table | one row per input FASTA record in input order |
| `evidence` | table | adapter-native normalized hit row grain |
| `no_hits` | view | one row per unique canonical sequence with terminal `no_hit` |

`sequence_map` has these columns in this order:

```text
InputOrder
InputID
InputHeader
SequenceID
MD5
Length
EvidenceStatus
EvidenceSource
```

`evidence` begins with `SequenceID`, followed by the selected adapter's native
normalized fields. It does not contain rows for terminal no-hits.

`annotations` is defined as a left join from `sequence_map` to `evidence` on
`SequenceID`. It presents the eight common columns first and then the adapter
fields. This makes the common input-protein path direct while preserving the
adapter's native row grain.

Consequences are deliberate:

- duplicate `InputID` values remain invalid input;
- two different `InputID` values with identical sequence content each receive
  the cached evidence rows for their shared `SequenceID`;
- a no-hit input remains visible with null adapter fields;
- eggNOG is normally close to one row per protein;
- InterPro/Pfam can expose several domain rows for one protein;
- a protein-level consumer must aggregate a one-to-many adapter before joining
  it to a one-row-per-protein table when that is the desired output grain.

### Internal Self-Description

The `_seqevi` schema contains:

| Table | Required content |
| --- | --- |
| `metadata` | exactly one row with result, adapter, runtime, resource, input and creation identities |
| `semantic_parameters` | one row per canonical semantic parameter with JSON value |
| `table_info` | public relation name, kind, row grain, join key, row count and description |
| `column_info` | public relation, ordinal position, column name, DuckDB type and description |
| `run_metrics` | exactly one row containing the successful invocation metrics currently carried by `AnnotationMetrics` |

`AnnotationMetrics.existing_finalizations` records actual
`CommitOutcome.EXISTING` results observed during ClaimSession finalization.
Compatibility readers default the additive value to zero when an older managed
runtime payload omits it; computed/cache provenance remains unchanged.

`_seqevi.metadata` includes at least:

```text
ResultFormatVersion
ResultSchemaID
SeqEviVersion
Adapter
AdapterContractVersion
UpstreamTool
UpstreamToolVersion
ToolRuntimeDigest
ResourceID
InputDigest
CreatedAt
```

The initial result-format identifier is `seqevi-duckdb/1`. Initial
adapter-facing schema identifiers are:

```text
eggnog-mapper/2
interproscan-pfam/5
dbcan-cazyme/5
```

`ResultSchemaID` describes the upstream-facing normalized schema family.
`AdapterContractVersion` remains SeqEvi's internal cache/parser semantics key.
`ToolRuntimeDigest` and `ResourceID` identify the exact execution and database
content. These identities must not be collapsed into one user-visible version.

The writer also records DuckDB table and column comments wherever the catalog
supports them. `_seqevi.table_info` and `_seqevi.column_info` remain the stable
machine-readable descriptions rather than relying on an IDE's comment support.

### Storage Compatibility And Atomicity

The implementation adds `duckdb>=1.5,<2` and creates files with an explicit
`storage_compatibility_version` of `v1.0.0`; it never selects `latest`.

Materialization uses a sibling temporary file:

1. create a new staged DuckDB with the fixed storage compatibility setting;
2. write tables without loading the complete result into Python memory;
3. create and validate views and internal metadata;
4. verify row accounting, schemas, adapter identity and required relations;
5. checkpoint and close the writer;
6. reopen the staged file read-only and execute contract probes;
7. atomically publish it with `os.replace()`.

An existing output path is rejected. A failure cannot expose a partial result
under the requested path. Temporary result files are removed on handled
failure; the external-tool diagnostic directory retains its current failure
semantics.

## Public Python API

### `seqevi.annotate`

The public signature accepts the same identity modes and override semantics as
the CLI:

```python
def annotate(
    fasta: str | Path,
    *,
    output: str | Path,
    profile: str | None = None,
    config: str | Path | None = None,
    adapter: AdapterName | str | None = None,
    executable: str | Path | None = None,
    resource: str | Path | None = None,
    store: str | Path | None = None,
    threads: int | None = None,
    timeout_seconds: float | None = None,
) -> duckdb.DuckDBPyRelation: ...
```

Profile, exact config and complete explicit identity remain mutually exclusive.
The Python function raises SeqEvi's typed exceptions; it does not translate
them into process exit codes.

### `seqevi.scan_annotations`

```python
def scan_annotations(
    path: str | Path,
) -> duckdb.DuckDBPyRelation: ...
```

The function validates the minimum result-format contract, opens the database
read-only and returns `main.annotations`. It must not write a WAL, upgrade the
storage version or mutate metadata. The returned native relation owns enough
connection lifetime to remain usable after the function returns and supports
its native `close()` operation.

### Native Discovery And Querying

Runtime schema discovery uses DuckDB itself:

```python
annotations.columns
annotations.types
annotations.description

schema = dict(
    zip(
        annotations.columns,
        annotations.types,
        strict=True,
    )
)
```

Documentation uses `.select(...)` rather than `.project(...)` for column
projection, while retaining the complete DuckDB relation API:

```python
annotations.select(...)
annotations.filter(...)
annotations.pl(lazy=True)
annotations.to_arrow_reader(...)
```

Polars interoperability requires Apache Arrow, so the core dependency changes
from `polars` to `polars[pyarrow]`. A Polars caller can inspect the converted
lazy schema with `collect_schema()`. SQL callers use `DESCRIBE annotations`,
the `_seqevi` tables and DuckDB catalog functions.

The design deliberately trades static string autocomplete for an honest,
single runtime schema. SeqEvi does not duplicate adapter schemas in Python
constant modules or ask users to import `v1`, `v2` or `v3` column namespaces.

## CLI Contract

`seqevi annotate` becomes a thin presentation adapter over the same application
path used by `seqevi.annotate(...)`.

The output option accepts a new file path and documents `.duckdb` as the
canonical extension:

```bash
seqevi annotate \
  --profile interpro-pfam \
  --fasta proteins.faa \
  --output interpro.duckdb
```

Add `--json` as an output-format option. It does not change execution. On
success stdout contains one JSON document with `schema_version`, status,
adapter, result schema, counts, output path and selected run metrics. On failure
stderr contains one structured error document and the process exits non-zero.
Default output remains concise human-readable text.

## Affected Components

| Component | Responsibility after the change |
| --- | --- |
| `src/seqevi/api.py` | public application API, profile/config/explicit resolution, adapter and Store lifecycle |
| `src/seqevi/annotate.py` | shallow exact lookup, miss computation, commit and result-input orchestration |
| `src/seqevi/result.py` | DuckDB writer, contract validation and read-only `scan_annotations` |
| `src/seqevi/cli.py` | Typer argument and human/JSON presentation only |
| `src/seqevi/__init__.py` | export `annotate` and `scan_annotations` with `__version__` |
| `src/seqevi/package.py` | removed after DuckDB parity is accepted |
| `pyproject.toml` / `pdm.lock` | add DuckDB and Arrow-backed Polars; remove `dplib-py` |
| architecture and testing docs | replace the Data Package contract with the versioned DuckDB result contract |

The shared Store schema, HTTP API, artifact identity and adapter-native Parquet
artifacts do not change.

## Compatibility Promises

Version support has three independent meanings:

1. reading an existing result DuckDB;
2. reusing evidence already present in a Store;
3. computing new cache misses with an older upstream runtime.

The first is controlled by `ResultFormatVersion` and DuckDB storage
compatibility. The second remains controlled by exact `EvidenceKey`. The third
requires an adapter implementation that still accepts the probed upstream
runtime. Adding a new adapter contract never overwrites older Store evidence,
but it does not silently promise permanent execution support for every old
external environment.

Profiles continue to name adapter families such as `eggnog` and
`interpro-pfam`. SeqEvi probes the external executable and resource, selects a
supported implementation, and records all version axes. Users do not select
internal `eggnog/1` or `interpro-pfam/1` identifiers in the common path.

## Rejected Alternatives

- Keep Data Package as the canonical result and merely add a reader wrapper.
- Maintain both Data Package and DuckDB output modes.
- Replace SQLite/PostgreSQL Store persistence with DuckDB.
- Append new results into an earlier invocation DuckDB.
- Return a SeqEvi `AnnotationResult` wrapper.
- Add `select_inputs()` or `extract_*()` selection objects.
- Add `seqevi.columns` or versioned column namespaces.
- Expose internal adapter contract IDs as normal profile names.
- Merge adapter schemas into one universal annotation table.
