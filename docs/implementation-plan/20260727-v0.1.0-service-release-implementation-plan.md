# SeqEvi 0.1.0 Service Release Implementation Plan

> Status: stable loopback service accepted
> Date: 2026-07-27
> Issue: FUQ-12
> Target: minimal stable packaging and loopback service promotion

## Outcome

Package the existing `seqevi serve` interface as a frozen-lock Python 3.13 OCI
image, define a persistent generic systemd deployment, publish a durable
operator runbook, strengthen release and deployment validation, and promote the
accepted node4 canary to the stable service without changing the SeqEvi domain
or Store contracts.

This is PR1 of the production-readiness work. It keeps the service on node4
loopback and deliberately excludes ingress, TLS, authentication, backups,
Prometheus, Kubernetes and performance optimization.

## Frozen Product Boundary

The implementation will prefer zero changes under `src/`. It will not change:

- sequence or evidence identity;
- the Store API, HTTP transport or client behavior;
- the PostgreSQL or SQLite schema;
- official adapters, execution profiles or external resources;
- annotation runtime installation or scheduling.

The SeqEvi service image will contain the SeqEvi server dependencies only. It
will not contain eggNOG-mapper, InterProScan, their supporting runtimes, or
their databases.

## Release Artifacts

### Python distribution

- Build sdist and wheel with `pdm build`.
- Install the wheel into a clean Python 3.13 environment with the `server`
  extra and exercise the installed `seqevi` command.
- Add `.github/workflows/publish.yml` because the PyPI and TestPyPI trusted
  publishers are bound to that exact workflow filename.
- Grant only the OIDC `id-token: write` permission needed for trusted
  publishing; do not use an API token.
- Permit manual `workflow_dispatch` publishing only through the `testpypi`
  environment and TestPyPI repository.
- Permit production publishing only from a tag exactly equal to
  `v<project-version>`, through the `pypi` environment and PyPI repository.
- Do not create or push a release tag and do not publish a production release
  as part of FUQ-12.

### OCI image

- Add a multi-stage Dockerfile using Python 3.13.
- Install from the committed `pdm.lock` with frozen resolution and produce a
  service runtime containing the built SeqEvi distribution plus the `server`
  extra.
- Run as a non-root user with the existing `seqevi serve` command as the
  entrypoint.
- Add a narrow `.dockerignore` so source-control, caches, tests, benchmarks and
  local artifacts do not enter the build context.
- Build and inspect the image in CI and locally, including an assertion that
  annotation runtimes and databases are absent.

## Persistent Service Contract

Add a generic systemd unit and environment example that:

- runs the immutable image through Docker;
- binds SeqEvi only to `127.0.0.1:18081`;
- reaches host PostgreSQL through a host-loopback topology rather than exposing
  PostgreSQL to the container network;
- supplies `SEQEVI_DATABASE_URL` without changing the application interface;
- bind-mounts the existing service-owned artifact root at a stable container
  path;
- requires the environment file, Docker, and artifact mount to exist before
  startup;
- verifies the artifact path is a mount before starting, preventing writes into
  an unmounted host directory;
- uses a restart policy appropriate for a persistent loopback service;
- identifies the exact image reference so rollback is an environment-file
  change rather than a mutable rebuild.

Secrets and node-specific absolute paths remain outside the repository. The
example documents permissions and placeholders without embedding credentials.

## CI Validation

Extend CI while retaining Python 3.12 and 3.13 application checks:

1. Install from the frozen lock and run `pdm run check` with the real PostgreSQL
   service so no PostgreSQL contract test is skipped.
2. Run `pdm build` and validate the distribution metadata and contents.
3. Install the wheel into a clean Python 3.13 environment with the server extra
   and verify the installed CLI and health service.
4. Build the Docker image and verify its Python/SeqEvi versions, non-root
   runtime, health response and absence of external annotation runtimes.
5. Start a fresh PostgreSQL service and artifact volume, allow the container to
   migrate it to the supported head, verify `/health`, restart the service
   container, and verify health and schema revision remain stable.

Repository completion requires `pdm run check` against real PostgreSQL,
`git diff --check`, clean distribution installation, and the OCI checks.

### Preflight and rollback

Before stopping the transient service:

1. Verify registry login, push and pull access to the narrow SeqEvi namespace.
2. Inspect the PostgreSQL container, its exact image, health, loopback port,
   restart policy and the named volume mount; do not recreate any of them.
3. Inspect the CephFS artifact root with `findmnt`, ownership, permissions,
   write access and current file count; do not move or copy it.
4. Read the current database schema revision and evidence/artifact counts.
5. Perform a cached evidence fetch through the transient service and retain the
   exact evidence key and expected artifact digests for post-cutover comparison.
6. Record the transient unit definition and confirm it can be restarted without
   rebuilding `/tmp/seqevi-fuq-11`.
7. Pull the candidate image by immutable digest and inspect that exact digest.

Rollback remains `seqevi-store-fuq11.service`. The stable unit is stopped and
the transient unit restarted if migration, health, restart, cached evidence
read, image verification, or artifact integrity fails. Because FUQ-12 changes
neither schema nor data contracts, rollback requires no database downgrade.

### Cutover and acceptance

1. Stop the transient unit only after all preflight checks pass.
2. Install the generic user unit and a mode-`0600` node4 environment file
   referencing the candidate image by digest, the existing PostgreSQL URL, the
   existing CephFS artifact root, and its numeric non-root owner.
3. Start the persistent unit and verify systemd and container state.
4. Read back the running container image ID and repository digest and require
   them to equal the promoted digest.
5. Require HTTP 200 from `/health` on `127.0.0.1:18081` with the expected
   limits.
6. Restart the stable systemd unit and repeat exact image, health and schema
   checks.
7. Fetch the preflight evidence key through the stable service and require the
   same evidence metadata and artifact digests.
8. Keep the transient unit installed but inactive until the stable acceptance
   record is reviewed.

No live action may recreate or replace the existing PostgreSQL container,
volume or artifact root. The accepted deployment uses `systemctl --user` to
supervise a non-root container through the host rootful Docker daemon at
`unix:///var/run/docker.sock`; user lingering is enabled on node4.

## Acceptance Criteria

1. The Python 3.13 image is reproducible from the committed frozen lock and
   runs the existing server interface as non-root.
2. The image contains no eggNOG/InterPro runtime or database.
3. CI proves build, clean wheel install, PostgreSQL migration, health and
   restart behavior.
4. Publishing uses the exact `publish.yml`, `pypi` and `testpypi` trusted
   publisher bindings with OIDC and no token.
5. Manual publishing cannot target production PyPI, and PyPI publishing is
   gated by an exact `v<project-version>` tag.
6. The persistent unit prevents accidental non-loopback exposure and
   unmounted-artifact startup.
7. Node4 continues using the existing PostgreSQL container, named volume and
   CephFS artifacts.
8. The stable unit runs the verified immutable image digest, survives restart,
   returns `/health`, and serves a real cached evidence record.
9. The prior transient service remains a tested rollback path during
   acceptance.

## Acceptance Result

All PR1 acceptance criteria passed on node4. The immutable image, persistent
user service, PostgreSQL/CephFS preservation, restart and real cached evidence
readbacks are recorded in
[SeqEvi 0.1.0 stable loopback service acceptance](../benchmarks/20260727-v0.1.0-stable-loopback-service-acceptance.md).

The service remains loopback-only. The excluded ingress, TLS, authentication,
backup, monitoring, Kubernetes and performance work remains outside FUQ-12.
