# Shared Store Claim Contention Hardening Plan

Version: v1.0  
Date: 2026-08-11  
Status: in progress; PR A observability and reproduction baseline  
Target: post-0.2.0 shared Store canary

## Problem statement

The first merged per-EvidenceKey lease implementation proved claim ownership
but the real two-project C2 run did not complete. One client received a generic
HTTP timeout while repeatedly acquiring busy overlap keys; the second client
continued its adapter work after its lease renewal stopped. The Store health
endpoint stayed responsive and no residual claim rows survived, so the current
evidence points to bounded database/claim-request contention rather than a
network or scientific result error. The exact endpoint and wait stage remain a
PR A diagnostic target.

The acceptance target is two claim-capable clients over 9,116 keys with 9,115
overlapping keys: one calculation per EvidenceKey, peer reuse for the overlap,
both processes exit successfully, and no expired or residual claims.

## Compatibility boundary

The public `annotate` CLI, profiles, adapter contracts, EvidenceKey schema,
lease semantics, `/health` response, and legacy Store endpoints remain
unchanged. No public timeout or concurrency flag is introduced. Internal
client scheduling and service pool/transaction settings may change behind the
existing versioned claim endpoints. No Redis, scheduler, or database schema
migration is planned.

## Delivery slices

### PR A: observability and deterministic baseline

- emit one secret-free JSON log record for each acquire, renew, release, and
  finalize request with request ID, operation, batch size, outcome, status, and
  duration;
- include HTTP method and claim endpoint in client transport failures;
- add focused tests proving log redaction and actionable timeout context;
- add a PostgreSQL pressure harness/readback procedure for 100, 1,000, 3,000,
  and 9,116 keys, including `pg_stat_activity` and lock-wait evidence.

PR A is complete only when the failing request path and wait stage can be
identified from fresh evidence.

### PR B: bounded claim scheduling

- use an internal claim mutation chunk below the public 1,000-key limit;
- replace submit-all renewal with a sliding window and one small per-client
  concurrency bound, prioritizing renewal before acquisition and cleanup;
- use jittered bounded retry for busy acquisition and return retryable service
  backpressure as `503` with `Retry-After`;
- configure the PostgreSQL pool and transaction lock/statement deadlines from
  named service settings, keeping every request deadline inside the lease
  runway;
- preserve atomic acquire, canonical lock order, owner/generation checks, and
  existing old-client/new-service compatibility.

The initial candidate values are four concurrent claim requests per client and
250-key internal chunks; PR A measurements may revise them before merge.

### Optional PR C: set-based persistence

If PR B still shows SQL or lock time dominating, convert renew/release and then
acquire persistence to set-based statements while retaining the existing
transaction and lock invariants. This slice is not presumed necessary.

## Validation gates

1. Claim-only PostgreSQL pressure passes at 100, 1,000, 3,000, and 9,116 keys.
2. Real C2 passes with 8 threads per process, then 32 threads; the user-requested
   2 x 64 run is a subsequent stress gate, not the first debugging surface.
3. Both processes exit 0; final evidence count is 9,116; overlap is reused;
   second-process replay reports 9,115 cache hits and zero computed records.
4. No claim expires during computation, no claim rows remain, and artifact
   writes are unchanged and read-only from callers.
5. Focused PostgreSQL/HTTP tests and the repository gate `pdm run check` pass.

The formal claim-lease architecture document is updated only after these
gates pass; until then this plan records a hardening slice, not a new release
claim.
