# InterProScan Pfam Official Parity Implementation Plan

> Status: complete
> Date: 2026-07-23
> Target: close the SeqEvi Phase 3 external-runtime gate

## Outcome

The external-runtime gate passed on 2026-07-23. Direct InterProScan and SeqEvi
produced the same 51 scientific Pfam rows for ten canonical sequences, with
nine hits and one no-hit. A repeated SeqEvi run reused all ten records with
zero external computation. The durable evidence is recorded in
[InterProScan Pfam runtime validation](../benchmarks/20260723-v1.0-interproscan-runtime-validation.md).

## Objective

Validate that the implemented `interpro-pfam` adapter preserves the scientific
result of official InterProScan `5.77-108.0` with its native `data/` directory
and Pfam `38.1`. The gate closes only when a direct upstream run and a SeqEvi
run agree under the same runtime, data and semantic parameters.

This work validates an existing adapter contract. It does not add another
adapter, install or distribute InterProScan, transform the upstream database,
or merge direct Pfam evidence with eggNOG-transferred `PFAMs`.

## Runtime Contract

The validation target is:

| Component | Required identity |
| --- | --- |
| InterProScan | `5.77-108.0` |
| Data release | `108.0` |
| Selected application | `Pfam` |
| Pfam model release | `38.1` |
| Lookup mode | local direct scan with precalculated lookup disabled |
| Native output | InterProScan TSV |

SeqEvi must receive the official `interproscan.sh` path and the exact native
InterProScan `data/` directory. Temporary files, Store files and output
packages must use writable local paths; the mounted runtime and database may
remain read-only.

## Execution Stages

### Stage 0: Runtime And Data Discovery

Locate and record:

- the official `interproscan.sh`;
- `interproscan-5.jar`;
- a compatible Java runtime;
- the exact `data/` root;
- `interproscan.properties`;
- the Pfam `38.1` model files used by the runtime.

Probe `interproscan.sh --version` and verify that SeqEvi resolves the expected
InterPro/Pfam release coordinate. Do not start annotation if the launcher and
data releases disagree or if the supplied directory is not the native
InterProScan `data/` root.

Current result: mapping-only resources such as `protein2ipr.dat.gz`,
`interpro.xml.gz` and derived Parquet mappings support identifier mapping and
must not be substituted for the native scan database. The accepted complete
distribution provides the runtime and native data, its launcher/version probe
passes under JDK 17, and the resource lock has been fully verified. Stage 0 is
complete.

### Stage 1: Deterministic Parity Fixture

Select a small local protein FASTA containing:

- at least one sequence with multiple Pfam domain rows;
- at least one expected no-hit sequence;
- stable sequence content that may be retained as a local validation fixture.

Canonicalize it through SeqEvi and retain the input SHA-256, sequence count,
amino-acid count and canonical sequence identifiers in the benchmark record.

### Stage 2: Direct InterProScan Baseline

Run the official launcher directly with the contract-equivalent settings:

```text
-appl Pfam
-f TSV
-dp
```

Use an isolated local working directory. Retain the command, version output,
wall time, peak RSS, exit status, stderr and native TSV. Confirm complete input
accounting before comparing SeqEvi.

### Stage 3: SeqEvi Cold Run

Run `seqevi annotate --adapter interpro-pfam` against an empty local Store with
the same executable, data, input and semantic parameters.

Verify:

- all input sequences are classified as hit or no-hit;
- InterProScan sequence MD5 values match SeqEvi canonical sequences;
- native Pfam domain row grain is preserved;
- operational run dates are excluded from normalized evidence;
- runtime, resource and semantic-parameter provenance are exact;
- the package descriptor and physical files agree.

### Stage 4: Direct-Parity Comparison

Compare the direct TSV and SeqEvi output after removing only the documented
operational run-date field. Require equality of:

- signature accession and description;
- sequence MD5 and length;
- domain coordinates;
- score, status and InterPro cross-reference fields;
- normalized row count and values;
- hit/no-hit classification.

Any unexplained difference blocks acceptance. Fixture expectations must not be
used to override actual upstream behavior.

### Stage 5: Cache Reuse And Resource Audit

Repeat the same SeqEvi annotation against the populated Store and require zero
external computation. Compare the cold and cached packages semantically.

Run explicit full resource verification when the data root is writable enough
to publish a `seqevi.lock`. If the official mount is read-only and has no lock,
record the full verification timing and retain correctness while reporting the
expected repeated hashing cost.

### Stage 6: Evidence And Contract Closeout

Write the reproducible result under `docs/benchmarks/` with:

- exact runtime release coordinates and content identities;
- input identity and commands;
- direct, cold SeqEvi and cached SeqEvi measurements;
- parity comparison results;
- any operational limitations.

After successful parity:

- mark Phase 3 complete in the MVP implementation plan;
- update the root README status;
- add the benchmark to `docs/README.md`;
- run `pdm run check`.

## Acceptance Criteria

The Phase 3 external-runtime gate is complete only when:

1. official InterProScan `5.77-108.0` and native data `108.0`/Pfam `38.1` are
   positively identified;
2. the direct and SeqEvi runs use identical scientific parameters;
3. direct native results and normalized SeqEvi evidence agree after removal of
   the documented run-date field;
4. hit/no-hit accounting is complete and disjoint;
5. a repeated SeqEvi run performs zero annotation computation;
6. runtime, resource and parameter provenance is recorded;
7. the benchmark record and repository-wide validation pass.

## Risks And Boundaries

- A visible CephFS mount does not prove that the official runtime and native
  data were published on that mount.
- InterProScan runtime and data releases are coupled; mixing them is invalid.
- The database can be read-only, but annotation work, Store data and outputs
  require local writable directories.
- A full resource hash can be expensive. It must be measured, not silently
  skipped, before making performance claims.
- Thread tuning is outside the parity gate. It begins only after one accepted
  direct/cold/cache comparison establishes scientific equivalence.
