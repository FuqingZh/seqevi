# Native OCI Integration Specification

Version: v1.0

Date: 2026-08-31

Status: accepted for Unit 1 implementation on 2026-08-31;
source implemented; validation/delivery status tracked by the parent plan;
runtime authority is storage architecture v1.8, not this specification

## Decision And Scope

Use unmodified zot minimal v2.1.20 and ORAS CLI v1.3.4 for new shared-store
artifacts. The [qualification report](../benchmarks/20260831-v1.0-native-oci-qualification.md)
supports proceeding to R2 implementation after acceptance of this specification.
The [parent plan](20260829-v1.0-artifact-upload-finalization-boundary-implementation-plan.md)
continues to own delivery order and authorization.

This proposal freezes the integration seams, not a second transfer engine.
Local SQLite/POSIX annotation stays unchanged. Existing shared POSIX bytes
stay in place and readable. No historical-byte or storage-location migration,
cleanup daemon, credential vault,
cross-restart recovery, full-cache export/import, production cutover, or
publication is included. A compatibility schema upgrade is required to mark
existing rows POSIX without changing their paths or bytes. Current authority
remains in the [documentation index](../README.md).

## Qualified Dependencies And Topology

- One zot instance owns its storage root; no shared-root multi-instance claim.
- Native clients require a matching installed ORAS v1.3.4 executable. SeqEvi
  checks its version and invokes argument arrays, never a shell or installer.
- Qualification covers Linux/amd64 on local filesystem storage. Existing
  SeqEvi host support is not removed; OCI on other host platforms needs its
  corresponding binary and execution evidence. Managed dbCAN remains
  Linux/amd64; ORAS availability does not expand the kit platform matrix.
- Use HTTPS with normal trust verification; optional private CA and standard
  Registry credentials belong to the invocation/deployment. Disposable
  loopback HTTP is a test setting, not an automatic TLS downgrade.
- Deployments configure the Registry endpoint and one repository explicitly.
  No cluster address, shared mount, or credential becomes a package default.

For deployment examples, use native `gc: true`, `gcDelay: "1h"`,
`gcInterval: "1h"`, `commit: true`, and no SeqEvi-tag expiry policy.
These are Registry settings, not a new SeqEvi cleanup schedule. Operators own
capacity monitoring and storage quotas. The qualification used a faster native
sweep interval and temporarily shortened protection only with uploads stopped.
Do not copy its two-second protection setting into an active deployment:
it caused an observed upload failure. A one-hour protection setting leaves
headroom around the existing 900-second staging budget; it is not a promise
of exact reclamation time or power-loss durability.

### Service-side configuration

Extend the existing `ServiceSettings` / `SEQEVI_` configuration boundary;
do not add another configuration store:

| Setting | OCI-mode rule |
| --- | --- |
| `artifact_backend` | `legacy-posix` by default; explicit `oci-registry` enables the new mode |
| `oci_registry_id`, `oci_registry_endpoint`, `oci_registry_repository` | Required nonsecret identity/address for the single configured Registry; these alone enter discovery |
| `oci_oras_executable` | Required absolute executable path, version-checked as 1.3.4 at service startup; no automatic install or service-home/PATH guess |
| `oci_registry_config` | Required absolute path to an operator-supplied standard self-contained auth file; use an explicit empty `auths` file for anonymous Registry access |
| `oci_registry_ca_file` | Optional absolute CA bundle path; absence uses normal system trust |

All service files must be readable/executable as appropriate by the actual
service account, with operator-controlled permissions and read-only mounts
when containerized. Do not chmod/copy host credentials or expose these paths
through discovery. Service metadata checks use its own read-scoped credentials,
never a client-uploaded file or the service account's implicit home config.
Reject service `credsStore`/`credHelpers` for this bounded headless configuration;
native interactive clients may still use their ordinary helpers. Missing
required OCI configuration prevents startup. Keep `artifacts_dir` for legacy
reads. These are explicit file inputs to ORAS, not new login/auth semantics.

## Discovery And Early Admission

Keep `/health` and its strict response shape unchanged. Add
`GET /v1/storage/discovery` with a separate typed response:

```json
{
  "protocol": "storage-discovery-v1",
  "artifact_backend": "oci-registry",
  "minimum_client_capability": "oci-artifacts-v1",
  "registry": {
    "id": "primary",
    "endpoint": "https://registry.example.org",
    "repository": "seqevi/artifacts"
  }
}
```

Non-OCI mode returns `artifact_backend: "legacy-posix"`, null minimum
capability, and null Registry. Validate the combinations strictly. Discovery
contains no credential or client-controlled target. Registry identifiers map
to administrator configuration; changing their endpoint/storage identity is
an operational change, not a transparent client fallback.

New client initialization performs health, discovery, native prerequisite
checks, then existing ClaimSession capability negotiation. Only an exact 404
for discovery after a valid health response selects the old-service path.
Malformed JSON, unsupported protocol, 401/403, TLS errors, and outages fail;
none means "old service." Missing ORAS/version/configuration fails before
claim acquisition or external annotation. Native Registry authentication
errors must be surfaced during preflight where discoverable. Credential
presence or successful read access is not proof of push permission: actual
write authorization remains enforced by the Registry, and a later denial
must prevent evidence finalization.

ORAS 1.3.4 folds zot's absent-blob response into an exact native `not found`
diagnostic. Preflight permits that diagnostic only for its own missing-digest
probe so an empty repository works; it does not treat arbitrary 404 responses
as success. A Registry may conceal denied access as 404, so this is not proof
of repository read permission either. Do not require catalog-list permission,
write a probe artifact, or introduce another authentication mechanism to infer
rights that the Registry must enforce on each actual operation.

In OCI mode, service admission requires
`X-SeqEvi-Client-Capability: oci-artifacts-v1` on every evidence, artifact,
and ClaimSession operation. Only health and discovery are exempt. Missing
or unsupported capability returns 426 with an actionable upgrade message
before lookup/acquire handlers run. The header is version negotiation, not
authentication. Both the ordinary client transport and ClaimSession transport
must send it; checking a new endpoint alone cannot reject silent old clients.

Code inspection places native Store construction before external annotation.
Managed execution constructs its Store inside the container, so early means
before the external annotation tool, not before Docker image acquisition or
container startup. Runtime old/new-client rejection tests remain a Unit 1
obligation; the Unit 0 evidence is feasibility and prerequisite-probe evidence.

## Artifact Identity And Stable Retention

Keep the existing raw SHA-256, byte size, and media type. Do not replace raw
artifact identity or EvidenceKey with a manifest digest. Registry storage has
a separate immutable manifest identity.

Publish one OCI image manifest with:

- `schemaVersion: 2` and `mediaType: application/vnd.oci.image.manifest.v1+json`;
- `artifactType: application/vnd.seqevi.evidence-artifact.v1`;
- empty config bytes `{}`, descriptor media type
  `application/vnd.oci.empty.v1+json`, size 2, and its standard SHA-256;
- exactly one layer, carrying the existing raw media type, raw digest, and
  exact size; its only annotation is
  `org.opencontainers.image.title: artifact.bin`;
- no timestamp, host filename, ClaimSession state, evidence authority,
  external descriptor URL, or mutable subject/reference.

Serialize UTF-8 JSON with lexically sorted keys and compact separators,
without a trailing newline. Manifest bytes, descriptor metadata, and digest
are deterministic for one accepted raw identity. The fixed extraction filename
is independent of the adapter-native content or schema.

Use tag `sha256-<manifest digest hex>`, not `sha256-<raw digest hex>`.
Read by immutable `repository@sha256:<manifest hex>`. A manifest-metadata
change cannot then move the retaining tag away from an older manifest with
the same raw bytes. Two clients publishing the same manifest converge on
one tag; different manifests have separate tags. Registry authorization and
operator policy must not permit accidental tag expiry or ordinary client
deletion of retained artifacts. No application GC is introduced.

SeqEvi still rejects conflicting media type or size for an already registered
raw digest. A conflicting upload can leave a tagged but unregistered artifact;
that accepted space overhead is not evidence. A Registry accepting two
descriptors for identical bytes does not decide SeqEvi media-type authority.

## Smallest Storage Schema And Legacy Reads

Extend the existing shared `artifact` table with a discriminated storage
reference, rather than introducing a multi-reference table:

| Kind | `relative_path` | `registry_id`, `repository`, `manifest_digest` |
| --- | --- | --- |
| `posix` | Required existing path | All null |
| `oci` | Null | All required |

Add `storage_kind NOT NULL` and an exclusive SQL CHECK for these cases.
Keep `artifact.digest` as the raw-content primary key and preserve evidence
foreign keys. `relative_path` becomes nullable; its existing uniqueness
constraint remains meaningful for POSIX rows. The next shared-schema migration
marks old rows `posix` without touching artifact bytes. Validate migration and
constraints with both SQLite and PostgreSQL under the existing maintenance
contract. Local Store layout/metadata is not converted to OCI.

One raw digest has one selected storage location in this delivery. If a valid
legacy row already exists, reuse it; do not upload a replacement merely to
change location. New distinct artifacts in OCI mode use OCI. In a concurrent
registration race, the existing row wins only after raw size/media consistency
and its selected storage reference are validated; never overwrite a legacy
path or conflate two byte identities. OCI proposals must also match canonical
manifest construction. Multi-location migration/failover is future work, not
a reason to add a reference table now.

Add an OCI-capable `POST /v1/artifacts/resolve` request by raw digest, returning
typed POSIX or OCI location metadata. Do not add fields to old strict evidence
response DTOs. POSIX references use the existing artifact GET path; OCI
references resolve only through the configured Registry ID/repository and
immutable manifest digest. Never store OCI URLs in `relative_path` or return
Registry-private filesystem paths. Legacy/non-OCI direct APIs remain available
according to the mode/version admission matrix; no OCI-to-old-client relay.

## Staging And Metadata-Only Finalize

The shared client owns this sequence:

1. Resolve/deduplicate exact raw identities; reuse validated legacy records.
2. For a new OCI artifact, start one monotonic 900-second outer staging budget.
   Use native `oras blob push` for config and raw bytes, addressed by expected
   digest, then `oras manifest push` for the deterministic stable tag.
3. Fetch/read back the retaining tag and immutable manifest digest. A lost
   response may be reconciled by standard readback within the same budget;
   failure without proven retention is not publication success.
4. Recheck session-loss state and capture fresh ClaimSession authority.
5. Start the existing short metadata deadline (at most 30 seconds, including
   split batches and reconciliation runway) and finalize evidence.

The representative annotation scaling unit is a sequence batch sharing its
batch-level normalized/raw artifacts, not one distinct artifact pair per
sequence. Retain digest deduplication and cover 1,000 commits sharing two
artifacts as a regression. Arbitrary heterogeneous commit/finalize batches may
consume the fixed budget sooner; do not infer a 1,000-distinct-artifact SLA or
change admission, concurrency, or deadline semantics without separate evidence
and authority.

Use native ORAS retries and completed-blob reuse. Do not build offset tracking,
chunk scheduling, a second retry loop, restart recovery, or local orphan
adoption. Store close, cancellation, authority loss, and timeout stop and reap
the owned subprocess/reader before claiming cleanup. Never extend the outer
budget by launching a new native command after exhaustion.

OCI finalize accepts a typed storage reference alongside existing artifact
metadata. The service independently validates the configured Registry and
repository, bounded canonical manifest bytes, matching manifest digest and
stable tag, and exact raw descriptor digest/size/media type. Verify the blob's
existence/size with a native descriptor request, without downloading it. Use
the same pinned ORAS for Registry metadata operations with deployment-owned
standard read credentials/CA; do not hand-build another Registry client.
Bound manifest-read output to 64 KiB and the remaining metadata deadline;
reject an over-limit response and reap the subprocess, rather than buffering
an arbitrary Registry response. The canonical single-layer manifest is much
smaller than this limit.
Reject additional layers, unexpected config/annotations, external URLs,
wrong targets, missing retention, or inconsistent metadata.

The service is not permitted to trust a client-supplied digest as retention
proof. Conversely, finalize must not reread/hash/copy the raw artifact.
Full SHA-256 belongs to ingestion/completion and verified download. Storage
reference and evidence registration occur under the existing ClaimSession
generation fence; staged data never substitutes for authority.

The 900-second and authority rules above are retained R2 obligations, not
claims established by the stand-alone Unit 0 probe's shorter command limits.

## Native And Managed Credential Inputs

Add optional invocation-only Python arguments:

```python
oci_registry_config: Path | None = None
oci_registry_ca_file: Path | None = None
```

CLI counterparts are `--oci-registry-config PATH` and
`--oci-registry-ca-file PATH`. Carry them through one immutable file-options
value at the application boundary. They do not enter profile TOML, kit
identity, EvidenceKey, Registry discovery, or a secret database. Reject these
options for local/non-OCI mode instead of silently ignoring a configuration
mistake. No password/token argv option, automatic login, certificate-verification
bypass, or public ORAS-path option is added.

Native mode invokes ORAS on PATH. Without explicit files it uses ORAS's
standard credential/helper and public CA behavior. With files it forwards the
standard `--registry-config` and `--ca-file` options. A Registry requiring no
authentication needs no login.

Managed mode uses `/usr/local/bin/oras` in an explicitly updated, digest-pinned
image and two optional exact-file read-only binds:

| Host invocation file | Inner path |
| --- | --- |
| Registry configuration | `/run/seqevi/registry/config.json` |
| Private CA bundle | `/run/seqevi/registry/ca.pem` |

Continue running under the caller's numeric UID/GID, not the image's default
user; validate file readability without changing host permissions. The inner
CLI receives only those paths. Shared execution uses a network-reachable
Registry hostname, not host `127.0.0.1` inside a bridged container.

Require a dedicated self-contained standard auth file for managed authenticated
execution. Reject `credsStore`/`credHelpers` there: an isolated container does
not inherit the host helper/keychain. Do not mount the entire Docker config,
home directory, credential helper, or Docker socket. The file should contain
only the target Registry credentials; access scope is still enforced by the
Registry. Anonymous managed access needs no auth file. mTLS certificate/private
key forwarding is not included in this slice.

Build the new image through the existing pinned-input mechanism, embedding
the verified ORAS executable and license. Preserve existing kit producer
images; update the new kit/image identity explicitly. Unit 0's existing-image
bind-mounted-binary canary proves only the file/network interface. New image
build, kit upgrade, clean-user verification, and publication are not already
done; publication remains separately authorized.

## Unit 1 Work And Validation

Delivery clarification accepted on 2026-08-31: this implementation delivers
source, a local candidate image and verification. The existing bundled kit
stays unchanged. Registration/distribution of a new selectable kit waits for
separately authorized image publication and its verified registry digest;
no placeholder digest or implicit old-profile upgrade is permitted.

One owning integrator freezes the DTOs and schema before optional parallel
implementation lanes. Suggested ownership: client/distribution lane for native
subprocess staging and file forwarding; service/storage lane for admission,
schema and retained-reference verification; independent read-only verification
lane. Shared transport models, tests, authority/index, and dependency files
remain with the integrator unless explicitly reassigned.

Required negative and regression coverage:

- old/new client and non-OCI/OCI service matrix, including silent old clients,
  exact discovery-404 fallback, invalid discovery, and both transports;
- missing binary/config/auth and managed exact-file inputs before external
  annotation, without claiming preflight can guarantee all future permissions;
- raw/media conflict, forged manifest, wrong Registry/repository, missing tag,
  same raw/different manifest retention, and digest-verified download;
- fresh authority after staging, authority loss, short metadata-only deadline,
  one staging budget, ambiguous readback, cancellation and subprocess reap;
- shared-schema migration/constraints on SQLite and PostgreSQL, legacy reads,
  local annotation without ORAS, and no raw-byte read during OCI finalize;
- actual new managed image/kit and portable clean-environment checks.

Run focused seam tests and the repository canonical `pdm run check` for that
runtime delivery. Publish successor storage/sequence contracts and code
together; this specification does not supersede them in advance.

## Activation, Rollback, And Stop Conditions

Development uses new disposable Registry roots and cloned/test metadata only.
Production activation requires its own exact backup, schema-upgrade, endpoint,
client-upgrade, target-filesystem and rollback authorization. Preserve old
bytes, but do not assume they let old software read new OCI-only records.
Switching the backend to POSIX or downgrading software is not a complete
rollback after OCI evidence has been registered.

Stop for renewed scope review if implementation requires a custom transfer
engine, Registry fork, cleanup service, new authentication system, expanded
platform support, or historical-byte migration. No such dependency was needed
for the qualified native path. This proposal was accepted on 2026-08-31;
Unit 1 implementation and its remaining delivery gates are tracked by the parent plan.
