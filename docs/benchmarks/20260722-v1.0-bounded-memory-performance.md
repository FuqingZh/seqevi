# Bounded-Memory And Operational Performance

> Status: fixture and staged real eggNOG validation passed
> Date: 2026-07-22

## Scope

This report measures SeqEvi orchestration after atomic FASTA staging,
file-backed artifacts, batch Store access, lazy Parquet materialization, and the
operational `--threads` option. Fixture timings are not annotation-tool
benchmarks.

The reproducible harness is `benchmarks/annotate_fixture.py`. It creates:

- A: all sequences are new;
- B: half of A is requested and fully cached;
- C: half the sequences are reused from A and half are new.

All workloads contain 80% hits and 20% terminal no-hits.

## Minimal eggNOG Runtime

A clean Micromamba environment was created with:

```bash
micromamba create \
  --root-prefix /home/fqzhang/micromamba \
  -n seqevi-eggnog-2.1.13-minimal \
  -c conda-forge -c bioconda --strict-channel-priority \
  python=3.10 eggnog-mapper=2.1.13 diamond=2.1.15
```

The solved environment contains 66 Conda packages and occupies 731 MB. Runtime
probes report eggNOG-mapper 2.1.13 and DIAMOND 2.1.15. The earlier cloned
validation environment contains 289 packages and remains the historical Phase 4
baseline; it is not the production recommendation.

The Bioconda package necessarily includes eggNOG-mapper dependencies such as
MMseqs2, HMMER, Prodigal, Biopython, NumPy, and PSUtil. SeqEvi does not bundle
this environment or any annotation database.

The complete A/B/C process took 569.03 seconds and a maximum 1,276,144 KiB RSS.
Peak RSS did not grow in proportion to sequence count from 10k to 100k. This
does not justify moving FASTA duplicate/order indexes to SQLite or temporary
Parquet in v1.

The 10k phase measurements identify local SQLite evidence commit as the main
fixture bottleneck. That is a bounded transaction implementation issue, not an
artifact-bytes or FASTA-index memory failure. Bulk metadata insertion may be
evaluated separately if local projects at this scale make the overhead material;
it does not justify a scheduler, claim protocol, or additional Store backend.

## Thread Contract

`--threads` defaults to 1, must be positive, and is passed to eggNOG-mapper and
InterProScan as `--cpu`. It is operational and does not enter `EvidenceKey`,
semantic parameters, runtime identity, or resource identity. Fixture-backed
official-adapter tests prove that 1-thread and 4-thread runs produce equal
scientific tables.

### 10 Unique Sequences

| Run | Result | Wall time | Peak RSS |
| --- | --- | ---: | ---: |
| 1 thread, new | 0 cached, 10 computed, 10 hits | 41m 56.71s | 4.39 GiB |
| 8 threads, new | 0 cached, 10 computed, 10 hits | 6m 10.18s | 4.43 GiB |
| 8 threads, cached | 10 cached, 0 computed | 4.94s | 0.24 GiB |

Eight threads provided a 6.80-fold wall-time speedup. The 1-thread and 8-thread
evidence and no-hit tables are value-equal. They have the same input digest,
ResourceID and ToolRuntimeDigest. Sequence maps are equal after excluding the
expected `EvidenceSource` provenance difference. The fully cached replay is
also scientifically equal and did not launch eggNOG-mapper.

The final 8-thread run used `benchmarks/annotate_real.py` and persisted exact
phase measurements. Adapter time was 366.59 seconds, of which 366.52 seconds
was the external tool. FASTA staging took 0.001 seconds, Store lookup 0.002
seconds, Store commit 0.009 seconds, Store fetch 0.002 seconds and package
materialization 2.65 seconds. In-process SeqEvi peak RSS was 223,304 KiB;
`/usr/bin/time` measured 4,649,988 KiB for the process tree and 689% CPU. The
warm-cache run reported eight filesystem input blocks, so this value is not
presented as a cold database-read benchmark.

### 100 Input Records With Partial Reuse

The 100-record prefix contains 95 unique sequences. Ten unique sequences were
already cached; the run computed the remaining 85. The completed package
contains 92 hits and 3 true no-hits. Input-level provenance contains 10 cached
rows and 90 computed rows because duplicate input records retain their own map
rows.

The 8-thread run took approximately 93m 37s, bounded by the benchmark log
creation and Data Package completion timestamps. The original SSH session was
interrupted, so `/usr/bin/time` output was not retained; process sampling
observed at least 7.17 GiB RSS. The package itself completed normally and a
fully cached replay proved value equality for evidence, no-hit and sequence-map
content. That replay reported:

- 95 cached unique sequences and 0 computed;
- 92 hits and 3 no-hits;
- 2.98 seconds annotation orchestration time;
- 0 seconds external-tool time;
- one Store lookup batch, one fetch batch and four unique artifact reads.

The nonlinear cost at 100 records established the staged stop boundary. A
100-record 1-thread run would be hours long based on the measured 6.80-fold
thread ratio, and 1,000-record variants would not answer another v1 contract
question. They were therefore not launched. This is an explicit benchmark
scope decision rather than a claim that those scales were measured.

`benchmarks/annotate_real.py` now persists in-process phase metrics and exact
runtime/resource identities as JSON. Future long-running measurements use that
runner instead of relying on an interactive terminal pipe.
