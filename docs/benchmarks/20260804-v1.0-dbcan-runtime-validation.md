## Direct Stage 0 Probe

The input was the first 50 records from the official `Xylona_heveae_TC161.faa`
test data:

| Property | Value |
| --- | ---: |
| Records | 50 |
| FASTA bytes | 24,038 |
| FASTA SHA-256 | `2f408a5a71f7b8e03f7274e424dde51c5b8cabb438c93585277fc846dab45287` |

The exact command shape was:

```bash
run_dbcan CAZyme_annotation \
  --input_raw_data Xylona-50.faa \
  --mode protein \
  --output_dir direct-50-full \
  --db_dir <locked-resource>/raw \
  --methods diamond,hmm,dbCANsub \
  --threads 1 \
  --e_value_threshold 1e-102 \
  --coverage_threshold_dbcan 0.35 \
  --e_value_threshold_dbcan 1e-15 \
  --coverage_threshold_dbsub 0.35 \
  --e_value_threshold_dbsub 1e-15
```

The official output header was exactly:

```text
Gene ID	EC#	dbCAN_hmm	dbCAN_sub	DIAMOND	#ofTools	Recommend Results	Substrate
```

The output contained five hit rows and no explicit rows for the remaining 45
sequences. The five DIAMOND values were `GH27`, `GH37`,
`AA5_2+AA5_2+CBM32`, `GH131` and `GT71`; HMM and dbCAN-sub columns were `-`
for this small input. The `Substrate` column was present and contained `-`.
The direct `overview.tsv` SHA-256 was
`5d40f951d6b5a7c955b83432761ac3ca668a5b420df4fb15c1f53e01f0cb01b2`.

A four-thread rerun completed with return code zero and produced the same five
scientific rows. Both `overview.tsv` files have SHA-256
`5d40f951d6b5a7c955b83432761ac3ca668a5b420df4fb15c1f53e01f0cb01b2`.
Thread timing is operational only; it is not included in the adapter evidence
identity.

The direct full run took approximately 5 minutes on the validation host. The
dbCAN-sub model loaded 53,411 HMMs and reported an estimated 24.5 GB model
footprint; observed process memory was materially lower but still substantial.
This is a runtime sizing observation, not a production capacity guarantee.

## SeqEvi Parity

SeqEvi invoked the same launcher and resource with:

```bash
seqevi annotate \
  --adapter dbcan-cazyme \
  --executable <runtime>/venv/bin/run_dbcan \
  --resource <locked-resource>/raw \
  --store seqevi-50-store \
  --fasta Xylona-50.faa \
  --output seqevi-50 \
  --threads 1
```

The cold run reported `0 cached, 50 computed`, with five hits and 45 no-hits.
Its DuckDB file contains `main.annotations`, `main.evidence`,
`main.sequence_map` and `main.no_hits`, plus the `_seqevi` metadata relations.
The native evidence schema is the eight-column overview schema with canonical
`SequenceID` linkage.

The direct and SeqEvi scientific values matched for all five hit proteins after
joining on the original FASTA record. SeqEvi deliberately stages canonical
`SequenceID` headers for the external command, so the native `Gene ID` value
inside `main.evidence` is the canonical sequence ID; the original user-facing
identifier remains in `main.annotations.InputID`. This makes the cache key
stable while preserving a direct `InputID` join for consumers.

The cold output and exact replay were different DuckDB files because each
invocation records its own creation timestamp and provenance source. Their
scientific relations were value-equal. The corresponding SHA-256 values were:

```text
seqevi-50        8778e9320a61e5172a102f4f523a792b8924f7b6381210af088fc1ddf2be2419
seqevi-50-cached  fe109d602c59fa801e837a3f48c83ace227f7c5be5c67c9cc8889c7116988eb0
```

The exact replay reported `50 cached, 0 computed`, confirming that no dbCAN
process was launched for cached sequences. The `_seqevi.run_metrics` rows
contained the corresponding `cache_hits`, `computed`, `hits` and `no_hits`
counts.

## Shared PostgreSQL Store Replay

The shared Store contract suite was run against the accepted isolated
`seqevi_test` PostgreSQL database with `SEQEVI_TEST_POSTGRES_URL` configured:

```text
182 passed, 1 warning
```

For the adapter-specific path, the 50 validated local evidence records and
their two content-addressed artifacts were seeded into a fresh PostgreSQL
schema through the real HTTP Store application. SeqEvi then ran the same FASTA
against that HTTP Store with an assertion adapter that raises if the launcher
is called. The result reported `50 cached, 0 computed`; after sorting by
`SequenceID`, both `main.evidence` (5 rows) and `main.no_hits` (45 rows) were
value-equal to the local DuckDB result. This is intentionally a cache/read
replay, not a second five-minute dbCAN computation; the scientific cold run is
the local real-runtime result above.

## Decision

The official dbCAN v5.2.9 protein launcher, the four-file resource snapshot and
the normalized eight-column result contract are accepted for direct execution,
50-record cold/cache parity, 51-record partial reuse and the isolated shared
PostgreSQL cache replay. Managed runtime distribution remains outside this
validation and is governed by the separate managed-onboarding plan.

The upstream launcher and package references are maintained at the
[run_dbcan repository](https://github.com/bcb-unl/run_dbcan) and
[dbCAN 5.2.9 PyPI release](https://pypi.org/project/dbcan/5.2.9/).
