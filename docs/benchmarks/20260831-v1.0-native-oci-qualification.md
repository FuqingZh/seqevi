# Native OCI Qualification — zot And ORAS

Version: v1.0

Date: 2026-08-31

Status: go for bounded R2 implementation after specification acceptance;
native qualification passed; not SeqEvi end-to-end or production acceptance

## Verdict And Scope

Unmodified zot minimal v2.1.20 and ORAS v1.3.4 passed the narrowed Unit 0
native interoperability and failure-behavior probes on Linux/amd64 with local
filesystem storage. No custom upload recovery, durability journal, or business
orphan collector was needed. The
[integration specification](../implementation-plan/20260831-v1.0-native-oci-integration-specification.md)
freezes the proposed R2 seams; it still requires acceptance before implementation.

The [parent plan](../implementation-plan/20260829-v1.0-artifact-upload-finalization-boundary-implementation-plan.md)
owns the delivery gates. No SeqEvi runtime, dependency, schema, production
Store, CAS, credential, image, or kit was changed by this qualification.
No commit, push, publication, or production activation was performed.

The historical Distribution durability counterexample remains historical
evidence under its then-current requirements; these results do not rewrite it.
Current runtime authority remains [storage v1.7](../architecture/20260830-v1.7-storage-deployment-architecture.md).

## Environment And Bounds

Native probe: two private Registry instances, loopback random ports, one
HTTP and one HTTPS with a disposable one-day CA/server certificate and
test-only htpasswd credentials. ORAS received explicit test auth files, never
the user's default credentials. Large-transfer experiments ran serially;
two-client publication used only the 32-byte fixture. Local shared-disk
contention was not controlled, so timings are observations, not a throughput SLA.

The native process containment had 2 GiB memory, 200% CPU, 128 tasks and
600-second runtime ceilings; each Registry used `GOMAXPROCS=2` and
`GOMEMLIMIT=512MiB`. Native commands had 90-second deadlines, fault cases
25 seconds. The complete passing run took 50.486 seconds. These bounds
neither implement nor prove SeqEvi's future 900-second staging deadline.

Storage used `commit: true`, `dedupe: true`, native GC and no tag-expiry
policy. Upload phases used `gcDelay: "1h"`, `gcInterval: "2s"`. Only after
publication and with uploads stopped, Registry A was stopped/reaped and
normally restarted on the same root with `gcDelay: "2s"`; the probe waited
for an actual completed GC sweep and checked both immutable manifest roots.
It restored one-hour protection before subsequent transfers/faults.

Managed canary: one internal Docker bridge, no published host ports, one
Registry and sequential short-lived clients, using a pre-existing local
SeqEvi image ID
`sha256:91b1142285433c961d7169c4fa8bd09db574e29678857c771371be4cb4d0b5a5`.
ORAS/zot executables were exact-file read-only mounts, not a rebuilt image.
Containers ran as caller UID/GID, with read-only roots, bounded tmpfs, one
CPU each, 512 MiB Registry / 256 MiB client memory and 64-task limits.
The successful managed run took 25.323 seconds. This is a network/file-input
interface canary, not qualification of a new managed dbCAN image or kit.

## Earlier Attempts And Corrections

The first native attempt passed normal transfer/auth/Layout cases but correctly
stopped when its interruption trigger did not fire. It reused a previously
stored large digest; zot's HEAD returned 200 and ORAS skipped transmission.
That attempt is not interruption evidence. Its harness SHA-256 is
`cf215a1bb0300e64261fe9d16c14744493390bcccd71a7356417d2ee00d61e4e`.

The second native attempt used a distinct fault input but stopped earlier:
512 MiB upload returned `blob upload unknown` with a missing upload path
after native GC ran. It had incorrectly used two-second protection during
active upload. Its harness SHA-256 is
`e8f551f358644be57ab3b3a6ff8c7d43e91819ebe4395948c18365e788e5649c`.
The pinned [native GC implementation](https://github.com/project-zot/zot/blob/v2.1.20/pkg/storage/gc/gc.go)
uses the configured delay when examining upload-file modification times as
well as unreferenced blobs. The logs and missing path are consistent with
that cleanup race; no syscall-injection proof was performed. The correction
was native configuration and a separated GC phase, not a Registry patch.

Review also changed raw-digest tags to manifest-digest tags, preventing
different metadata for identical raw bytes from moving the retaining tag.
The passing test checks immutable manifest bytes as well as downloaded layer
bytes, so another manifest pointing to the same blob cannot hide this error.

The first managed attempt completed authenticated transfer, then failed a
too-specific test assertion expecting the word `unauthorized`. ORAS actually
returned nonzero with `basic credential not found`. The revised assertion
checks that real diagnostic; the fresh run also completed CA and missing-binary
negative controls. Its earlier harness SHA-256 is
`8fd787d7bcc3eca9d164a5b79aa0c0a199475314ba320a3e6c0cb627e9ab178d`.
Earlier failed attempts remain failed; their successful subsets are not
substituted for the complete passing run.

## Compatibility Findings And Remaining Evidence

Read-only code review established feasible early-admission, dual-transport
header injection, typed legacy/OCI resolution and metadata-only-finalize seams.
It also confirmed that managed execution overrides image USER with caller
UID/GID. These findings produced the linked specification, not implemented
features or a passing old/new-client integration matrix.

Still required in Unit 1: actual discovery/admission tests, reference
validation, SQLite/PostgreSQL schema checks, fresh ClaimSession authority,
900-second/no-reset and 30-second metadata deadlines, local mode without ORAS,
new image/kit packaging, and canonical repository validation. Before production
activation: target filesystem, exact deployment trust/capacity and backup/rollback
acceptance. Native CA validation in a disposable bridge is not production
credential or connectivity proof.

Not promised: partial-upload persistence across process/machine restart,
power-loss durability, multi-instance shared storage, every-speed recovery,
native GC exact expiry times, scientific cache reuse of unregistered output,
or complete offline-cache restore. `commit: true` is configuration, not a
newly demonstrated durability guarantee.

## Cleanup And Validation Disposition

All probe process groups were reaped; authoritative transient-unit readback
showed inactive/dead with empty control groups. All disposable Docker containers
and both internal bridge networks were removed and absence read back. No
pytest run, Registry daemon, container, network or monitor remains from this
qualification.

Temporary inputs, binary copies, Registry/Layout bytes and disposable
credential/certificate material were removed after evidence extraction. The
five private task roots occupied approximately 7 GiB before cleanup and
536 KiB afterward. Only small scripts, manifests, configuration and diagnostic
records remain as local reproduction evidence;
the checked-in report/reproducer is the durable project record, not a promise
that `/tmp` paths persist. Cleanup targets only these explicitly created probe
resources, never production or pre-existing runtime data.

Repository changes are qualification/specification documentation only.
Diff whitespace checks passed, including the untracked new documents;
`python scripts/check_markdown_links.py` reported 229 relative links and
zero broken links. Extracting the two Python code blocks from the reproducer
matched both executed passing harness hashes exactly. No full package or
scientific annotation gate was repeated for unchanged runtime. R1's code-diff and untracked
test hashes above remain unchanged; this does not reclassify R2's outstanding
runtime tests as passed.
