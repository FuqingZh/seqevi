# eggNOG Full-Proteome Scaling

> Status: benchmark complete
> Date: 2026-07-23

## Scope

This benchmark measures eggNOG-mapper 2.1.13 with DIAMOND 2.1.15 and the
eggNOG 5.0.2 database on server 217. It replaces the 10-sequence tuning result
as the operational sizing reference because it exercises both the DIAMOND
search and eggNOG annotation phases at realistic proteome scale.

## Thread Scaling

The thread sweep kept DIAMOND defaults: block size 2 and four index chunks.

| Threads | Wall time | Mean CPU use | Peak RSS | Relative to 32 |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 50m 42.32s | 27.84 cores | 8.28 GiB | 1.00x |
| 48 | 45m 59.47s | 41.87 cores | 8.40 GiB | 1.10x |
| 64 | 45m 07.19s | 56.12 cores | 8.54 GiB | 1.12x |
| 80 | 44m 52.72s | 71.50 cores | 8.69 GiB | 1.13x |
| 96 | 48m 44.31s | 86.51 cores | 8.95 GiB | 1.04x |

All five cases produced identical annotations, seed orthologs and candidate
hits. The lowest measured latency was at 80 threads, but it saved only 14.47
seconds over 64 threads while reserving 16 more cores. At 96 threads the
annotation phase regressed and total time increased.

Use 48 threads when shared-worker allocation efficiency matters. Use 64 as the
general default on comparable hardware. Do not use 80 or 96 as the default;
the additional allocation has negligible or negative end-to-end value.

## Block And Index Comparison

The parameter comparison fixed the thread count at 64. `default` means block
size 2 and four index chunks.

| Block size | Index chunks | Wall time | Mean CPU use | Peak RSS | Result identity |
| ---: | ---: | ---: | ---: | ---: | --- |
| default | default | 45m 07.19s | 56.12 cores | 8.54 GiB | baseline |
| 2 | 1 | 36m 28.01s | 58.66 cores | 20.74 GiB | identical |
| 1 | 1 | 47m 10.28s | 59.46 cores | 11.20 GiB | changed |
| 4 | 1 | 32m 32.44s | 57.76 cores | 39.98 GiB | changed |

Changing only index chunks from four to one reduced wall time by 19.2% while
preserving all three outputs exactly. Peak memory increased by 12.20 GiB, or
2.43 times. This is the balanced low-latency configuration when a worker can
provide at least 24 GiB to the process.

Block size 1 did not reproduce the small-input result: it was slower than the
default and changed the selected seed ortholog and annotation for 3,256
queries. Block size 4 was the fastest case but changed 6,172 queries and
required about 40 GiB. Candidate-hit differences were larger:

| Configuration | Changed annotation queries | Changed hit queries | Hit rows |
| --- | ---: | ---: | ---: |
| default | 0 | 0 | 144,547 |
| block 2, chunks 1 | 0 | 0 | 144,547 |
| block 1, chunks 1 | 3,256 | 12,090 | 178,305 |
| block 4, chunks 1 | 6,172 | 14,141 | 118,991 |

These are content comparisons after removing comments, not physical-file hash
comparisons. All configurations annotated the same 53,291 query IDs. Thread
count and index chunks did not change output content. Changing block size
changed DIAMOND's candidate search and propagated into selected seed orthologs
and final annotations for some of those same queries.

## Product Decision

- Recommend 64 threads for a dedicated full-proteome run on comparable
  hardware; use 48 on a shared worker.
- Keep block size 2. It is part of the current scientific result contract.
- Keep four index chunks as the low-memory default.
- Permit one index chunk as an explicit performance profile only when the
  worker has sufficient memory. It preserves content in this full-proteome
  benchmark but raises peak RSS from 8.54 to 20.74 GiB.
- Do not adopt block size 1 or 4 as an operational optimization. A block-size
  change is a scientific-contract change and requires a distinct evidence
  identity or adapter version.
- Treat the earlier 10-sequence result as a startup-cost benchmark, not a
  production sizing recommendation.

No eggNOG-mapper or DIAMOND process remained after the benchmark completed.

## Reproducibility

The benchmark used the same eggNOG-mapper scientific arguments in every case:

```text
--itype proteins
-m diamond
--seed_ortholog_evalue 0.001
--tax_scope auto
--target_orthologs all
--go_evidence non-electronic
--pfam_realign none
```

DIAMOND documents block size as result-affecting and index chunks as a
performance and memory tradeoff. See:

- <https://github.com/eggnogdb/eggnog-mapper/blob/2.1.13/emapper.py>
- <https://github.com/bbuchfink/diamond/wiki/3.-Command-line-options>
