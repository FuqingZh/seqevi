# DuckDB Result Prototype

> Status: Slice A-E result cutover gate passed; real-adapter fixture gate passed
> Date: 2026-08-04
> Harness: `benchmarks/duckdb_result_prototype.py`

## Scope

This is the first measured gate for the v1.1 result-consumption contract. The
harness builds the deterministic hit/no-hit fixture through the DuckDB relation
builder. Historical Data Package values are retained below as the 0.1.0
baseline; the production writer and public API now use DuckDB only. The harness
checks public relation row accounting, duplicate/no-hit behavior in the focused
tests, and read-only reopen of a file-backed result.

The comparison is materialization-only. It does not include FASTA parsing,
Store lookup, external annotation, or Store commit time.

## 10,000-Record Fixture

Environment: Python 3.12.13, Linux 4.18 x86-64, DuckDB 1.5.5, Polars 1.43.2,
PyArrow 25.0.0, one Polars worker, 90% hit rows and 10% no-hit rows.

| Materializer | Wall time | Output bytes | Rows |
| --- | ---: | ---: | ---: |
| 0.1.0 Data Package baseline | 5.56s | 1,648,079 | 10,000 input / 9,000 evidence / 1,000 no-hit |
| DuckDB prototype | 6.12s | 3,158,016 | 10,000 annotations / 9,000 evidence / 1,000 no-hit |

The DuckDB number includes creation of the four public relations, the
`_seqevi` metadata catalog, contract probes, checkpoint, and file close. The
The historical baseline includes its Parquet/TSV files and descriptor. DuckDB
is larger on disk at 10k because it carries the catalog and joinable relations
in one file. The 10k DuckDB wall time was 10.0% slower, within the plan's 20%
regression gate.

Focused contract tests also prove:

- two input IDs sharing one `SequenceID` receive the same adapter row;
- a no-hit remains visible with null adapter fields;
- `main.no_hits` has one row per unique no-hit `SequenceID`;
- the native relation exposes common columns before adapter-native columns;
- `_seqevi.column_info` describes the relation for consumers that do not know
  the adapter schema in advance;
- a file can be reopened read-only after the writer connection closes.

## 100,000-Record Gate

The same host was rerun after other sessions released thread capacity. The
fixture contains 100,000 input rows, 90,000 evidence rows and 10,000 no-hit
rows:

| Materializer | Wall time | Output bytes |
| --- | ---: | ---: |
| 0.1.0 Data Package baseline | 7.03s | 16,562,039 |
| DuckDB prototype | 6.67s | 12,595,200 |

DuckDB is 5.1% faster and smaller at 100k. Peak RSS for the complete harness
was 503,192 KiB in the original gate. A post-cutover rerun on 2026-08-04
measured 1.84s DuckDB materialization, 7.32s total elapsed time, the same
12,595,200-byte file, and 581,992 KiB peak RSS. The RSS difference is recorded
as a host/runtime observation rather than silently changing the accepted
wall-time gate. The explicit storage compatibility setting was used and the
file reopened read-only in the focused test.
