# OCI Registry Qualification — Distribution v3.1.1

Version: v1.0

Date: 2026-08-30

Status: candidate no-go; Unit 0 stopped at the durability prerequisite;
integration specification not frozen; not runtime authority

> Disposition update, 2026-08-31: the
> [revised plan](../implementation-plan/20260829-v1.0-artifact-upload-finalization-boundary-implementation-plan.md)
> withdraws the per-PATCH durable-ack gate and exact capacity/expiry equivalence.
> The verdict below records the requirement and decision at the time of the
> probe; it is not a current exclusion of Distribution or a zot qualification
> pass. Measurements and frozen execution identity are unchanged. Runtime
> authority is identified by the [current documentation index](../README.md).

## Verdict

CNCF Distribution v3.1.1 with its filesystem backend does not pass the
accepted durable-upload-acknowledgment requirement. In an isolated real HTTP
probe, injected `fsync=EIO` errors were followed by a successful PATCH response
confirming 13 bytes, while that upload's partial data file contained zero
bytes. After a normal process restart, its recoverable state still contained
zero bytes.

This blocks Unit 1 of the
[upload/finalization plan](../implementation-plan/20260829-v1.0-artifact-upload-finalization-boundary-implementation-plan.md).
It does not reject OCI as a protocol, establish a failure of other Registry
implementations/backends, or authorize a fork or weaker durability contract.
The broader qualification matrix and integration specification remain open;
this is a completed negative decision for this candidate, not a Unit 0 pass.

No SeqEvi runtime, dependency, database, production CAS, or deployed service
was changed. Current v1.6 runtime contracts remain authoritative.

## Paired HTTP Probe

1. Start the unmodified binary normally; POST an upload session.
2. PATCH the 13-byte payload, observe the response and partial-file size,
   complete with the expected digest, and compare downloaded bytes exactly.
3. Create a second empty session normally and retain its returned opaque
   `Location`. Stop and reap only the probe-owned Registry process group.
4. Restart the same Registry/storage/secret under child-local strace
   `inject=fsync:error=EIO`; PATCH the same payload into the second session.
5. Record the HTTP response, that session's partial-file size, and injected
   syscall failures. Stop and reap only this probe process group.
6. Restart normally, GET status using the faulted PATCH's returned `Location`,
   inspect the same session file, then cancel that session through DELETE.

| Observation | Positive control | Injected-sync-error session |
| --- | --- | --- |
| PATCH response | `202`, `Range: 0-12` | `202`, `Range: 0-12` |
| Partial data after acknowledgment | 13 bytes | 0 bytes |
| Injected sync errors | None | Four `fsync(...) = -1 EIO (INJECTED)` records |
| Completion and downloaded-byte check | PUT `201`; GET `200`; exact input match | Not attempted |
| Status after normal restart | Completed positive-control blob still downloadable | GET `204`, `Range: 0-0`; partial data still 0 bytes |
| Cancellation | Not applicable after completion | DELETE `204` |

The required negative-case outcome was an error without advancing the
acknowledged position, not a successful acknowledgment of unsaved bytes.
The observed `202` plus zero-byte partial file falsifies that requirement.
The harness reports `durable_ack_counterexample=true`. Its exit status zero
means characterization completed, not that qualification passed.

### Limits of the result

- The faulted session was never completed. The later blob GET refers to the
  earlier positive control with the same digest, not to successful completion
  of the faulted session. No finalized-artifact-loss claim follows.
- The injection affects every `fsync` in this disposable child process. The
  trace records file descriptors but not their paths. Precise attribution to
  hash-state versus data-file sync comes from source analysis, not that trace.
- `Range: 0-0` alone is ambiguous for an empty upload. The exact session's
  zero-byte data file is the independent size observation.
- Stops used SIGTERM, not SIGKILL, machine crash, power loss, or CephFS fault
  injection. The data file was already empty before stopping the process.
- This is one deterministic counterexample, not a failure-frequency estimate.
  Normal success does not qualify all durability boundaries.

## Source Explanation And Additional Gap

At the pinned source revision, `blobUploadResponse()` calls `Upload.Close()`
before constructing its response, but discards the error. It then obtains
the in-memory size and returns the advanced upload position. The issue is
ignored failure, not an assertion that this path always responds before
attempting sync. See
[upload response](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/handlers/blobupload.go#L322-L360).

`blobWriter.Close()` first persists hash state, returning immediately if that
fails, and only then closes the data writer, flushing and syncing it. A tiny payload can
therefore remain buffered when hash-state persistence fails. The filesystem
writer does call `Sync()`, but its errors cannot reach the HTTP response when
the caller ignores them. See
[blob writer](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/storage/blobwriter.go#L150-L160)
and [filesystem writer](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/storage/driver/filesystem/driver.go#L410-L431).

A separate static concern remains: completed-blob publication uses the
filesystem driver's `Move()`, which calls `os.Rename()` without an explicit
destination-parent directory sync. Other `PutContent()` directory syncs do
not by themselves prove global blob-directory durability. This is an
unproven machine-crash boundary, not a second demonstrated loss. See
[Move](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/storage/driver/filesystem/driver.go#L293-L309).

## Resource And Retention Review

These are pinned-source findings, not capacity or GC runtime acceptance.
They remain material policy decisions even if the sync-error bug is fixed.

| Accepted target | Native candidate behavior | Disposition |
| --- | --- | --- |
| 512 MiB supported artifact | Upload handler has no cumulative size ceiling | Support at the required rate/budget was not tested; a hard ceiling is a separate enforcement question |
| 4 GiB partial reservation, eight maximum-size sessions | No native partial reservation or active-session admission counter | Not met natively; do not substitute a whole-filesystem quota and call it equivalent |
| One-hour idle expiry | Purger uses immutable creation time, not durable-byte activity | Not met natively |
| 24-hour absolute expiry | Configurable age scan; default age 168h, interval 24h, initial random 0–59 minute delay | Eventual creation-age cleanup, not exact lifetime or idle cleanup |
| Cleanup-failure accounting and disk watermark | No durable reservation/failure ledger or native watermark policy; periodic scan may retry deletion | Not equivalent to the accepted accounting guarantee |
| Retention through completed-blob GC | Manifests and referenced blobs are marked by default; `--delete-untagged` changes protection | Standard artifact manifests remain the proposed mechanism; runtime/concurrency proof pending |

Source anchors:
[unbounded PATCH copy](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/handlers/blobupload.go#L146-L173),
[purger configuration](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/handlers/app.go#L1057-L1137),
[creation-age cleanup](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/storage/purgeuploads.go#L33-L119),
and [GC marking](https://github.com/distribution/distribution/blob/9a8d98b679740cd514aa7e7d84d23d442a5ef54c/registry/storage/garbagecollect.go#L69-L104).

The scheduled purge caller discards returned result/error lists; periodic
cleanup is not a durable admission-release ledger. Active uploads have no
activity-based exemption from creation-age purging. Completed-object GC is
distinct from partial purging and requires stopped/read-only writers under
[Distribution's GC procedure](https://distribution.github.io/distribution/about/garbage-collection/).
No GC was run in this qualification attempt.

## Integration Findings, Not A Frozen Specification

Read-only inspection confirmed that reuse must preserve these seams:

- Artifact byte digest, byte size, and media type remain SeqEvi metadata;
  manifest digest is a different storage identity. The current persistence
  layer rejects conflicting metadata for one artifact digest.
- Local Store and legacy shared-Store reads/writes currently assume POSIX
  CAS. Adding a Registry URL to the existing relative-path field would not
  update all readers and is not an accepted migration mechanism.
- Candidate integration needs explicit additive discovery, retained-reference
  mapping, old-client compatibility, and coordinated backup/restore/rollback
  decisions. `/health` and evidence authority must not change incidentally.
- A deterministic standard OCI image manifest with an empty config and one
  artifact layer is a plausible retention representation, not yet an approved
  SeqEvi wire/storage contract. Lost responses and concurrent retention still
  require tests; blob HEAD alone does not prove retention.

Inspection targets were `src/seqevi/store/{client,artifact,transport,local,schema}.py`,
`src/seqevi/service/{app,persistence}.py`, and `tests/test_shared_store.py` at
the stated SeqEvi baseline. No interface or migration implementation was
started because the candidate's prerequisite failed.

## Stopped Or Unverified Gates

The first hard durability failure made expansion unnecessary for this no-go
decision. The following remain explicitly not tested, rather than passed:

- 10/100/512 MiB at 1/5/20 MiB/s; 8/16/32 MiB chunk comparison; full
  900-second envelope, inactivity enforcement, and resource measurements;
- response loss, range mismatch, backpressure, near-completion SIGKILL,
  lost manifest completion, concurrent publication, and cancellation races;
- manifest publication/readback, runtime GC retention, quota exhaustion,
  purge failures, and native-policy operational alternatives;
- machine-crash durability and an explicitly approved isolated CephFS path;
- SeqEvi regression/adapter implementation, old/new API matrix,
  SQLite/PostgreSQL integration, migration, backup/restore, and rollback.

No expensive annotation was rerun. The local 13-byte probe does not replace
the dominant-scale gate when qualification resumes.

## Reopening Conditions And Handoff

Keep OCI reuse as the preferred direction. Return candidate selection and
the native-policy deviations to design review. Eligible next directions
include a supported upstream fix/release or a different mature implementation
whose actual storage engine passes the same counterexample. Changing only a
product wrapper is not evidence that the underlying failure changed.

Do not silently weaken acknowledged-byte durability, add a custom stateful
upload/admission engine, fork Distribution, or move into Unit 1. A chosen
successor must first pass the paired sync-error check, resolve completion
durability, and receive explicit approval for any changed capacity/expiry
policy. It must then complete the remaining qualification matrix and freeze
the integration specification before Unit 1 can start.
