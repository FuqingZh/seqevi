## Scope

This benchmark measures eggNOG-mapper 2.1.13 with DIAMOND 2.1.15 and the
eggNOG 5.0.2 database on server 217. It uses the same 10 unique protein
sequences and scientific options as the Phase 6 runtime validation. Each case
starts a new process and writes to an isolated directory. Filesystem cache was
warm after the first case, so these are compute and memory comparisons rather
than cold-storage measurements.

The host has 96 physical cores, 192 logical CPUs, four NUMA nodes and 503 GiB
RAM. Raw commands, logs, outputs and the machine-readable summary are retained
under:

## Thread Scaling

The thread sweep kept DIAMOND defaults: block size 2 and four index chunks.

| Threads | Wall time | Mean CPU use | Peak RSS | Speedup vs 8 threads |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 6m 10.18s | 6.89 cores | 4.43 GiB | 1.00x |
| 16 | 3m 13.74s | 13.00 cores | 4.45 GiB | 1.91x |
| 32 | 1m 48.56s | 23.21 cores | 4.48 GiB | 3.41x |
| 64 | 1m 08.26s | 39.40 cores | 4.49 GiB | 5.42x |

All four runs produced value-identical final annotations and seed orthologs.
The tested workload still benefits from 64 threads, but utilization falls from
81% of configured threads at 16 to 62% at 64. For a shared worker, 32 threads
is the balanced default. A dedicated worker can use 64 when minimum latency is
more important than allocation efficiency. These conclusions are specific to
this small warm-cache workload and this four-socket host.

## Block And Index Matrix

The main matrix used 32 threads. `default` means DIAMOND block size 2 and four
index chunks.

| Block size | Index chunks | Wall time | Mean CPU use | Peak RSS |
| ---: | ---: | ---: | ---: | ---: |
| default | default | 1m 48.56s | 23.21 cores | 4.48 GiB |
| 1 | 4 | 1m 47.04s | 23.26 cores | 3.31 GiB |
| 1 | 1 | 1m 05.01s | 20.52 cores | 3.32 GiB |
| 2 | 1 | 1m 04.18s | 20.70 cores | 4.82 GiB |
| 4 | 1 | 1m 10.82s | 21.00 cores | 9.49 GiB |
| 4 | 4 | 1m 50.72s | 23.17 cores | 8.61 GiB |

The best resource balance was block size 1 with one index chunk. At 64
threads, that combination completed in 46.56 seconds with 3.35 GiB peak RSS.
It was 32% faster and used 25% less peak memory than 64 threads with DIAMOND
defaults.

All cases produced identical final annotations and seed orthologs. Block size
1 produced one additional lower-ranked raw hit for one query, while the chosen
seed ortholog and annotation remained unchanged. This observed difference
matches DIAMOND's warning that block size can affect results.

## Product Decision

- Keep `threads` operational and outside evidence identity.
- Do not change the `eggnog/1` block-size default. DIAMOND documents it as an
  algorithm-affecting option, and the benchmark observed a raw-hit difference.
- Treat any future configurable block size as a scientific parameter included
  in the evidence key, or introduce it in a new adapter contract.
- Keep index chunks coupled to that versioned tuning decision even though this
  benchmark found no result difference from changing index chunks alone.
- Use 32 threads as the conservative shared-worker recommendation and 64 only
  for dedicated latency-sensitive runs on comparable hardware.

## Upstream Guidance

eggNOG-mapper exposes `--cpu` and forwards it to the search and annotation
phases, but does not prescribe one universal thread count. DIAMOND defaults to
all detected virtual cores when invoked directly. Its documentation recommends
tuning against the actual hardware and workload.

DIAMOND documents block size 2 as the normal default, estimates memory at
roughly six times the block-size value in GB, and warns that changing block
size can alter results. It documents four index chunks as the default and one
chunk as the faster, higher-memory option. It also recommends local temporary
storage or `/dev/shm` instead of a network filesystem when temporary I/O is a
bottleneck.
