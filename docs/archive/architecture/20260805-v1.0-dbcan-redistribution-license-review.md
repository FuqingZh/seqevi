# dbCAN Managed Redistribution And License Review

> Status: historical; archived; see `docs/README.md` for current authority
> Date: 2026-08-05

This review assumed that SeqEvi might publish the dbCAN database as a managed
resource. That assumption was removed from the product boundary. Use the
[v1.1 runtime image release review](../../architecture/20260805-v1.1-dbcan-runtime-image-release-review.md)
for current release decisions.

## Decision Boundary

This is a technical release-readiness review for the proposed P0 managed
`dbcan-cazyme` image. It is not legal advice and does not approve publication.
The current local and shared scientific adapter is accepted, but the managed
image/profile-v2 gate remains blocked until a maintainer with authority for
redistribution confirms the obligations below.

The target image is a SeqEvi-maintained aggregate containing a compatible
SeqEvi release, dbCAN, DIAMOND, Python dependencies and notices. It is not the
upstream dbCAN image. The four dbCAN database files remain a separately staged
resource and are not included in the image.

## Blocking Findings

1. **Database redistribution terms are not evidenced.** The publisher's
   documentation names the files and download path, but the local manifest has
   no license or redistribution field. A public managed kit must not assume
   that software GPL terms also cover database contents.
2. **The DIAMOND archive is incomplete as a release input.** The executable is
   hash-pinned, but its archive does not carry the license/notice materials
   needed by a redistributor. Use an upstream source release or add a verified
   license/source bundle before building an image.
3. **dbCAN source provenance is ambiguous.** The cached 5.2.9 wheel links to
   `bcb-unl/run_dbcan_new`, while the current upstream project is
   `bcb-unl/run_dbcan`. The exact source repository, tag/commit and build
   recipe must be recorded in the image provenance.
4. **The aggregate image needs explicit release artifacts.** A digest-pinned
   image must ship an SPDX/CycloneDX SBOM, a NOTICE/license bundle, exact
   source or corresponding-source instructions for GPL components, and a
   reproducible mapping from every binary/package to its source and checksum.

## Required Sign-Off Package

Before Slice A can activate profile v2 or change the repository product-boundary
map, produce and review all of the following:

- written permission/terms for redistributing the four dbCAN database files;
- exact dbCAN and DIAMOND source commits/releases and build inputs;
- dependency license inventory, including pyHMMER and HMMER/Easel notices;
- SPDX or CycloneDX SBOM for the image and the separately published resource;
- NOTICE/license files and GPL source/corresponding-source handling;
- a release record binding image digest, resource lock, manifest version and
  smoke result;
- explicit maintainer/legal sign-off recorded against that release record.

Until that package exists, do not publish a public managed image, bundle the
resource in a wheel/container, mark the redistribution gate passed, or
activate profile v2 as a current contract. Local v1 profiles and the existing
explicit runtime path remain unchanged.
