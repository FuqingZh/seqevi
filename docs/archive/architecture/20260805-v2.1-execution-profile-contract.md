# Execution Profile v2.1 Contract

Version: v2.1
Date: 2026-08-05
Status: historical; archived; see `docs/README.md` for current authority
dispatcher implemented; real managed-v2 parity gate pending
Supersedes: [v2.0 proposal](20260804-v2.0-execution-profile-contract.md)

## Purpose And Authority

Profile v2.1 describes one immutable managed OCI runtime selected by
`seqevi setup`. It extends the current
[profile v1 contract](../../architecture/20260724-v1.0-execution-profile-contract.md); it does not
replace or reinterpret v1.

The current reader accepts and strictly validates `version = 1` and `version =
2`; Slice B setup writes v2 profiles after image, resource and smoke checks.
OCI execution is now dispatched through the Slice C ephemeral Docker boundary.
Existing v1 profiles remain readable and
behaviorally unchanged after v2.1 is introduced.

## Selection Semantics

The existing three explicit invocation modes remain:

1. `--profile NAME` selects one XDG named profile;
2. `--config PATH` selects one exact caller-owned profile document;
3. explicit local mode supplies `--adapter`, `--executable` and `--resource`.

There is no implicit current profile, repository discovery, site profile,
profile inheritance or partial identity merge. `--fasta` and `--output` remain
explicit. A cluster or workflow selects the same profile or exact config as any
other caller.

## Document Shape

Managed setup publishes a complete document equivalent to:

```toml
version = 2
adapter = "dbcan-cazyme"
resource = "/data/dbcan/db_v5-2-9_5-5-2026/raw"
store = "/home/user/.local/share/seqevi/store"
threads = 8
# timeout_seconds = 86400

[runtime]
kind = "oci"
kit_id = "dbcan-cazyme-5.2.9-db-2026.05.05"
engine = "docker"
image = "ghcr.io/fuqingzh/seqevi-dbcan@sha256:<digest>"
```

Required root keys are `version`, `adapter`, `resource` and `runtime`. Optional
root keys are `store`, `threads` and `timeout_seconds`. The runtime table
requires `kind`, `kit_id`, `engine` and an image reference containing an
immutable digest.

P0 accepts only `kind = "oci"` and `engine = "docker"`. Unknown fields,
unsupported versions, mutable image references, invalid paths, unsafe profile
names and invalid operational values fail before Store access or container
launch.

Profile v2.1 does not contain `executable`, `path_prepend`, registry
credentials, arbitrary Docker arguments, mount lists or network switches.
Container-internal paths and command structure belong to the first-party kit
manifest. Secrets come from an external environment or secret boundary at
invocation time.

## Resource Semantics

The `resource` key is the caller-owned database root. Setup validates and
records that exact path but does not download, copy or redistribute database
files. Relative paths remain resolved against the profile document. Runtime
containers mount the resolved resource read-only.

The supported dbCAN kit requires the exact four-file release declared by the
kit manifest. A missing path, missing component, wrong size, digest conflict or
incompatible `seqevi.lock` fails explicitly. SeqEvi does not search other paths
or consult an institutional configuration layer.

## Authoring And Upgrade

The first v2.1 writer is `seqevi setup`. On first setup, the resource path is
resolved as follows:

1. an explicit `--resource PATH` wins;
2. an interactive terminal may prompt for the path when it was omitted;
3. non-interactive setup without a resource fails before mutation.

When the target named profile already exists, setup may reuse its recorded
resource for an exact readiness check or repair. It does not merge partial CLI
values into a different profile or silently replace profile contents.

`--profile-name` is the explicit side-by-side mechanism for a different kit or
resource. A later kit does not mutate a profile or hidden current alias. Users
may inspect, copy or version the TOML like any v1 profile.

`profile validate` remains static: it validates schema, local paths, immutable
image syntax and supported values without pulling an image or launching
Docker. Setup apply runs the mandatory short-lived smoke; annotation
delegation runs only after the profile and exact kit identity are resolved.

## Runtime Availability

The profile pins the public GHCR package by digest. Setup inspects Docker's
local content cache and pulls only when that digest is absent. The package must
be public, so the common path needs no registry login.

Annotation may restore the same exact digest after local cache cleanup. This is
a pull-if-missing operation, not an upgrade: the image reference and kit remain
unchanged. Annotation never pulls or discovers a database. An unavailable
registry or missing resource produces an actionable error that identifies the
exact unresolved state.

An internal registry mirror is deployment policy and is not represented by a
site-profile layer. A restricted deployment may pre-load the image through its
own tooling while preserving the same profile and scientific contract.

## Delegation Contract

When `annotate` resolves a v2.1 profile, the host delegates the complete
annotation invocation to the compatible SeqEvi inside the selected image. The
kit supplies the container executable and internal mount destinations. The
host supplies only narrowly resolved input, output, resource, temporary Store
and operational values.

The delegated invocation preserves the same adapter, Store and DuckDB
contracts as v1 local execution. A host rejects a result when the observed
SeqEvi version, adapter contract, runtime identity, resource identity or result
schema conflicts with the kit manifest.

Containers are ephemeral. Setup smoke and every annotation launch a unique
container and remove that exact container on success, failure, timeout or
cancellation. Only the image cache, profile, caller resource, Store and output
persist.

The current dispatcher accepts credential-free shared HTTP(S) Store URLs. URLs
with embedded userinfo, query or fragment values are rejected rather than
placing a secret in argv or Docker metadata; an external credential boundary
is a remaining release-hardening item.

## Compatibility

- V1 profiles remain valid local-runtime profiles.
- V2.1 adds OCI execution; it does not reinterpret v1 keys.
- `--profile`, `--config` and explicit local mode keep their current precedence
  and mutual-exclusion rules.
- Internal adapter contract IDs remain absent from ordinary user selection.
- No cluster, site or workflow-specific profile variant is introduced.
- A future schema version requires an explicit compatibility and migration
  decision; readers do not silently coerce unknown versions.

## Acceptance Gate

Before v2.1 is declared implemented, tests must prove:

- strict parsing and v1 regression compatibility;
- static validation performs no Docker or filesystem mutation;
- first-run resource resolution and non-interactive failure semantics;
- exact profile publication is atomic and no-overwrite;
- image present, image absent and exact rerun behavior;
- mount, network, UID/GID, secrets and cleanup boundaries;
- local-v1 and managed-v2.1 scientific/result equality on the accepted dbCAN
  runtime;
- clean wheel installation followed by setup and cold/cached annotation;
- successful reuse after a later process start without re-entering the
  resource path.

Slice C currently has fixture-backed coverage for the dispatcher command,
read-only mounts, caller UID/GID, local-store network isolation, result
metadata validation and exact-container cleanup. A real dbCAN local-v1 versus
managed-v2 cold/cached parity run is still required before this contract is
declared release-complete.
