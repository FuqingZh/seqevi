# Managed Adapter Distribution Architecture

Version: v1.1
Date: 2026-08-05
Status: historical; archived; see `docs/README.md` for current authority
Initial kit: `dbcan-cazyme`
Supersedes: [v1.0 proposal](20260804-v1.0-managed-adapter-distribution-architecture.md)

## Purpose

This document defines the future product-edge layer that takes a GitHub or
PyPI user from an installed SeqEvi CLI to a verified annotation runtime without
requiring a host installation of dbCAN, DIAMOND or their Python dependencies.
It does not make annotation databases part of SeqEvi distribution.

The target common path is:

```bash
pipx install seqevi
seqevi setup dbcan-cazyme --resource /path/to/dbcan/raw
seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

Slice A implemented strict kit/profile reading and a read-only plan. Slice B
adds explicit setup apply, digest pull-if-missing, caller-owned resource
verification, an ephemeral read-only smoke and atomic v2 profile publication.
OCI annotation delegation remains a later slice; this document is the accepted
boundary for that later implementation.

## One Public User Model

SeqEvi exposes one setup and annotation contract. It does not classify callers
as workstation, cluster, institutional or workflow users.

The public product contains no:

- site or institution profile layer;
- CephFS, Cromwell, WDL, Kubernetes or scheduler discovery;
- built-in internal Harbor address;
- automatic filesystem search for a database;
- cluster-specific setup branch.

A deployment system may pre-pull the exact public image or create the same
ordinary named profile that a person would create. That is deployment policy,
not a separate SeqEvi user model.

## Boundary

Managed onboarding is a first-party distribution edge around the existing
scientific contracts. It must not enter the evidence domain model.

| Owner | Responsibility |
| --- | --- |
| SeqEvi core | sequence identity, adapter contracts, Store reuse, result publication and profile selection |
| scientific adapter | invoke one supported upstream tool contract and validate adapter-native output |
| distribution edge | kit manifest, setup planning, runtime-image preparation, resource verification, smoke validation and profile publication |
| release publisher | build and publish immutable images, manifests, SBOMs, notices and source correspondence |
| caller or deployment | acquire the external database and provide its exact root path |

The distribution edge may depend on core contracts. Core adapters, Stores and
DuckDB results must not import Docker, download or registry concepts. SeqEvi
has no runtime dependency on biofetch. A caller may use biofetch, an upstream
downloader or another process to acquire resources, but SeqEvi neither knows
which was used nor imports its lock format.

## P0 Platform And Runtime Image

P0 supports exactly:

- Linux on `amd64`;
- Docker Engine supplied by the caller;
- `dbcan-cazyme` protein annotation;
- dbCAN `5.2.9` and DIAMOND `2.1.15`;
- resource release `db_v5-2-9_5-5-2026` supplied externally;
- one digest-pinned SeqEvi-managed runtime image;
- local POSIX Store or an explicit HTTP(S) shared Store.

Docker Engine is a host precondition. SeqEvi setup does not install a container
engine, modify operating-system packages, invoke `sudo`, create a micromamba
environment, or install dbCAN and DIAMOND into the caller's host Python.

The runtime image contains the compatible SeqEvi release, dbCAN, DIAMOND,
Python and locked result-bearing dependencies. It contains no annotation
database. It is a SeqEvi-maintained image built from official upstream
releases, not an upstream-official dbCAN image.

## Public Registry Contract

The public P0 package is:

```text
ghcr.io/fuqingzh/seqevi-dbcan@sha256:<digest>
```

The GitHub Container Registry package must be public so an ordinary setup does
not require `docker login`. A kit manifest always selects it by repository and
immutable digest. Tags may be published for human discovery, but setup never
uses a mutable tag such as `latest`.

An internal Harbor instance may cache or mirror the identical image for a
deployment. Its address is not embedded in the public kit, profile schema,
scientific identity or CLI. P0 adds no public registry-mirror option; a
restricted deployment may pre-load the exact image through its own deployment
automation.

Image publication requires:

- an SPDX or CycloneDX SBOM;
- `LICENSE` and `NOTICE` material for bundled components;
- correspondence between bundled binaries/packages and retrievable source;
- OCI source and revision labels linking the image to this repository;
- a recorded digest and reproducible build inputs.

## External Resource Contract

The dbCAN P0 resource contains exactly the result-bearing files:

```text
CAZy.dmnd
dbCAN.hmm
dbCAN-sub.hmm
fam-substrate-mapping.tsv
```

The caller supplies the directory containing these files through `--resource`
or an existing named profile. SeqEvi verifies the supported release, required
paths, sizes, SHA-256 values and native `seqevi.lock` semantics. It does not:

- download the database files;
- copy them into an XDG-managed directory;
- publish or redistribute them;
- interpret a biofetch manifest;
- search broad local or shared filesystems for them.

If the resource directory is writable and has no lock, the existing resource
contract may atomically create `seqevi.lock`. A valid read-only directory
remains supported: SeqEvi calculates the identity without requiring a write.
Published annotation containers mount the resource read-only.

Because SeqEvi does not distribute the four database files, database
redistribution permission is not an image-release gate. Public documentation
must still identify the exact supported upstream release and acquisition
prerequisite honestly.

## First-Party Kit Manifest

The wheel bundles one strongly validated first-party manifest for the P0 kit.
It fixes at least:

```text
ManifestSchemaVersion
KitID
Adapter
SupportedPlatform
SeqEviVersion
ImageReference
ImageDigest
ContainerExecutable
RuntimeComponents
ResourceRelease
ResourceComponents
Licenses
SmokeFixture
ExpectedSmokeContract
```

Each resource component records only its canonical relative path, expected byte
size and SHA-256. The manifest contains no resource URL, download destination,
database redistribution instruction, arbitrary command template or registry
credential.

Unknown fields, path traversal, duplicate resource paths, unsupported
platforms, mutable image references, invalid sizes and invalid digests are
errors. There is no mutable remote kit catalog or best-effort version fallback
in P0.

## Setup Lifecycle

Setup has one typed plan and human or versioned-JSON presentation:

```text
inspect -> resolve resource -> plan -> confirm -> pull if missing
        -> verify resource -> smoke -> publish profile
```

`--dry-run` stops after planning and is strictly read-only. `--json` changes
presentation only. Without `--yes`, setup displays the complete plan and asks
for one confirmation. `--yes` suppresses that confirmation but never weakens
validation.

The first-run decision table is fixed:

| Image | Resource | Result |
| --- | --- | --- |
| absent | supplied | pull exact digest, verify, smoke and publish profile |
| present | supplied | verify, smoke and publish profile without pulling |
| either | omitted in an interactive terminal | request the path before planning |
| either | omitted in non-interactive mode and no profile exists | fail before Docker or filesystem mutation |

When the target profile already exists, an omitted `--resource` reuses its
recorded path. An exact rerun is a no-op or repairs a missing image. Setup does
not report success for an image-only state that cannot annotate. A same-name
profile with different effective content is a conflict; setup never silently
rewrites it.

The profile is the final publication step after image, resource and smoke
identities pass. A failed setup leaves no usable-looking partial profile.

## Persistence And Reuse

Setup does not create a persistent annotation container. The durable state is:

- the exact image in Docker's content cache;
- one named profile under the existing XDG profile directory;
- the caller-owned resource at its original path;
- the selected Store outside the container.

Smoke and annotation each use a short-lived container. A later annotation uses
the profile without asking for the resource again. If the exact image was
removed from the local cache, execution may pull that same digest again. It
never downloads a database during annotation. If the resource path no longer
exists, the error reports the recorded path and an explicit setup repair
command rather than searching the filesystem.

## OCI Delegation

A profile v2.1 invocation delegates the complete annotation application
boundary to the compatible SeqEvi inside the image. The host does not model a
container as a fake local executable, and adapter runners do not gain Docker
branches.

The fixed runtime boundary is:

- FASTA and resource mounts are read-only;
- output, temporary work and an optional local Store mount are narrowly
  writable;
- the container runs with the caller's numeric UID/GID;
- the Docker socket, home directory and complete working directory are never
  mounted;
- local Store execution uses `--network none`;
- network is enabled only for an explicit shared HTTP(S) Store;
- credentials cross a redacted environment boundary and never appear in the
  profile, image metadata, argv or logs;
- one unique container is inspected and removed on success, failure, timeout
  and cancellation.

All Docker commands use argument arrays and `shell=False`.

## Identity And Compatibility

An OCI image digest is a distribution and supply-chain identity; it does not
replace scientific `ToolRuntimeDigest`. The adapter fingerprints the actual
result-producing runtime components inside the container. Managed and local
execution of the accepted kit must agree on:

- adapter contract and semantic parameters;
- `ToolRuntimeDigest` and `ResourceID`;
- hit/no-hit classification and normalized values;
- public DuckDB schema and provenance.

Profile v1 remains supported unchanged. Profile v2.1 adds one managed OCI
runtime without adding a user-facing adapter-contract version selector,
implicit current profile or silent upgrade.

## Readiness And Activation Gate

The dbCAN `5.2.9` direct-runtime parity and prerequisite merge gates have
passed. Slice B has also implemented the profile writer, digest pull, resource
verification, smoke and atomic publication. The remaining gates are:

1. a supported caller completes the real caller-mounted resource smoke against
   the immutable public digest;
2. OCI annotation delegation proves local-v1 versus managed-v2 parity.

Profile v1 remains authoritative for annotation until OCI delegation ships;
Slice B's setup smoke launches only a short-lived validation container and does
not make v2 annotation available.

## Non-Goals

- A generic package manager, downloader framework or plugin SDK.
- Database download, copying, redistribution or embedding.
- A site-profile hierarchy or cluster-specific CLI.
- A remote marketplace or arbitrary third-party kit execution.
- Mutable image tags, automatic kit upgrades or silent profile rewrites.
- Podman, Apptainer, Kubernetes, Slurm, WDL or Cromwell management in P0.
- A combined eggNOG/InterPro/dbCAN image or `setup all`.
- Cross-adapter result merging or changes to Store evidence identity.
