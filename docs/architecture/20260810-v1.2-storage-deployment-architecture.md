# Storage and Deployment Architecture

Version: v1.2
Date: 2026-08-10
Status: approved target architecture

This document supersedes
[v1.1](20260729-v1.1-storage-deployment-architecture.md). Its PostgreSQL,
artifact filesystem, process, authentication, endpoint, and Store-location
boundaries remain normative. This version changes only evidence calculation
coordination; it does not change deployment topology or add infrastructure.

## Claim Storage

Alembic `0003` adds `evidence_claim`, a separate ephemeral PostgreSQL or SQLite
table keyed by the same complete five coordinates as terminal evidence. It
stores canonical semantic parameters, opaque owner credential, monotonic
generation, expiry, and timestamps. Terminal evidence remains immutable in
`evidence`; no evidence status is added for work in progress.

Release marks a matching generation expired so subsequent acquisition advances
generation. Finalization and legacy terminal commit retire matching claim rows
because terminal evidence prevents reacquisition. Operational residue means no
active unexpired leases; after terminal publication the matching row is absent.

## Transaction and Lock Order

All multi-key claim mutations sort complete EvidenceKeys canonically and return
results in caller order. PostgreSQL locks or retires claims before inserting
terminal evidence, and legacy commit uses the same order as claimed finalize.
SQLite shares that logical order under its single writer lock. Time is sampled
per item after the applicable writer or row lock so waited-on authority cannot
be returned or mutated after expiry.

After all bounded-batch lock waits and validation, successful acquire and
renew operations refresh every returned lease immediately before transaction
commit. PostgreSQL acquire also rechecks terminal evidence at that boundary,
retiring a claim and returning cached metadata when terminal truth appeared
during the transaction. Every PostgreSQL claim mutation and legacy commit
takes the same transaction-scoped advisory lock for each complete EvidenceKey
in sorted unique signed-lock-ID order, including when neither a claim nor
evidence row exists. Legacy and claimed publication then use one shared-row
phase order: claims, sequences, artifacts, evidence.

Finalization consumes the exact unexpired owner and generation in the same
transaction that inserts or verifies immutable evidence. A rollback restores
the claim. Legacy commit first retires any matching claim and then inserts or
verifies terminal evidence, so an old client remains scientifically correct
and any claim-capable calculator subsequently observes lost authority.

## Service Compatibility

Existing deployment, authentication, `/health`, lookup, fetch, artifact, and
commit endpoints are unchanged. Dedicated versioned claim endpoints are
additive. Capability HTTP 404 alone selects legacy fallback; authentication,
authorization, transport, and server failures remain errors. Claim requests
are strict and bounded to 1,000 or the lower configured client/service limit.
No Redis, scheduler, new daemon, or Store-location configuration is introduced.
