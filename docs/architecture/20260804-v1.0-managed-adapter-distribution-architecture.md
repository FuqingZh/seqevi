# Managed Adapter Distribution Architecture

Version: v1.0
Date: 2026-08-04
Status: superseded proposal; never implemented
Initial kit: `dbcan-cazyme`

Superseded by the
[v1.1 managed distribution architecture](20260805-v1.1-managed-adapter-distribution-architecture.md),
which keeps databases caller-supplied and selects a public GHCR runtime image.

## Purpose

This document defines the future product-edge layer that can take a new
GitHub/PyPI user from an installed SeqEvi CLI to a working, verified annotation
runtime. It does not change the current SeqEvi v1 boundary: today, annotation
tools and resources remain user-supplied external dependencies.

The target common path is:

```bash
pipx install seqevi
seqevi setup dbcan-cazyme --yes
seqevi annotate \
  --profile dbcan-cazyme \
  --fasta proteins.faa \
  --output dbcan.duckdb
```

`seqevi setup` is not implemented in the current repository. This document
remains proposed until the readiness gates pass and it is activated together
with the profile v2 contract and repository product-boundary guidance. That
activation authorizes implementation; it does not claim that the CLI is
available. Setup becomes shipped behavior only after its implementation, tests
and release artifacts pass the public release gate.

## Boundary

Managed onboarding is a first-party distribution edge around the existing
scientific contracts. It must not become part of the evidence domain model.

| Owner | Responsibility |
| --- | --- |
| SeqEvi core | sequence identity, adapter contracts, Store reuse, result publication and profile selection |
| scientific adapter | invoke one supported upstream tool contract and validate adapter-native output |
| distribution edge | kit manifest, setup planning, OCI/resource staging, smoke validation and profile publication |
| release publisher | build, verify and publish immutable images, manifests, SBOMs and notices |
| resource publisher | host upstream database files identified by immutable size and digest |

The distribution edge may depend on core contracts. Core adapters, Stores and
DuckDB results must not import distribution, Docker or download concepts.
SeqEvi has no runtime dependency on biofetch. Release automation may use
biofetch or another publisher tool to prepare manifest inputs, but public setup
consumes only the bundled SeqEvi kit manifest.

## P0 Platform And Kit

P0 supports exactly:

- Linux on `amd64`;
- Docker Engine;
- `dbcan-cazyme` protein annotation;
- dbCAN `5.2.9` and DIAMOND `2.1.15`;
- resource release `db_v5-2-9_5-5-2026`;
- one digest-pinned SeqEvi-managed runtime image;
- local POSIX Store or an explicit HTTP(S) shared Store.

Docker Engine is a host precondition. SeqEvi setup does not install a container
engine, modify operating-system packages, invoke `sudo`, or install dbCAN and
DIAMOND into the caller's host Python environment.

The image is built from the supported official dbCAN release. It is not an
upstream-official dbCAN image and must not be described as one. Public image
publication requires an explicit redistribution/license review, SBOM and
license/NOTICE artifacts.

The image contains the compatible SeqEvi release, dbCAN runtime, DIAMOND,
Python and locked result-bearing dependencies. It does not contain annotation
databases. A kit always refers to the image by repository plus immutable
digest, never by a mutable tag such as `latest`.

## Resource Publication

The dbCAN P0 resource contains only:

```text
CAZy.dmnd
dbCAN.hmm
dbCAN-sub.hmm
fam-substrate-mapping.tsv
```

Each manifest entry records the canonical destination, source URL, byte size
and SHA-256. Setup downloads into a recognizable incomplete directory, verifies
all declared content, creates the native `seqevi.lock`, and only then publishes
the versioned resource directory atomically.

Annotation never downloads a resource. Published resources are mounted
read-only. CGC, PUL, SignalP, DeepTMHMM and other non-protein-only assets are
outside the initial kit.

## Kit Manifest

The wheel bundles a strongly validated manifest for each supported kit. The P0
manifest fixes at least:

```text
ManifestSchemaVersion
KitID
Adapter
SupportedPlatform
SeqEviVersion
ImageReference
ImageDigest
ContainerExecutable
RuntimeComponents
ResourceRelease
ResourceFiles
DownloadBytes
ExpandedBytes
Licenses
SmokeFixture
ExpectedSmokeContract
```

Unknown fields, path traversal, duplicate resources, unsupported platforms,
mutable image references, invalid sizes and invalid digests are errors. There
is no remote mutable kit catalog or best-effort version fallback in P0.

## Plan And Apply Lifecycle

Setup has one typed plan and two presentations: human and versioned JSON.

```text
inspect -> plan -> confirm -> pull -> stage -> lock -> smoke -> publish
```

`--dry-run` stops after planning and is strictly read-only. It may inspect the
manifest, platform, Docker access, disk budget and existing state. It must not
pull, download, create directories or locks, run a smoke, or publish a profile.

Apply uses the same plan. `--yes` suppresses confirmation but does not weaken
validation. A profile is the final publication step, after the exact image,
resource lock and smoke identities pass. Therefore no failed setup can leave a
usable-looking profile pointing at partial state.

An exact rerun is a no-op or resumes verified staging. A same-name profile with
different effective content is a conflict; setup never overwrites it. A new
kit uses a new `KitID` and, when desired, an explicit side-by-side profile name.

## OCI Delegation

A profile v2 invocation delegates the complete annotation application boundary
to the compatible SeqEvi inside the image. The host does not model a container
as a fake local executable and adapter runners do not gain Docker branches.

The fixed boundary is:

- FASTA and resource mounts are read-only;
- output, temporary work and an optional local Store mount are narrowly
  writable;
- the container runs with the caller's UID/GID;
- the Docker socket, home directory and complete working directory are never
  mounted;
- local Store execution uses `--network none`;
- network is enabled only for an explicit shared HTTP(S) Store;
- credentials cross a redacted environment boundary and never appear in the
  profile, image metadata, argv or logs;
- one unique container is inspected and removed on success, failure, timeout
  and cancellation.

All Docker commands use argument arrays and `shell=False`.

## Identity And Compatibility

An OCI digest identifies a distributed artifact; it does not replace the
scientific `ToolRuntimeDigest`. The adapter still fingerprints actual
result-producing runtime components inside the container. Managed and local
execution of the same accepted kit must agree on:

- adapter contract and semantic parameters;
- `ToolRuntimeDigest` and `ResourceID`;
- hit/no-hit classification and normalized values;
- public DuckDB schema and provenance.

Profile v1 remains supported unchanged. Profile v2 does not select a mutable
current kit and is never silently upgraded. Internal adapter contract revisions
remain provenance/cache details rather than ordinary user-facing selectors.

## Readiness And Activation Gate

Implementation must not begin until:

1. direct dbCAN `5.2.9` parity passes with the exact four-file resource;
2. public image redistribution and license obligations are reviewed;
3. the proposed profile v2 contract is accepted;
4. the repository product-boundary guidance is updated in the same accepted
   change that starts managed implementation.

Until then, the current v1 rule remains authoritative: users supply external
executables and resources, and `seqevi setup` is unavailable.

## Non-Goals

- A generic package manager, downloader framework or plugin SDK.
- A remote marketplace or arbitrary third-party kit execution.
- Databases embedded in wheels or images.
- Mutable tags, automatic upgrades or silent profile rewrites.
- Podman, Apptainer, Kubernetes, Slurm, WDL or Cromwell management in P0.
- A combined eggNOG/InterPro/dbCAN image or `setup all`.
- Cross-adapter result merging or changes to Store evidence identity.
