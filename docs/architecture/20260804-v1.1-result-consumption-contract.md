# SeqEvi v1.1 Result Consumption Contract

> Status: approved target architecture
> Contract version: 1.1
> Date: 2026-08-04
> Supersedes: output-package sections of the 2026-07-20 v1.0 architecture and adapter contracts

## Purpose

This contract defines the delivery object for one successful annotation
invocation. The evidence Store remains the incremental cache; this document
defines only the immutable snapshot returned to a caller.

The result is one self-describing DuckDB database. It is intended to be opened
by Python, SQL, R, notebooks, or an external workflow without first learning
SeqEvi's internal artifact filenames.

## Boundary And Invariants

1. One invocation uses exactly one adapter and produces one new `.duckdb` file.
2. The file is a complete snapshot of the requested FASTA, including cached and
   newly computed evidence. Computation is incremental; result materialization
   is not an append operation.
3. The result never participates in the Store `EvidenceKey`. Rewriting a
   delivery file cannot change scientific evidence identity.
4. Adapter-native evidence stays physically and logically separate. There is
   no universal eggNOG/InterPro/dbCAN ontology table.
5. A successful no-hit remains visible through the sequence map and the
   `annotations` view; it is not represented by a missing input row.
6. The output path is published atomically and an existing path is rejected.

## Database Layout

The `main` schema contains exactly four public relations:

| Relation | Kind | Row grain |
| --- | --- | --- |
| `annotations` | view | one row per input record and matching adapter evidence row; one null-evidence row for a no-hit input |
| `sequence_map` | table | one row per FASTA record, in input order |
| `evidence` | table | selected adapter's native normalized hit-row grain |
| `no_hits` | view | one row per unique `SequenceID` with terminal `no_hit` |

`sequence_map` columns are fixed and ordered as follows:

```text
InputOrder, InputID, InputHeader, SequenceID, MD5, Length,
EvidenceStatus, EvidenceSource
```

`evidence` starts with `SequenceID`, followed by the adapter's native
normalized fields. The adapter may retain one-to-many rows, such as multiple
Pfam domains for one protein. It must not reuse the eight common column names.

`annotations` presents the eight `sequence_map` columns first, followed by the
adapter fields. It is a left join on `SequenceID`:

```sql
SELECT sequence_map.*, evidence.<adapter-columns>
FROM main.sequence_map AS sequence_map
LEFT JOIN main.evidence AS evidence USING (SequenceID)
```

The view therefore has direct `InputID` joins for normal consumers while
retaining `SequenceID` as the content identity used by cache reuse and audit.
Two input IDs sharing one sequence receive the same evidence rows. A no-hit
input receives one row with null adapter fields. Consumers that need one row
per protein must aggregate a one-to-many adapter relation explicitly.

## Self-Description

The private `_seqevi` schema is part of every successful result. It is not a
second consumer-facing result format; it is the catalog needed to discover the
first-party relations without memorizing their columns.

| Table | Required content |
| --- | --- |
| `metadata` | one row of result, adapter, runtime, resource, input and creation identities |
| `semantic_parameters` | one row per canonical semantic parameter and its JSON value |
| `table_info` | relation name, kind, row grain, join key, row count and description |
| `column_info` | relation, ordinal, column name, DuckDB type and description |
| `run_metrics` | one row containing the invocation metrics as canonical JSON |

Invocation metrics include `existing_finalizations`, the number of proposed
terminal records whose ClaimSession finalization observed immutable evidence
already finalized by a peer. Older managed-runtime payloads that omit this
additive metric deserialize it as zero. It does not alter `computed` or
`cache_hits` provenance.

`_seqevi.metadata` contains at least:

```text
ResultFormatVersion, ResultSchemaID, SeqEviVersion, Adapter,
AdapterContractVersion, UpstreamTool, UpstreamToolVersion,
ToolRuntimeDigest, ResourceID, InputDigest, CreatedAt
```

The result format identifier is `seqevi-duckdb/1`. Initial adapter-facing
schema identifiers are:

```text
eggnog-mapper/2
interproscan-pfam/5
dbcan-cazyme/5
```

`ResultSchemaID` describes the upstream-facing normalized schema family.
`AdapterContractVersion` remains the internal parser/cache contract. A caller
does not need to translate an upstream version into an internal contract ID to
read a result.

DuckDB table and column comments may be present for IDEs that display them, but
`_seqevi.table_info` and `_seqevi.column_info` are the stable discovery API.

## Versioning And Compatibility

The file format and public relation schemas are versioned independently from
the Store evidence key:

- `ResultFormatVersion` changes when the database layout or publication rules
  change incompatibly.
- `ResultSchemaID` changes when an adapter's normalized public fields or row
  grain change.
- `AdapterContractVersion` changes when parsing, hit/no-hit semantics,
  linkage, or evidence meaning changes.

SeqEvi 0.2.0 is pre-1.0 and intentionally has one canonical output format. The
old directory Data Package is not a second output mode. A future reader may
support older `ResultFormatVersion` values, but a writer never silently
downgrades a result.

## Publication Rules

The writer creates a sibling staging file using DuckDB storage compatibility
`v1.0.0`, writes all tables and views, populates the `_seqevi` catalog, and
executes row-count/schema/provenance probes. It then checkpoints and closes
the writer, reopens the staged file read-only, runs the same probes, and uses
`os.replace()` to publish the requested path. A failed invocation cannot expose
a partial file.

The Slice A prototype exercised relation construction and catalog discovery in
memory and in a temporary file. The Slice B writer now implements the atomic
publication and file-backed artifact transfer rules above. Slice C exposes the
same boundary through `seqevi.annotate`, `seqevi.scan_annotations`, and the
delegating CLI; Slice D removes the obsolete directory writer.

## Consumer Discovery Example

No generated `seqevi.columns` constants are required:

```python
import duckdb
import seqevi

annotations = seqevi.scan_annotations("annotations.duckdb")
print(annotations.columns)
print(duckdb.sql("DESCRIBE SELECT * FROM 'annotations.duckdb'.main.annotations"))

with duckdb.connect("annotations.duckdb", read_only=True) as db:
    print(db.table("_seqevi.column_info").filter("RelationName = 'annotations'"))
```

The native relation API supplies projection, filtering, joins, lazy execution,
and export methods. The catalog supplies names and descriptions when the user
does not yet know the adapter's exact columns.
