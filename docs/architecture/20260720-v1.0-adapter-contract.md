# Adapter Contract

> Status: approved target architecture
> Contract version: 1.0
> Date: 2026-07-20

## Purpose

An adapter connects SeqEvi's exact cache protocol to one external annotation
tool. It defines scientific identity, tool invocation, raw-output validation,
thin normalization, and output package resources. It does not install tools,
download databases, schedule infrastructure, or merge another adapter's schema.

V1 ships only explicit first-party adapters. There is no dynamic plugin loading
or arbitrary command template.

## Adapter Responsibilities

Each adapter must provide:

1. A stable adapter name and `AdapterContractVersion`.
2. Validation of adapter-specific configuration and accepted residues.
3. An immutable `ToolRuntimeDigest`.
4. An immutable `ResourceID` for the exact annotation database.
5. Canonical `SemanticParameters`, including explicit defaults.
6. A deterministic input FASTA for cache-miss sequences.
7. A structured external command specification.
8. Validation of process status and primary raw output.
9. Thin normalization into adapter-specific Parquet resources.
10. Classification of every input sequence as `hit` or `no_hit`.
11. Data Package resource schema and provenance fields.

An adapter cannot infer missing version information. If the runtime or resource
identity cannot be proven, annotation fails before Store lookup or execution.

## External Runtime Boundary

SeqEvi invokes a user-supplied executable or container environment. The adapter
accepts the runtime location through explicit configuration, but the location is
not itself scientific identity. Identity is the resolved immutable digest.

The public `annotate` command accepts concrete local inputs as `--executable`
and `--database`. An adapter probes those locations before Store lookup and
derives `ToolRuntimeDigest` and `ResourceID`; paths themselves never enter the
evidence key.

An exact database root may contain a SeqEvi-owned `seqevi.lock`. The lock stores
canonical relative component paths, sizes and SHA-256 values. Normal annotation
validates the lock and file metadata without rereading large file contents;
`seqevi resource verify` performs a full content audit. A locked database root
is immutable: a mismatch fails and is never refreshed in place. New database
content is published in a new versioned directory. Upstream database tools and
formats do not depend on or interpret this lock.

The internal tool runner is a small semantic boundary built on Python process
APIs. It must support:

- argument lists with `shell=False`;
- explicit working directory and environment overlay;
- separate stdout and stderr artifact paths;
- timeout enforcement while the process is running;
- process-group termination on timeout or cancellation;
- exit status, timestamps, and resource identity in a structured run result.

SeqEvi does not depend on `axiomkit.run_cmd`: its current behavior does not cover
the required working-directory, environment, stream, timeout, and process-group
contract. This runner remains private to SeqEvi and is not a new generic process
execution library.

## Third-Party Input and Output

Adapters should accept the upstream tool's native database layout and primary
machine-readable output as directly as practical. SeqEvi does not require users
to pre-convert a database into a private format.

For each successful cache-miss batch, the Store retains:

- one compressed primary third-party output;
- the adapter-specific normalized evidence artifact;
- immutable provenance and digests needed to reproduce the evidence contract.

The Store does not retain temporary search indexes, working directories, or
ordinary stdout/stderr logs as scientific evidence. A failure may expose logs in
the invocation output for diagnosis, but no evidence key is committed.

Adapters parse native text outputs as streams, validate rows before exposure,
and write fixed-size row batches to temporary Parquet parts. Polars lazy scans
sort and sink those parts into the normalized artifact. Orchestration and Store
boundaries carry stable file references with media type, size, digest, and
ownership lifetime; they do not carry complete artifact bytes.

## Thin Normalization Rules

Normalization exists to make cache lookup and Parquet output reliable, not to
invent a cross-tool ontology.

Adapters must:

- preserve the third-party row grain;
- preserve original column names and meanings where Parquet permits;
- add canonical `SequenceID` linkage;
- normalize only required scalar types, null values, and invalid encodings;
- document any derived or renamed field;
- keep adapter outputs physically and logically separate.

Columns with the same name in different adapters are not assumed equivalent.
SeqEvi never horizontally merges eggNOG and InterPro/Pfam evidence.

## Official Adapter: eggNOG-mapper

The `eggnog` adapter runs eggNOG-mapper in protein mode against a user-supplied
eggNOG database.

Contract requirements:

- `ToolRuntimeDigest` identifies the exact eggNOG-mapper runtime;
- `ResourceID` identifies the exact eggNOG database release and content;
- semantic parameters include all search mode, taxonomic scope, sensitivity,
  orthology, and output-affecting options;
- the primary annotation table remains the source schema;
- `seed_ortholog` is evidence about a match, not the input protein's UniProt ID;
- transferred `PFAMs` remains auxiliary eggNOG evidence.

The adapter does not expose DIAMOND as a separate SeqEvi adapter even when
eggNOG-mapper uses DIAMOND internally.

The initial `eggnog/1` contract accepts eggNOG-mapper 2.x only and validates the
canonical 21-column annotations header. Its runtime identity covers the launcher,
installed `eggnogmapper` package files, selected DIAMOND executable and normalized
mapper/DIAMOND versions. Generated bytecode and installation paths are excluded.
The three required upstream database files (`eggnog.db`, `eggnog.taxa.db`, and
`eggnog_proteins.dmnd`) are hashed into the resource identity. Other major
mapper/database generations require a new contract instead of heuristic column
compatibility.

## Official Adapter: InterProScan Pfam

The `interpro-pfam` adapter runs InterProScan with the Pfam application selected,
equivalent to an explicit `-appl Pfam` contract. It performs direct sequence
scanning and is authoritative for SeqEvi Domain/Pfam evidence.

Contract requirements:

- `ToolRuntimeDigest` identifies the exact InterProScan runtime;
- `ResourceID` identifies the bundled InterPro/Pfam data release;
- semantic parameters include application selection and every result-affecting
  execution option;
- native TSV row grain for domain matches is retained;
- sequence MD5 from InterProScan is verified against SeqEvi canonical input;
- no precomputed remote lookup is silently mixed into a local direct-scan
  contract when `--disable-precalc` is declared.

InterProScan `5.77-108.0` emits the complete 15-column native TSV layout. The
final GO and pathway columns remain present as `-` placeholders when those
features are disabled. The v1 adapter validates both placeholders and excludes
them from normalized evidence; non-empty values require a different semantic
contract rather than silent acceptance.

HMMER remains an InterProScan/Pfam implementation detail rather than a separate
v1 adapter.

For this adapter, `--database` is the exact official InterProScan `data/`
directory. The runtime digest uses the same path-independent component contract
to cover the reported InterProScan release, launcher, runtime JAR, and bundled
HMMER files. The resource identity records the
InterPro/Pfam release coordinate and SHA-256 of the exact configured
`pfam_a.hmm` model.

The native TSV run-date column is validated but excluded from normalized
evidence and per-sequence payload digests because it is operational metadata.
The complete native TSV is retained as the compressed raw artifact.

## Semantic Parameters

Adapters define a typed semantic-parameter model. Every result-affecting default
is materialized before hashing. Operational values that do not affect scientific
results, such as temporary directory, thread count, output path, retry count, or
log verbosity, are excluded.

Changing CPU count must not invalidate evidence if the upstream tool guarantees
identical semantics. Changing an e-value threshold, taxonomic scope, search mode,
or enabled application must invalidate evidence.

Each adapter maintains tests that classify every supported option as semantic or
operational. Unclassified tool options are rejected rather than omitted from the
key.

## Adapter Contract Versioning

Increase `AdapterContractVersion` when a change can alter any of:

- interpretation of raw rows;
- hit/no-hit classification;
- sequence-to-result linkage;
- normalized evidence semantics or row grain;
- output fields relied on by consumers.

A parser bug fix may therefore require a new adapter contract even when the tool
and database are unchanged. If retained raw output is sufficient, SeqEvi may
reparse it under the new adapter contract without rerunning the external tool.
That is an explicit compatibility path, never an automatic assumption.

## Output Package

Each successful `annotate` invocation writes an adapter-specific directory:

```text
evidence.parquet
sequence-map.tsv
no-hits.parquet
datapackage.json
```

- `evidence.parquet` contains only the selected adapter's normalized hit rows.
- `sequence-map.tsv` links all input records to canonical identities and status.
- `no-hits.parquet` contains sequences with a successful terminal `no_hit` state.
- `datapackage.json` follows Data Package v2 and carries a versioned `seqevi`
  extension for evidence provenance.

`rejected.tsv` is emitted only as a failed-invocation diagnostic. It is not part
of a successful Data Package.

The descriptor records at least adapter contract, runtime digest, resource ID,
semantic parameters, input digest, resource schemas, row counts, artifact
digests, creation time, and SeqEvi version.

## Atomicity and Determinism

The adapter processes a deterministic, SequenceID-ordered cache-miss FASTA. It
must account for every requested sequence exactly once as hit or no-hit.

Raw validation and normalized validation complete before Store commit. Store
artifacts are content-addressed and promoted atomically. A process crash may
leave removable temporary files but cannot expose a partial evidence record.

When two executions produce the same exact evidence key, their normalized
scientific payload must agree. A mismatch is a reproducibility/integrity error,
not a last-writer-wins update.

Scientific equality is defined by canonical payload content. Different Parquet
compression, row groups, or writer metadata may produce different artifact
digests without creating an evidence conflict when the canonical payload digest
is unchanged. The first committed artifact reference remains authoritative for
that evidence key.

## Adapter Acceptance

An official adapter is complete only when it has:

- a frozen contract version and semantic parameter model;
- runtime and resource identity probes;
- a direct-tool parity fixture;
- hit, no-hit, malformed-output, timeout, and cancellation tests;
- deterministic normalization tests;
- Data Package schema tests;
- local and shared Store parity tests.
