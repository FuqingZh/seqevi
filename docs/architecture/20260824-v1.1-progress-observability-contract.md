# Annotation Progress Observability Contract

> Status: approved target architecture; implemented in current source
> Contract version: 1.1
> Date: 2026-08-24

## Scope

One `seqevi annotate` invocation presents truthful, width-aware human progress
on a capable interactive terminal. The display answers what SeqEvi is doing,
how many unique input sequences have terminal evidence, what fraction of that
exact work is ready and how long the complete invocation has been running.

This contract applies to local eggNOG-mapper, dbCAN and InterProScan/Pfam
orchestration. Managed OCI remains an outer liveness envelope because the
parent process does not receive the inner Store transitions. SeqEvi still
accepts one FASTA per invocation; input scheduling and cross-process progress
aggregation remain outside the product boundary.

This document supersedes the implemented opt-in presentation in
[v1.0](../archive/architecture/20260824-v1.0-progress-observability-contract.md).

## CLI And Stream Contract

The human CLI surface is:

```text
seqevi annotate ...                # automatic on capable interactive stderr
seqevi annotate ... --progress     # explicit enablement; retained spelling
seqevi annotate ... --no-progress  # explicit disablement
seqevi annotate ... --json         # always disables human progress
```

Dynamic progress is enabled only when progress has not been disabled, stderr
is an interactive terminal, `TERM` is not `dumb` and `--json` is absent. An
explicit `--progress` does not force cursor control into an incapable stream.
Non-TTY, dumb-terminal and JSON execution remain progress-free.

The live display is transient stderr output. It is cleared before the durable
human success summary on stdout or the existing error presenter runs. After
successful CLI parsing, `--json` continues to emit exactly one success document
on stdout or one typed application-error document on stderr. Human progress
and summary text are not stable machine formats.

## Exact Work Meaning

The only invocation-level ratio is:

```text
unique sequences with terminal evidence / unique input sequences
```

The label is `Unique sequences`, matching the final summary. Duplicate FASTA
records with identical sequence content share one SequenceID and one unit in
the denominator.

A SequenceID becomes ready only when Store lookup establishes terminal
evidence or local/peer computation has been finalized to the Store. A miss,
claim acquisition, upstream process exit or uncommitted parse does not advance
the ratio. Readiness is monotonic, identity-deduplicated and never greater than
the denominator.

When exact work is not available, the event and display carry no ratio. Active
tool batches remain indeterminate even when SeqEvi knows their batch number and
size. SeqEvi does not parse adapter logs or infer subprocess completion from
sequence count.

## Presentation Contract

The full layout contains the active phase, total invocation elapsed time, a
bar, exact `completed/total` counts and a percentage derived from those same
values. A narrow terminal drops the bar first and retains active work, exact
counts, percentage and elapsed time on one line. Color is never the only state
signal.

Elapsed time uses one monotonic clock from application entry through Store
teardown, result publication and validation. No phase duration, throughput or
ETA is displayed.

After readiness reaches 100%, later packaging or validation is represented by
its active indeterminate phase rather than a retained completed bar. On
success, the cleared live region is replaced by a durable summary of this
form:

```text
✓ Annotated 2,729 unique sequences in 13m27s (1,920 cached, 809 computed); output: RESULT
```

On typed failure, untyped failure or interruption, the live region is cleared
and terminal state is restored. The existing error text and exit code remain
the only durable failure authority.

## Private Event Boundary

The private immutable event model separates cumulative evidence work from
phase-local batch metadata:

```python
@dataclass(frozen=True, slots=True)
class WorkProgress:
    completed: int
    total: int
    unit: ProgressUnit


@dataclass(frozen=True, slots=True)
class BatchProgress:
    number: int
    size: int


@dataclass(frozen=True, slots=True)
class ProgressEvent:
    phase: ProgressPhase
    state: ProgressState
    message: str
    evidence_ready: WorkProgress | None = None
    batch: BatchProgress | None = None
```

Construction rejects negative or over-complete work and non-positive batch
metadata. Annotation orchestration owns semantic state only; it does not own
clocks, terminal width, Rich objects or formatting. The CLI owns presentation
and lifecycle. The model remains private: there is no package export, public
callback or serialization schema.

The application boundary emits finalization across local Store teardown and
result re-open, or managed-result validation. Managed OCI emits only outer
liveness and never fabricates an internal ratio.

## Failure And Compatibility

Progress sink and renderer failures are logged and contained. They cannot
change adapter commands, upstream stdout/stderr files, evidence computation,
Store mutation, claim coordination, result publication, cancellation, timeout
or process cleanup.

This successor changes the direct interactive-terminal default and adds Rich
as a direct CLI runtime dependency. It does not change EvidenceKey,
ToolRuntimeDigest, ResourceID, batch size, DuckDB schema, JSON documents,
scientific results or the public Python API. Existing `--progress` commands
remain valid; users can recover the prior quiet interactive behavior with
`--no-progress`.

The following remain deferred until a concrete consumer and compatibility
contract exist:

- input manifests or multi-input scheduling;
- `progress watch`, JSONL progress or another public protocol;
- heartbeat/stale-process classification and cross-process aggregation;
- adapter-native progress parsing or managed inner-event forwarding; and
- ETA without representative benchmark evidence.
