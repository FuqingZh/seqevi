# Storage Deployment Architecture

Version: v1.7

Date: 2026-08-30

Status: superseded by [v1.8](20260831-v1.8-storage-deployment-architecture.md); retained R1 contract

Supersedes: [v1.6](20260814-v1.6-storage-deployment-architecture.md)

This revision retains v1.6 schema revision 0004, maintenance, deployment,
private-network access, synchronous public APIs, legacy compatibility,
ClaimSession fencing and reconciliation, download verification, reader/resolver
subprocess ownership, and deterministic Store shutdown. It changes only the
ClaimSession upload/finalize timing boundary and service upload I/O described
below. No Registry, database migration, or production cutover is introduced.

## Staging Before Metadata Finalization

One public `finalize_many()` remains one admitted transport operation. It
validates duplicate keys, exact claims and conflicting artifact metadata, then
stages all unique uncached artifacts through the existing digest-addressed PUT.
Each artifact has one fixed 900-second monotonic absolute staging deadline;
each HTTPX connect/read/write/pool phase has a timeout of at most 60 seconds,
clamped to the remaining total time. A phase timeout is not a rolling
minimum-throughput measurement. These are private protocol defaults, not new
public constructor or CLI options. Legacy non-session requests retain their
existing timeout behavior.

Artifacts are sequential; the whole call can therefore take up to the sum of
their individual budgets, followed by metadata finalization and cleanup.
Heartbeat renewal remains active on the independent session path. Before each
artifact and again after staging, closed/lost sessions stop finalization. Loss
during an in-flight PUT may leave staged bytes; it cannot authorize evidence.
R1 does not proactively abort that PUT merely because heartbeat loss is observed.

Only after staging does the caller capture fresh authority and start one
metadata deadline: the earlier of 30 seconds from that point or the current
renewal deadline. All split metadata batches share it. Mutations end one second
before it to reserve reconciliation; lookup/authority reconciliation uses the
original metadata deadline. Neither upload nor batch splitting resets this
metadata budget. The service's database authority/fencing checks remain final.

A successful PUT is not an evidence commit. R1 adds no automatic PUT retry,
readback route, partial-upload resume, or interruption/restart recovery promise.
A later invocation can PUT identical bytes safely. Existing cached successful
uploads may be reused within an HttpEvidenceStore; finalization still verifies
storage and metadata. Missing/corrupt content must fail, not create evidence.

## Service Filesystem Ownership

Async PUT consumes network chunks on the event loop, but mkdir, existing-file
hash verification, writes/hashing, flush/fsync, link, close, and unlink run off
that loop. The service admits at most eight concurrent artifact writers by
default, configurable with `SEQEVI_MAXIMUM_CONCURRENT_ARTIFACT_UPLOADS` (1–64).
Each admitted writer submits at most one filesystem operation at a time and
waits for it before consuming the next chunk. The semaphore limits SeqEvi
artifact work, not other users of the loop's shared default executor. It is
not a disk reservation, partial-upload quota, or independent worker pool.
It also does not bound arbitrary clients' body-idle or queue time: a stalled
client can retain a slot. Only the first-party ClaimSession client has the
staging deadlines above. Slow-client availability limits remain a separate
service/ingress obligation, not an R1 guarantee.

Cooperative cancellation, including repeated cancellation, drains admitted I/O
and closes/unlinks temporary files before releasing the slot or returning.
The first operation/cancellation error remains primary; cleanup failures remain
observable as exception notes. There is no detached cleanup owner. An
uninterruptible filesystem operation may delay cancellation indefinitely;
R1 does not claim a hard deadline or timely completion while the kernel blocks.
Host hard kill can leave temporary files and is not cooperative cancellation.

Publication retains exact size and SHA-256 verification, file fsync, hard-link
publication and directory fsync. If directory fsync fails after linking, a
visible target can remain; only the temporary file is cleaned. Subsequent PUT
revalidates the existing target. No success is returned for the failed attempt.
An existing-target or concurrent-publication PUT performs its own directory
sync after verifying the bytes; it does not borrow an unobserved peer's sync.

## Diagnostics And Integrity Limits

Client upload errors retain their original cause and expose phase, digest,
declared bytes, elapsed/remaining time, request ID, HTTP status when available,
and a bounded exception-type chain. Arbitrary exception messages, URLs,
credentials and response bodies are excluded from this display. The existing
service logger emits `seqevi.artifact_request` records with operation/phase,
duration, outcome, status and exception type. A client `X-Request-ID` is reused
only if it is 32 lowercase hexadecimal characters; otherwise the service
generates an ID. Existing response models and `/health` fields are unchanged.
The redaction guarantee applies to the normal CLI error text and structured
service record, not arbitrary traceback rendering by library callers. The
programmatic cause is retained for diagnosis and may contain sensitive text;
callers must not publish raw chained tracebacks without their own redaction.

Full-file verification on existing objects, metadata finalize and downloads
remains in R1. The short finalize can consequently still fail on slow reads.
Removing that read requires a trusted verified-storage record and immutable
storage boundary; digest filenames or byte size alone are insufficient proof.
This is a later R2 obligation, not an R1 performance guarantee.

The 512 MiB advertised value remains an admission ceiling in R1. Synthetic
local transfer evidence does not establish the planned 1 MiB/s interrupted-link
envelope, OCI retention, target-filesystem durability, or production repair.
See the [execution plan](../implementation-plan/20260829-v1.0-artifact-upload-finalization-boundary-implementation-plan.md)
for those gated obligations and the original incident's diagnostic limits.
