# Storage Deployment Architecture

Version: v1.6

Date: 2026-08-14

Status: superseded by [v1.7](20260830-v1.7-storage-deployment-architecture.md)

Supersedes: [v1.5](../archive/architecture/20260813-v1.5-storage-deployment-architecture.md)

SeqEvi retains the v1.5 revision-0004 schema, sweepers, SQLite teardown and
target resolution, fencing, migration, preservation, deployment, private HTTP
runtime, cancellation, resolver, artifact-reader, and resource-ownership
contracts.

For an acknowledged existing revision-0002 Store, the public maintenance
surface exposes a bounded, identity- and revision-bound 0002-to-0003
preparation and its 0003-to-0002 rollback. These transitions use the same
canonical SQLite target binding or bounded PostgreSQL maintenance acquisition,
advisory lock, table fence, commit classification, and fresh readback rules as
the 0004 path. They never advance to 0004. The separately acknowledged
0003-to-0004 command remains mandatory; ordinary service startup is not an
operator migration procedure. The exact sequence and stop gates are defined in
the [v1.2 maintenance runbook](../operations/20260818-v1.2-claim-session-store-maintenance.md).

PostgreSQL ClaimSession maintenance has two independent fixed 60-second
monotonic budgets. The mutation/fence deadline starts once for the maintenance
operation; the post-commit reconciliation deadline starts separately and does
not borrow unused mutation time. Before every PostgreSQL maintenance
connection acquisition, including the initial mutation/fence connection and a
fresh reconciliation readback after invalidation, the private acquisition
boundary computes the positive remainder of that phase's original absolute
deadline. The normal CLI creates and owns a fresh `Engine` immediately before
maintenance. The private boundary fails before installing temporary listeners
if that Engine already has an instance-local SQLAlchemy `checkout` or
`do_connect` listener; arbitrary application hook execution is outside this
maintenance-only contract. SQLAlchemy's own first-connect dialect
initialization remains inside the boundary. Waiting for acquisition
serialization and SQLAlchemy pool checkout
is charged to that remainder. Pool checkout uses the lesser of the pool's
existing timeout and the positive remainder, so a stricter existing internal
limit is never relaxed; the remainder is recomputed immediately before
checkout after temporary listener setup. Any new physical psycopg connection
receives a `connect_timeout` clamped to a positive whole-second value no greater
than the usable remainder and no lower than libpq's effective two-second
minimum; an interval too short to represent fails before physical connect. An
unset or zero configured value is replaced rather than preserving an unbounded
connect.
After target resolution and immediately before `dialect.connect()`, the private
boundary rechecks irreversible watchdog expiry under the acquisition-state lock,
recomputes the usable remainder and per-attempt timeout, and rechecks expiry
again before allowing physical creation to start.
After the DBAPI socket is created, a monotonic watchdog remains active through
SQLAlchemy pool checkout and first-connect dialect initialization. After expiry,
it continues low-frequency psycopg `cancel_safe` attempts, each individually
bounded, until acquisition unwinds. Thus a query already in flight or beginning
after slow Python initialization is interrupted without concurrently finishing
libpq from another thread. A reused DBAPI connection is published to the
watchdog before pool pre-ping and again at the maintenance-owned checkout
boundary, without mutating session or transaction state. A stale ping retains
SQLAlchemy's normal disconnect/reconnect handling, and both temporary
publication boundaries are structurally restored on every path.
The private boundary requires psycopg to report native bounded-cancel support
(client libpq 17 or newer) before checkout; a callable fallback that can block
in older libpq is rejected before acquisition. A physical connection returned
after expiry is closed by its acquiring thread
before SQLAlchemy can use it.
Nonempty positional or keyword `conninfo` is rejected before physical connect
because embedded hosts and services cannot be audited by the private attempt
boundary. The maintenance-owned `do_connect` hook performs physical creation
after the fresh-Engine precondition has excluded competing instance hooks.
The watchdog callback has a bounded cleanup grace and is synchronously joined
and proven stopped before acquisition returns,
and the connection is invalidated/discarded while the phase deadline remains
the reported failure. On success or error, a watchdog join failure invalidates
and closes an already checked-out connection before propagation while retaining
the primary error and cleanup notes.
Before physical connect, every hostname without a paired `hostaddr` is resolved
inside the same absolute phase deadline by the isolated private resolver helper
in an interruptible subprocess. Deadline cancellation terminates, then kills if
needed, tolerates an already-exited child at either signal race, and exactly
reaps the resolver before returning while preserving the primary deadline
classification. Any other exceptional exit after process creation applies the
same exact-reap ownership while preserving its primary exception. The resolved
addresses are written only into the copied psycopg parameter dictionary as aligned
`host`/`hostaddr`/`port` lists. This preserves libpq's hostname-dependent
authentication and TLS behavior, and leaves `/` filesystem Unix socket targets
untouched while preventing libpq from performing unbounded synchronous DNS.
Linux `@` abstract Unix socket targets are rejected before driver connect
because psycopg resolves them synchronously before publishing a cancellable raw
handle. Scoped IPv6 resolver results retain their numeric
interface scope identifiers. Explicit nonempty `host` and `hostaddr` lists must
have equal lengths; only an omitted or empty counterpart is broadcast. The
positive whole-second remainder after all DNS
work is divided across the actual resolved and explicit address attempt count,
so the sum of per-attempt timeouts cannot exceed the original phase deadline,
including when one hostname expands to multiple addresses.
Failure to resolve one multihost target skips that target within the same
absolute deadline; resolution fails only when no usable target remains.
Effective
`PGHOST`/`PGHOSTADDR`/`PGPORT`/`PGCONNECT_TIMEOUT` values are frozen when
explicit parameters omit them or supply null or wholly empty values that libpq
treats as omitted. A positive effective connection timeout remains a stricter
cap after Psycopg-compatible fractional-to-whole-second conversion; an unset or
nonpositive value is replaced by the phase cap. In addition,
`target_session_attrs=prefer-standby` (including its environment
form) counts both libpq passes even for a hostless/default target. Empty port
entries use the active client libpq's compiled default for private DNS
resolution while remaining empty in the aligned outbound parameters,
preserving mixed explicit and default-port multihost semantics. Service-derived targets fail closed because
their effective attempt set cannot be audited without external service-file
state. Resolution uses psycopg's `AF_UNSPEC`, stream, TCP protocol, and zero
flags. A resolver error observed after the absolute deadline is classified as
deadline expiry. The private listener never persists resolved targets or its
phase timeout into SQLAlchemy's creator parameters.
Checkout does not reset either deadline. If checkout completes after
the deadline, the acquired connection is invalidated and closed before the
timeout is reported. Pool and connection parameters are private implementation
state restored after acquisition even if listener setup or removal fails.
The listener is deactivated before removal, so a residual listener after a
removal failure is a no-op and cannot poison later physical connections after
its captured deadline.
Discard after a post-checkout failure attempts both invalidation and close,
preserving the deadline failure while attaching cleanup failures as notes.
Maintenance cleanup inspects invalidation before raw-handle discovery and never
uses SQLAlchemy's reconnecting connection accessor. An invalidated physical
session already released its transaction and advisory locks, so cleanup returns
without attempting a new physical connection after the bounded listener is gone.
For supported ordinary PostgreSQL connection configuration, the fixed
acquisition deadline covers pool wait, isolated DNS, libpq network attempts,
and SQLAlchemy initialization. OS-uninterruptible client-side file access such
as a FIFO or an unavailable network filesystem is unsupported and is not a
synchronous wall-clock guarantee; maintenance does not proxy DBAPI connection
creation through another process. These fixed safety budgets add no public
client, CLI, service, or configuration knob and do not change SQLite behavior.

Each `HttpEvidenceStore` privately owns one long-lived asyncio event-loop
thread and one `httpx.AsyncClient` connection pool for all ClaimSession-owned
HTTP operations. Construction is internal and deterministic; there is no
public client or async-client factory. Tests may supply an underscore-prefixed
transport seam, which does not transfer lifecycle ownership. Every bare request
owns a reentrant private logical operation; finalize holds one outer operation
across upload, mutation, terminal lookup, and authority reconciliation. One
public finalize call captures one authority-relevant absolute deadline; every
split batch and uncached artifact shares it, with uploads and mutations ending
before its reconciliation runway while readback uses the original deadline.
Store close rejects new outer operations and drains admitted operations under
their original deadlines while allowing their internal follow-up requests. It
then closes the async client, always stops its loop, joins its thread, and
publishes one deterministic close result. That single Store-level result also
covers its owning synchronous client and download `TemporaryDirectory`
cleanup; the first cleanup failure is preserved while later cleanup is still
attempted. Initialization preserves its original failure while applying the
same all-resource cleanup rule. Exactly one caller owns close; concurrent
callers wait for that result, and close from inside its own operation is
forbidden. Request deadline cancellation remains task-local and preserves
other operations using the same pool.

`ClaimSession.close` first and idempotently stops and joins its local heartbeat,
then attempts remote close only while transport admission remains available.
Store shutdown may make that remote notification unavailable, but cannot leave
the heartbeat running or turn repeated close calls into duplicate requests.

The dedicated event loop replaces only its own hostname resolver with a private
subprocess-backed `getaddrinfo` boundary. Resolution is performed per new
physical connection, so the long-lived client retains pooling, proxy, hostname,
Host-header, TLS SNI, and DNS-change behavior. Cancellation terminates/kills and
exactly reaps resolver work; no public resolver API, dependency, service, or
configuration is added. Both private Python helper commands use isolated
interpreter mode, so caller cwd and `PYTHONPATH` cannot substitute a shadow
`seqevi` package. Resolver `D` state uses the same synchronous-owner physical
exception as the artifact reader below.

ClaimSession artifact uploads stream through one upload-owned private Python
reader subprocess using a framed pipe; the async event loop consumes that pipe
without a thread executor. The subprocess holds at most one 1 MiB chunk and
adds no public factory, service, dependency, or configuration. Normal EOF and
reported reader errors are awaited and reaped. Deadline cancellation and Store
close terminate, then kill if needed, and synchronously await/reap a reader in
interruptible user-space or interruptible kernel I/O before returning. No
request succeeds and no finalization proceeds until cleanup completes. The
transport request path explicitly `aclose`s a suspended upload stream even when
the server returns before consuming its complete body.

Linux uninterruptible `D`-state I/O is the physical exception: `SIGKILL` cannot
make such a task disappear until the kernel operation returns. SeqEvi therefore
does not claim deadline completion in that state. The synchronous upload or
Store close remains the sole cleanup owner and continues waiting for exact
reap, with no background handoff, success response, or evidence finalization.
This private reader rule adopts the frozen fail-closed Linux boundary without
introducing issue #37's general external-tool `cleanup_stuck` API or machinery.
A separate per-session HTTP pool is not needed because active cancellation and
isolation pass on the shared pool.

Released non-session operations continue through the synchronous client and
retain their v0.2.0 behavior. The private async boundary adds no public async
Store method, deployment component, service, timing knob, or connection-pool
configuration.
