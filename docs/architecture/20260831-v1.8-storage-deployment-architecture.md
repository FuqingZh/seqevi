# Storage Deployment Architecture

Version: v1.8

Date: 2026-08-31

Status: approved target architecture; unreleased R2 implementation

Supersedes: [v1.7](20260830-v1.7-storage-deployment-architecture.md)

This revision retains v1.7's local POSIX behavior, legacy shared HTTP transfer,
private-network admission, scientific identities, ClaimSession fencing and
reconciliation, and owned process cleanup. It adds an explicitly configured
native OCI backend for new shared artifacts and schema revision 0005. No
production migration, Registry deployment, image publication, or new selectable
managed kit is implied by source implementation.

## Storage Ownership

Local Stores still use SQLite/POSIX and need no ORAS executable or Registry.
Shared Stores use PostgreSQL and one explicit `artifact_backend`:

| Backend | New artifact bytes | Existing artifact bytes |
| --- | --- | --- |
| `legacy-posix` (default) | Existing digest-addressed HTTP PUT / POSIX CAS | Existing verified POSIX path |
| `oci-registry` | ORAS CLI 1.3.4 directly to an independently deployed Registry | Registered POSIX stays in place; registered OCI resolves through configured Registry identity |

The qualified Registry is unmodified zot minimal 2.1.20. One instance owns its
root. No cluster hostname, mount, credential, container engine, or Registry
installer enters the scientific domain. Normal HTTPS verification is required;
HTTP is accepted only for an explicitly configured literal loopback IP. Native
OCI execution inherits the existing Linux process-containment boundary.

Raw SHA-256 remains the artifact/evidence identity. Each `artifact` database row
has exactly one immutable storage reference: `posix` with `relative_path`, or
`oci` with `registry_id`, `repository`, and a separate 64-hex `manifest_digest`.
The database CHECK makes these representations mutually exclusive. Identity,
media type, size, and storage location cannot silently change on conflict.

The deterministic manifest has one layer named `artifact.bin`, with the raw
digest, byte size, and adapter-native media type. Its config is exactly `{}`
with OCI empty-config media type, and artifact type is
`application/vnd.seqevi.evidence-artifact.v1`. JSON uses sorted keys and compact
separators. A stable `sha256-<manifest hex>` tag retains the manifest; reads use
`repository@sha256:<manifest hex>`. Changing media type changes manifest
identity, not raw identity. Verification rejects any noncanonical manifest,
extra layer/URL/annotation, changed tag, or mismatched descriptor.

Registry-native upload/retry/completed-blob reuse and garbage collection remain
third-party responsibilities. No SeqEvi offset journal, cross-restart resume
promise, expiry ledger, orphan cleaner, or second local live Store is added.
Retained but unreferenced manifests may be reused by an identical later
invocation; they are not scheduled for business-level deletion by SeqEvi.
OCI Image Layout interoperability is qualified separately, not exposed as a
complete Store backup/import feature.

## Discovery And Admission

`GET /health` retains its old shape. `GET /v1/storage/discovery` returns the
strict `storage-discovery-v1` response: backend, minimum client capability, and
nonsecret Registry id/endpoint/repository. Legacy mode has null Registry and
capability. Only an exact discovery 404 plus a valid health response permits
new clients to fall back to the old service. Malformed responses, unsupported
protocols, authentication and transport failures do not.

OCI-mode evidence, artifact, and ClaimSession operations require
`X-SeqEvi-Client-Capability: oci-artifacts-v1`; missing/unsupported values return
426 before data handlers. This is version negotiation, not authentication.
Old clients remain usable against legacy mode and are rejected before external
annotation against OCI mode. The existing trusted/private-network Store
boundary is unchanged.

`POST /v1/artifacts/resolve` maps a raw digest to registered media type, size,
and the typed storage reference, or null. Clients do not supply arbitrary
Registry endpoints in finalization. A known POSIX artifact is reused without
copying it. OCI mode rejects new direct-CAS PUTs and does not proxy OCI downloads.

## Staging, Finalization And Integrity

Each uncached artifact has the existing fixed 900-second staging deadline.
All native commands, including ambiguous-manifest readback, share its remaining
budget. ORAS owns transfer retries; SeqEvi does not reset the budget or add a
transfer state machine. A failed manifest command with an ambiguous outcome can
be reconciled by readback; explicit authentication, integrity, cancellation,
and deadline failures are not treated as successful publication.

Heartbeat loss, explicit ClaimSession close, and Store close signal native
staging cancellation. `ToolRunner` owns termination and reaping of its process
group before return. ClaimSession close fences new staging/finalization and
waits for its already-admitted operations, including pending artifact-resolution
HTTP cleanup and ORAS child reaping, before returning. Repeated/concurrent
close calls observe the same completion; a session close does not shut down
other sessions' shared transport. Calling close from that session's own active
operation is rejected to avoid self-deadlock. Cancellation does not roll back
an already-committed remote operation; existing readback/fencing rules remain.
Native stdout/stderr are bounded and removed after each
command; errors expose safe categories, not raw credentials or command output.
Uninterruptible kernel I/O can still delay synchronous cleanup: the deadline
is not a guarantee that a stuck kernel operation can be forcibly completed.

Staging resolves a caller-relative artifact path to an existing absolute path
before any Registry write. Changing the native command's working directory
does not change which input is uploaded or mutate the caller's artifact value.

After staging, finalization captures fresh ClaimSession authority and retains
one metadata deadline, the earlier of 30 seconds and the renewal deadline.
Split batches/reconciliation share that deadline. The service independently
verifies Registry identity, canonical manifest/tag/digest and blob descriptor
existence/size before its fenced PostgreSQL transaction. OCI metadata checks
do not download or hash the large layer. Registered legacy POSIX uses its
trusted immutable registration, exact path and size; new legacy-mode PUT and
finalize retain their full verification behavior.

The annotation path shares one batch-level normalized artifact and one raw
artifact across its sequence commits, and finalization deduplicates Registry
verification by raw digest. A 1,000-sequence annotation batch therefore has at
most two distinct artifact verifications under the shared deadline. The public
commit/finalize APIs can represent heterogeneous batches with more distinct
artifacts; those remain fail-closed under the same fixed budget. This revision
does not promise a 1,000-distinct-artifact throughput SLA or introduce a
different admission limit, parallel verifier, or per-chunk deadline reset.

Download verifies the canonical OCI metadata, uses `oras pull`, then computes
the entire raw SHA-256 in an isolated standard-library subprocess under the
same remaining deadline and cancellation signal. Only matching size and digest
permit target publication. This does not assume that ORAS independently
rehashes the bytes. POSIX downloads retain complete size/digest verification.
Successful staging alone never creates evidence.

## Configuration And Distribution

Service configuration uses existing `SEQEVI_` settings. OCI mode requires
`ARTIFACT_BACKEND=oci-registry`, `OCI_REGISTRY_ID`, `OCI_REGISTRY_ENDPOINT`,
`OCI_REGISTRY_REPOSITORY`, absolute `OCI_ORAS_EXECUTABLE`, and absolute
`OCI_REGISTRY_CONFIG`; `OCI_REGISTRY_CA_FILE` is optional. Keep `ARTIFACTS_DIR`
for old POSIX reads. An anonymous service uses an explicit `{"auths":{}}` file.
Service auth is deployment-owned/read-scoped and headless: credential helpers
are rejected. Files and permissions belong to the operator, not discovery.

Python annotation accepts invocation-only `oci_registry_config` and
`oci_registry_ca_file`; CLI equivalents are `--oci-registry-config` and
`--oci-registry-ca-file`. Without overrides, native clients use ORAS's standard
credential/helper and system-CA behavior. Explicit files are rejected for
local/non-OCI Stores; they never enter a profile, evidence identity or secret
database. No automatic login or TLS-verification bypass is added.

Preflight checks the pinned version, explicit files and discoverable transport/
authentication failures before annotation. A missing-digest probe permits only
the exact native missing-reference diagnostic for that probe, allowing an
empty repository. A Registry may conceal denied access as 404; preflight is
not proof of read/write permission. Each actual Registry operation enforces
authorization. No catalog-list privilege or write-probe artifact is required.

Container source embeds pinned ORAS and its license. A future explicitly
published kit can bind only the supplied config/CA files read-only at
`/run/seqevi/registry/config.json` and `/run/seqevi/registry/ca.pem`, preserving
caller UID/GID. No host home directory, helper or Docker socket is mounted.
The existing bundled kit/profile/image identity remains unchanged and rejects
these new file inputs; candidate image validation and new kit registration
are separate delivery boundaries, not automatic upgrades.

## Schema And Evidence

Fresh SQLite/PostgreSQL Stores bootstrap to `0005_oci_artifact_storage`.
Existing 0004 fails closed until an acknowledged one-step maintenance upgrade;
0003→0004 remains a separate step. Old rows become `posix` without changing
paths, bytes or scientific evidence. 0005→0004 is refused while any OCI row
exists. Follow the [0005 maintenance runbook](../operations/20260831-v1.3-oci-store-maintenance.md).

The [R2 specification](../implementation-plan/20260831-v1.0-native-oci-integration-specification.md)
records accepted implementation scope. The
