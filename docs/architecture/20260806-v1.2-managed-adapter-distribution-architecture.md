# Managed Adapter Distribution Architecture

Version: v1.2
Date: 2026-08-06
Status: approved target architecture; dbCAN managed acceptance passed
Initial kit: `dbcan-cazyme`
Supersedes: [v1.1](../archive/architecture/20260805-v1.1-managed-adapter-distribution-architecture.md)

## Scope

This version inherits v1.1 except for the acceptance rules below. It preserves
the public distribution boundary: `seqevi setup dbcan-cazyme` and named managed
profiles use only SeqEvi's bundled digest-pinned GHCR image. There is no public
`--image`, hidden environment override, mutable tag, site-profile layer, or
persistent configuration mutation.

## Distribution And Execution Evidence

Distribution publication and scientific managed execution are independent
acceptance surfaces. The existing GHCR publication record remains accepted.
A caller site's inability to transport that digest is a non-blocking site
issue and does not weaken the public image contract.

The scientific gate may use a Linux/amd64 release-equivalent local candidate
built from the published source revision, release Dockerfile, lock files,
`REVISION`, pinned base digest, and SHA-verified release inputs. It is addressed
only by its immutable local image ID and must not claim or imitate the public
digest. An in-process validation harness may substitute that ID at the OCI
launch boundary; it must not write a profile or alter the public kit.

## Runtime And Scientific Identity

The OCI digest is distribution identity. `ToolRuntimeDigest` fingerprints the
actual result-producing runtime. Direct and managed executions using the same
candidate must therefore have the same `ToolRuntimeDigest`.

A separately installed host runtime may have a different exact runtime
fingerprint. A host-versus-container comparison does not require equal runtime
digests, but it still requires equal adapter contract, semantic parameters,
`ResourceID`, hit/no-hit classification, normalized scientific values, and
public DuckDB schema.

## dbCAN Acceptance

The initial kit is accepted when direct candidate execution, a managed cold
run, and a separate later-process cache replay prove:

- identical adapter contract, candidate `ToolRuntimeDigest`, `ResourceID`, and
  semantic parameters;
- identical hit/no-hit classification, normalized values, and public schema;
- replay metrics of 50 cache hits and 0 computed records;
- read-only input/resource mounts, caller UID/GID, local Store network
  isolation, resource immutability, and exact-container cleanup.

The passed evidence is recorded in the
[v1.3 candidate gate](../benchmarks/20260806-v1.3-dbcan-managed-candidate-gate.md).
