# Execution Profile v2 Contract

Version: v2.0
Date: 2026-08-04
Status: superseded proposal; never implemented

Superseded by the
[v2.1 execution profile contract](20260805-v2.1-execution-profile-contract.md),
which records caller-owned resources and one public digest-pinned GHCR runtime.

## Purpose And Authority

Profile v2 describes one immutable managed OCI runtime selected by a future
`seqevi setup` command. It is a proposed extension of the current
[profile v1 contract](20260724-v1.0-execution-profile-contract.md), not a
replacement for it.

The current implementation accepts only `version = 1`. This document remains
proposed until the managed-distribution readiness gates pass and it is
activated with the repository product-boundary guidance. Approval authorizes
implementation but does not make v2 available to users; v2 becomes shipped
behavior only after the implementation, tests and release gate pass. Existing
v1 profiles remain readable and behaviorally unchanged after v2 is introduced.

## Selection Semantics

The existing three explicit invocation modes remain:

1. `--profile NAME` selects one XDG named profile;
2. `--config PATH` selects one exact caller-owned profile document;
3. explicit local mode supplies `--adapter`, `--executable` and `--resource`.

There is no implicit current profile, repository discovery, profile inheritance
or partial identity merge. `--fasta` and `--output` remain explicit.

## Document Shape

Managed setup publishes a complete document equivalent to:

```toml
version = 2
adapter = "dbcan-cazyme"
resource = "/home/user/.local/share/seqevi/resources/dbcan-cazyme/db_v5-2-9_5-5-2026"
store = "/home/user/.local/share/seqevi/store"
threads = 8
# timeout_seconds = 86400

[runtime]
kind = "oci"
kit_id = "dbcan-cazyme-5.2.9-db-2026.05.05"
engine = "docker"
image = "registry.example.org/seqevi/dbcan@sha256:<digest>"
```

Required root keys are `version`, `adapter`, `resource` and `runtime`. Optional
root keys are `store`, `threads` and `timeout_seconds`. The runtime table
requires `kind`, `kit_id`, `engine` and an image reference containing an
immutable digest.

P0 accepts only `kind = "oci"` and `engine = "docker"`. Unknown fields,
unsupported versions, mutable image references, invalid paths, unsafe profile
names and invalid operational values fail before Store access or container
launch.

Profile v2 does not contain `executable`, `path_prepend`, arbitrary Docker
arguments, mount lists, network switches or credentials. Container-internal
paths and command structure belong to the first-party kit manifest. Secrets
come from an external secret/environment boundary at invocation time.

## Authoring And Upgrade

The first v2 writer is `seqevi setup`. It publishes a profile only after the
kit image, resource lock and smoke contract pass. Setup never overwrites an
existing profile.

`--profile-name` is the explicit side-by-side upgrade mechanism. A later kit
does not mutate a v2 profile or a hidden current alias. Users may inspect, copy
or version the TOML like any v1 profile.

`profile validate` remains static: it validates schema, local paths, immutable
image syntax and supported values without pulling an image or launching
Docker. Runtime access belongs to setup smoke or a later explicit preflight
command.

## Delegation Contract

When `annotate` resolves a v2 profile, the host delegates the complete
annotation invocation to the compatible SeqEvi inside the selected image.
The kit supplies the container executable and internal mount destinations. The
host supplies only narrowly resolved input, output, resource, temporary Store
and operational values.

The delegated invocation must preserve the same adapter, Store and DuckDB
contracts as v1 local execution. A host must reject a result when the observed
SeqEvi version, adapter contract, runtime identity, resource identity or result
schema conflicts with the kit manifest.

## Compatibility

- V1 profiles remain valid local-runtime profiles.
- V2 adds OCI execution; it does not reinterpret v1 keys.
- `--profile`, `--config` and explicit local mode keep their current precedence
  and mutual-exclusion rules.
- Internal adapter contract IDs remain absent from ordinary user selection.
- A future v3 requires an explicit contract and migration decision; readers do
  not silently coerce unknown versions.

## Acceptance Gate

Before v2 is declared implemented, tests must prove:

- strict parsing and v1 regression compatibility;
- static validation performs no Docker or filesystem mutation;
- exact profile publication is atomic and no-overwrite;
- mount, network, UID/GID, secrets and cleanup boundaries;
- local-v1 and managed-v2 scientific/result equality on the accepted dbCAN
  runtime;
- clean wheel installation followed by setup and cold/cached annotation.
