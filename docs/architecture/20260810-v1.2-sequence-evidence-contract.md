# Sequence Evidence Contract

Version: v1.2
Date: 2026-08-10
Status: approved target architecture

This contract supersedes the concurrency and explicit no-lease coordination
portion of the [v1.0 sequence-evidence contract](20260720-v1.0-sequence-evidence-contract.md).
All sequence identity, canonicalization, complete five-coordinate
`EvidenceKey`, immutable evidence, artifact, adapter-native schema, and
scientific conflict rules in
[v1.1](20260804-v1.1-sequence-evidence-contract.md) remain normative except
where this document adds the lease coordination surface below. The
[v1.1 result-consumption contract](20260804-v1.1-result-consumption-contract.md)
remains normative and is not superseded by this coordination contract.

## Terminal Evidence and Ephemeral Claims

Evidence remains terminal-only and immutable. A separate ephemeral claim row
coordinates calculation for exactly one complete EvidenceKey; it is never an
annotation result and never changes scientific truth. The row stores canonical
semantic parameters, an opaque owner credential, a monotonically increasing
generation, expiry, and timestamps.

Atomic acquire returns cached, acquired, or busy. Only acquired carries owner
and generation authority. Busy carries the key and retry/expiry metadata and
must not reveal another owner's credential. Authority ends at expiry. Renew,
release, and finalize require the exact unexpired owner and generation.
Release retains an expired generation tombstone; takeover or reacquisition,
including by the same token, advances generation. Finalize atomically consumes
the matching lease and publishes immutable evidence, after which no claim may
authorize mutation.

Expiry is evaluated at the backend's locked mutation linearization point. A
renewal that first linearizes while its exact generation is unexpired remains
authorized to commit the transaction's shared fresh expiry even if wall clock
passes the old expiry before commit. A mutation that first linearizes at
`expires_at <= now` is rejected and cannot resurrect authority.

Healthy claim-capable clients normally have one active calculator per key.
Crash, partition, or pause remains at-least-once compute; terminal immutable
evidence remains authoritative and SeqEvi does not promise exactly-once.

## Compatibility

The released `EvidenceStore` protocol and lookup, fetch, commit, artifact, and
health response contracts remain unchanged. Claims are exposed through the
separate `ClaimCapableEvidenceStore` protocol and dedicated strict HTTP
endpoints. `/v1/evidence/claims/capabilities` advertises support; HTTP 404 means
a new client uses the released lookup/idempotent-commit path against an old
service. An old client sees the exact released `/health` body from a new
service. Lease loss maps to HTTP 412; immutable evidence conflict retains HTTP
409.

Duplicate EvidenceKeys in claim acquisition are rejected consistently because
acquire results are positional, even if their enclosing queries differ.
Released lookup continues to de-duplicate repeated queries.
Annotate coordination and HTTP claim requests are at most 1,000 and
additionally honor the client's configured limit; persistence methods retain
their general public batch contract. Scientific adapter batches remain at most
10,000 and receive only identities acquired by that invocation. When one
logical HTTP acquisition spans multiple service-sized chunks, the client
renews authority returned by early chunks on absolute per-claim deadlines until
the complete ordered result is ready for its caller. New chunks cannot postpone
an earlier deadline. Acquisition and renewal failures make one bounded
`release_many` attempt over the active snapshot without masking the primary
error; transport chunking stops that cleanup on its first failed chunk. An
expired handle is never returned. Background HTTP renewal uses the client's
finite request timeout. Service-sized renewal chunks execute independently so
one slow chunk cannot consume the leases of all later chunks; ordered results
are returned only if every refreshed handle remains live. HTTP renewal orders
service chunks by earliest expiry, runs at most 32 requests concurrently, and
caps each request timeout at its expiry-minus-runway budget. A live claim
already inside the runway receives only its remaining absolute lifetime for an
emergency refresh; the response must still restore the full runway. Queued
overload therefore fails before stale authority can be returned instead of
creating unbounded threads or connections. Invocation-level outer renewal
batches use the same absolute-deadline order before entering that bounded HTTP
scheduler. If terminal evidence
wins during chunked acquisition renewal, metadata lookup replaces that claim
result with cached terminal truth and only lost nonterminal authority fails.
Both acquisition and invocation renewal schedule against the earlier of the
server cadence and expiry minus one fixed five-second runway. Handoff
synchronously refreshes claims within one scheduling interval of that runway,
and renewal responses below the same runway are rejected and cleaned up.
Claim capability discovery therefore requires `lease_seconds > 5` and a
renewal cadence no greater than `lease_seconds - 5`; incoherent services fail
capability validation. The first-party 60-second lease and 20-second cadence
satisfy this invariant.

## Coordination and Concurrency

Renewal starts when claims are acquired and remains active through miss FASTA
creation, adapter execution, commit construction, artifact transfer, and all
finalize chunks. Completed keys are removed atomically from both claim and
query renewal state. Failure stops renewal before best-effort release of only
the remaining active leases, including cancellation through `BaseException`.
Busy retry cadence is carried from service
metadata across polling rounds; peer completion is metadata-looked-up and
counted as cache, never local compute.

Terminal evidence may appear while an acquired adapter is still computing.
Before and during chunked finalization, the client partitions current authority
from metadata-confirmed terminal keys. Peer-terminal keys are completed as
cache; a 412 finalization race is narrowed and retried only for the remaining
authoritative subset. Lost authority without terminal evidence remains fatal.

Multi-key mutations use canonical full-key order while preserving caller
result order. Time and expiry are refreshed for each item after the relevant
write/row lock, then every successful acquire or renewal receives one shared
transaction-tail expiry update rather than a per-row refresh window.
PostgreSQL mutations also take transaction-scoped per-key
advisory locks sorted and de-duplicated by their actual signed 64-bit lock IDs,
which serializes claim creation with legacy terminal publication even when no
claim row exists and remains deadlock-safe under a hash collision. Legacy
commit and claimed finalize retire claims, then write shared sequence,
artifact, and evidence rows in the same canonical phase order. This prevents
both cross-table and different-key/shared-row lock inversion. A successful
legacy commit also retires any matching claim, so terminal truth immediately
invalidates lease authority.

## Validation Contract

Contract delivery requires strict transport and compatibility tests, SQLite
concurrency and boundary tests, migration from `0002`, and real PostgreSQL
tests for winner selection, renewal/release, expiry takeover, stale-generation
rejection, legacy/finalize races, deterministic lock ordering, and terminal
convergence. Concurrent partial-overlap fixture annotations must prove the
overlap reaches an adapter once and produces equivalent DuckDB results. The
canonical repository gate is `pdm run check`.
