# Sequence Evidence Contract

Version: v1.2
Date: 2026-08-10
Status: approved target architecture

This contract supersedes v1.1 for Store coordination. All sequence identity,
canonicalization, complete five-coordinate `EvidenceKey`, immutable evidence,
artifact, adapter-native schema, and scientific conflict rules in
[v1.1](20260804-v1.1-sequence-evidence-contract.md) remain normative except
where this document adds the lease coordination surface below.

## Terminal Evidence and Ephemeral Claims

Evidence remains terminal-only and immutable. A separate ephemeral claim row
coordinates calculation for exactly one complete EvidenceKey; it is never an
annotation result and never changes scientific truth. The row stores canonical
semantic parameters, an opaque owner credential, a monotonically increasing
generation, expiry, and timestamps.

Atomic acquire returns cached, acquired, or busy. Only acquired carries owner
and generation authority. Busy carries the key and retry/expiry metadata and
must not reveal another owner's credential. Authority ends at expiry. Renew,
release, and finalize require the exact unexpired owner and generation.
Release retains an expired generation tombstone; takeover or reacquisition,
including by the same token, advances generation. Finalize atomically consumes
the matching lease and publishes immutable evidence, after which no claim may
authorize mutation.

Healthy claim-capable clients normally have one active calculator per key.
Crash, partition, or pause remains at-least-once compute; terminal immutable
evidence remains authoritative and SeqEvi does not promise exactly-once.

## Compatibility

The released `EvidenceStore` protocol and lookup, fetch, commit, artifact, and
health response contracts remain unchanged. Claims are exposed through the
separate `ClaimCapableEvidenceStore` protocol and dedicated strict HTTP
endpoints. `/v1/evidence/claims/capabilities` advertises support; HTTP 404 means
a new client uses the released lookup/idempotent-commit path against an old
service. An old client sees the exact released `/health` body from a new
service. Lease loss maps to HTTP 412; immutable evidence conflict retains HTTP
409.

Duplicate claim acquisition is rejected consistently because acquire results
are positional. Released lookup continues to de-duplicate repeated queries.
Claim HTTP and persistence batches are at most 1,000 and additionally honor
the client's configured limit. Scientific adapter batches remain at most
10,000 and receive only identities acquired by that invocation. When one
logical HTTP acquisition spans multiple service-sized chunks, the client
renews authority returned by early chunks until the complete ordered result is
ready for its caller.

## Coordination and Concurrency

Renewal starts when claims are acquired and remains active through miss FASTA
creation, adapter execution, commit construction, artifact transfer, and all
finalize chunks. Completed keys are removed atomically from both claim and
query renewal state. Failure stops renewal before best-effort release of only
the remaining active leases. Busy retry cadence is carried from service
metadata across polling rounds; peer completion is metadata-looked-up and
counted as cache, never local compute.

Terminal evidence may appear while an acquired adapter is still computing.
Before and during chunked finalization, the client partitions current authority
from metadata-confirmed terminal keys. Peer-terminal keys are completed as
cache; a 412 finalization race is narrowed and retried only for the remaining
authoritative subset. Lost authority without terminal evidence remains fatal.

Multi-key mutations use canonical full-key order while preserving caller
result order. Time and expiry are refreshed for each item after the relevant
write/row lock. PostgreSQL mutations also take a canonical transaction-scoped
per-key advisory lock, which serializes claim creation with legacy terminal
publication even when no claim row exists. Legacy commit and claimed finalize
retire claims before terminal insertion in the same canonical order,
preventing cross-table lock inversion. A successful legacy commit also retires
any matching claim, so terminal truth immediately invalidates lease authority.

## Validation Contract

Contract delivery requires strict transport and compatibility tests, SQLite
concurrency and boundary tests, migration from `0002`, and real PostgreSQL
tests for winner selection, renewal/release, expiry takeover, stale-generation
rejection, legacy/finalize races, deterministic lock ordering, and terminal
convergence. Concurrent partial-overlap fixture annotations must prove the
overlap reaches an adapter once and produces equivalent DuckDB results. The
canonical repository gate is `pdm run check`.
