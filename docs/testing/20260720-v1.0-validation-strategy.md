# SeqEvi v1 Validation Strategy

> Status: approved validation contract
> Date: 2026-07-20

## Objective

Validation must prove scientific cache correctness, not only code coverage. The
main risks are false cache hits, missed reuse, partial commits, adapter semantic
drift, and local/shared divergence.

## Test Layers

| Layer | Purpose | External tools required |
| --- | --- | --- |
| Unit | Canonicalization, identifiers, keys, schemas | No |
| Property | Sequence normalization and idempotency invariants | No |
| Store contract | Lookup, commit, fetch, concurrency, corruption | No |
| Runner contract | Exit, timeout, cancellation, streams | Fixture executable |
| Adapter contract | Native parsing and semantic identity | Fixtures |
| Tool parity | Compare with direct upstream execution | Yes |
| Deployment parity | Compare local and shared packages | PostgreSQL |
| Release smoke | Clean install and documented workflow | Selected tools |

Fast tests must run without downloading third-party annotation databases.
External-tool and PostgreSQL tests use explicit markers and controlled fixtures.

## Normative Incremental-Reuse Scenario

The primary acceptance fixture contains three FASTA inputs:

```text
A = 2000 unique canonical sequences
B = 1000 sequences selected from A
C = 1000 sequences selected from A + 500 novel sequences
```

Expected behavior under one exact adapter contract:

| Run | Hits before compute | Sequences computed | Final evidence |
| --- | ---: | ---: | ---: |
| A | 0 | 2000 | 2000 |
| B | 1000 | 0 | 1000 |
| C | 1000 | 500 | 1500 |

Input headers and order differ between the FASTA files. Reuse must still follow
canonical sequence content. The output `sequence-map.tsv` must retain each
invocation's own headers and order.

## Sequence Contract Tests

Cover at least:

- case and whitespace canonicalization;
- one removable terminal `*`;
- rejection of internal `*`, gaps, digits, punctuation, non-ASCII, and empty
  sequences;
- acceptance of alphabetic ambiguous residue codes at the identity layer;
- duplicate `InputID` rejection;
- multiple different input IDs mapping to one `SequenceID`;
- deterministic GA4GH `SQ.` vectors and MD5 aliases;
- whole-invocation failure when any record is invalid;
- no global persistence of full FASTA headers.

Hypothesis properties:

- canonicalization is idempotent;
- accepted case/whitespace/terminal-stop variants share one identity;
- changing one accepted residue changes the primary identifier;
- parser chunking and record count do not alter identities;
- output sequence maps preserve input order.

Use published refget digest vectors where available and fixed repository vectors
for protein sequences.

## Evidence-Key Tests

For one sequence, independently vary:

- adapter contract version;
- tool runtime digest;
- resource ID;
- each semantic parameter;
- parameter ordering and explicit defaults;
- operational-only values such as thread count and temporary path.

Expected behavior:

- every semantic change produces a cache miss;
- canonical ordering of equivalent parameter objects produces the same key;
- operational-only changes do not alter the key;
- no request resolves to an older or latest version;
- `no_hit` is a reusable terminal result;
- failures are never cache hits.

## Store Contract Suite

Run the same abstract suite against local SQLite/POSIX and shared
PostgreSQL/POSIX implementations:

- insert and fetch sequence content;
- exact evidence lookup;
- hit and no-hit commit;
- artifact digest verification;
- duplicate identical commit is idempotent;
- duplicate different payload raises integrity error;
- transaction rollback leaves no visible partial evidence;
- missing/corrupt artifact raises a health/integrity error;
- output materialization groups and filters shared batch artifacts correctly;
- migration from every supported prior schema;
- incompatible newer schema fails startup.

## Concurrency Tests

V1 accepts duplicate computation but not duplicate mutable state. Tests launch
multiple processes or clients that:

- observe the same miss;
- create identical results concurrently;
- commit in different orders;
- retry after a connection failure;
- attempt a conflicting payload for the same key.

Acceptance:

- exactly one immutable logical evidence record exists;
- every identical client receives success or existing-identical;
- conflicting content is rejected;
- no final artifact is truncated;
- no claim, lease, or heartbeat behavior is assumed.

## Tool Runner Tests

A fixture executable covers:

- successful stdout and stderr capture;
- non-zero exit;
- missing expected output;
- malformed output;
- timeout while streams are active;
- child process creation and process-group termination;
- user cancellation;
- paths containing spaces;
- explicit environment and working directory;
- argument safety with `shell=False`.

The test must confirm that a timed-out child process is not left running.

## Adapter Tests

Each adapter has golden native-output fixtures for:

- one hit with multiple rows;
- multiple hits for one sequence;
- no hit;
- mixed hit/no-hit batch;
- unsupported residue rejection;
- duplicate or unknown output identifiers;
- truncated and malformed primary output;
- tool/resource version mismatch;
- deterministic row ordering and Parquet schema.

Every supported adapter option is classified in a table-driven test as semantic
or operational. Adding an unclassified option fails the contract test.

Specific assertions:

- eggNOG `seed_ortholog` is never promoted to input-protein identity;
- eggNOG `PFAMs` remains in eggNOG evidence only;
- InterProScan sequence MD5 matches the canonical SeqEvi sequence;
- InterPro/Pfam native domain row grain is preserved;
- direct Pfam evidence is not merged with eggNOG-transferred PFAMs.

## Direct Tool Parity

For a small redistributable or locally provisioned fixture FASTA, run the
upstream tool directly and through SeqEvi with the same runtime, database, and
semantic parameters.

Compare:

- complete input accounting;
- native raw primary output after removal of documented operational fields;
- normalized row count and values;
- hit/no-hit classification;
- runtime/resource/parameter provenance.

SeqEvi is not accepted if cache normalization changes the scientific result.

## Output Package Tests

Validate every successful package contains exactly the declared resources:

```text
evidence.parquet
sequence-map.tsv
no-hits.parquet
datapackage.json
```

Assertions include:

- Data Package v2 descriptor validation;
- resource paths remain inside the output directory;
- declared schemas match physical files;
- row counts and SHA-256 digests match;
- all input records appear in `sequence-map.tsv`;
- hit and no-hit sets are complete and disjoint;
- adapter-specific evidence does not include another adapter's columns;
- `rejected.tsv` is absent from successful packages;
- local and shared modes produce semantically equivalent packages.

Creation timestamps and explicitly documented environment diagnostics may differ
between local and shared runs. Scientific resources and evidence provenance may
not differ.

## Failure Atomicity Tests

Inject failures at each boundary:

- after FASTA parsing;
- while writing cache-miss FASTA;
- during tool execution;
- during raw validation;
- during normalized artifact write;
- after artifact promotion but before metadata commit;
- during metadata transaction;
- during output package materialization.

No failure before Store commit may expose evidence. Failures after a valid Store
commit may leave an incomplete invocation output, but rerunning must reuse the
committed evidence and rebuild the package safely.

## Performance Measurements

V1 records measurements rather than inventing pass/fail thresholds:

- FASTA parsing and hashing throughput;
- SQLite and HTTP lookup throughput by batch size;
- cache-hit package materialization throughput;
- peak memory for large FASTA and Parquet batches;
- artifact upload/download throughput;
- frequency and cost of duplicate concurrent computation;
- external tool time separated from SeqEvi overhead.

A native extension, distributed lease, or new storage backend requires evidence
from these measurements.

## Standard Commands

The initialized repository exposes one aggregate check:

```bash
pdm run check
```

During development, targeted commands are:

```bash
pdm run format
pdm run lint
pdm run typecheck
pdm run test
```

External integration suites are marked `requires_tool`, `requires_postgres`, or
`slow` and must be included in release validation with their required
environments explicitly provisioned.

## Release Acceptance

A release candidate is acceptable only when:

1. Unit, property, Store, runner, adapter, and package suites pass.
2. A/B/C incremental reuse passes in local and shared modes.
3. Tool, resource, parameter, and adapter changes invalidate exactly as defined.
4. No-hit results are cached and failures are not.
5. Concurrent duplicate commits are idempotent and conflicts fail.
6. Direct-tool parity passes for both official adapters.
7. Local and shared packages are semantically equivalent.
8. A clean wheel install can execute the documented smoke workflow.
