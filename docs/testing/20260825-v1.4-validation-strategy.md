# SeqEvi Validation Strategy

Version: v1.4
Date: 2026-08-25
Status: approved validation strategy

This strategy is the current authority for selecting SeqEvi validation gates.
It supersedes the gate-selection language in the Regression And Release Gate
section of [v1.3](20260824-v1.3-validation-strategy.md), while retaining its
semantic progress and presentation gates and the adapter, Store, result, CLI,
packaging, and ClaimSession gates retained from
[v1.1](20260810-v1.1-validation-strategy.md).

## Gate Classes

| Class | Purpose | Trigger |
| --- | --- | --- |
| Focused decision gate | Falsify the changed behavior or contract at its owning seam | Every implementation or contract change |
| Canonical integration gate | Detect repository-wide interaction, typing, formatting, and regression failures | Runtime behavior; public or compatibility contracts; generated artifacts; executable workflows; validation, build, package, dependency, or lock changes; broad refactors; final release candidates; or no reliable focused coverage |
| Environment-specific gate | Exercise behavior that differs by supported backend or execution environment | Only when that backend or environment is affected |
| Expensive acceptance gate | Prove real-tool, scale, distribution, or deployed behavior | When the corresponding execution identity or acceptance boundary changes |
| Delivery gate | Decide whether an exact candidate may merge or publish | At the repository's pull-request, release, or publication boundary |

`pdm run check` remains SeqEvi's canonical integration command. Its existence
does not make it a prerequisite for a documentation-only wording, navigation,
or archival change that is completely covered by documentation consistency,
relative-link, formatting, diff, and any directly affected contract checks.

## Selection Rules

- Start with the focused test or check that owns each changed seam.
- Documentation-only wording, navigation, and archival changes use diff and
  relative-link checks. Run a focused architecture or documentation contract
  test when the changed path or literal is mechanically asserted.
- User-visible CLI or runtime behavior requires focused tests and the canonical
  integration gate.
- Public contract changes require the authoritative architecture update,
  focused contract tests, and the canonical integration gate.
- Shared-Store behavior, schema, migration, or concurrency changes require
  focused SQLite and real PostgreSQL coverage in addition to the canonical
  integration gate. PostgreSQL is not added to an unrelated local-only change.
- Packaging, dependency, lock, generated-artifact, CI, or validation-harness
  changes require the canonical integration gate and their owning build or
  artifact readback.
- A focused failure is diagnosed at its seam. It broadens validation only when
  the diagnosis exposes another obligation.
- A green CI execution may satisfy the same exact-head canonical obligation;
  local execution is not repeated solely for ceremony. Exact-head review and
  unresolved-thread checks remain delivery gates, not local correctness tests.

## Continuous Integration Routing

The `CI` workflow always runs its change classifier and Markdown relative-link
check, then exposes one stable aggregate `gate` job. It selects heavier jobs by
the affected boundary:

- documentation index, archive, benchmark records, how-to guides,
  implementation plans, and tutorials use the documentation gate only;
- architecture, operations, validation policy, tests, scripts, repository
  instructions, and unknown paths run the Python test matrix;
- source and package inputs additionally run both distribution-image gates;
- the service Docker boundary and dbCAN runtime-image boundary run their own
  image gate; and
- mixed changes take the union of their required gates, while empty or unknown
  classifications fail closed to the complete workflow.

The root `README.md` is a package input and therefore is not classified as
documentation-only. Workflow-level path exclusion is not used, so a required
check remains observable even when heavy jobs are skipped. The protected-branch
ruleset currently requires the Python 3.12 and 3.13 matrix contexts, so those
jobs retain a lightweight success path for documentation-only changes while
skipping dependency installation and `pdm run check`.

## Expensive Acceptance And Evidence Reuse

Real eggNOG, dbCAN, or InterProScan acceptance is not repeated when code,
harness, input, ToolRuntimeDigest, ResourceID, semantic parameters, and the
affected acceptance contract are unchanged. A change or focused failure at an
adapter command, upstream output, evidence identity, Store, result, scale,
distribution, or deployment boundary reopens the corresponding acceptance
decision.

## Reporting

Completion reports name the claim, affected seams, selected checks, skipped
checks, and residual risk. A bounded documentation claim may be complete
without the canonical integration gate; a runtime, compatibility, release, or
otherwise canonical-triggering claim may not.
