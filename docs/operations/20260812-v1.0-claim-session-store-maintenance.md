# ClaimSession Store Maintenance

Version: v1.0

Date: 2026-08-12

Status: approved candidate runbook; activation pending

1. Stop every Store service and claim-capable client and keep them stopped.
2. Verify the deployment process/writer boundary is empty (`pg_stat_activity`
   for PostgreSQL; open database/lock holders for SQLite).
3. Record the canonical database identity and current revision and create a
   single-use acknowledgement bound to both.
4. Run the explicit fenced 0004 maintenance path. Ordinary startup deliberately
   refuses this transition:
   `seqevi store-maintenance-upgrade --database-url "$SEQEVI_DATABASE_URL"
   --acknowledge-database "<redacted SQLAlchemy database identity>"
   --acknowledge-revision 0003_evidence_claim_leases`. For SQLite, also pass
   `--store-root <Store directory>`.
5. Verify revision `0004_claim_sessions`, all six coordination tables, absence
   of `evidence_claim`, and unchanged sequence/artifact/evidence counts/digests.
6. Restart one service, verify `/health` and ClaimSession capabilities, then
   restore clients.

Any timeout, uncertain commit, unexpected schema, live writer, stale
acknowledgement, or timeout-reset readback failure is fail-closed. Keep writers
quiesced and classify revision/schema from a fresh connection. Rollback requires
the same fence, recreates empty 0003 coordination, and never changes terminal
evidence or artifacts. With writers still stopped, run
`seqevi store-maintenance-downgrade --database-url "$SEQEVI_DATABASE_URL"
--acknowledge-database "<redacted SQLAlchemy database identity>"
--acknowledge-revision 0004_claim_sessions`; for SQLite also pass `--store-root`.
Then verify revision `0003_evidence_claim_leases`, an empty `evidence_claim`,
absence of all six 0004 coordination tables, and unchanged terminal row digests.
