# OCI Store Maintenance

Version: v1.3

Date: 2026-08-31

Status: approved execution runbook; production execution not authorized

Supersedes: [v1.2](20260818-v1.2-claim-session-store-maintenance.md)

Retain v1.2's quiescence, canonical target identity, backup/before-state record,
bounded lock, fail-closed readback, and 0002 preparation rules. Existing 0003
still advances only to 0004 per acknowledged call. For the new source runtime,
keep writers stopped after that step and perform the additional 0005 upgrade
below; do not restart the new binary against 0004. This procedure never moves
historical artifact bytes or changes their storage location.

## Upgrade 0004 To 0005

Stop all writers and prove their process/database boundaries empty. Record a
backup and fresh canonical redacted database identity, exact revision
`0004_claim_sessions`, sequence/artifact/evidence counts, and terminal-row
digests. Then run the already-existing maintenance command with a new exact
acknowledgement:

```text
seqevi store-maintenance-upgrade --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0004_claim_sessions
```

For SQLite add `--store-root <canonical Store directory>`. The fenced SQLite
table rebuild temporarily disables connection-local foreign-key enforcement,
checks foreign keys before commit, and restores enforcement after commit or
rollback. It is not permission to run live writers during maintenance.

Verify from a fresh connection: revision `0005_oci_artifact_storage`; unchanged
terminal counts/digests and old paths; old artifact rows marked `posix` with
null OCI columns; nullable `relative_path`; named exclusive storage-reference
CHECK; no lingering database default for `storage_kind`; unchanged ClaimSession
tables. New runtime explicitly supplies the row kind.

Schema upgrade and switching `SEQEVI_ARTIFACT_BACKEND` are distinct operator
actions. Legacy mode can remain selected after the upgrade. OCI enablement
additionally requires deployment-owned Registry, ORAS and file inputs described
by [storage v1.8](../architecture/20260831-v1.8-storage-deployment-architecture.md),
and upgraded clients. Verify health, discovery, old-data readback, new staging,
finalization, and download on a separately authorized deployment canary before
restoring general clients.

## Rollback 0005 To 0004

With the same complete writer fence and a fresh exact acknowledgement:

```text
seqevi store-maintenance-downgrade --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0005_oci_artifact_storage
```

On success the command reports the actual one-step target
`0004_claim_sessions`. A separately acknowledged 0004 downgrade reports
`0003_evidence_claim_leases`; neither message implies that a second step ran.

For SQLite also pass `--store-root`. Any OCI artifact row refuses rollback;
do not delete rows/Registry content to bypass this boundary. An empty-of-OCI
Store can return to 0004 without moving POSIX bytes. Verify revision, removal
of OCI columns/CHECK, restored non-null POSIX paths and unchanged terminal
data before restarting the compatible old runtime. Further 0004→0003 or
0003→0002 rollback remains a separate acknowledgement under v1.2.

On stale identity/revision, active writers, timeout, uncertain commit, or data
drift, preserve observable state and investigate from a fresh connection.
Never retry blindly or infer that a failed command necessarily rolled back.
