# ClaimSession Store Maintenance

Version: v1.2

Date: 2026-08-18

Status: superseded by [v1.3](20260831-v1.3-oci-store-maintenance.md); retained 0002-0004 procedures

Supersedes: [v1.1](20260813-v1.1-claim-session-store-maintenance.md)

This procedure supports an existing Store at
`0002_artifact_byte_size_bigint`. It separates the reversible 0002-to-0003
preparation from the destructive-coordination 0003-to-0004 transition. Do not
use ordinary service startup as a migration command: it may commit 0003 and
then deliberately fail closed before 0004.

## Fence and before-state record

1. Stop every Store service and claim-capable client and keep them stopped.
2. Prove the deployment process/writer boundary empty (`pg_stat_activity` for
   PostgreSQL; open database and lock holders for SQLite). A maintenance
   advisory/file lock does not replace this quiescence proof.
3. For SQLite, resolve `--store-root` and the existing canonical absolute
   `<store_root>/store.sqlite3`. Refuse a missing, symlink, URI/query-ambiguous,
   or different target. Record the canonical redacted SQLAlchemy database
   identity. For PostgreSQL, record the normalized redacted identity.
4. From a fresh read-only connection, record revision, relevant tables,
   sequence/artifact/evidence counts, and deterministic terminal-row digests.
   Create a single-use acknowledgement bound to that identity and exact
   revision. Any disagreement or incomplete readback stops maintenance.

## Prepare 0002 to 0003

When the recorded revision is `0002_artifact_byte_size_bigint`, run:

```text
seqevi store-maintenance-prepare --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0002_artifact_byte_size_bigint
```

For SQLite also pass `--store-root <Store directory>`. The command accepts only
0002, applies only `0003_evidence_claim_leases`, and performs a fresh completion
readback. Verify revision 0003, an empty `evidence_claim`, absence of all six
0004 coordination tables, and unchanged terminal counts and digests. If the
Store was already 0003, do not run preparation with a fabricated 0002 ack;
record and validate that actual state instead.

Before 0004, rollback preparation—only while writers remain stopped—with:

```text
seqevi store-maintenance-prepare-rollback \
  --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0003_evidence_claim_leases
```

For SQLite also pass `--store-root`. Verify revision 0002, absence of
`evidence_claim` and the six 0004 tables, and unchanged terminal data. The
rollback checks expiry against the database clock and refuses to drop 0003
while any unexpired `evidence_claim` remains.

## Upgrade 0003 to 0004

After recording a new single-use 0003 acknowledgement, run:

```text
seqevi store-maintenance-upgrade --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0003_evidence_claim_leases
```

For SQLite also pass `--store-root`. Verify revision `0004_claim_sessions`, all
six coordination tables, absence of `evidence_claim`, and unchanged terminal
counts and digests. Only then restart one exact released service, verify
`/health` and ClaimSession capabilities, and restore clients.

Rollback 0004 with the same canonical identity and fence:

```text
seqevi store-maintenance-downgrade --database-url "$SEQEVI_DATABASE_URL" \
  --acknowledge-database "<canonical redacted SQLAlchemy database identity>" \
  --acknowledge-revision 0004_claim_sessions
```

This returns to empty 0003. Verify revision, tables, and terminal data. If the
approved rollback target is the original 0002, issue a fresh 0003
acknowledgement and then run the preparation rollback above.

Any live writer, identity error, stale acknowledgement, lock/timeout failure,
uncertain commit, mixed or unexpected schema, terminal-data drift, or failed
fresh readback is fail-closed. Keep writers quiesced, preserve the observed
state, and classify it from a new connection before any retry or rollback.
